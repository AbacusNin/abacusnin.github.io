io-detect: writeup

I built a coordination-detection pipeline and scored it against a labeled influence-operation dataset.

The dataset is gated and no-derivatives, so I redistribute none of it. To reproduce this you need your own copy from Zenodo under the same terms. Verify it against the checksum above.

A second dataset ingests through the same canonical schema, the FiveThirtyEight release of the Clemson/Linvill-Warren IRA tweets. It is positives-only, with no control class. I score nothing on it.

Method

  1. Normalize the source into one canonical record schema.
  2. Compute behavioral signals per account and per account pair: co-repost timing, duplicate text, hashtag flooding, mention and reply swarming, automation.
  3. Build a weighted co-activity network from those signals.
  4. Extract dense clusters from that network. A coordinated group knots together into a small, heavily weighted cluster. Ordinary accounts sit in a sparse web, and the extraction keys on that difference.
  5. Sort each flagged cluster into a likely-automated core and the accounts that amplify it.
  6. Tag behaviors with DISARM techniques.
  7. Score the flagged set against the published labels.

The pipeline outputs DISARM tags and never reads them back. No tag or label reaches the feature, detection, or scoring path to decide what gets flagged.

Scoring and controls

The negative class comes from the is_control field that ships with the data. Indiana includes organic control posts beside the campaign posts. Those come from accounts discussing the same topics in the same windows. Without a native control class the detector has nothing to be wrong about, so no honest precision figure exists.

The pipeline flags accounts, so I score at account level. Each account gets a majority vote over its own posts. An account counts as IO when the data labels at least half of them as campaign posts. I then compare the flagged set against those labels.

Limits

Lab metrics like these set an upper bound. This dataset is curated and labeled, with a native control class built in. Live traffic has none of that structure.

Indiana built Russia_2 at 91% IO rows. No real feed looks like that. Precision degrades as the base rate drops toward natural, much lower levels of IO, because the same false-positive rate produces much worse precision at that lower rate. The 0.54 above describes Russia_2. It does not predict what a live feed would produce.

Co-repost timing, duplicate content, hashtag floods and mention swarms signal coordination. They say nothing about authenticity. A tightly organized genuine community trips the same thresholds a paid one does, so a flag from this pipeline is not attribution. Neither is it proof that an account is fake. Someone still has to look at it before anyone acts on the result.

The parquet release hashes the posting-application field instead of shipping a readable client string. That kills the automation signal on this data. Russia_2 carries 304 distinct hash values, and none match the literal markers the automation check looks for. The automated share comes back 0.0 for every account, the bot-account technique never fires, and triage gets no automation signal here. That zero came out of the anonymized field. It says nothing about whether Russia_2 actually used automation, and I did not invent automation results to fill the gap.

Schema notes

The second source forced three decisions.

The two sources don't share a control class. Indiana has one; Clemson is positives-only. A bare boolean would have hidden that difference. A label field plus a label-scheme field records where the class came from. The original boolean survives as a projection of it, so the scoring code did not change. A third source writes its own scheme value.

Repost linkage and entity fields do not survive Clemson. Indiana gives the reposted post and account for each retweet. Clemson's retweet column is a bare flag with no pointer back to the original, so those fields stay null. Clemson also embeds hashtags and mentions in the tweet text instead of shipping them as fields. Both come back empty. A detector reading those fields sees a real absence.

The analyst-coded persona label only annotates. Clemson ships Linvill and Warren's own categories (RightTroll, NewsFeed, and so on). They exist only on Clemson rows. Nothing in the detection path reads them, because building on them would make my results source-dependent.

Build

I wrote the tool in Python. polars handles the data work and networkx builds the graph. I developed it test-first, so it ships with 30 tests. I license it under Apache 2.0. A synthetic fixture drives a one-command demo of the full pipeline, so the tool runs without the gated dataset.

Data note

I work from public and licensed research datasets only. I redistribute no dataset here and publish no account identifiers, cluster memberships, or post content. Only aggregate measurements appear on this page. Nothing here identifies individuals or attributes the campaign to an actor.
