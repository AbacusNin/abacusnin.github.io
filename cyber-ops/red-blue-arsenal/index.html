Red and blue arsenal

I built and link-verified a 1,443-tool offense and defense reference for our CTF team, then measured how much of it a security distribution actually ships.

Our university team competes in CCDC and attack/defend CTFs. In one you defend a live, scored network against a real red team. In the other, two teams attack and defend each other on shared infrastructure. Before every event the same question comes up. What tools do we actually have, and are we covered against everything the game can throw at us? I decided to answer it once and do it properly.

The catalog

I built a reference of 1,443 open-source security tools, split close to evenly between offense and defense, sorted into 28 categories. Every tool carries a one-line description of what it does and a short note on why it earns a place in a live exercise. Each one also carries a maintenance flag, so we know what is still safe to rely on.

The two sides are organized differently on purpose. The offensive categories follow the shape of an attack: recon, initial access, credentials, command and control, lateral movement, and the rest. The defensive categories are grouped by the job they do: detection, forensics, hardening, deception. Then I paired them. Every attacker capability has a matching defensive category that answers it, so we can look at an attack and its counter side by side instead of bolting detection on at the end.

Making it trustworthy

A tool list is worthless if the links are dead. I fixed the links on projects that had moved or been renamed. Archived and superseded tools got marked as such, and I flagged anything commercial or hosted outside GitHub. A lot of well-known tools have quietly moved or gone unmaintained and wanted to prevent chaff & 404s in the middle of a competition.

Comparing against BlackArch

BlackArch ships the largest security tool collection of any distro, so I compared the catalog against its full set of 2,858 packages to see what we were missing. Most of the difference was noise, old scripts and single-use proofs of concept. However, 147 tools were generally worth it and brought the catalog to 1,443.

The comparison also gave me the most useful result of the whole project. I ran it against the 1,296 tools the catalog held at that point. Only 337 of them are in the BlackArch repository. The rest, about three quarters, are not, so a fresh BlackArch image still leaves most of the arsenal to install by hand.

Two caveats sit on that number. The comparison matched on package names, so anywhere a package name and a repository name disagree, the gap is overstated. Arch's own base repositories also carry marquee tools that BlackArch's list leaves out. Nmap, metasploit, and hashcat are all in the catalog and none of them show up as gaps, so the real by-hand share sits somewhat below three quarters.

The shape of the result matters more than the exact figure. Coverage is concentrated on the offensive side and close to nothing on the defensive side. That points the team straight at where to spend setup time. The red kit is mostly a package install away, and the blue kit is the part that takes real work.

A readiness board

The last piece is a shared board the team fills in together. We pick the tools we plan to run and mark each one selected, installed, or practiced. Every pick gets a name attached. The board then shows our coverage across all 28 categories, so we can spot the gaps and the categories nobody owns while there is still time to fix them.

Why it stays private

The full inventory and the interactive tools stay inside the team, so nothing on this page links to them. This is a competition prep tool and I don't want our tooling catalog sitting out in the open. So this page is the approach. FWIW; Readiness is coverage plus ownership.
