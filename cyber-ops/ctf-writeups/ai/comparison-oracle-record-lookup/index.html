The Kiosk That Told Me Which Way to Guess

The kiosk kept its record ID to itself. Then it told me which side of each guess the record was on. That was enough.

Summary

The challenge. Find the one valid four-hex-digit record identifier within the kiosk's attempt cap and receive the flag.

What I did. I learned the response grammar with a well-formed miss, searched the remaining ordered space by midpoint, and submitted the final candidate.

The result. The case record reports that the final identifier was accepted and the flag was released.

The limit. The interaction transcript and attempt-cap value were not retained; the bundled scripts validate the method against a synthetic oracle, not the live kiosk.

1. Problem Statement and Threat Scenario

The self-service kiosk had exactly one record it would accept. Its identifier had a fixed prefix and four hexadecimal characters. I could send candidate IDs to the kiosk, but I could not inspect a local database or download an artifact. The goal was to give it the valid ID and collect the flag it released.

Four hex digits make 65,536 possible suffixes. That is small for a computer and much too large for a chat interface with an attempt cap and a cooldown. The prompt also described the kiosk as honest about what it found. I took that seriously. If the kiosk's answer contained more than a plain yes or no, the answer might be more useful than the guess.

The exercise did not supply a real attacker or a real service. In the defensive sections I treat the kiosk as a model of an unauthorized record-lookup endpoint. That analogy depends on a specific boundary: a caller who has not proved a right to the record can still ask the service a question about the secret ID.

2. Techniques, Tooling, and Actions Taken

I started with one well-formed candidate I did not expect to match. The kiosk said the record "sorts AFTER" it. That response gave me a direction. I no longer needed to sample random IDs: every miss could rule out a whole part of the ordered space.

I also tried asking for the identifier directly and for its leading characters. The kiosk refused to disclose it in either form and pushed me back to candidate comparison. That refusal mattered. The obvious disclosure route was closed, but the ordering route stayed open. The refusal was outside the comparison budget recorded in the case notes.

I worked across 0x0000 through 0xFFFF, probing the middle of the current window. An AFTER answer moved the low bound above my guess. A BEFORE answer moved the high bound below it. I continued until one suffix remained, submitted that identifier, and received the flag according to the case record. The recovered ID and flag stay out of the public page.

I considered sending several guesses in one message to save cooldown time. I did not run that variant. Each useful midpoint depends on the previous answer, so a batch would spend scarce attempts on guesses chosen before I knew which half survived. I used one adaptive probe at a time.

3. Tooling and Scripts

I made the challenge submissions by hand. The supplied comparison search module captures the method and the mock oracle lets me test it without a live kiosk. The module expects an oracle(candidate) function, inclusive integer bounds, and an optional maximum query count. It returns the matched value, query count, and trace. It raises an error for a response outside AFTER, BEFORE, or MATCH rather than silently treating it as a direction.

Here is the decision at the center of the loop:

mid = (lo + hi) // 2
response = oracle(mid)
if response == "MATCH":
    return mid
if response == "AFTER":
    lo = mid + 1
elif response == "BEFORE":
    hi = mid - 1
else:
    raise ValueError("unexpected oracle response")

For this exact floor-midpoint routine, the first candidate over the full 16-bit range is ID-7FFF. A synthetic secret above it produces this kind of trace:

ID-7FFF -> AFTER   remaining 0x8000-0xFFFF
ID-BFFF -> BEFORE  remaining 0x8000-0xBFFE
ID-9FFF -> AFTER   remaining 0xA000-0xBFFE
...                 keep narrowing from the last answer

The prefix is a stand-in. I use fixed-width uppercase hex in this example because it preserves numeric order under ordinary lexicographic comparison. That assumption needs checking against a real endpoint's casing and collation rules. The files use only Python's standard library. Running the module in its intended artifacts/ and fixtures/ layout performs an offline self-check; it does not send requests to the challenge.

4. Concept Explanation

A comparison oracle tells me where a hidden value sits relative to my candidate: higher, lower, or equal. One answer partitions the remaining space. With a midpoint guess, the larger surviving side is about half as big as the previous window. The kiosk's phrase "sorts AFTER" was enough to recognize that interface.

There are 16^4 = 65,536 = 2^16 possible suffixes. Sixteen yes/no answers can distinguish that many possibilities in principle. The supplied algorithm keeps asking until it receives MATCH. Across every possible 16-bit secret, its observed query distribution peaks at 16 except for 0xFFFF, which needs 17 calls. The difference matters under a hard cap: narrowing the window to one candidate can establish the answer after 16 directional responses, while asking the kiosk to accept that candidate can spend one more attempt. The first exploratory miss could also cost an attempt if the platform counts it. I cannot give an exact session total because the interaction log and cap value were not retained.

The integer model works for equally long uppercase hexadecimal suffixes under ordinary character ordering: 0 through 9 precede A through F in both representations. A variable-width ID, case-sensitive mixed alphabets, locale-aware collation, or server-side normalization could break the equivalence. I would test the endpoint's real ordering before relying on the math outside this exercise.

5. Exploit / Analysis Mechanics

The kiosk wanted a valid identifier before releasing the flag. Its direct-disclosure rule held when I asked for the ID. The leak was in the comparison answer. Each AFTER or BEFORE response exposed a function of the protected value to an unauthenticated caller. Repeating that question adaptively recovered the value.

The method needs a finite ordered keyspace, a truthful and stable comparison, and enough queries to finish. Those conditions were present in the puzzle. Starting at [0x0000, 0xFFFF], I removed every value on the wrong side of each guess. A MATCH would end the search immediately; otherwise the surviving interval stayed contiguous and kept the secret inside it. Once only one value remained, the ordering responses had already identified it. The final accepted submission was the case's success check.

The record does not include a full prompt-by-prompt transcript, so I cannot replay the live kiosk's path or quote every response. The deterministic convergence and query bound are independently testable with the synthetic oracle. They support the method; they do not substitute for a preserved live response log.

6. Lessons Learned

The useful probe was the one that taught me the response grammar. If I had started guessing IDs without reading the miss carefully, I could have spent the whole allowance on random values. I had 16 bits to recover and a cap above the search cost, so I needed the answer to each guess to do more work than a blind hit-or-miss test.

The direct request refusal was also informative. It showed the kiosk had a disclosure rule, but that rule did not cover relational answers. I would look for the same gap in a real lookup API: different errors, sort hints, prefix checks, or timing differences may expose state even when the service never prints the secret.

I would fold the grammar check into the first useful midpoint next time if the query budget were tight. In this case, one exploratory probe was affordable and made the strategy clear before I committed the rest of the attempts.

7. Operational Extrapolation

The following work is my defensive extension of the puzzle. It describes what I would inspect in a real service. The challenge itself was a puzzle, with no intrusion evidence.

Individual Practitioner Development

The case gave me a clean place to practice three habits: count the keyspace, characterize the response before automating, and track the surviving interval after every answer. A noisier timing or padding oracle would need repeated measurements and uncertainty handling. Here the oracle spoke in exact directions, so the interval proof was enough.

Security Operations

For a real record endpoint, I would ask whether an unauthorized caller ever sees a relational response and whether logs retain enough context to spot adaptive narrowing. The synthetic bisection detector models one hunt: it walks request events in time order, checks whether candidates follow the interval that previous answers created, and separates a strong bisection sequence from a few ordinary lookups. It requires actor, endpoint, candidate, response class, and timestamp. Those fields are sensitive; access and retention should be limited.

If the pattern appeared in production, I would preserve the request IDs and response classes, determine whether any protected record was returned, contain the actor's access, and remove the comparison response from the endpoint. A rate rule can slow a session, but the server still needs to close the information channel.

Intelligence Operations

There was no adversary infrastructure, attribution, or campaign evidence here. I would share a behavior description with a detection team if we found this pattern in a real endpoint. I would not turn this one CTF sequence into a threat-actor claim.

8. Reusable Tools, Scripts, and Artifacts

The challenge-method files are the search module and mock comparison oracle. The module takes a truthful three-outcome callable and a bounded keyspace. Its self-check and the mock's test harness exercise generic synthetic secrets. The code does not model cooldowns or know a live service's attempt cap, case rules, or response parsing.

The separate defensive proof of concept is the bisection hunt, with synthetic events, expected findings, local tests, and a run and field guide. It consumes newline-delimited JSON request events and prints JSON findings. The positive actor follows midpoints and ordering answers. A benign actor makes a few unrelated lookups. A near miss repeats a candidate without narrowing. These are tests of local logic, not measurements from a production sensor.

The distinction matters. The search module demonstrates how the puzzle was solved. The hunt is something a defender could adapt after mapping real application fields and privacy requirements. Neither file contains the recovered ID or flag.

10. Threat Intelligence and Standards Integration

The puzzle produced no durable IOC: no hostile domain, IP address, file hash, malware sample, or actor identity. A STIX Indicator or TAXII feed entry would imply evidence I do not have. If this behavior were seen across real applications, a knowledge-base entry describing the comparison-oracle pattern and a proposed Course of Action could help teams share a fix. I did not create a STIX bundle for one synthetic sequence.

The most useful exchange item now is a field-level detection contract: endpoint name, actor or session key, candidate suffix, ordering response class, event time, and request ID. With that, an application team can test the local hunt on approved telemetry and decide whether the behavior merits a rule. A production detector still needs field mapping, baseline traffic, access controls for logged IDs, and false-positive review.

11. Controls Mapping and Mitigation Realization

These controls are proposed for a real service. I did not change or retest the kiosk.

Standards Mapping

Guidance Case-specific use Boundary
CWE-204 mitigation Give unauthorized callers the same minimal miss response, without sort direction or detailed error differences. A uniform message must also be checked for status, size, and timing differences.
NIST SP 800-63B rate limiting Apply when the ID is actually an authentication secret. This is authentication guidance, not a universal numeric limit for record lookup APIs.
OWASP API6:2023 Bound automation of a sensitive lookup flow. Anti-automation controls supplement the response fix.

Mitigation Realization

First, remove the AFTER and BEFORE branches from the external response contract. Return a uniform unauthorized result, and keep detailed diagnostics on the trusted side. Then test the full observable surface: body text, status code, length, and timing. That is the primary fix for the channel I used.

Second, stop treating a four-hex-digit identifier as proof of authorization in any real application. If an ID is meant to be secret, issue a high-entropy unpredictable value and bind access to authenticated identity and object-level authorization. The service should verify the actor can access this record even when the ID is correct. A bigger ID makes guessing harder; it does not replace that check.

Third, set per-actor and per-resource attempt controls using real usage data. The source cap was above the cost of this search, so it could not protect this 16-bit secret while directional answers remained. Throttling and alerting buy response time. They do not make a truthful comparison safe to expose.

12. Indicators, Artifacts, and Detection Engineering

There are no host or network IOCs to list. The behavioral signal is a series of lookup guesses by one actor that follow the shrinking interval implied by earlier AFTER and BEFORE replies. A raw volume threshold would see some of this, but it would also see legitimate bulk use. The midpoint sequence is more specific.

The proposed Python hunt expects JSONL events with timestamp, actor, endpoint, candidate, and response. It groups by actor and endpoint, orders events, and checks consecutive midpoint guesses against the interval implied by each response. Its threshold is configurable and deliberately a local triage setting. It reports the actor, endpoint, query count, and request times. It does not publish candidate IDs in the finding.

The fixture gives a positive sequence, a low-volume benign sequence, and a repeated-guess near miss; expected findings state the one synthetic result. The tests also check a long gap and reject a timestamp without a timezone. The guide includes field mapping, run command, tuning, privacy, and validation limits. A real API may use several sessions, multiple records, normal binary-search features, or hidden candidate transformations. Those cases need an endpoint-specific design and baseline. This test has no production telemetry, no measured precision or recall, and no claim of a deployable SIEM rule.

For incident response, I would preserve the exact request and response sequence with a narrow retention window, check whether the final lookup succeeded, and compare the account's authorization state to the record accessed. I would then revoke access if needed and fix the response behavior. The sequence can show attempted enumeration; it cannot by itself identify the human behind the requests.
