Three Keys Were Already in the File

I chased the compression marker first. The useful bytes were sitting in the file's own labels.

Summary

The challenge. Recover a flag from a roughly 169-byte file whose prompt hinted at three keys.

What I did. I checked the claimed format, tried and rejected decompression and simple XOR keys, then dragged a known flag prefix across the payload.

The result. The account reports a 16-byte key assembled from three file regions and a 40-byte decode with a flag and four trailing bytes matching the next key bytes.

The limit. The challenge binary, exact offsets, full flag, and grading receipt are absent, so the reported recovery cannot be replayed from this account.

At-a-Glance Attack Chain

The prompt said three keys. I first read that as three separate secrets. The file gave me a better answer: three visible regions supplied pieces of one repeating XOR keystream. I needed the expected flag prefix to find the first piece, then the nearby structure let me assemble the rest. The flow above keeps the failed paths in view because each narrowed the search.

1. Problem Statement and Threat Scenario

I received one small binary, about 169 bytes, and a hint that "three keys" would unlock its flag. The leading bytes made it look like an Apple icon container. My goal was to recover an embedded plaintext string. There was no service to query and no source code to run. I could inspect the bytes, test hypotheses, and compare any recovered text with the expected flag form.

The real-world analogy is a file that advertises one format while carrying an obfuscated payload. This challenge did not establish a malware sample, actor, or evasion campaign. The format claim and payload construction gave me a way to practice file triage and key reconstruction.

2. Techniques, Tooling, and Actions Taken

2.1 File fingerprinting and structure walk

I started with file, strings, a size check, and a hex walk. The magic suggested an icon container, but the neighboring bytes did not fit the structure I expected. The notes describe repeated format-like tokens after null bytes, a name chunk, an lzma marker, a label ending in :, and a five-byte compression-looking header. A 169-byte icon is small, but size alone cannot decide validity. The useful discrepancy was the claimed structure failing to make sense when I walked it, not a universal one-kilobyte minimum.

2.2 Hypothesis 1 - Direct decompression (rejected)

The compression marker made decompression worth a quick test. I tried the full file, the bytes from the apparent stream header, a version with the label removed, raw-mode parameter sweeps over dictionary and lc/lp/pb settings, and alternate uncompressed-size fields. Each path failed with a corrupt-stream result. The colon-terminated label sat where a straightforward compressed stream should have continued. I stopped treating the marker as proof of compressed payload data. The missing binary prevents a fresh parser replay here, so those failures are recorded from the solve notes.

2.3 Hypothesis 2 - Simple repeating XOR with visible tokens (rejected)

I tried each printable token as a repeating XOR key, then pairs and triples of those tokens, and a full 256-value single-byte XOR sweep. None exposed the expected flag prefix. Layering separate XOR streams can create a longer effective period, but it did not resolve this file. My mistake was assuming the key would consist only of whole printable tokens. The answer included version and length bytes and part of an adjacent label.

2.4 Hypothesis 3 - Known-plaintext crib drag (productive)

I slid the expected six-byte flag prefix across the suspected payload and XORed it with each six-byte window. The implied key fragment at offset 0 was mostly printable but ended in a control byte. At offset 1, the fragment matched the file's repeated outer chunk marker and its version byte. That match connected the cipher to the file's own header. The byte before the payload was :, consistent with the label terminator I had seen in strings. I moved the payload start one byte forward.

The crib-drag function reproduces the calculation on invented data. Its printable score only ranks candidates. A matching file-region byte sequence and a complete decode are stronger checks.

2.5 Hypothesis 4 - Structural keystream concatenation (correct)

I extended the fragment by comparing candidate plaintext characters with the next ciphertext bytes and checking the implied key bytes against visible regions. The notes describe three pieces:

Keystream positions File-derived piece Length
0-4 Outer chunk marker and version byte 5
5-10 name chunk data: a three-byte token, length-style byte, and two-byte token 6
11-15 Compression chunk's four-byte type token and first label byte 5

Those pieces gave one 16-byte keystream, repeated across a 40-byte payload. The recorded decode contained the flag and four more bytes equal to the next four keystream bytes. That last observation fits four zero bytes in the ciphertext tail, because 0 XOR key = key. It does not by itself prove the encoder zero-padded the plaintext. The exact file bytes and offsets were not retained, so I cannot independently rebuild this challenge key.

3. Tooling and Scripts

3.1 Triage one-liners

These commands established size, file-type claim, visible strings, and offsets:

file artifact.bin
stat -c '%s' artifact.bin
sha256sum artifact.bin
strings -a -n 3 artifact.bin
strings -e l artifact.bin
hexdump -C artifact.bin | head -40

I also used an od -A x -t x1z -v view when the hex and ASCII columns were easier to line up there. A hash records which file I inspected; it does not prove the file's origin or make a format claim true. The actual artifact hash is not available in this account.

3.2 Reusable crib-drag primitive

For each candidate offset, the calculation is implied_key[i] = ciphertext[offset+i] XOR crib[i]. I score printable bytes as a quick sort, then look for a concrete match in the file. At offset 1, the reported match was the repeated format marker plus a version byte. The linked bounded lab exposes crib_drag() and tests this exact style of offset-one alignment with an invented fixture in test_pocs.py. A printable fragment alone is common and cannot prove the alignment.

3.3 Generic structural-keystream decoder

Once I knew the three source regions, the decode was ordinary repeating XOR:

key = region_one + region_two + region_three
plaintext = bytes(value ^ key[i % len(key)] for i, value in enumerate(ciphertext))

The decoder takes explicit zero-based KeyRegion offsets, a payload offset and length, and the local file bytes. It validates slice bounds and never executes the result. The exact challenge offsets are absent, so the README and tests use synthetic regions rather than publishing placeholder hex values as runnable code.

3.4 Self-consistency sanity check

I checked the four bytes after the recorded flag terminator. Under the recovered key, the decrypted tail matched the next four key bytes. The corresponding ciphertext tail was zero. This checks the candidate key and boundary against a second observed pattern. It provides no cryptographic integrity guarantee: an arbitrary file could be constructed to satisfy it, and I cannot retest the challenge without the binary. The linked zero_ciphertext_tail() makes that limited check explicit and the tests include a one-byte boundary near miss.

3.5 Fallback path (not executed but prepared)

If the file bytes had not supplied the key, I would have estimated a repeating key length with normalized Hamming distances, then tried per-column frequency analysis using the known flag prefix and brace. That was a prepared path, not an executed solve. With only 40 payload bytes, any key-length ranking would have limited evidence; I would compare several candidates rather than trust the smallest score.

4. Concept Explanation

4.1 XOR as a stream cipher

XOR undoes itself: a XOR b XOR b = a. A secure one-time pad needs a uniformly random, secret keystream at least as long as the message and never reused. This file used a short repeating key assembled from public bytes in the same artifact. Its security did not resemble a one-time pad.

4.2 Why a known plaintext is fatal to repeating-XOR

For C_i = P_i XOR K_(i mod L), each known plaintext byte reveals one corresponding key byte: K_(i mod L) = C_i XOR P_i. If I know one correctly aligned window of at least L bytes, I can recover every key position. A shorter flag prefix still anchors a fragment. I used the file's visible structure to extend it. The format and content of a CTF flag helped this case; a real sample would need its own reliable crib.

4.3 Crib drag

I did not know the payload boundary at first. Sliding the prefix across the candidate ciphertext let me compare implied key fragments at offset 0 and offset 1. The second fragment matched bytes already in the file, which turned a loose printable score into a concrete structural hypothesis. That is why I kept the : separator in the reasoning rather than stripping it without comment.

4.4 The structural-keystream pattern specifically

The three pieces were not secret keys in any practical sense. A reader with the file could extract the same 5+6+5 bytes. The unusual part of this challenge was determining their order and including nonprintable structure bytes. Once I had that, the 16-byte repetition made the rest mechanical.

4.5 File-format masquerade

Magic bytes are a first clue to file type, not a complete parse. The account reports a container length disagreement, unexpected chunk types, and a trailing layout inconsistent with the icon claim. A format-aware parser would be the next check on a real copy. I do not have the bytes to prove every claimed mismatch now. The linked shallow ICNS structure check tests header length and element boundaries on invented files; it does not validate icon image payloads or all allowed element types.

5. Exploit/Analysis Mechanics

5.1 The invariant that was violated

The file carried its own repeating key. I only needed a known plaintext window to identify the first piece and enough structural context to assemble the rest. The key period was 16 while the recorded payload was 40 bytes, so bytes from the same key positions were used more than once. The keystream's location inside the artifact removed any secrecy claim.

5.2 The math

With 16 key bytes, I decoded each of 40 ciphertext bytes as P_i = C_i XOR K_(i mod 16). The three region lengths were 5, 6, and 5. I did not need factoring, key search, or decompression after that reconstruction.

5.3 The operational steps

I cataloged the file's printable and structural regions with offsets, tested decompression, swept obvious XOR keys, dragged the expected prefix, matched the offset-one fragment to the repeated chunk marker, concatenated three file regions, and decoded all 40 bytes. I checked the four-byte tail separately. My notes describe a flag-shaped plaintext that named its own key sources, but do not retain the full text or a grading receipt. That result remains a reported outcome.

5.4 The self-consistency tell

The final four decrypted bytes equaled the next four key bytes. That implies four zero ciphertext bytes at those positions for this candidate key. It supports the key alignment and payload boundary. It cannot prove the exact encryption workflow or flag acceptance. In a real case I would keep the raw file, exact offsets, code, and output so another analyst could check the inference.

6. Lessons Learned (Practitioner Perspective)

6.1 What the exercise validated

The small triage commands helped me see that the file type claim and internal markers needed more scrutiny. The offset-one crib match was the real pivot. I kept the bad offset-zero candidate and failed decompression attempts because they explain why I looked one byte past the colon.

6.2 Gaps and inefficiencies surfaced

The compression marker held my attention longer than it deserved. I also tried whole printable tokens before considering version and length bytes. Next time I would catalog all nearby bytes and offsets at the start. That would still leave decompression as a cheap check, but it would keep the structure in view.

6.3 Transferable principles

This case A later investigation
Compare magic with parsed structure Keep the file-type claim separate from parser evidence
Preserve the failed stream parse Explain why a marker was camouflage rather than content
Test the crib at adjacent offsets Avoid assuming the separator is part of ciphertext
Match implied key bytes to the file Require an actual byte-level link beyond printable output
Check the tail against the key Use a second invariant while keeping its limits clear
7. Extrapolation

7.1 Individual practitioner skill development

I would carry this method into malware unpacking and suspicious-file triage: record exact offsets, reconstruct a key or transform from file bytes, and test a known plaintext window. Stronger ciphers with bad modes and nonce reuse need different analysis; this simple XOR result does not generalize to AES or RC4 by itself.

7.2 Security operations (SOC, IR, threat hunting)

A useful production hunt would begin with files that claim a format yet fail a real structural parser, then ask which process wrote them and which process later consumed them. A small size can prioritize triage, but a fixed <1024 bytes rule would miss padded payloads and flag legitimate tiny files. File extension, magic, declared length, element boundaries, origin, and process context matter together. The linked ICNS structure aid supplies a local first pass; a full icon validator would need more checks.

The event-correlation idea also needs the right sensors. Sysmon Event ID 11 records file creation, and Event ID 1 records process creation. Neither by itself proves a later read of the file. A writer-then-reader hunt needs file-access or EDR open telemetry with a stable file identity, plus a process record. No such events were supplied in this challenge.

7.3 Intelligence operations

If I saw this construction in multiple real samples, I would catalog the exact region order, separators, key period, and decoded content alongside hashes and collection context. Reuse might be a clustering clue. A shared lzma string or icon magic is common enough that it cannot identify an actor. No campaign comparison or attribution was performed here.

8. Reusable Tools, Scripts, and Artifacts

8.1 Triage decision tree

I start with size, magic, declared length, and a bounded structural parse. If that is inconsistent, I list visible tokens and their offsets, then test the suspected payload with a known crib at nearby boundaries. When an implied key fragment matches file bytes, I assemble candidate regions and decode the whole payload. If it does not, I can return to key-length estimation or other encoding families. I avoid turning a parser failure alone into a maliciousness verdict.

8.2 Modular primitives (already provided in Section 3)

The structural XOR lab contains crib dragging, explicit region concatenation, repeating XOR, and the narrow zero-ciphertext-tail check. The structure check walks ICNS-style length fields. The tests cover a malformed claim, a structurally plausible benign fixture, a non-icon near miss, a three-region synthetic key, an offset-one crib, and invalid ranges. The guide states the inputs, outputs, bounds, and what the checks do not establish. My Hamming/frequency fallback was not used in the solve and is not presented as a validated tool.

8.3 Solve-pattern checklist

I would save and hash the file, record its claimed type and exact size, inspect strings and a full hex view, test a format parser, identify candidate payload ranges, crib-drag at nearby offsets, match implied key bytes to structural regions, decode all bytes, and check the tail. The final record should include original bytes, offsets, code, and result. This case account lacks those challenge bytes, so the linked fixture stays clearly synthetic.

9. Framework Mapping

9.1 MITRE ATT&CK

T1036.008, Masquerade File Type and T1027.013, Encrypted/Encoded File describe plausible adversary uses of this pattern. The challenge file demonstrates the mechanics, without evidence of a real adversary deployment. T1140 concerns adversary-side decoding during execution; my manual recovery is a defender action. T1001 would require a communication channel, which this offline file does not have.

9.2 MITRE D3FEND

File analysis and content inspection fit the defensive work I did. File carving can help locate an embedded payload boundary, and a real companion unpacker might call for dynamic analysis in an isolated environment. No executable unpacker or endpoint policy was supplied. I would select specific D3FEND mappings after defining the actual detector and collection point.

9.3 MITRE CAPEC

CAPEC-636, hiding malicious data or code within files, is an analogy if a real file carries a malicious payload. This CTF account does not show executable code or malicious use. I also considered CAPEC-468, cross-domain theft, but found no evidence of it here.

11. Controls Mapping and Mitigation Realization

11a. Standards Mapping

The notes mapped NIST SP 800-53 SI-3, SI-4, SI-7, AU-2, AU-6, and CM-7, plus CIS 8.5, 13.6, and 16.10. For a real file-ingest product, structural validation and useful logging would be sensible design work. Application allowlisting may limit a known unpacker, but it does not prevent arbitrary readers from opening media files. No host policy or SIEM was assessed here.

11b. Mitigation Realization

The proposed YARA had redacted magic bytes and a made-up minimum size, so it was not runnable. Its second rule mixed icon magic, an lzma string, a colon, and a size threshold; those pieces can occur without a hidden XOR payload. I would test an actual file parser before promoting a signature. The shallow structure aid checks header and element lengths on local bytes, and tests include a bad claim, plausible fixture, and non-icon near miss. It does not validate icon image content.

The proposed Sigma rule promised a file write followed by a non-media process read. Its event selection mixed Sysmon Event ID 11 with Event ID 1, which reports process creation rather than file reads. The SPL grouped mixed events by a file name field that may not exist on both. A usable correlation would need actual file-open telemetry, event field mapping, identity, and a time window tested against benign workflows. I would implement structural parsing during ingestion with a maintained parser for the exact accepted format and bound file size and parser work. This local proof does not claim full parser coverage.

12. Indicators, Artifacts, and Detection Engineering

12.1 IOCs (illustrative; sanitize for your environment)

No real hash, path, domain, host, or actor indicator is retained. A small file, extension mismatch, lzma label, or interpreter process pair is a triage condition, not an IOC by itself. I would keep parser evidence and file provenance with any alert.

12.2 YARA, Sigma - provided in Section 11b

I did not publish those placeholder rules as tested detections. The local structural checker and XOR lab are linked above, with their boundaries in the guide. They can help an analyst understand a file; they do not replace a format-aware production parser or correlated endpoint telemetry.

12.3 SIEM queries

The proposed ES|QL and KQL joined a file-create event to process execution within five minutes, sometimes by host alone or by command-line text. That would not prove the process read this file. Some suggested fields, including FileSize on a Sysmon FileCreate event, require enrichment from another source. I would first test the event schema and obtain file-open telemetry, then join on stable file and process identifiers. There is no SIEM backend or fixture from this challenge to validate an SPL, KQL, or ES|QL query.

12.4 Log source and data pipeline requirements

The local parser needs the file bytes and a bounded read. A production correlation needs a trusted parser verdict, file-create and file-open events, process identity, clocks, and retention suited to the investigation. Sysmon FileCreate and ProcessCreate alone are insufficient for the proposed read sequence. Zeek files.log might provide network file context when a sample traverses monitored traffic, but this challenge had no network source.

12.5 Detection engineering notes

The static structure aid has a positive malformed sample, a benign structurally plausible sample, and a non-ICNS near miss. A valid length walk still cannot prove a file is a valid icon. Size thresholds and extension filters need a measured local baseline; no one-kilobyte cutoff or thirty-day baseline was measured here. An attacker could pad above a threshold. I would prefer parser evidence and process context, then test false positives before alerting.
