# Defensive proofs of concept: file-derived XOR key

These files are newly authored analysis aids. They contain an invented fixture, no challenge binary, no original key offsets, no flag, and no platform receipt. Run `python -B test_pocs.py` from this folder. The three tests cover malformed, benign, and near-miss file structure; a three-region 16-byte key and offset-one crib; a zero ciphertext tail; and invalid ranges.

`structural_xor_lab.py` takes bytes from a file an analyst already has, explicit zero-based `KeyRegion` offsets and lengths, and a payload offset/length. It returns bytes and never executes them. The maximum input is 1 MB, with up to 16 key regions and 4096 key bytes. Preserve the original file and record its hash separately. A printable crib fragment is only a candidate; verify it against file bytes and the full decode. The zero-tail check confirms a ciphertext-tail property for a chosen boundary. It does not establish what plaintext padding the encoder used.

`icns_structure.py` is a shallow structural triage check. It verifies the `icns` magic, declared total length, and a complete walk of element length fields under a 1 MB bound. It reports `not_icns`, structurally invalid, or structurally plausible. It does not know all allowed icon element types or validate embedded image data, so a plausible result is not proof of a valid icon. A 169-byte file can be valid or invalid depending on its structure; size alone is not a verdict. The positive fixture has a bad declared length; the benign fixture has internally consistent lengths; the near miss has no `icns` magic. No actual icon corpus, endpoint sensor, YARA/Sigma backend, or production workflow was tested.

The scripts consume local bytes rather than telemetry. A production file-ingest pipeline would need bounded format-specific parsing, provenance, and error handling. A SOC hunt would need real file bytes or a trusted parser result plus separately mapped process events; Sysmon file creation alone cannot prove a later file read.
