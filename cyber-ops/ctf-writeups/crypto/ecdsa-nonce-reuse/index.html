Three Firmware Signatures, One Reused Nonce

Twelve firmware signatures were enough to expose a signing key. Three of them shared the same r value.

Summary

The challenge. Identify the firmware versions with a reused ECDSA nonce, recover the signing key in decimal, and decrypt the flag.

What I did. I grouped the signatures by r, solved the two-signature equations, compared all three pairs, and tried the recorded AES key candidates.

The result. The recorded solve found one scalar across all three pairs and a flag-format plaintext after SHA-256 truncation and AES-128 decryption.

The limit. The JSON log, private scalar, ciphertext, plaintext, and acceptance receipt are unavailable here for an independent replay. The linked signing-log audit uses invented events.

1. Problem Statement and Threat Scenario

I started with a fictional device's firmware-update log. It described ECDSA on secp256k1 with SHA-256, gave the signer's public key, and listed twelve firmware versions. Each record carried a message hash and signature (r, s). A separate 16-byte encrypted flag made this more than a signing-key question: I had to identify the versions that shared a nonce, recover the private scalar as a decimal integer, then find the AES key that decrypted the flag.

The log was the whole investigative surface. I had no signer, firmware image, or live device. In a real update service, signatures and public keys may be widely visible while the private key stays protected. Reusing an ECDSA nonce breaks that boundary. This challenge simulated the math of that failure; it did not document an actual compromised signing service.

2. Techniques, Tooling, and Actions Taken

I parsed the twelve records into (r, s, h) integers and grouped them by r. Three versions landed in one group. That was the cheapest useful check: one pass through the log before touching modular arithmetic. The version strings are not included in this public record.

I then used two distinct message hashes from that group to solve for a candidate nonce k and private scalar d modulo the secp256k1 group order. I repeated the calculation for all three pairs; the recorded results agree on one scalar. The step order is a reconstruction, not a live terminal transcript.

There was a brief detour over the shared r. It was reported as incorrect, so the value was parsed again. The second parse matched byte for byte and the objection was retracted as a read error. I kept the value and moved on. The later uncertainty was real: the challenge had not specified how to turn d into an AES key. The recorded sweep contains seven candidates, six rejected outputs, and one candidate with exact PKCS#7 padding and the expected prefix. Section 3 names five of those candidate forms and the two others noted in the trace; it is a reconstruction, not a terminal transcript.

3. Tooling and Scripts

Python's json module handled the log. Integer arithmetic and pow(x, -1, n) supplied modular inverses. The recorded AES step used PyCryptodome and hashlib. Here is the recovery core in a form that shows the actual input relationship without exposing the challenge values:

N = 0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFEBAAEDCE6AF48A03BBFD25E8CD0364141

def recover_same_k(h1, s1, h2, s2, r):
    k = ((h1 - h2) * pow((s1 - s2) % N, -1, N)) % N
    d = ((s1 * k - h1) * pow(r, -1, N)) % N
    return k, d

The equation assumes the two signatures used the same signed nonce. ECDSA can also give the same r for k and n-k; low-s normalization can change the observed sign of s. A general verifier should test the applicable sign branches and check that d*G equals the supplied public key. The recorded three-pair convergence is strong internal consistency, but I have no public-key comparison output to report.

The candidate forms were raw 32-byte d, its first or last 16 bytes, MD5 of the hex representation, MD5 of decimal text, full SHA-256, and the first 16 bytes of SHA-256 of d bytes. The recorded winner was SHA256(d_bytes)[:16]. A 32-byte candidate would request AES-256, while a 16-byte candidate requests AES-128; the code must choose the matching key length. The ciphertext was one 16-byte block, so AES-ECB was the challenge's single-block test. I would not carry ECB into a new product design.

from hashlib import sha256
from Crypto.Cipher import AES

d_bytes = private_scalar.to_bytes(32, "big")
aes_key = sha256(d_bytes).digest()[:16]
plain_block = AES.new(aes_key, AES.MODE_ECB).decrypt(ciphertext_block)
pad = plain_block[-1]
assert 1 <= pad <= 16 and plain_block[-pad:] == bytes([pad]) * pad

4. Concept Explanation

An ECDSA signature starts with a private scalar d, message hash h, and one-use secret scalar k. The signer computes R = k*G, takes r = R.x mod n, then computes s = k^-1(h + r*d) mod n. The public key is Q = d*G. The value r is public, and under a fixed curve it is tied to the nonce's elliptic-curve point.

If two distinct messages are signed under the same key with the same nonce, their s equations share the same unknowns. Subtracting them cancels r*d, leaving k; substitution then gives d. A repeated r is the cheap symptom to investigate. It can also occur when the same digest and signature are logged twice, when deterministic signing repeats an identical message, or through the k versus n-k symmetry. I would separate those cases before calling an operational alert a confirmed key loss.

5. Exploit/Analysis Mechanics

The failed invariant was a fresh effective nonce for each distinct message. For two signatures with the same signed k, the calculation is:

s1 - s2 = k^-1 (h1 - h2)                   mod n
k = (h1 - h2) * (s1 - s2)^-1              mod n
d = (s1*k - h1) * r^-1                    mod n

The inverses exist when their operands are nonzero modulo the prime group order. I would reject a pair where s1-s2 or r has no inverse rather than force a result. In the record, all three pairwise calculations converged. With the actual log and public point available, the additional check would be d*G == Q, followed by signature verification. Convergence alone does not replace those checks.

Once d was known, the encryption layer was a separate puzzle. The recorded result says SHA256(d_bytes)[:16] decrypted the 16-byte block to 13 bytes of plaintext and three bytes of PKCS#7 padding. Valid padding on its own is a weak discriminator for a single trial. The expected prefix and reported acceptance made the chosen derivation persuasive. The public record withholds the raw block and answer, so that validation cannot be rerun here.

6. Lessons Learned (Practitioner Perspective)

I liked how little work the first check needed. Grouping twelve r values exposed the interesting trio immediately. The hard part was refusing to promote that first collision into a complete result before checking the hashes, the sign branch, and the recovered scalar.

Three pairwise recoveries agreeing gave me more confidence than one equation. The KDF sweep then reminded me that key recovery and payload decryption are different claims. I tried simple encodings and hash forms because the challenge supplied no derivation rule. Six candidates failed by the recorded output checks. That is a bounded search, not evidence that every possible KDF was considered.

The mistaken "incorrect" signal for r was useful in another way. I went back to the bytes rather than changing the arithmetic to fit a comment. The reparse matched. When the evidence is reproducible, a disagreement should trigger a check of representation and scope before a new theory.

Exercise move Practice I would carry forward
Group r values first Search public signing records before expensive analysis.
Compare all three pairs Check independent paths and the published public key.
Try bounded KDF forms Record rejected encodings and the exact acceptance test.
Reparse after the objection Resolve a reading dispute from bytes, not intuition.
7. Extrapolation

In a real firmware pipeline, I would begin with the signer's own audit trail: key ID, curve, digest, signature, artifact version, and timestamp. If one key emits the same r on distinct digests, I would preserve the events, verify the signatures, test the algebra on a protected copy, and start the signing-key exposure response. Rotation, revocation, re-signing, release inventory, and entropy-source review follow only after scoping which key and releases are affected.

The same secp256k1 family appears in other signing settings, including transaction ecosystems, but this case does not establish a vulnerable blockchain wallet or a real firmware vendor. A pattern of shared r values may link signatures to a faulty signer; that alone cannot identify an actor. Bias without an exact collision would call for different analysis, possibly a lattice method, and substantially more evidence.

8. Reusable Tools, Scripts, and Artifacts

The reusable offensive primitive is the two-signature algebra in Sections 3 and 5. To apply it responsibly to a new record, I would collect (key_id, curve, r, s, h) per operation, group by key and r, exclude identical-digest repeats, account for s sign conventions, recover candidate scalars from distinct messages, and verify against the public key. The final step is to inventory what that key signed, not to stop at the number printed by a script.

For defenders I made a small JSONL collision reviewer. It emits a review lead when one key and curve reuse r with different signature data, and marks distinct message hashes as urgent. The invented fixture contains a collision, an identical retry, and a different-key near miss. The four checks cover those paths and malformed input. The README specifies the signing-service fields, 5 MB and 50,000-line bounds, output, and limits. None of these files contains the challenge signature or a recovered key.

10. Threat Intel and Standards Integration

I have no actor, malicious infrastructure, campaign, or real exposed signing key to share. The challenge-specific r, private scalar, and ciphertext are withheld. I would not manufacture a STIX object or TAXII feed from them. If the same flaw surfaced in an actual product, an advisory would need affected key IDs, release scope, fix status, and distribution guidance; those facts are absent here.

The useful standards connection is how a signer chooses and protects k. RFC 6979 specifies deterministic ECDSA nonce generation from private-key and message material through an HMAC-based process. FIPS 186-5 is a digital-signature standard, but citing it does not make a secp256k1 implementation FIPS validated. There is no system configuration here from which to assign a STIG finding.

11. Controls Mapping and Mitigation Realization
Control Application to a real signer
NIST SP 800-53 SC-12 / SC-13 Govern key management and cryptographic protection. Select an approved, maintained signing implementation for the deployment's actual compliance scope, protect private keys, and test nonce generation.
NIST SP 800-53 SI-7 Verify firmware integrity and maintain a trustworthy release/signing record. A collision review can inform incident response; it does not itself prove every distributed image is valid.
CIS Controls v8 16.5 Use maintained, trusted components in the signing pipeline; pin and review the library and its build provenance.

Python's SigningKey, SECP256k1, and sign_deterministic can illustrate deterministic signing. The important distinction is between a message and an already-computed digest. Passing a digest to an API that hashes again changes what is signed. A message-level example is:

from hashlib import sha256
from ecdsa import SECP256k1, SigningKey
from ecdsa.util import sigencode_der

sk = SigningKey.from_secret_exponent(private_scalar, curve=SECP256k1)
signature = sk.sign_deterministic(firmware_bytes, hashfunc=sha256, sigencode=sigencode_der)

That code shows the intent. It does not establish deployment readiness or FIPS validation. A production signer should use the selected library's documented digest API if the firmware hash was computed elsewhere, maintain key isolation and release approval, and test signature verification and nonce behavior before rollout.

12. Indicators, Artifacts, and Detection Engineering

The detection idea is a repeated r under one key, on different message digests. A real sensor is the signing service or a verified feed of its signature records. A network-only SIEM feed that logs only "sign succeeded" cannot run this check. A Sigma selection on EventType=Signed captures candidate events but does not express the cross-event collision. SPL must group by key and curve as well as SignatureR; otherwise it can mix unrelated signers. I would start with a query shaped like this, after mapping actual field names:

index=codesigning EventType=Signed
| stats dc(MessageHash) as distinct_hashes count values(ArtifactVersion) as versions by KeyId Curve SignatureR
| where distinct_hashes > 1
| table KeyId Curve SignatureR versions count distinct_hashes

This is a proposed hunt, not a tested Splunk rule. The local reviewer implements the key/curve/r grouping on synthetic events, and its test file includes a benign identical retry and a different-key near miss. An operational response would re-read the raw signature bytes and verify the public key before treating the lead as confirmed compromise. There is no measured false-positive rate, backend conversion, live sensor, or production deployment here. A repeated r on distinct hashes is urgent; a duplicate log, normalization issue, or key-ID error still needs to be ruled out.

No challenge-specific scalar, ciphertext, or r belongs in an IOC feed. This case's reusable artifact is the detection condition and the response path, not a value to block across organizations.
