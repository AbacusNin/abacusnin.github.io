The Caesar Shift That Changed at Every Position

I had an 83-character ciphertext, a verse-shaped hint, and the expected opening of the answer. The first few letters gave away the shift pattern.

Summary

The challenge. Recover the plaintext from one positionally shifted ciphertext using the in-band hint and known answer format.

What I did. I compared ciphertext letters with the known prefix, derived offsets 0 through 5, and decoded the whole string using absolute character positions while leaving punctuation unchanged.

The result. The recorded local decode produced coherent plaintext with the expected prefix and format. No scoreboard acceptance receipt is available.

The limit. The challenge ciphertext and answer are withheld. The linked reviewer and fixture use an invented 42-character example, not the 83-character challenge input.

Positional Shift Cipher (Progressive Caesar)

1. Problem Statement and Threat Scenario

This one was small enough to hold in my head. The challenge gave me an 83-character ciphertext and a hint written as a verse. It described a shift applied one character at a time, increasing as the string advanced. Braces and underscores stayed as they were. The expected answer format gave me a few plaintext letters at the front.

There was no host, file format, packet capture, or adversary action to reconstruct. The useful question was whether a weak position-based substitution could be recovered from a known prefix. That is a narrow cryptographic exercise, and I kept the operational claims narrow too.

2. Techniques, Tooling, and Actions Taken

I began with the hint instead of trying every classical cipher. A constant Caesar shift could not explain the different offsets forced by the known prefix. Six alphabetic crib positions gave offsets of 0, 1, 2, 3, 4, and 5. That pointed to a shift that grows by one at each absolute character index.

Step What I checked
ST.1 I classified the transform as alphabetic shifting with nonletters passed through. The ciphertext length was 83 characters.
ST.2 I aligned the known answer prefix to the ciphertext. The six letter positions implied offsets 0 through 5; a single fixed shift could not satisfy them all.
ST.3 I used the absolute index in the original string. Braces and underscores stayed visible but still advanced the counter. An alphabetic-only counter would diverge after the first delimiter.
ST.4 I decoded the full string with Python and checked readability, the known prefix, and the expected answer format. The recorded local result passed those checks.

My only meaningful ambiguity was the counter. Before the first punctuation mark, absolute and letter-only indexing give the same letters. I did not separately execute an alphabetic-only rejection in the original solve; the absolute-index output read coherently across all 83 positions. There were no wrong submissions or dead-end branches to explain.

For each ASCII letter at absolute index i, the decoded alphabet position is:

plain[i] = (cipher[i] + i) mod 26

The equation uses letter values 0 through 25, with case preserved. The nonletters are copied to the output, while their places still count toward the next i. A general step s would use i * s; the crib here supported s = 1. The zero offset at position 0 is expected for any step, while positions 1 through 5 check the step repeatedly.

3. Tooling and Scripts

The solve used an inline Python transformation. I later wrote a small reviewer to make the indexing choice visible. The linked offline reviewer tests both absolute and letter-only indices and all 26 step values against a known prefix. Its invented ciphertext, test cases, and guide are separate from the challenge text.

def decode(ct, step=1):
    out = []
    for i, ch in enumerate(ct):
        if ch.isascii() and ch.isalpha():
            base = ord("A") if ch.isupper() else ord("a")
            out.append(chr(base + (ord(ch) - base + i * step) % 26))
        else:
            out.append(ch)
    return "".join(out)

The original illustrative code checked that the offsets were consistent with step 1, rather than solving for every possible step. The linked reviewer enumerates the steps and shows a useful near miss: a short flag{ crib lets both index bases through, because they agree until the first delimiter. Extending the crib past the brace separates them in the invented example. A prefix match still needs full-text review.

4. Concept Explanation

A Caesar cipher moves letters by one fixed amount. Here the amount changes with position. Knowing even a short piece of plaintext gives equations for that change. I measured the letter offsets from the crib, then checked whether one rule explained all of them. Because punctuation stays in place, I also had to decide whether those characters advanced the counter. The readable full decode settled that choice in the recorded solve.

This is a weak substitution, not modern encryption. A correct known prefix and one consistent step can make it easy to undo. A short crib can also match by accident, which is why the whole decoded text matters.

5. Exploit / Analysis Mechanics

I treated the format prefix as a crib. At the first alphabetic position, the offset was zero. The next five offsets increased by one. Adding the absolute index modulo 26 to each ciphertext letter produced the candidate plaintext. I copied braces and underscores without shifting them, while continuing to count their positions.

The example in the linked fixture is 42 characters, far shorter than the 83-character challenge ciphertext. It decodes as flag{Positional_Shift_Cipher_Example_Text} under absolute indexing, step 1. This is a demonstration of the rule, not a disclosure of the challenge answer.

6. Lessons Learned (Practitioner Perspective)

The hint narrowed the search, but the known prefix did the real measurement. I could rule out a constant shift before writing code because the offsets differed. The brace and underscores then became useful tests of indexing, even though they were not themselves encrypted.

This also reminded me to distinguish deriving a rule from merely seeing readable text. The crib constrained the step; readability and format checked the rest of the string. Without the ciphertext or a scoreboard receipt here, I keep the outcome at the recorded local verification level.

7. Extrapolation

For an authorized content review, a position-based shift is worth checking when a string has readable delimiters, a recognizable prefix shape, and alphabetic text that fails a fixed Caesar test. The offline reviewer gives an analyst candidate decodes. It does not decide whether a message is malicious.

I would not build a network alert that fires on this cipher name. A real hunt would need a source of content, a reason the content is suspicious, and context about the sender or process. Those observations were outside this puzzle.

8. Reusable Tools, Scripts, and Artifacts

The reviewer accepts one local printable-ASCII line up to 4,096 bytes and a crib, then reports candidate step and index basis with the decoded text. The guide describes its inputs, limits, and sensitive-output handling. Five tests cover the intended positive, a short-crib false positive, a benign nonmatch, a wrong-basis near miss, and invalid input.

The tool is a local reasoning aid. With no crib, no useful source context, or a wrong character set, it cannot certify a cipher family. A matching prefix is a candidate; the rest of the text and any independent answer check still carry the decision.
