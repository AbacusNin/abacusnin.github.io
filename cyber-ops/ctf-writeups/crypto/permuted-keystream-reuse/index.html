The Key That Changed Shape but Stayed the Same

The generator had a weak PRNG, but I did not need to attack it. The cover message gave me a cheaper way in.

Summary

The challenge. Recover a 25-byte secret from a 50-byte lowercase cover ciphertext, a second ciphertext, and the source of a homegrown XOR stream cipher.

What I did. Read the generator, derive the known bits and parity equations, enumerate four key bytes per position, then test the wrapper and plaintext constraints.

The result. The case record reports a solved secret and checks against the recovered lowercase cover. A later audit corrected the reported candidate count.

The limit. The generator, ciphertexts, cover plaintext, and submission receipt are not available for independent replay. The linked code uses synthetic examples.

1. Problem Statement and Threat Scenario

I had the source of a homemade XOR stream cipher and two ciphertexts. The first covered a 50-byte message drawn from lowercase a through z. The second covered a 25-byte secret. The generator used a 25-byte parent key for the first half of the cover, derived a child block for the second half, and encrypted the secret with each parent key byte's bits reversed.

The claim behind the construction was that both outputs looked random. The challenge was to recover the secret without an encryption oracle or a live service. I stayed with the published source and ciphertext relationship. If a design like this protected real data, the same analysis would belong in an application security review. This exercise does not establish a deployed product, an attacker, or an incident.

2. Techniques, Tooling, and Actions Taken

I started with the lengths: 50 bytes for the cover and 25 for the secret. That gave me N=25 and a plausible K || child(K) layout. I read the generator before trying to predict its PRNG. The key came from Python's random.randbytes, which is a real cryptographic problem, but the cover alphabet and the child schedule exposed a shorter path. I did not perform Mersenne Twister state recovery or brute force the 25-byte key.

My steps were these:

Step What I checked Result
ST.1 Ciphertext lengths 50 / 25, giving a 25-byte parent block and a 25-byte child block
ST.2 Generator source A lowercase cover, a child block made from parent-bit parities, and bit reversal for the secret
ST.3 Cover alphabet The top three bits of every cover plaintext byte are 011, so the top three keystream bits are known
ST.4 Child schedule Its exposed high bits give three equations over pairs of parent-key bits
ST.5 Remaining freedom Four exact key candidates per byte before the narrower a-z range test
ST.6 Reversed key The known parent bits become the secret keystream's low nibble
ST.7 Independent wrapper check The reported candidate set reproduced the required prefix and suffix; five positions were forced
ST.7a Uppercase and caret reading This branch failed the wrapper at eight positions, so I set it aside
ST.8 Language resolution The challenge's English leetspeak clue supplied the last choice in the recorded solve
ST.9 Later recount The full alphabet range test and explicit assumptions changed the claimed residual counts

That wrapper check was useful because I derived the key candidates from the cover, before asking what a flag should look like. If I had used the wrapper to construct the candidates, seeing it again would have been a circular check. The solve stayed static; the source record reports validation by re-deriving the lowercase cover and child relation, not by running a live target.

3. Tooling and Scripts

The original work used Python's standard library to turn the equations into per-position candidates. The important inputs are one cover ciphertext byte under K[j], one under child(K)[j], and the secret ciphertext byte under reverse_bits(K[j]). The output is a set of possible plaintext bytes, with an optional exact a-z range filter.

Here is the compact version of the derivation used in the synthetic keystream lab:

known = (cover_parent_ct ^ 0x60) & 0xE0
parities = ((cover_child_ct ^ 0x60) >> 5) & 7
b5 = (known >> 5) & 1
b4 = b5 ^ (parities & 1)
known |= b4 << 4

for b0 in (0, 1):
    for b2 in (0, 1):
        b1 = b0 ^ ((parities >> 2) & 1)
        b3 = b2 ^ ((parities >> 1) & 1)
        key = known | (b3 << 3) | (b2 << 2) | (b1 << 1) | b0
        if 0x61 <= (cover_parent_ct ^ key) <= 0x7A:
            candidate = secret_ct ^ reverse_bits(key)

The full lab makes its own 25-byte examples, generates lowercase covers, encrypts a synthetic FLAG{...} string, and checks that the true byte survives at every position. Its three fixed-seed trials passed locally. Each has 4^25 = 2^50 raw candidate combinations before the range filter. Those tests reproduce the mechanism; they do not replay this challenge's unavailable ciphertexts. The lab guide gives the inputs, expected outputs, and limits.

4. Concept Explanation

XOR gives the whole opening. If ciphertext = plaintext XOR keystream, a known plaintext bit gives the matching keystream bit immediately. Every lowercase ASCII letter has top bits 011. I did not need to know which letters the cover used. Its character class gave me three exact bits from every parent and child ciphertext byte.

The generator's supposed rekeying reversed bits within each parent-key byte. That moves information but adds none. If I know bit 7 of a parent byte, I also know bit 0 of the reversed byte. The second encryption remains tied to the first even though the key bytes look different on a hex dump.

The child schedule has its own problem. It puts four parities of parent-key bit pairs into a byte's high nibble, then adds random.getrandbits(4). With the low nibble initially zero, that addition cannot carry into bit 4. The fresh bits never disturb the high bits that expose the parent's parities. The key source is also Python's Mersenne Twister. Python warns that random is unsuitable for cryptographic use. My recovery did not depend on predicting it.

A true one-time pad requires independently random key material at least as long as each message and no reuse. This construction supplies enough output bytes to cover its messages, but that output is derived from the same parent material. Its lack of independent randomness and cross-message reuse defeat the one-time-pad argument. The extra child bytes are not 25 new independent key bytes.

5. Exploit/Analysis Mechanics

Let parent byte K[j] have bits b7 ... b0, and let C[j] be its child byte. The cover gives b7, b6, and b5 directly. Reading the second half of the cover gives these relations because the child high nibble stores pair parities:

bit7(C[j]) = b0 XOR b1
bit6(C[j]) = b2 XOR b3
bit5(C[j]) = b4 XOR b5

I already know b5, so the last relation gives b4. That leaves b0 and b2 free; the other two low bits follow from the first two parity equations. There are exactly four parent-key bytes at each position before checking the full lowercase range. The child byte's low nibble does not reveal the remaining parent bits; those random bits still leave multiple possible child values.

Bit reversal now turns the leak toward the secret. Known parent bits b7..b4 land in output bits 0..3. The secret plaintext's low nibble is fixed at every position. Its high nibble has four possible values. For N=25, the raw combination count is 4^25 = 2^50, compared with 2^200 possible 25-byte plaintexts before using these constraints. The source's later recount places the result around 2^47 after enforcing 0x61..0x7A rather than only the shared 011 prefix.

The reported solve also worked backward from the recovered secret to a parent key, XORed the cover ciphertext, and obtained lowercase letters at all 25 parent positions. The child parity relation reportedly held at all 25 positions as well. Those are stronger checks than seeing a plausible flag wrapper. I cannot independently repeat them without the ciphertext bytes or generator output. The actual cover plaintext and secret bytes are not printed here.

6. Lessons Learned (Practitioner Perspective)

I almost had an easy story: the recovered text fit, so the remaining search space must have been tiny. My later count showed that I had blurred a cryptographic constraint with a language assumption. At solve time I described three _ versus o choices and called the residue eight strings. That was too confident without stating which other characters I had already ruled out.

Constraint applied Free positions Candidate strings Basis
Bit leak, character set, and wrapper 12 4096 Ciphertext structure and format
Add the exact a-z range filter 10 1024 Cover alphabet
Assume lowercase leetspeak 2 4 Convention, outside the cipher
Require the clue's English reading 0 1 Language interpretation

The source's eight-string account and its later four-string table do not describe the same constraint set. I cannot make them equal by quietly changing the premises. What the artifacts force is the 4096 count under the first listed constraints and 1024 after the full alphabet range check. The last choices depend on how strictly I read "leetspeak" and English. The answer can be right while the confidence claim is wrong.

The range filter was sitting there all along. Top bits 011 allow 0x60..0x7F, but lowercase letters occupy only 0x61..0x7A. I had stopped when the answer checked, rather than exhausting that simple constraint. Next time I want the candidate count next to each assumption before I declare a unique recovery.

7. Extrapolation

This exercise gave me practice treating a character class as partial known plaintext and propagating simple equations over GF(2). Similar habits help with fixed headers, protocol magic values, and structured fields in other weak cryptographic designs. The transferable move is to count the uncertainty after each constraint, then say which constraint came from observed bytes and which came from an analyst's guess.

For a deployed application, I would start at the source and key lifecycle. A homegrown cipher protecting stored records can expose past data as well as future data, so an incident review would trace when the code first shipped and which ciphertexts were produced under it. That is a scoping plan, not a claim that this challenge represents an actual breach. Ordinary network or endpoint logs do not reveal that a bit permutation has reused key information. Code review and tests are the useful primary surfaces.

8. Reusable Tools, Scripts, and Artifacts

I packaged the keystream lab for the algebra, a source review lead generator, and tests for both. I also retained the source's proposed Semgrep rules with their unverified status marked in the file. The README explains what each accepts and what it cannot establish. The lab's candidates() function can be adapted to a different constrained alphabet by replacing its known-bit premise and the exact range check. A different key schedule needs fresh equations; copying these parity relations blindly would be wrong.

My short triage list for a similar cipher is: measure ciphertext and block lengths; look for a constrained plaintext class; identify transforms of existing key material; inspect where any fresh randomness enters; write the resulting bit constraints; apply every range restriction the input supports; and record which final choices come from format or language. I would use an expected flag format as a separate falsification check only after deriving candidates from the ciphertext relationship.

11b. Mitigation Realization

I would replace the construction with an authenticated-encryption implementation from a maintained library, such as AES-GCM or ChaCha20-Poly1305, and generate key material from a cryptographically secure source such as secrets.token_bytes. An AEAD key can encrypt multiple messages when its scheme's nonce rules are followed. The enforceable invariant is that the same key and nonce pair is never reused for two encryptions, with the library's size and lifecycle limits observed. Reversing or rotating an existing key does not count as a new key.

For the development process, I would put a narrow source review check in CI and require a second reviewer for crypto changes. The reviewer should be able to answer where each new key bit comes from, what nonce discipline applies, and whether a test actually distinguishes repeated use from independent encryption. The linked AST checker is a local proof of concept, not a production gate.

12. Indicators, Artifacts, and Detection Engineering

The source record proposed two Semgrep patterns: one for random.randbytes followed by reuse under a transform, and one for random.getrandbits(n) added to a value whose high bits are deterministic. It also reported that both patterns fired on one vulnerable sample, neither fired on a secrets.token_bytes plus AES-GCM control, and Bandit B311 produced three findings. The rule text and those reported counts are useful leads, but the scan output and control fixture are unavailable here. I cannot present them as independently validated detector performance. The second pattern is particularly broad: low-bit addition alone does not prove a key-schedule weakness without tracking the surrounding data flow.

I built a more limited AST code reviewer for a check I could run. It reads Python source, reports direct random.randbytes assignments, and adds a transformed-reuse lead when the same local scope calls encrypt(key, ...) and encrypt(transform(key), ...). Its tests gave two findings on the vulnerable fixture, none on benign sampling plus a secrets key, and one weak-key finding on the near miss that encrypted only once. That is local syntax and logic coverage. It does not track aliases, call paths, real data flow, nonce handling, or production false-positive rates. Its output is for a reviewer, not an automatic security verdict.

The source repository is the sensor; the relevant fields are file path, line, rule ID, and key variable name. A CI integration would need path scoping, triage ownership, a reviewed exception process, and tests against representative application code. Bandit B311 can flag cryptographic use of random, but it also flags benign uses; I would tune it by context rather than treat every result as a breach. There is no case IOC or event stream from which a defensible KQL, SPL, or Sigma rule could identify this cipher design. A deployed application might have useful access logs for exposure scoping, but the flaw itself need not produce a distinct runtime event.
