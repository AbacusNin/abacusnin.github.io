The Signature That Gave Away Its Key

Three short messages went into the signing service. Two signatures checked out. The one on `0x03` changed the whole plan.

Summary

The challenge. Recover the encrypted flag from a TCP signing oracle that exposes an RSA public key and occasionally returns a faulty CRT signature.

What I did. Check each response with the public exponent, take a GCD from the faulty signature, reconstruct the private exponent, and decrypt the target ciphertext.

The result. The case record reports factor recovery and a valid flag string. The toy lab independently reproduces the mathematical failure with invented parameters.

The limit. The 2048-bit modulus, faulty signature, ciphertext, service transcript, and grading receipt are unavailable for challenge replay. Defensive tests use synthetic events.

1. Problem Statement and Threat Scenario

I had a TCP signing service and an encrypted flag ciphertext. The service's banner gave me a 2048-bit RSA modulus n and public exponent e = 65537. It accepted a hexadecimal message and returned a signature. There was no authentication in the challenge interface. The ciphertext was encrypted under the same RSA key pair, so a recovered private exponent would open it.

The production analogue is a signing API or hardware security module front end that uses RSA's Chinese Remainder Theorem optimization and returns a bad computation without checking it first. That is a conditional design scenario, not evidence of a compromised production signer. The case's objective was concrete: find a mathematical failure in the oracle output, recover the key, and decrypt the ciphertext.

2. Techniques, Tooling, and Actions Taken

2.1 Transport Layer

The exercise environment had no netcat, and installing it was not available. I used a short Python socket client to read the banner, send one newline-terminated hex message, and capture the reply. My first client used short sleeps and a timeout to drain responses. That fit this small text service, but a reusable client needs byte and time bounds and the service's exact prompt.

2.2 Initial Banner Capture

The banner exposed n, e, and message (hex):. I kept the public parameters beside each response so the verification check used the key for that session. The retained case notes do not include the full values or a transcript, so the challenge operation is reported here from the solve record.

2.3 Oracle Characterization

I sent 0x02, 0x03, and 0x05. For raw textbook RSA, a returned signature s on representative m should satisfy pow(s, e, n) == m % n.

Message Recorded public check
0x02 Valid
0x03 Invalid
0x05 Valid

That middle result was the entire opening. It was one bad signature among three probes, not a high-volume attack. A network-volume threshold would have missed the observed sequence.

2.4 Methodology Note: Initial Hypothesis and Pivot

At first I expected the raw signing function to serve as a decryption oracle. In textbook RSA both operations apply x^d mod n, so submitting the ciphertext might have returned the plaintext. I also prepared multiplicative blinding if a direct ciphertext request was blocked. I did not need either path. I briefly considered the bad signature a copy or transport error; checking all three against the same public invariant made the fault impossible to dismiss as a merely odd-looking response.

The direct-decryption and blinding paths are recorded as prepared alternatives, not completed attacks. The one actually used was factor recovery from the faulty output.

2.5 Exploitation

I computed gcd(pow(s_faulty, e, n) - 3, n). The case record reports a nontrivial factor. Dividing n by it gave the other factor, and their product checked back against n. From there I calculated d = e^-1 mod ((p-1)(q-1)) and decrypted the ciphertext. The recorded plaintext had the expected flag form. The actual 2048-bit numbers and result are not available for my replay.

3. Tooling and Scripts

3.1 Python TCP Client (netcat substitute)

My challenge client sent a hex string followed by a newline and parsed a line containing sig = 0x.... Its shape was simple:

with socket.create_connection((host, port), timeout=10) as sock:
    banner = read_until_prompt(sock, max_bytes=16384, timeout=5)
    sock.sendall((message_hex + "\n").encode("ascii"))
    response = read_until_prompt(sock, max_bytes=16384, timeout=5)

My challenge client used a sleep-and-drain helper rather than read_until_prompt; the bounded form above shows what I would take into another engagement. No target host, port, or live service is included in the linked lab.

3.2 Oracle Characterization - Detect Faulty Signatures

The check was one line, applied to every pair (m, s):

def valid_raw_rsa_signature(m: int, s: int, e: int, n: int) -> bool:
    return pow(s, e, n) == m % n

The challenge script parsed sig = 0x... from text and printed VALID or FAULTY for each probe. A failed check by itself does not prove a one-sided CRT fault; I needed the next GCD to distinguish a useful residue fault from arbitrary corruption.

3.3 Full Exploit - Factor Recovery to Plaintext

The decisive sequence was:

from math import gcd

factor = gcd(pow(s_faulty, e, n) - m_faulty, n)
if factor in (1, n):
    raise ValueError("No nontrivial factor from this response")
other = n // factor
assert factor * other == n
d = pow(e, -1, (factor - 1) * (other - 1))
plaintext_integer = pow(ciphertext, d, n)

I printed only a prefix of each factor and the decrypted bytes during the solve. The toy RSA fault lab runs this complete sequence on invented small primes, including the check that a valid signature produces no useful factor. It does not hold the challenge key or ciphertext.

3.4 Fallback - Multiplicative Blinding

This branch was ready but unused. If a raw-RSA service refuses a ciphertext c while still signing arbitrary representatives, choose r with gcd(r, n) == 1, submit c' = c * r^e mod n, and unblind the returned s' with r^-1 mod n. The result equals c^d mod n for raw RSA. It depends on the exact oracle semantics and fails as a general shortcut for padded RSA signature schemes. In this case, the fault made that route unnecessary. The toy lab includes and tests these two functions on invented integers.

4. Concept Explanation

4.1 RSA Fundamentals

An RSA modulus is n = p*q, where p and q are large primes. With public exponent e, the private exponent d satisfies e*d = 1 mod phi(n) for phi(n) = (p-1)(q-1). Raw public and private operations are exponentiation modulo n:

Operation in this raw challenge Formula
Encrypt c = m^e mod n
Decrypt m = c^d mod n
Sign s = m^d mod n
Public check s^e mod n == m mod n

These are the challenge's textbook operations. A production signature scheme encodes the message and checks the full signature scheme; it does not sign an arbitrary user-supplied integer this way.

4.2 RSA-CRT Optimization

CRT performs the private operation modulo the smaller factors: sp = m^dp mod p, sq = m^dq mod q, with dp = d mod (p-1) and dq = d mod (q-1). It recombines them using q^-1 mod p. That saves work, but it introduces a fault boundary. If one residue is correct and the other is wrong, the returned value can reveal the factor associated with the correct half.

4.3 Textbook RSA Is Not a Signature Scheme

The first weakness is the raw interface itself. With no padding or operation separation, signing and decryption both apply the private exponent, and RSA's multiplicative structure permits blinding tricks. RFC 8017 specifies schemes such as RSASSA-PSS and RSAES-OAEP with different encodings and purposes. I would use separate keys for signing and encryption and a maintained implementation of the selected schemes. PKCS#1 v1.5 signatures remain in use in some systems, but that is a compatibility decision with its own review, not a reason to expose raw RSA.

4.4 The Bellcore/Lenstra Fault Attack

This is the Bellcore/Lenstra fault result. Suppose the q residue is wrong but the p residue is right. The faulty result s' still satisfies (s')^e = m mod p but fails modulo q. So p divides (s')^e - m, while q does not. The GCD with n returns p. The attack needs one useful faulty output, not a fast way to factor a sound 2048-bit RSA modulus.

In the challenge the fault's cause was not established. Hardware fault injection, transient faults, and software defects are possible sources in real implementations, but the case record only establishes an invalid output and a successful GCD recovery.

5. Exploit Mechanics

5.1 Detection

The recorded checks were pow(s_2,e,n)==2, pow(s_3,e,n)!=3, and pow(s_5,e,n)==5. I treated the result on 3 as a candidate fault and tested the specific mathematical consequence. That separates a signal from an arbitrary parser mistake.

5.2 Factor Recovery

For the faulty signature on 3, gcd(pow(s_3,e,n)-3,n) reportedly produced a nontrivial factor. The subtraction can be negative; Python's gcd handles that. A GCD of 1 or n would mean this response did not isolate one prime, and I would go back to the transcript or collect another sample.

5.3 Private Key Reconstruction

I divided n by the factor, checked p*q == n, and computed d from phi(n). Those consistency checks matter because a malformed parse could also lead to an invalid but unhelpful signature.

5.4 Decryption

I applied pow(ciphertext, d, n) and converted the integer to bytes. The solve notes report a valid flag string. That result supports the factor recovery, though no exact ciphertext or grading receipt was retained for independent confirmation here.

5.5 Why Validation Would Have Prevented This

The signing service should check the raw RSA representative before returning a CRT output:

if pow(signature, e, n) != encoded_representative:
    log_fault_without_key_or_message()
    raise CryptoFaultDetected("signature withheld")
return signature

For RSA-PSS, encoded_representative is the encoded block produced by the scheme; comparing directly with the original message integer would be wrong. The service must use a vetted library and reject before response serialization. An assert is not a reliable production guard because optimized Python can remove assertions. The linked lab demonstrates an explicit exception blocking the toy fault before it escapes.

6. Lessons Learned (Practitioner Perspective)

6.1 What the Exercise Validated

The small probes were cheap, and checking them was cheaper. I could have chased the signing-as-decryption route because the service shape suggested it. Instead, the invariant turned one unexpected reply into a testable hypothesis. The GCD and recovered plaintext supplied the follow-through. I want that order in future work: capture the output, run the public checks on every sample, then choose the attack path.

6.2 What the Exercise Surfaced

I initially gave the bad reply too little weight and spent time thinking about transport errors. The missing netcat also cost time until I switched to Python sockets. Both were local workflow issues, unrelated to RSA. My receive loop had loose time and byte bounds; the client sketch above makes those limits explicit.

6.3 Transferable Principles

A single bad output yielded a factor Treat a cryptographic self-check failure as a key-exposure event
A direct-decryption idea was prepared but unused Keep alternate hypotheses labeled as alternatives

A toy guard blocks the fault before return Place validation at the trusted signing boundary
7. Extrapolation

7.1 Individual Practitioner Skill Development

The useful skill here was recognizing an implementation failure in a sound mathematical primitive. It sits beside padding-oracle work and side-channel analysis, but this case specifically needed a one-sided CRT fault and an unguarded response. The method does not imply that ordinary RSA moduli can be factored from any invalid signature.

7.2 Security Operations (SOC, IR, Threat Hunting)

The highest-value operational signal would be an internal output-validation failure. The signer should withhold the result, log a key identifier and fault event, and alert the key owner. If a faulted signature may have left the service, responders should assume that key could be recoverable, contain signing operations, rotate or revoke it, and review issued artifacts and downstream trust. The exact response depends on whether the key signed software, certificates, tokens, or something else.

Low-variance small-message traffic is a weaker hunt lead. The challenge used only three probes, and normal health checks can look the same. Connection logs cannot tell whether the RSA representatives were small after TLS. Application logs need to record a safe length or class, client identity, and fault outcome; they should not log private key material or full sensitive messages.

7.3 Intelligence Operations

If a real signing key were compromised, its public key fingerprint could help scope certificates, signed binaries, or issued tokens that rely on it. That is a conditional correlation task. No actor, campaign, certificate, or key fingerprint was provided in this exercise, so there is no campaign attribution or shareable case IOC.

8. Reusable Tools, Scripts, and Artifacts

8.1 RSA Oracle Triage Decision Tree

My triage path is short: record n and e; identify the signature encoding; collect a few authorized test responses; verify each with the correct scheme; and, for a raw-RSA failure, test whether gcd(s^e-m,n) is nontrivial. If all raw checks pass, the direct-decryption and blinding ideas are separate questions about what the interface accepts. If the service returns (r,s) pairs instead of RSA integers, move to the signature scheme actually in use rather than applying RSA arithmetic. The original decision tree also mentioned repeated ECDSA r; that is an adjacent nonce-reuse check, not part of this solve.

8.2 RSA Analysis Primitives (Abstracted)

The toy fault lab contains the reusable arithmetic in runnable form: public verification, gcd factor recovery, d reconstruction, synthetic decryption, and explicit pre-return blocking. Its fixed primes are deliberately tiny. The tests check that a valid signature does not yield a factor and that the guard rejects a corrupted CRT result. Those functions illustrate the failure mode; they are not cryptographic library code for an application.

8.3 Oracle Engagement Checklist

Before I trust a conclusion, I want the banner and key recorded, the response parser checked against the exact protocol, each submitted message paired with its returned signature, and every public invariant result saved. I also want to note authentication and rate limits, which path I actually used, and whether a challenge answer was accepted. If I move to a live service outside a CTF, the test scope and rate are part of the engagement plan. This record supports the factor route and a decrypted flag string; it does not contain the original service transcript.

9. Framework Mapping

9.1 MITRE ATT&CK

I considered T1190, T1552.004, T1600/T1600.001, and T1606.001/.002. T1190 Exploit Public-Facing Application is a plausible analogue if a public signing service had this defect. T1552.004 Private Keys describes finding exposed key material, whereas this key was calculated from a faulty operation. T1600.001 Reduce Key Space concerns weakening encryption on network devices; nobody changed a network device here. T1606's web-cookie and SAML-token subtechniques are possible downstream uses only if the recovered key serves those systems. None is observed in the challenge.

9.2 MITRE D3FEND

The defender actions are clear even where a taxonomy ID adds little: restrict who can call the signer, verify each cryptographic result before release, audit faults, and scope the key's use if a fault occurs. I considered certificate analysis, credential verification, inbound session volume analysis, network isolation, and remote authentication protocol analysis. Certificate review and session analysis would be conditional on a deployed service. I do not label a local toy guard as a validated D3FEND control.

9.3 MITRE CAPEC

CAPEC-97 Cryptanalysis is a broad match for recovering secret material from a flawed construction. I also considered CAPEC-463 Padding Oracle and CAPEC-624 Hardware Fault Injection. No padding oracle or physical injection was observed, so those are adjacent techniques only. CAPEC-475 Signature Spoofing by Improper Validation concerns a verifier accepting a spoofed signature; this case concerns a signer releasing its faulty output. I would not treat it as a direct parent of the failure. STRIDE can still frame the design risk as information disclosure during review; OWASP's web-app categories add little to this raw-TCP case.

10. Threat Intel and Standards Integration

10.1 STIX 2.1 Representation

I sketched STIX attack-pattern, indicator, and course-of-action objects during analysis. The indicator idea used a challenge port and an unsupported payload-count property; neither is a portable observation of CRT failure. There is no actual IOC to exchange, and no TAXII collection was used. If an organization sees a real leaked signature, it can share an incident record or a validated analytic with its own schema. An illustrative attack-pattern description might explain the method, but it must not imply an actor or observed campaign.

10.2 CIS Controls v8

The useful CIS 16.11 connection is to use vetted cryptographic components. I also considered safeguards for data at rest and in transit, configuration, alerting, and network-flow collection. Those are deployment-dependent supporting controls; none substitutes for checking the RSA-CRT output before return. I would first establish the actual key role and application architecture, then map the supporting controls to that environment.

10.3 STIG Reference

I considered platform and application STIG identifiers and a FIPS 140-3 module requirement. This challenge has no declared government system, CUI boundary, operating system baseline, or validated module identity. I cannot turn those references into a compliance finding here. For a real deployment, I would check the current applicable STIG release and the exact module, version, operating environment, and approved mode before making a FIPS claim. A certificate page fetched by a CI script does not prove that the deployed signer uses that validated configuration.

11.2 Mitigation Realization

SC-13 / SI-10 - Cryptographic Output Validation

The root fix is an explicit check inside the signer, before any bytes leave it. On failure, discard the result and record a fault event. The toy lab demonstrates that blocking point. A real service should use its cryptographic library's scheme-aware verification and fault handling rather than copy the toy CRT implementation into production.

SC-12 / SC-17 - Key Management and Separation

I would keep signing and encryption keys separate, with permitted operations enforced by the key store. That removes the extra consequence this puzzle gives the attacker: factoring the signing key also decrypts the challenge ciphertext. A production policy needs ownership, rotation, access review, and an incident path for a suspected leak. A sample policy using 3072-bit keys and annual rotation would need review against the actual system and current requirements.

SI-7 - Integrity Verification

Dependency and module provenance matter. A CI check that only searches a configuration file for a CMVP ID and a webpage for "Active" would not establish the module binary, version, platform, and approved mode actually deployed. I would verify those against the vendor and NIST CMVP evidence during procurement and release review. I would still test the application's rejection of a faulted result; module status alone does not prove this application boundary works.

AU-6 - Detection via SIEM

The signing audit detector and Sigma seed use an application-emitted fault_validation_failed event. That event is the best alert candidate. Three small-message requests within ten minutes generate a weaker review lead. The original network-only threshold of more than 50 connections would not have caught the three-probe solve.

CMMC SC.L2-3.13.11 - FIPS-Validated Cryptography

If a real system has a CMMC obligation, the owner would document the applicable boundary and verify its module evidence and configuration. No certification or CMMC control satisfaction is established by this exercise, the local code, or a public certificate listing.

12. Indicators, Artifacts, and Detection Engineering

12.1 Detection Data Sources

I considered Zeek conn.log, TLS certificate logs, Sysmon network events, Windows object access, Linux auditd, HSM operation logs, application logs, and PKI issuance logs. They serve different questions. Connection logs can show a client reached a signer, but cannot see small raw messages or invalid signatures inside TLS. Application or HSM telemetry can expose validation failures and operation counts. Host and PKI records can help scope key use after an alert. Windows EID 4662 is not a generic private-key read detector without the right audited object and provider.

The linked audit guide defines the synthetic fields: timestamp, client ID, key ID, event kind, and message bit length. It deliberately excludes raw requests and signatures. The case itself supplied no such production logs.

12.2 Sigma Rule - Signing Service Enumeration

An early Sigma sketch assumed more than 20 tiny messages, although this solve used three, and its aggregation syntax needed work. The tested local event-stream check uses three message_bits <= 3 requests from one client/key inside ten minutes as a lead. Its benign health-check fixture produces the same lead, so it should never be treated as a stand-alone exploit verdict. The test suite shows a near miss outside the window produces none.

12.3 YARA Rule - Identifying Fault Exploit Tooling

I considered a YARA rule matching strings such as from math import gcd, a gcd(pow(...)-m,n) expression, and an RSA decryption call. That could identify an analyst's toy script as readily as adversarial tooling. It offers little help for a service leaking faulty signatures, and I did not validate it against a file set. The operational artifact targets the signer's fault event.

12.4 SIEM Query - Splunk SPL

My first SPL idea grouped Zeek flows by the challenge port, counted connections, and treated orig_bytes as payload variance. Connection byte counts do not tell us which representatives were signed, and the three observed probes fall below that threshold. For a real Splunk deployment I would ingest the application event and query kind=fault_validation_failed by key_id, client_id, and time. The log schema must be mapped before writing a production SPL expression; none is available here.

12.5 SIEM Query - Microsoft Sentinel (KQL)

I had also sketched a KQL query using CommonSecurityLog and RequestClientApplication as a stand-in for payload variance. That field does not measure RSA message diversity. In Sentinel I would first map the signer's own event to a custom table, then alert on validation failures and use small-message frequency only for context. No Sentinel table or backend conversion was available to test this query.

12.6 Detection Engineering Notes

The local tests cover a positive sequence, a benign health check, a near miss, a valid-signature negative, and a fault that the signer blocks. The Sigma rule is YAML-parsed but has no backend conversion or live telemetry test. The synthetic event detector is local logic, not production accuracy. TLS hides message content from a passive network sensor, and many legitimate tests use small representatives. The alert worth engineering first is a signer-side output failure, followed by key containment and exposure review.
