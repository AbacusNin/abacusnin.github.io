The Slashes That Looked Like Morse

The file looked eager to be read as Morse. The slashes were only pretending to be dots and dashes.

Summary

The challenge. Decode a short slash-and-backslash message and submit its lowercase phrase in the event's flag wrapper.

What I did. I checked the bytes, tried Morse in both directions and several binary readings, then used repeated tokens and a thematic crib to recover the phrase.

The result. My case record reports a rejected dictionary fill followed by an accepted answer selected with the prompt's theme.

The limit. The exact ciphertext, recovered phrase, flag, and submission transcript are withheld, so I cannot independently replay the case result.

1. Problem Statement and Threat Scenario

I had a short text file for a 500-point collegiate cryptography challenge. It contained forward slashes, backslashes, and spaces. Each space-delimited token held one to four marks. The prompt gave me a pop-culture theme, and the task was to return a short lowercase English phrase in the event's flag wrapper, with no spaces inside the phrase.

That tiny alphabet made the file look like Morse. It was a good first guess, and it was wrong. This was a static puzzle with no attacker, victim, host, or network traffic. The operational discussion later in this page concerns methods someone could adapt to analyzing opaque messages; it does not describe an incident in the challenge.

2. Techniques, Tooling, and Actions Taken

I inspected the file as bytes before I tried to read it. That established the two marks, the single-space token separators, a fixed number of tokens, and lengths from one through four. I have not retained the actual byte count or token count in this public record, so I cannot put numbers on them now.

I tried / as dot and \ as dash, then reversed them. Both Morse readings produced invalid letter groups and output that did not read as English. I also tried treating the marks as bits: different group widths and offsets, reversed bit order, and a single-byte XOR sweep. None of those tested readings produced the expected phrase. A stream's length missing a clean byte boundary is a clue, but it cannot alone rule out binary; padding and offsets exist.

The spaces finally became useful when I stopped treating each mark as a bit. I treated each entire token as one cipher symbol and assigned stable abstract IDs in order of appearance. Repeated tokens now stood out. A long opening word suggested a thematic crib; that assignment propagated through tokens shared with a short word and the ending. The record says this recovered most of the phrase.

The middle word was the snag. Some of its tokens were local to that region, leaving multiple fills compatible with the recovered mapping. I picked one by dictionary fit and submitted it. The platform rejected it. I went back to the prompt, used its theme to choose another compatible word, and the case record reports that submission was accepted. Those submission results are reported observations; the transcript and exact candidate strings are not available for an independent check.

3. Tooling and Scripts

The original solve used byte inspection, two Morse polarities, binary trial readings, an abstract token pattern, a dictionary search, and candidate consistency checks. The source describes using an English word list and wordfreq for candidate analysis but does not retain a command, ranking output, or version for those steps. I can describe their role without claiming a reproducible score.

For an authorized copy of a similar file, I would start with the same simple checks:

wc -c cipher.txt
od -c cipher.txt

I made a standalone two-symbol analyzer for that first pass. It accepts a slash-and-backslash file, validates the token format, prints a stable numeric token pattern, and tries Morse with either mark as the dot. An optional candidate check enforces one token to one letter across the whole message and rejects wrong lengths. Optional, analyst-supplied word lengths identify tokens confined to one proposed word segment. The usage guide explains the commands and the synthetic tests check the behavior. These new files have only been run against invented inputs; they do not recover the withheld challenge phrase.

One correction matters here. Mapping distinct tokens to distinct temporary IDs shows the ciphertext's repeated-token positions. It does not give me a complete plaintext letter pattern in a homophonic cipher. Two different tokens can represent the same letter. I therefore test a candidate in the token-to-letter direction and allow several tokens to map to one letter. A zip-based check also needs an explicit length check, since zip silently stops at the shorter input.

4. Concept Explanation

Morse uses dots and dashes, so two marks in groups of one to four invite that reading. I compared both mark assignments with the ITU-R international Morse table. An invalid A-Z group defeats a strict letter-by-letter Morse interpretation. Non-English output is weaker evidence by itself; the assignment or spacing could still be wrong. A binary interpretation also needs a chosen bit order, grouping, alignment, and possibly padding. The attempted settings failed here, but that is narrower than a proof against every binary encoding.

In a simple monoalphabetic substitution, one plaintext letter has one cipher symbol. A homophonic substitution can use several cipher symbols for the same plaintext letter, which spreads out the counts that ordinary frequency analysis uses. The repeated-token scaffold remains visible: identical tokens must decode consistently, and a token shared by two positions links those positions. Distinct tokens need not decode to distinct letters.

Here is an invented example, separate from the challenge data. The word banana could be written with b as /\, n as /\\, and the three a positions alternating between // and \\:

plaintext: b   a   n    a   n    a
tokens:    /\  //  /\\   \\  /\\   //

The example is deliberately small. It shows why counting distinct tokens as distinct plaintext letters can mislead me, while the repeated /\\ token still links the two n positions.

5. Exploit / Analysis Mechanics

The spaces marked token boundaries, so I could inventory complete symbols without guessing a fixed number of marks per character. I reduced each distinct token to a stable numeric ID and looked at where the same ID recurred. I also used the prompt's theme to test a long opening-word crib. The record reports that its token assignments were compatible with other positions and helped fix a short word and the ending.

The interior word did not become unique from that propagation. The source calls its symbols local to the word and also says some letters were fixed through shared symbols. Those statements cannot both be literally true for every token in that word. The defensible reading is that some positions had shared-token constraints while other positions remained local. Its reported second/fifth-letter repeat narrowed the shape, but the public record does not include the ciphertext or a complete segmentation to verify that exact position. I would need the token stream and word boundaries before claiming a unique pattern match.

My first fill passed the internal consistency check but failed on the platform. That failure separated a valid substitution from the intended answer. The pop-culture hint supplied the missing choice, and the case record says the next submission was accepted. A consistency check is necessary, not sufficient: it detects a token mapped to two different letters, but it cannot tell me that only one English phrase or themed answer fits.

The mechanism exploited by the solve was leakage of token repetition and cross-position constraints. Homophones can flatten frequency, yet a short message with stable token values and a strong crib can still reveal a frame. I cannot quantify how much frequency was flattened, or reconstruct the exact mapping, because the token stream is withheld.

6. Lessons Learned

The most useful mistake was the rejected middle word. I had treated a cipher-consistent dictionary fill as if it were the answer. Now I ask whether another fill could satisfy the same token mapping before I submit. If local tokens leave a segment open, I label that uncertainty and look for an external constraint. Here the prompt's flavor text carried that constraint.

I would also keep the first-pass work in this order: record the actual bytes, test the obvious encodings in both directions, preserve their failed outputs, and only then move to a substitution model. The Morse shape was persuasive enough to waste time if I had not checked it directly. A failed decode should narrow a hypothesis, not vanish from the record.

The other lesson is about language. A temporary abstract symbol pattern is still useful, but in a homophonic cipher it cannot enforce a one-to-one relationship between distinct tokens and letters. I need to propagate the constraints I really have, then ask what remains unresolved.

7. Operational Extrapolation

Individual Practitioner Development

This exercise gave me practice separating an attractive encoding guess from a tested one. I also got a useful confidence habit out of the wrong submission: report a candidate as consistent, ambiguous, or externally confirmed, depending on the evidence. I can use the analyzer on another permitted sample to inventory symbols and spot local tokens before I try a themed fill. Its synthetic tests are a starting check, not proof that it solves arbitrary homophonic ciphers.

Security Operations

The challenge supplied no application, endpoint, or network telemetry. I have no event fields from which to build a credible KQL, SPL, or Sigma alert, and there was no observed attack to hunt. In an authorized investigation of an opaque message embedded in logs, an analyst could extract the message and run the same offline triage as an analysis aid. That would require a real sensor, preserved message bytes, a lawful collection scope, and separate evidence linking the message to a security event. The tool does not monitor a system or decide whether content is malicious.

Intelligence Operations

An intelligence analyst might encounter short symbolic text in a seized document or open source. This method would help test whether it behaves like a tokenized substitution. The result would still need source provenance, context, and alternate readings. This challenge contains no collection operation, source attribution, or signal that supports a real-world intelligence finding.

8. Reusable Tools, Scripts, and Artifacts

The two-symbol analyzer is the reusable proof of concept. It reads a bounded UTF-8 file containing only /, \, and single-space separators. It reports token counts, a stable ID sequence, Morse outputs under both polarities, and optional candidate-consistency findings. When I supply proposed word lengths, it also reports which token IDs occur only within each proposed segment. The boundaries come from the analyst, since the token separators alone do not identify words.

The README records inputs, output fields, limits, and commands. The invented sample stream shows the input shape. The synthetic test suite covers a compatible homophonic candidate, ordinary Morse, a wrong-length candidate, a conflicting token assignment, malformed input, and a local-token near miss. The local tests check the program's logic. They do not verify the original solve, dictionary uniqueness, production telemetry, or any SIEM conversion.

My working checklist for a new case is: inventory bytes and token lengths; try both Morse polarities; document the binary groupings actually attempted; assign stable token IDs; test cribs with one-way token consistency; mark positions that lack cross-message constraints; enumerate plausible fills; use the prompt or another independent source to settle the remaining choice; and distinguish a reported platform result from an independently replayed one.

9. Framework Applicability and Mapping

I checked for an ATT&CK technique before making a mapping. This challenge showed a static cryptogram, no adversary operation, and no target. It therefore supplies no observed ATT&CK behavior. CAPEC, D3FEND, STRIDE, OWASP, and CWE also need an attack pattern, defensive mechanism, system, or software weakness that this puzzle did not provide. The classical-cryptography label describes the method without making a framework finding.

In a separate operational case, decoding an encoded message could be one step in analyzing an intrusion. I would map the observed intrusion behavior from that case, with its own evidence, rather than map this puzzle's use of slashes to a technique ID. I have no such behavior here.

10. Threat Intelligence and Standards Integration

The file contains no infrastructure, malware, account, hash, or victim indicator. I cannot make a STIX indicator or TAXII exchange out of the flag phrase. The ITU-R Morse recommendation helps me test the decoy, but says nothing about a threat campaign.

If a real case yielded a decoded message, I would keep the original bytes, extraction location, collection time, exact transform, alternative decodes, and confidence together. A derived phrase without that chain can be mistaken for a confirmed actor statement. Nothing in this challenge authorizes a claim about an actor or campaign.

11. Controls Mapping and Mitigation Realization

No protected system or control failed in this exercise. There is no basis for a NIST SP 800-53, CIS, STIG, CMMC, or sector-control assessment, and there is no mitigation to claim as deployed. The reusable action is an analyst workflow: preserve the message, test competing encodings, and record uncertainty before using a decoded phrase in a report. That process would need an organization's own evidence-handling rules if used on real data.

12. Indicators, Artifacts, and Detection Engineering

The challenge artifact was the short two-symbol file and its prompt. Neither is an IOC. The rejected guess and reported accepted answer are puzzle outcomes, not production detections. With no event source or malicious behavior, publishing KQL, SPL, Sigma, or YARA here would give a rule an unsupported purpose.

The analyzer is an offline triage tool. A real workflow could save an opaque message from an authorized source, run the analyzer, and attach its JSON output to an investigation record. The useful fields are the original file's provenance, the mark alphabet, token ID pattern, Morse checks, optional segmentation, and any candidate conflicts. A positive-looking pattern would start review; it would not alert on compromise. The synthetic tests check positive, benign, and near-miss inputs locally, with no measured false-positive rate in live content.
