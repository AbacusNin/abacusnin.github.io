Rotation and Recovery

Exploiting a stateful cryptographic protocol: recovering a 128-bit key through an adversary-in-the-middle position, a verification oracle, and reducible ring structure, while minimizing edit cost.

Field Value
Category Cryptography, protocol exploitation, WebAssembly, adversary-in-the-middle simulation
Difficulty Advanced
Tags MITM, message tampering, verification oracle, polynomial quotient-ring arithmetic over GF(2), CRT, two-stage residue lifting, WASM ABI, cost-objective optimization, detection engineering
Scenario An adversary intercepts and edits protocol messages to recover a protected 128-bit key while minimizing weighted mutation cost.

1. Problem Statement and Threat Scenario

I controlled an adversarial position (MITM/AiTM) in a simulated message-exchange protocol with three other legitimate participants. I could see messages in flight, hold one at a time, edit it as long as I kept its length the same, release it back into the channel, and submit a recovered 16-byte key through a host-provided success function. Scoring was the combined cost of my nibble-level edits, billed as ink and whiteout.

This scenario was predicated on a protocol whose endpoints assumed transport integrity while the channel underneath allowed mutation. The message surface included key-rotation messages, MAC-authenticated tokens carrying epoch context, verification requests, acknowledgements, and retries upon ACK loss. In the most basic form; the protocol exposed malleable and insufficiently authenticated messages, including state-changing key-rotation controls and an inadequately context-bound MAC.

Threat Model:

Element Description
Adversary An active network-positioned interceptor that can hold one message and send edits under a same-length constraint.
Adversary objective Recover the target participant's initial 16-byte key and submit it through the success function.
Defender position Endpoints verify MACs, rotate keys, and enforce delivery timing, but accept authenticated-looking messages without consistently binding security-critical fields to the authenticated context. The edit-cost accounting was a challenge scoring constraint, not a defensive control.
Protected asset The target's initial MAC key, as it establishes MAC generation and the key-rotation schedule.
Exposed surface Messages on the wire; MAC verification responses, key-rotation messages, acknowledgement behavior, and retry timing.
Trust boundaries The network channel to the protocol endpoint; the parser to the state machine; the verification service to protected key state; the WASM guest to the host ABI; and any intermediary or broker to the end recipient. Sender, recipient, epoch, and rotation fields are security claims crossing those boundaries rather than trust boundaries themselves.

Chaining two exploitable protocol primitives was pretty cool and represented substantial growth in skill. I combined chosen key transitions with a verification oracle, and the impact of that chain was amplified by a reducible quotient-ring structure in the key schedule. That let me turn a nominal 128-bit recovery into independent small-component searches whose oracle-query costs could be added rather than attempting a monolithic search. My deliverable was a WebAssembly client that talked only through allowed host imports and recovered the key at runtime from per-tick state.

2. Techniques, Tooling, and Actions Taken

Initial Artifact Triage

  • The challenge archive gave me the execution model, the WebAssembly ABI, and a Python simulator. Pretty good starting stack.
  • The ABI needed a WASM module that exported memory, scratch_ptr, scratch_cap, mallory_run, and importing host functions for advance, intercept, release, edit, and a gotcha.
  • The simulator was deterministic under a 32-byte seed, so local reproduction was stable but that hid a trap where live scoring used per-tick seeds, so any solver tied to a specific local seed wouldn't survive runtime.

Two-track Methodology

My first attempt at solving was a proof-of-concept Web Assembly WASM module that hardcoded the recovered key for a local seed and called the success function directly. The big takeaway was confirmation of the ABI mechanics; host imports resolved, memory layout was correct, and the success call was accepted. This was a throwaway for live submission and per-tick scoring.

My second attempt needed a seed-independent solver that recovers the key from the protocol's runtime state and meant I'd need to dig into the key rotation's algebra and clarify semantics of the verification response.

Seed-Independent Solver

My solver chained five primitives:

  1. Held the target's initial key state as long as possible to capture a reference MAC-authenticated token under that key. I did this two separate ways: first by editing an attacker-initiated rotation message into an identity rotation, and second by routing it away from the target. Both landed in the same downstream state.
  2. Built a practical key-equivalence oracle out of the target's verification behavior. A captured token verified under rotation period n when the selected period used the same effective MAC key and authenticated input as the original, subject to the negligible probability of an HMAC collision and any tag-truncation assumptions.
  3. Forced key rotations by editing attacker-initiated rotation packets and encoding tests for the unknown key's residue modulo small polynomial factors.
  4. Resolved each factor by oracle scanning. For a repeated factor, I used a two-stage residue/coset lift from modulo p to modulo p^2, avoiding a full repeated-factor scan.
  5. CRT-recombined the residues into the full 128-bit key and called the success function.

Optimization Efforts

Once correctness was established, the problem shifted to cost minimization under King-of-the-Hill scoring. Optimization candidates were evaluated locally against published per-tick seeds:

Variant Class Outcome
Brute-force repeated factor Direct scan of 2^10 = 1024 candidates for the squared factor Correct; but resulted in high oracle-query count
Two-stage residue/coset lift Recover mod p (up to ~32 candidate checks), then enumerate the corresponding lifts mod p^2 (up to ~32 more) My biggest single measured win on the tested seeds: approximately 30% off combined cost

Dead End - A Retransmission Donor Scheduler

An interesting optimization I was looking into involved retransmission behavior under acknowledgement suppression. In my local simulator observations, when the attacker's acknowledgements did not reach the originating party, that party retransmitted its 32-byte key-rotation packet every 16 simulator ticks for the duration of the run. Each retransmission was a no-edit-cost, 32-byte donor message that could potentially reduce dependence on the periodic MAC-authenticated message stream for rotation donors.

I tested three scheduler variants locally.

  1. Opportunistic donor selection to use retransmissions only when immediately interceptable. It ran safe but produced no measured improvement, noting that the alternative donor stream was almost always available.
  2. An all-retransmission donor with active acknowledgement suppression. Local runs blew past the time budgets and stalled.
  3. Hybrid skip-and-wait variant skipped available donors to wait for a retransmission but produced no improvement, and noting that higher skip counts crossed timing thresholds.

The optimization baseline was predicated on these facts: A. I could hold only one message at a time, and intercept, edit, and release all advanced simulator time. B. Active acknowledgement suppression therefore had to juggle competing in-flight messages and ensure that no key-rotation packet slipped past during a host call.

My development efforts ran into time constraints: C. I couldn't generate precomputed CRT tables quickly enough to advance my runtime fork, my theorized donor scheduler needed additional development time, and each variant fork prevented active scoring. D. Similar to the runtime-computed tables, a real-time scheduler could probably realize a theoretical gain, but it needed careful message and priority queues plus digit-length boundary handling for rotation-field encoding.

Other Dead Ends

  • Treating the local deterministic seed as a live solution input. This was me figuring out how the challenge worked in real time.
  • Submitting through a manually constructed API route when the live interface expected a WASM upload. Figuring out how the challenge worked consumed critical early cycles in HTTP debugging before I recognized the internal-runner mechanism.
  • Assuming the mathematically canonical payload was the cheapest one to produce. It was not as edit cost was weighted by nibble transition and algebraically equivalent payloads could still cost different amounts of ink and whiteout against the same donor. This realization came too late, during live-event development and real-time scoring.

Edit-cost Calculator Primitive

# Sanitized cost-model helper. The real matrix is challenge-specific and
# must be supplied explicitly from the local simulator. Failing closed avoids
# accidentally benchmarking every mutation as free.

REWRITE_COST: list[list[tuple[int, int]]] | None = None


def edit_cost(old: bytes, new: bytes) -> tuple[int, int]:
    """Return (ink, whiteout) required to rewrite old bytes into new bytes.

    Edit length must match. Each byte is split into two 4-bit nibbles;
    cost is summed over both nibbles per byte.
    """
    if REWRITE_COST is None:
        raise RuntimeError("load the challenge-specific rewrite-cost matrix")
    if len(old) != len(new):
        raise ValueError("same-length edits only")

    ink = 0
    whiteout = 0
    for old_byte, new_byte in zip(old, new):
        for shift in (4, 0):
            old_nibble = (old_byte >> shift) & 0xF
            new_nibble = (new_byte >> shift) & 0xF
            delta_ink, delta_whiteout = REWRITE_COST[old_nibble][new_nibble]
            ink += delta_ink
            whiteout += delta_whiteout
    return ink, whiteout

Polynomial Multiplication and Reduction Over GF(2)

# GF(2)[x] multiplication and modular reduction.
# The real degree-128 reduction polynomial must be supplied explicitly.


def gf2_mul_mod(x: int, y: int, modulus: int) -> int:
    """Multiply two polynomial elements over GF(2), then reduce by modulus."""
    if modulus <= 0:
        raise ValueError("modulus must be a nonzero polynomial")

    product = 0
    while y:
        if y & 1:
            product ^= x
        x <<= 1
        y >>= 1

    # Reduce terms at or above the modulus degree by XOR-shifting the modulus.
    mod_bits = modulus.bit_length()
    while product.bit_length() >= mod_bits:
        shift = product.bit_length() - mod_bits
        product ^= modulus << shift

    degree = mod_bits - 1
    return product & ((1 << degree) - 1)

Two-stage Residue Coset Lift for Repeated-Factor Recovery

# A two-stage residue recovery for a squared polynomial factor.
# It replaces one 2^(2*deg(p)) scan with two scans of at most 2^deg(p).

def gf2_poly_mul(x: int, y: int) -> int:
    """Carryless polynomial multiplication over GF(2), without reduction."""
    product = 0
    while y:
        if y & 1:
            product ^= x
        x <<= 1
        y >>= 1
    return product


def recover_repeated_factor(residues_mod_p, factor_p, oracle):
    """Recover q modulo p^2 using a base-residue scan and coset lift."""
    base = None

    # Stage 1: recover q mod p.
    for q0 in residues_mod_p:
        if oracle(candidate_for_mod_p=q0):
            base = q0
            break

    if base is None:
        raise RuntimeError("no base residue found in mod-p search")

    # Stage 2: lift to q mod p^2.
    # Every lift has form q = q0 XOR (p * t) for some t in [0, 2^deg(p)).
    for t in residues_mod_p:
        lifted = base ^ gf2_poly_mul(factor_p, t)
        if oracle(candidate_for_mod_p_squared=lifted):
            return lifted

    raise RuntimeError("no lifted residue found in mod-p^2 search")

4. Concept Review

The protocol's invariant failures

Two exploitable protocol primitives, amplified by the algebraic key-schedule structure, made recovery achievable.

  1. The first is that state-changing key-rotation messages are accepted based on protocol position without sufficient end-to-end authentication. The target reads the first 16 bytes of a key-rotation message as a multiplier and the next 16 as an offset, then updates its key using an algebraic rule. Because I, as the attacker, could edit a rotation message in transit, I gained a chosen-key-transition primitive.

Sanitized update rule:

new_key = multiplier * (old_key XOR offset) mod REDACTED_MODULUS
  1. The second is that MAC-authenticated tokens carry a plaintext rotation-epoch selector and isn't covered by the token's authenticated scope, where verification chooses its key by reading that selector. I could therefore capture a token from one epoch and replay it through a verification request that selected a different epoch's key. A VALID response overwhelmingly indicated that the selected epoch used the same effective MAC key and authenticated input as the original, assuming a full-length secure HMAC construction and negligible collision probability; I did not have to learn either key directly.

The Verification Oracle

The verifier becomes a practical key-equivalence oracle over the key schedule. 1. Given a captured token carrying a tag generated under key K_a, a verification request that selects key K_b returns VALID when the selected key and authenticated input reproduce the captured tag. 2. Under the challenge's HMAC assumptions, this overwhelmingly indicates K_a == K_b, although it is not a literal mathematical "if and only if" because collisions are theoretically possible and truncated tags can weaken inference. 3. Each query produces one binary observation; because I was testing candidate equality rather than balanced subsets, an N-candidate scan generally required linear rather than logarithmic query cost.

The Algebraic Structure

The 128-bit key is naturally an element of GF(2)[x] / m(x), where m(x) is the fixed reduction polynomial used by the target. In this ring XOR is addition and the key update is polynomial multiplication followed by modular reduction.

  1. The critical algebraic weakness is that the modulus is reducible in GF(2)[x]. If m(x) = ∏ p_i(x)^{e_i} with distinct irreducible factors p_i, the polynomial CRT gives an isomorphism from GF(2)[x] / (m) to the direct product of the smaller component rings GF(2)[x] / (p_i^{e_i}).
  2. The component cardinalities still multiply to 2^128; what became manageable was the oracle-query cost, and; because I could recover the components independently, then the small scan costs instead of searching the full space monolithically.
  3. Reducibility alone would not disclose the key; it became exploitable because the chosen-transition primitive and verification oracle let me isolate and test those components. A. Each ordinary factor of degree d contributes a residue space of 2^d candidates. B. A squared factor p^2 with deg(p) = d contains 2^(2d) residues, but the available oracle let me recover it through a base-residue scan modulo p followed by a scan of the 2^d corresponding coset lifts modulo p^2.

Why Two-Stage Residue Lift Matters

  1. For a degree-5 factor p, naively scanning the p^2 component enumerates 1024 residue candidates.
  2. The two-stage approach first recovers the base residue modulo p with up to 32 tests, then writes each lift modulo p^2 as q = q_0 XOR (p * t) and searches the 32 possible values of t.

That is at most about 64 candidate tests instead of 1024, and fewer on average when a scan stops as soon as it finds the matching candidate.

The lift-candidate construction had a subtle, challenge-specific algebraic requirement. A. In my implementation, when the solver maintained an accumulated affine state across rotations, the additive delta between the accumulated state and the test rotation reduced inside each targeted component to the generator X, not to the multiplicative identity; which meant an in-component value of 0x02, not X + 1 (0x03). B. Using the wrong value shifted one recovered residue and caused final verification to fail. C. This is the kind of bug that produced consistent good looking algebraics but still required me to commit component-level testing, during live scorin

Why Cost Optimization Matters

Edit cost was weighted asymmetrically: 1. Each old-to-new nibble transition carried an (ink, whiteout) cost. 2. Two algebraically equivalent test rotations could therefore have very different rewrite costs against the same donor message.

Once I had a correct exploit, the rest became a weighted-mutation problem to minimize edit cost over:

A. Which equivalent algebraic payloads I use B. Which donor I select C. How I ordered testing

Cost optimization became an inflection point for me during this writeup. 1. Finding the vulnerability is one skill; 2. Engineering the exploit against an objective is a second one.

In KoTH events or engagements with a constrained action budget, the second skill decides how you finish.

5. Exploit/Analysis Mechanics

Step 1: Establish Primitives Over the Message Flow

The solver waits for interceptable messages and treats any sufficiently long in-flight message as a candidate donor.

Operational constraints: a. I can only hold one message at a time. b. Edits preserve content length. c. Intercept, edit, and release all advance simulator time. d. Uncontrolled key-rotation messages can perturb a target's key state and desync the affine model.

Step 2: Preserve or Capture the Original Key State

The target starts at rotation epoch 0 with the protected initial key as keys[0]. 1. I, as the attacker, take the first initiated rotation and either edit it to an algebraic identity (multiplier = 1, offset = 0) or route it away from the target entirely. 2. Both produce the same relevant result: the target's MAC key remains the initial key, so the next MAC-authenticated message produced under Carol-style traffic carries a tag generated under the original secret.

Step 3: Capture a Reference MAC

The solver captures the first MAC-authenticated token produced after Step 2. 1. That token is my reference probe. 2. I do not have to forge it because the target hands me a valid tag under the initial key. 3. I can reuse the token and tag in later verification requests while altering the unauthenticated rotation selector.

Step 4: Build a Key-Equality Oracle

The solver then crafts verification requests that reuse the reference token and MAC while altering the rotation field to select a different epoch's key. 1. The verifier recomputes HMAC with the selected key. 2. A matching tag overwhelmingly indicates that the selected epoch uses the same effective MAC key and authenticated input as the original. 3. This gave me a binary key-equivalence oracle over the rotation schedule.

Step 5: Drive Chosen Key Rotations

The immediate-test equation for a single rotation against the initial key is:

multiplier * (K XOR offset) ≡ K (mod REDACTED_MODULUS)

In practice, I ran tests over a chain of rotations. 1. The state I needed to control was the accumulated affine pair (alpha, beta), with current_key = alpha * initial_key XOR beta. 2. Each new test rotation (a, b) updates this to:

alpha_new = a * alpha
beta_new  = a * (beta XOR b)

I engineered the solver: 3. To choose (a, b) so that the test for "current key equals initial key" or; equivalently alpha * K XOR beta == K, or (alpha XOR 1) * K == beta, encoded a chosen residue test on K modulo, which was the component of the factored modulus I was targeting. 4. My implementation kept (alpha, beta) per session and emitted each test rotation as an edit to an attacker-initiated rotation donor. 5. Correctness also depended on the chosen coefficient isolating the intended component without introducing multiple passing candidates through a zero divisor; that property was validated against the simulator and component tests.

My proof sketch: A. Let c = alpha XOR 1. Construct c and beta through CRT so that, in every non-target component, c_j = 0 and beta_j = 0; satisfying c_j * K_j = beta_j automatically. B. In the target component, choose c_i as a unit and set beta_i = c_i * r for the candidate residue r. C. The equality test reduces to c_i * (K_i XOR r) = 0, which holds exactly when K_i = r because multiplication by a unit is injective. D. For repeated-factor components, explicitly avoiding coefficients divisible by p prevents zero divisors from allowing multiple candidates to pass.

Step 6: Recover Residues Factor by Factor

For each ordinary factor of degree d, the solver scans up to 2^d candidate residues. 1. The per-factor candidate counts stay small: 16 for the degree-4 factor, 32 for degree 5, 64 for degree 6, and 128 for degree 7. 2. Each test attempt produces either VALID or INVALID; under the challenge's oracle assumptions and my component-isolation construction. 3. The matching residue is the candidate that returns VALID.

Step 7: Recover the Repeated Factor Through a Two-Stage Residue Lift

Then I recover the squared factor in two stages. 1. First, I scan up to 2^d candidates for the base residue modulo p. 2. Next, I express each lift as q = q_0 XOR (p * t) and scan up to 2^d values of t to identify the matching residue modulo p^2. 3. The in-component algebra uses the challenge-specific scaling value noted in Section 4 (X, not X + 1), as encoded in the solver's stage table. 4. The worst-case number of candidate checks is approximately 2 * 2^d = 2^(d+1), rather than 2^(2d).

Step 8: Reconstruct the Full Key

After I recover all residues, the solver uses CRT to recombine them. 1. The reconstruction uses precomputed basis elements E_i, where each E_i is congruent to 1 modulo the ith prime-power component and 0 modulo every other component. 2. The recovered key is XOR_i (residue_i * E_i).

Step 9: Submit the recovered key

Finally, 1. I have the solver write the reconstructed key into WASM memory at a known offset. 2. Then, call the host success function with a pointer to that memory. 3. A successful return code confirms that my reconstruction matches the target's protected initial key.

6. Lessons Learned

Methodology Validation

This challenge was explicit instruction to treat interactive protocols as a state machine, not a bag of random isolated messages. 1. The exploit did not come from one malformed packet. 2. It came from chaining key rotation, MAC generation, verification, and replay into a single recovery workflow where the primitives composed under the protocol's own state transitions. 3. Keep my concerns about the challenge environment separate from solver correctness. a. My initial fixed-seed validator wasn't a viable live solver, but it earned its place because it proved memory layout, import resolution, and call mechanics before I even touched the algebra. b. The big takeaway was to validate the runtime, then build the exploit.

Gaps and/or Inefficiencies

My biggest experienced inefficiency was me assuming that a mathematically correct payload was also cost-efficient. 1. Once the solver worked, the live scoring made donor choice and edit cost equally important as cryptographic correctness. 2. Recognizing that the problem shifted into cost efficiency and performance improvement took valuable cycles waiting for new seed to post. 3. These efforts required real-time R&D and then deploy time, all taking away from live scoring cycles.

The second gap I had was understanding the scheduler's fragility under host timing. 4. Several optimizations looked clean in my IDE but failed and wasted cycles. 5. This is because each host call advanced simulator time and I could only hold one message. I

In my post-mortem/AAR; big takeaway was on timing and queue state, that they are part of the attack surface for active protocol exploitation, not implementation considerations.

The third, honestly, was tool selection. 6. My initial solver validated the ABI mechanics but left me grasping for a live solve. 7. Recognizing when an approach had hit its ceiling and pivoting decisively was an operational discipline the exercise underscored. 8. The adrenaline of live R&D and implementation was exciting. 9. My unfamiliarity with the problem and with WebAssembly had me spending more R&D time during live scoring, costing scoring cycles and creating frustration.

FWIW, I was able to pivot to the live-solve mechanism, but at the cost of team scoring and performance optimization.

SecOps, IR, and Threat Hunting

IRL, security practitioners would most reliably see this behavior through abnormal application-protocol state transitions: repeated validation failures, unusual key-rotation sequences, and retry storms. 1. Directly detecting in-flight message mutation would require specialized visibility, such as captures on both sides of an intermediary, instrumented relays, or endpoint pre-send and post-receive hashes. 2. My defensive extrapolation is that application behavior would likely produce the first useful detection before a known signature for cryptographic misuse popped off.

These are my Threat Hunting hypotheses:

A. Repeated verification attempts against the same MAC-authenticated object across multiple key epochs. B. Key-rotation messages with unusual frequency, sender, or recipient paths. C. Acknowledgement suppression followed by retransmission storms with stable content. D. Same-length message mutations with preserved framing, but only where instrumented transport, paired captures, or endpoint hashing provides before-and-after visibility. E. Verification failure bursts that eventually succeed after many candidates.

Which then give way to these Incident Response implications:

F. Preserve application-layer protocol logs, not just packet metadata. G. Log key-rotation identifiers and verification rotation indices. H. Alert on repeated use of older tokens against newer epochs. I. Treat retry behavior as a security signal when paired with validation anomalies.

Detection Engineering Theory

These are detection theories I want validate.

  1. Verification endpoints that leak success or failure across an attacker-controlled context selector should be treated as oracle surfaces and instrumented for repeated-query detection.
  2. Protocols whose MAC scope excludes attacker-controlled selectors such as rotation, epoch, or version should bind those fields—along with sender, recipient, message type, and freshness data—into a canonical authenticated context.

Fidelity expectations:

  1. Repeated invalid verifications combined with epoch diversity is the highest-fidelity primary signal. Either alone is noisier.
  2. Key-rotation volume alone is lower fidelity because legitimate retries during transport instability look similar.
  3. ACK suppression is higher fidelity when rotations and ACKs are paired through stable identifiers and unchanged repeated content; ACK loss alone can fire on broker outages or ordinary transport instability.

False-positive surfaces:

  1. Integration testing with stale tokens or replayed traffic.
  2. Distributed systems with delayed message delivery causing legitimate verification failures.
  3. Blue-team exercises and red-team engagements that intentionally replay MAC-authenticated or signed messages.
  4. Client version skew during rollout creating epoch mismatches.

Tuning considerations:

  1. Baseline normal verification failure rates per service before alerting.
  2. Suppress known load-test and migration windows.
  3. Require both failure volume and epoch diversity for the oracle-probing alert.
  4. Use a retransmission-ratio condition, not absolute counts, for the retry-storm alert.

    Yes: Identify length, routing, timing, and cost constraints.
    No: Focus on passive leakage or endpoint compromise.

  Is key material transformed by algebraic operations?
    Yes: Inspect the quotient-ring or field assumptions, modulus factorization, and state invariants.
    No: Model the state transition in ordinary protocol terms.

  Is scoring cost-based?
    Yes: Optimize donor choice, mutation cost, call count, and scheduler safety.
    No: Prioritize reliability and final answer format.

Problem Identification - Oracle Abuse

1. Does verification accept a user-controlled epoch, key index, or rotation number?
2. Can a valid object from one epoch be replayed into another epoch?
3. Does the verifier reveal separate success and failure states?
4. Does failure remove, blacklist, rotate, or otherwise change state?
5. Can an attacker generate chosen state transitions before asking the oracle?
6. Are retry or acknowledgement behaviors observable and attacker-influenceable?
7. Are logs available for both request framing and verification result?
8. Is the MAC or signature scope bound to sender, recipient, message type, epoch, and a monotonic counter?
9. Are repeated verification failures aggregated and alerted on at the SIEM layer?

Cost-Aware Payload Selection

from dataclasses import dataclass
from typing import Callable

@dataclass(frozen=True)
class CandidatePayload:
    content: bytes
    sender: str
    recipient: str
    semantic_id: str


def choose_cheapest_payload(
    donor: bytes,
    candidates: list[CandidatePayload],
    cost_fn: Callable[[bytes, bytes], tuple[int, int]],
    *,
    ink_weight: int = 1,
    whiteout_weight: int = 1,
) -> CandidatePayload:
    """Select the lowest weighted-cost payload among equivalent candidates."""
    same_length = [c for c in candidates if len(c.content) == len(donor)]
    if not same_length:
        raise ValueError("no same-length candidates available")

    def score(candidate: CandidatePayload) -> int:
        ink, whiteout = cost_fn(donor, candidate.content)
        return ink_weight * ink + whiteout_weight * whiteout

    return min(same_length, key=score)

Usage notes:

  1. Generate multiple semantically equivalent payloads before calling this helper.
  2. Use the actual current donor bytes, not a generic template.
  3. Supply the actual scoring weights rather than assuming ink and whiteout have equal value.
  4. Reject candidates that are cheaper but destabilize the scheduler.
  5. Include host-call, delay, and failure-risk costs in a higher-level objective when they materially affect the live score.

Secure Design Pseudo-Code

The original protocol's MAC input was not bound to the wider security context, which enabled the rotation-field replay. 1. A secure replacement should use explicit, canonical length prefixes, domain separation, protocol versioning, key identifiers and purposes, and receiver-enforced freshness. 2. A nonce or counter only prevents replay when the receiver verifies monotonicity or tracks prior use.

import hashlib
import hmac
import struct
from collections.abc import Mapping

PROTOCOL_DOMAIN = b"example-protocol/mac/v1"
ALGORITHM_ID = b"HMAC-SHA-256"


def length_prefixed(*fields: bytes) -> bytes:
    """Concatenate fields with explicit 4-byte big-endian length prefixes.

    Length prefixes prevent canonicalization collisions: with a single-byte
    delimiter, an attacker who controls one field can shift the boundary
    between fields by including the delimiter in their value. Length
    prefixing makes the encoding unambiguous.
    """
    return b"".join(struct.pack(">I", len(f)) + f for f in fields)


def mac_protocol_message(
    key: bytes,
    context: Mapping[str, object],
    message: bytes,
) -> bytes:
    """Bind the MAC to protocol identity, state, purpose, and freshness."""
    canonical = length_prefixed(
        PROTOCOL_DOMAIN,
        ALGORITHM_ID,
        str(context["protocol_version"]).encode(),
        str(context["key_id"]).encode(),
        str(context["key_purpose"]).encode(),
        str(context["sender"]).encode(),
        str(context["recipient"]).encode(),
        str(context["message_type"]).encode(),
        struct.pack(">Q", int(context["rotation_epoch"])),
        struct.pack(">Q", int(context["counter"])),
        bytes(context["nonce"]),
        message,
    )
    return hmac.new(key, canonical, hashlib.sha256).digest()


def verify_protocol_mac(expected: bytes, supplied: bytes) -> bool:
    """Use a constant-time comparison after freshness and authorization checks."""
    return hmac.compare_digest(expected, supplied)

Example KQL Detection (Microsoft Sentinel / Azure Data Explorer)

// Detect repeated verification failures spanning multiple key epochs.
// Field names are illustrative; map to the local application audit schema.
AppProtocolEvents
| where EventType == "VerifyResult"
| summarize
    Failures = countif(Result == "INVALID"),
    Successes = countif(Result == "VALID"),
    EpochDiversity = dcount(RotationEpoch),
    FirstSeen = min(TimeGenerated),
    LastSeen = max(TimeGenerated)
  by TokenHash, SrcEntity, DstEntity, bin(TimeGenerated, 10m)
| where Failures >= 20 and EpochDiversity >= 5

This illustrative KQL uses fixed ten-minute bins rather than a true sliding window. In production, I would need to consider the scheduled lookback and suppression behavior to prevent boundary misses.

Example Splunk SPL Detection

Verification-oracle analytic:

index=<app_index> sourcetype=<protocol_audit> EventType="VerifyResult"
| bin _time span=10m
| stats
    count(eval(Result="INVALID")) as invalid_verify,
    dc(RotationEpoch) as unique_epochs,
    count(eval(Result="VALID")) as valid_verify
  by _time, TokenHash, SrcEntity, DstEntity
| where invalid_verify >= 20 AND unique_epochs >= 5

Rotation and Acknowledgement Analytic:

index=<app_index> sourcetype=<protocol_audit>
  (EventType="KeyRotationSent" OR EventType="Ack")
| eval CorrelationId=coalesce(RotationId, AckedRotationId, RotationHash)
| bin _time span=10m
| stats
    count(eval(EventType="KeyRotationSent")) as rotations,
    count(eval(EventType="Ack")) as acks
  by _time, CorrelationId, SrcEntity, DstEntity
| eval ack_ratio = if(rotations > 0, acks / rotations, 1.0)
| where rotations >= 10 AND ack_ratio < 0.2

The two behaviors are separated because: 1. Verification events and rotation/ACK events do not necessarily share TokenHash. 2. The retry analytic correlates ACKs through a stable rotation identifier or message hash; schemas in prod should normalize sender and recipient direction before calculating the ratio. 3. A threshold below 0.2 tolerates some background loss while still surfacing sustained retry behavior.
