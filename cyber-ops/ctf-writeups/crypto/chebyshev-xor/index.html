The Loop That Would Outlive the Ciphertext

The script looked one fix away from working. Then I saw its loop count: 10 to the 25th.

Summary

The challenge. Recover the plaintext from a 35-byte encrypted file and a Python decryptor that could not finish as written.

What I did. I read the code, identified the recurrence, checked a logarithmic evaluator against the slow loop, and cycled the recovered key bytes across the full file.

The result. The account reports a flag-shaped plaintext and trailing newline after cycling the keystream. The local lab verifies the method with invented data.

The limit. The ciphertext bytes, actual base value, full plaintext, and platform receipt are absent here, so I could not independently replay the challenge solve.

Lightweight Overview

I started with flag.enc and a Python script meant to decode it. The script could not read the file as written, and its central loop tried to run 10**25 iterations. The recurrence inside that loop was the useful clue. It computes a Chebyshev polynomial in a prime field, so I could evaluate the same term with doubling in about 84 bit steps. My first XOR covered only 32 of the file's 35 bytes. Cycling the computed key bytes gave the complete flag-shaped result reported in the challenge account. The flow above shows those checkpoints.

1. Problem Statement and Threat Scenario

The prompt asked why a decode script did not work. I had two challenge items: a 35-byte flag.enc and a Python decryptor. The goal was plaintext recovery, not merely making the script run. A string method was called on a file name, a recurrence loop had a counter of 10**25, and the final zip() would stop after one short key block. Each defect mattered at a different point in the solve.

For a defensive analogy, imagine recovering a binary blob and an incomplete decoder from a suspicious host. I would want to identify the transform, make it tractable, and preserve the decoded bytes for triage. This exercise did not include a host, intrusion, or adversary sample. It demonstrated how a custom transform could slow an analyst who simply runs the code.

2. Techniques, Tooling, and Actions Taken

2.1 Initial triage of the supplied script

I read decode.py before executing it. ("flag.enc").read_bytes() fails because a string has no read_bytes() method; Path("flag.enc").read_bytes() is the intended shape. The key - 1 loop was the real blocker, with key = 10**25. At a hypothetical hundred million modular operations per second, that many iterations would still take roughly 3.2 billion years. The actual Python rate would be different, but no benchmark is needed to know the linear loop is unusable.

The file had 35 bytes. long_to_bytes(secret) yields at most 32 bytes for an element below the 256-bit prime, and zip(ciphertext, key_bytes) silently discards the tail. My first run produced a 32-byte partial output, so this was a concrete mismatch.

2.2 Identification of the recurrence

The loop carried (prev, current) = (1, x) and updated current with (2*x*current - prev) % p. Those are the starting values and recurrence for the Chebyshev polynomial of the first kind, T_n(x). The modulus was the secp256k1 base-field prime, 2**256 - 2**32 - 977. I did not need elliptic-curve group operations. Here it is a large prime modulus for arithmetic on the recurrence.

I briefly checked whether the expression was a Lucas U_n or V_n variant. The initial pair (1, x) and the 2*x coefficient made the Chebyshev reading direct. That mattered because I could use its doubling identities instead of trying to speed up the original loop with a faster machine.

2.3 Replacing the linear recurrence with logarithmic computation

I maintained adjacent values (T_k, T_{k+1}) and stepped through the bits of n. The identities are T_{2k} = 2*T_k**2 - 1 and T_{2k+1} = 2*T_k*T_{k+1} - x, all reduced modulo p. 10**25 has 84 bits. The work depends on those bits rather than on twenty-five digits' worth of iterations. The linked Chebyshev lab contains the exact bounded implementation and an independent matrix evaluator.

2.4 Verification before execution

I compared the fast routine with the slow recurrence for indices 0, 1, 2, 3, 5, 17, 100, 1000, 12345. My notes report exact agreement at all nine. I kept that gate before evaluating 10**25: a swapped pair or sign error in a doubling formula would produce plausible-looking bytes and a wrong key. The newly authored tests repeat the nine checks with invented x, and compare against a separate matrix implementation. They also compare the fast and matrix paths at 10**25; the actual challenge base value is not available.

2.5 First decryption attempt - partial output

With the fast recurrence in place, the first XOR returned 32 bytes. The recorded text began with the expected flag prefix and then stopped without a closing brace. That matched the zip() limit from my static read. I did not treat the plausible prefix as a finished solve. Three ciphertext bytes remained.

2.6 Resolving the length mismatch

I tried three ways to cover the tail:

Candidate Recorded result
Cycle the long_to_bytes(secret) block Printable completion, closing brace, trailing newline
Add zero bytes Nonprintable tail
Concatenate neighboring T_k values Nonprintable tail

Cycling was the only candidate consistent with the full recorded output. My notes describe a 32-byte block in this run, but long_to_bytes uses the shortest big-endian representation of an integer, so another value could use fewer bytes. I preserve that exact conversion before cycling. The challenge's encryptor is absent here; the reported plaintext and failed alternatives support the cycle inference.

2.7 Dead ends documented for tradecraft

I considered a hidden key in the constants and a different Lucas-sequence interpretation. The recurrence shape and its starting pair made those detours unnecessary. I also kept the zero-pad and neighboring-polynomial failures because the length fix was an inference from output, not a rule I could read directly from the supplied decryptor.

3. Tooling and Scripts

3.1 Working decryption

The essential replacement is small. The linked lab runs it with synthetic inputs, and the exact decryption requires the missing challenge values:

from pathlib import Path
from Crypto.Util.number import long_to_bytes
from itertools import cycle, islice

ct = Path("flag.enc").read_bytes()
secret = chebyshev_T(base_val, 10**25, p)
key_bytes = long_to_bytes(secret)
keystream = bytes(islice(cycle(key_bytes), len(ct)))
plaintext = bytes(c ^ k for c, k in zip(ct, keystream))

My example uses illustrative BASE_VAL = 0x1337C0DE, separate from the challenge base. The linked lab uses Python's built-in int.to_bytes to reproduce long_to_bytes's minimal big-endian behavior for a nonnegative field element, avoiding an extra dependency. It bounds the index size and rejects an empty keystream.

3.2 Reference-versus-fast equivalence harness

The slow reference starts with 1, x and repeats prev, cur = cur, (2*x*cur - prev) % p. I ran it only at small indices. The local tests compare that reference against fast doubling, independent matrix exponentiation, and the generic recurrence evaluator at the nine recorded indices. Agreement on test points supports the implementation. It does not validate the missing ciphertext or the reported flag.

3.3 Fallback path (not executed but prepared)

If the doubling derivation had failed, I could use the companion matrix [[2*x, -1], [1, 0]]. For n >= 1, its (n-1)st power acting on [x, 1] has T_n in the first component. Matrix exponentiation also takes logarithmic steps. I did not need that route for the reported challenge. The lab's independent matrix evaluator now gives the shortcut another mathematical check. The account's written formula for the full power matrix had the indices shifted; the vector form above is the relation I tested.

4. Concept Explanation

4.1 Chebyshev polynomials of the first kind

T_0(x)=1, T_1(x)=x, and T_{n+1}(x)=2*x*T_n(x)-T_{n-1}(x). I evaluated these polynomials modulo p, so every step stayed in a finite field. Chebyshev polynomials also have a composition property, but this case did not implement key exchange. It derived one deterministic integer and turned that integer into a repeating XOR block. The named secp256k1 prime did not make that construction an elliptic-curve cipher.

4.2 Why the doubling identity exists

The recurrence is second order, so a two-value state is enough. The companion matrix advances [T_{k+1}, T_k] by one step; squaring its power advances by twice as many. That structure gives the even and odd identities used in the fast evaluator. I checked both routes rather than relying on the label "Lucas doubling" alone. NIST's Digital Library of Mathematical Functions documents the Chebyshev recurrence family.

4.3 Why naive O(n) was the trap

The original algorithm was correct in shape but impossible at 10**25 steps. The shortcut changed the growth of the work from linear in n to linear in the number of bits of n, with modular multiplications at each bit. The particular processor speed did not decide this challenge. Recognizing the recurrence did.

4.4 XOR keystream with a fixed key

Once I had the polynomial result, the ciphertext was repeating-key XOR. The same key bytes recur after one block. With known plaintext, repeated messages, or the visible derivation, that offers no modern confidentiality guarantee. The 35-byte file exposed the repetition boundary because the key block covered fewer bytes than the file. The challenge shows a vulnerable construction, not a cryptographic library to reuse.

5. Exploit/Analysis Mechanics

The assumption behind the obfuscation was that evaluating T_(10**25) required 10**25 loop iterations. I used the identities to compute the same field element, converted it to its minimal big-endian bytes, and repeated those bytes to the ciphertext length. The first 32-byte prefix kept me from overlooking the final three bytes. The recorded full output had a flag-shaped envelope and a trailing newline. Without the 35 ciphertext bytes and real base value, I cannot independently confirm the bytes or grading result. The toy 35-byte round trip confirms that cycling, rather than zip() truncation, handles the same length condition.

6. Lessons Learned (Practitioner Perspective)

6.1 What this validated

Reading the whole script saved me from treating a type error as the whole problem. The recurrence, its starting values, and the length mismatch were all visible before the expensive run. I trust the fast implementation because it agreed with a slow reference on small cases, not because its output looked cryptographic.

6.2 What this surfaced as a gap

I had to recognize a particular recurrence and know where to look for a fast form. A more general fallback is companion-matrix exponentiation. I added the bounded generic evaluator for future analysis, with tests against this case and Fibonacci. It handles constant coefficients; it does not turn an arbitrary nonlinear loop into a linear recurrence.

6.3 Transferable principles

In this solve What I would carry forward
Read before running Separate trivial code errors from the real computational blocker
Compare slow and fast Catch recurrence mistakes before a huge index
Check zip() length Verify every ciphertext byte was processed
Try a few tail constructions Keep failed candidates when they constrain the inferred encryptor
Recognize shape over constants Search for the update rule, then assess what the modulus contributes
7. Extrapolation

7.1 Individual practitioner skill development

This case gave me practice with modular arithmetic, fast exponentiation, and testing an optimized implementation against a simple one. The companion-matrix method applies to other constant-coefficient recurrences. Finite-field square roots and elliptic-curve operations are adjacent subjects, but neither was needed here.

7.2 Security operations (SOC, IR, threat hunting)

If I found this in a real loader, I would preserve the sample and its surrounding process context, identify where the base value and counter came from, then decode a copy. The recovered configuration could supply network addresses or behavior to investigate, but this challenge gives no such real indicators. A high-CPU Python process by itself is a poor alert: data science, builds, and legitimate math jobs do the same thing. The more specific source-code review hypothesis is the recurrence shape next to a large integer constant. The linked static reviewer tests that narrow pattern on Python source, with positive, benign, and near-miss fixtures in the tests. A match asks for review; it does not classify malware.

7.3 Intelligence operations (SIGINT, IO/IW, OSINT, attribution)

I would catalog the recurrence, modulus, key-byte conversion, and XOR framing as traits of a real sample. Reuse could help cluster samples, but public code copying and common constants weaken any attribution claim. A shared secp256k1 prime alone is especially weak. I would require independently collected samples and corroborating behavior before linking an actor. No such collection occurred in this challenge.

8. Reusable Tools, Scripts, and Artifacts

8.1 Triage decision tree for "custom recurrence" obfuscation

When I see new = f(previous, current, constants) % p, I first write down the initial values and identify the recurrence order. The pair (1, x) with 2*x*current - previous points to Chebyshev T_n. A constant-coefficient second-order recurrence can be expressed as a two-by-two matrix; higher-order constant-coefficient cases use larger companion matrices. A huge iteration count makes the fast form worth deriving. A cubic expression does not automatically become a linear recurrence merely because it has several state variables.

8.2 Reusable primitive - generic linear-recurrence fast evaluator

The companion-matrix evaluator accepts coefficients, the matching initial values, index, and modulus. It computes a term in logarithmic index steps, with matrix work depending on the recurrence order. I bound the order at 16 and the index at 4096 bits. The test suite checks it against T_n at nine small points and against Fibonacci's 20th term. For the actual challenge path, the specialized doubling function is simpler and faster. The guide names every input, output, and limit.

8.3 Solve-pattern checklist for custom-cipher CTF or malware

My sequence is to read the code, list the defects, identify the recurrence, test a fast form against a slow one, verify key and ciphertext lengths, and inspect every output byte. For a real malware sample I would add provenance for each input and keep decoded bytes isolated from execution. The linked math lab uses invented parameters and contains no challenge flag.enc.

9. Framework Mapping

I considered ATT&CK T1027.013 for a real encoded or encrypted file used to hide behavior. The challenge's local file alone does not establish adversary use. T1140 describes adversary decoding during execution; my analyst decryption is the defensive counterpart, not an observation of that adversary technique. T1059.006 would need evidence that an attacker ran Python. The fact that the supplied solver is Python is not enough.

CWE-327 fits the risky repeating-XOR construction as a software weakness. CWE-1240 is also a candidate for a risky cryptographic implementation. CWE-330 is less precise here: the visible issue is a deterministic, repeated keystream, with no documented random-value generation path. CAPEC-97 Cryptanalysis describes an attack pattern, but the work in this record is analyst recovery of a challenge artifact. CAPEC-20 brute forcing was considered and rejected; I used structure. D3FEND file analysis fits the defensive workflow broadly. The slow-reference test was mathematical validation, not sandboxed dynamic analysis of malware. STRIDE and OWASP did not add useful detail to this file-and-script exercise.

11. Controls Mapping and Mitigation Realization

11a. Standards Mapping

I mapped NIST SP 800-53 SC-13, SC-12, SA-11, SA-15, and SI-10, plus NIST SP 800-175B and CIS 16.10/16.11. For a real product, I would use these as review prompts: choose vetted primitives, govern key material, test the security code, and validate input framing. Any FIPS or STIG conclusion requires the exact module and system boundary. A blanket rule that every key must come from a KMS or HSM would miss legitimate designs and does not by itself establish compliance.

11b. Mitigation Realization

The practical source-code gate for this case is a review finding when a Python file contains a large integer literal and a modular 2*a*b-c recurrence. The AST reviewer is a small proof of concept for that signal. It reads at most 256 KB, parses without executing, and reports the line. The tests include the target shape, a benign large-prime calculation, and the recurrence with a small modulus. It will miss reordered expressions, constants imported from elsewhere, compiled code, or different languages. I would require a human review of a match before blocking a build.

I also considered an SBOM/source review, designated crypto reviewer, and a length check at decryption boundaries. I would scope each to the actual repository and threat model. A code review checklist is a useful process artifact but does not prove that a protection ran; assert is also unsuitable as a production input guard because optimization can remove it. The public README states the tested boundary of the executable reviewer.

12. Indicators, Artifacts, and Detection Engineering

12.1 Sanitized IOCs

The recurrence expression and secp256k1 prime are code traits, not compromise indicators. The prime occurs in legitimate software. Their combination merits inspection if I find it in an unexpected source tree, but it does not establish actor identity or malicious intent. No actual path, hash, domain, or process event was retained as an IOC.

12.2 YARA rule

The proposed YARA combined a regex for (2*name*name-name)%name, the tail of the secp256k1 prime, and Python imports. That is a useful seed for source-like files, but I have no representative malicious sample set, benign corpus, or YARA-engine test here. Its regex is also narrow: syntax and variable rearrangements can break it. I published the locally tested Python AST reviewer instead of calling the YARA rule a validated detector.

12.3 Sigma rule

The proposed Sigma rule selected Python process creation and excluded a few ordinary commands. Its title claimed high CPU and no network I/O, but a process-creation event supplies neither CPU duration nor network absence. I would need correlated resource and network telemetry, and a useful baseline, before writing that behavior rule. A syntax-valid Sigma file alone would not close that gap.

12.4 SIEM detection (Splunk SPL)

The proposed SPL joined Sysmon process-create, network-connect, and terminate events by ProcessGuid; the KQL joined Defender process and network tables. Neither query established CPU use. A process start-to-stop duration is not CPU time, and a missing network event can mean a collection gap. Field names, process identity, and join windows also need testing on the actual backend. I have not deployed or validated those queries, so I did not publish them as ready-to-run detection.

12.5 Log source and data pipeline requirements

The code-review proof needs accessible Python source and a review event with file path and finding line. A behavior hunt would separately need process lifetime, per-process CPU measurements, network events, stable process identifiers, clock alignment, and documented collection gaps. Sysmon IDs 1, 3, and 5 can help with process and network context when configured, but they do not supply CPU saturation. A five-minute retention granularity would be too coarse for some joins; I would choose event fidelity from the hunt question.

12.6 Detection engineering notes

My static reviewer trades coverage for a clear, testable shape. Its positive and negative fixtures passed locally. Legitimate numerical code can still match, while an obfuscated or compiled implementation will not. I would tune it on a real repository, require a reviewer to explain matches, and record false positives before promoting it to a blocking gate. The long-running-Python hypothesis remains untested.
