The Codebook That Was Just Base Nine

I could read 39 of 42 tokens and still had the wrong mechanism. The three I could not explain were the clue.

Summary

The challenge. Recover the plaintext of two encoded fragments and explain the encoding rule without any key material.

What I did. I decoded the letter-only fragment with Atbash, built a partial word-shape table for the numeric one, then revisited its digit set after a rejected submission.

The result. The recorded correction decodes all 42 numeric tokens as base-9 ASCII with zero exceptions; the Atbash fragment also reads as English. The first submitted model was rejected.

The limit. The actual fragments, full plaintexts, and final platform receipt are withheld. The base-9 mechanism was found after the initial solve, and the linked examples use invented text.

1. Problem Statement and Threat Scenario

I was given two inline text fragments and no key, file, host, or service to interrogate. Fragment A had 42 space-delimited, three-digit tokens. Fragment B was a short lowercase string with spaces. The task was to recover both plaintexts. The story attributed the messages to a group staging and brokering documents, but the evidence I could analyze was only the text. I did not observe collection, transfer, or an intrusion.

The useful real-world question is whether unfamiliar text is actually encrypted. An analyst with a content sample and no key can still test its alphabet, field widths, and reversible transforms. Here one fragment was a keyless classical substitution; the other was ASCII code points written in a different base. Mistaking the second for a secret codebook consumed most of the solve. Treating the fictional prose as evidence of a real actor would add a different mistake.

2. Techniques, Tooling, and Actions Taken

Both fragments were worked statically. I had no telemetry or target to validate against. The later verification code was written after the hand solve.

Methodology notes

Fragment B was mercifully short. The alphabet made a keyed search unnecessary at first, and Atbash gave a readable sentence immediately. The actual sentence is withheld. The point is that every letter transformed under one consistent involution, with spaces preserved.

Fragment A gave me a dangerous kind of success. Long words constrained the substitution table, so 39 tokens acquired plausible letter values. The remaining three tokens sat in the leading group and encoded digits, outside what English word-shape reasoning could infer. Their numeric values were about 54 units below the other non-separator tokens, with a gap between clusters. I interpreted the two clusters as variants of a cipher alphabet and invented a homophonic layer to join them. The submitted explanation was rejected. The table fit many outputs but did not explain why those numeric values existed.

The correction came later. I had noticed the 8 when ruling out octal, yet I had not asked what radix permits 8 and excludes 9. Once I did, base 9 became the smallest candidate. The complete 42-token decode, not the digit observation by itself, supported it. This timing matters to me: the plaintext guess came during the solve; the generating rule was recovered afterward.

3. Tooling and Scripts

I did not run a decoder during the initial hand solve. Later I wrote a small verifier around three operations: infer the minimum radix from observed digits, decode every fixed-width token as a positional numeral, and inspect the entire output for printable ASCII. Here is the core:

def infer_radix(tokens):
    return max(2, max(int(d) for token in tokens for d in token) + 1)

def decode(tokens, radix):
    values = []
    for token in tokens:
        value = int(token, radix)
        if value > 127:
            raise ValueError("outside ASCII")
        values.append(chr(value))
    return "".join(values)

def validate_blocks(plaintext):
    codes = sorted({ord(c) for c in plaintext})
    return all(32 <= code <= 126 for code in codes), codes

infer_radix gives a lower bound, not a proof. A higher base can happen to omit its largest digits in a finite sample. I check all tokens and compare candidate outputs. The invented text 24 keys stored in the archive encodes as 29 three-digit base-9 tokens; the local fixture holds those tokens. It has no connection to the withheld challenge text. The runnable reviewer reports candidate radices and hashes of decoded strings rather than printing message bodies. Its tests include a base-9 positive, an ambiguous decimal-ASCII example, and a near miss containing 9. The README explains the input and sensor assumptions.

For Fragment B, the transform was just alphabet reflection. For each lowercase letter at position x from a=0, use 25-x; leave spaces and punctuation alone. An invented demonstration is gsv wilk klrmg rh xlmurinvw, which reads the drop point is confirmed. Applying Atbash again returns the input. The reviewer includes that function and its round-trip check, but it was not a tool used during the first solve.

4. Concept Explanation

Positional notation is a representation, not a cipher

A three-digit numeral in base b means d2*b^2 + d1*b + d0. For example, 055 in base 9 is decimal 50, the ASCII code for 2. There is no secret parameter to recover; changing the base changes the written form of a value. That is why a fitting substitution table was the wrong model, even though it produced plausible words.

The largest digit observed sets a minimum valid radix. Seeing 8 rules out bases 2 through 8. A missing 9 makes base 9 worth testing, but absence alone cannot rule out base 10 or a higher base. This is the correction to the more confident inference I first wanted to make. The complete decode and the token grouping carry the validation burden.

Three base-9 digits span 0 through 9^3-1 = 728; two span only 0 through 80. Three positions can represent the full seven-bit ASCII range 0-127, with leading zeros preserving width. That explains the field size without requiring a codebook. Other designers could choose a wider field, so width is supporting evidence rather than unique proof.

What the decode image reveals

The recorded fragment had 20 distinct numeric tokens. Under base 9, they mapped to ASCII space at 32, digits in the 48-57 range, and lowercase letters in the 97-122 range. Those code-point blocks explain the two value clusters I had mistaken for separate cipher alphabets. ASCII's gap from 9 at 57 to a at 97 is 40 decimal code points; the approximately 54-unit gap I saw was in the encoded token values, not the ASCII code points themselves.

The image is stronger than a few recognizable words because it covers every token. Still, printable output is not a mathematical uniqueness proof. A decimal ASCII string can also decode to printable text under base 9; the linked synthetic fixture deliberately demonstrates this false positive. Word boundaries, semantic fit, and the stated challenge context matter after the structural checks.

Atbash

For a 26-letter alphabet, Atbash maps position x to 25-x. Applying the same mapping twice restores x, so encoding and decoding are the same operation. It needs no key. The letter frequencies are permuted, not flattened, which makes it poor concealment. In Fragment B, one pass produced coherent English; I did not need to stack ROT-N or a keyed cipher on it.

5. Exploit/Analysis Mechanics

My first model failed at a clear boundary: three tokens encoded digits, while my word-shape method assigned letters. No better word list could resolve a character class the method excluded. I covered that gap with a proposed homophonic substitution layer, but that layer had no independent evidence. The later base-9 rule explained all 42 positions with one positional operation and no exceptions.

The corrected chain is short. Preserve each three-digit field and its leading zeros. Observe that 8 occurs and 9 does not. Test base 9, then decode every field as an ASCII integer. Check all results for range, printability, word boundaries, and coherent text. Compare plausible alternative radices. An invalid digit or widespread controls would refute a candidate; a few words alone would not establish it.

The homophonic idea also deserved its own test. Such a cipher gives multiple symbols to some plaintext letters, often to alter letter frequencies. I had only 42 positions and no evidence of a frequency-flattening design. The claim served mainly to excuse three unmapped tokens. The right response was to revisit the token values. The rejected submission gave me that pressure, but the contradictory values were already visible before it.

6. Lessons Learned (Practitioner Perspective)

What the exercise validated

Character-set triage paid off immediately on Fragment B. Atbash was cheap to test and gave a consistent reading. On Fragment A, starting with the longest groups was a reasonable way to constrain a substitution hypothesis. It yielded 39 of 42 token values without conflict. That partial result was real work, even though the hypothesis behind it was wrong.

What the exercise surfaced as gaps

I used the digit 8 to eliminate octal, then stopped. It also told me which nearby base to test next. The missing 9 was a clue, subject to sample-size limits. Reading a failed hypothesis only as a rejection, without asking what the same fact supports, kept me on the longer path.

The offset sweep gave another near miss. The apparent differences stepped through 52, 53, 54, and 55 at irregular boundaries. I tried to fit a constant offset where base-9 carry behavior was changing the written numeral. The failed additive model was evidence about the representation, not an invitation to invent a more elaborate offset.

The confidently stated homophonic layer was the costly error. My table reproduced most observed output but had no generating rule. When the three exceptions appeared, I made the explanation larger instead of checking the character classes. The challenge's own name also contained a numeral hinting at the maximum base-9 digit. I had noticed it and put it aside as a possible red herring. The title and the digit set were two separate hints that I failed to connect until afterward.

Transferable principles

What happened here What I would do in an investigation
I inspected the alphabet before transforming Fragment B. Characterize bytes, delimiters, and lengths before choosing a decoder.
Octal failed on digit 8. Ask what a disqualifying observation positively implies.
Three tokens escaped the word table. Treat unreachable data as a model problem, not noise to normalize away.
A table fit 39 positions. Ask for a rule that generates every value; matching output alone cannot establish a mechanism.
I invented a layer after contradiction. Separate a hypothesis from evidence, and withdraw it when its needed assumptions multiply.
Base 9 emerged in later review. Record when the mechanism was identified; do not backdate the insight into the live solve.
7. Extrapolation

The transferable skill is rapid representation triage. A content sample may be encoded, compressed, encrypted, or simply written in an unfamiliar notation. Character sets, magic bytes, field widths, and reversibility narrow the possibilities. Index-of-coincidence and Kasiski tests can help with later polyalphabetic cases; known-plaintext XOR and endianness checks are different but adjacent tools. Neither was needed for these two fragments.

For a defender, the realistic hypothesis is narrow: inspect content at an authorized point where message bodies are available and look for fixed-width numeric text whose candidate radix yields printable output. The local reviewer demonstrates that mechanics and also gives a benign decimal-ASCII false positive. A content lead needs destination, volume, business context, and policy correlation. There were no network captures or endpoint logs in this case, so no operational detection was validated.

I would not infer an actor from the choice of Atbash and base 9. Two fragments under two simple schemes establish only that those schemes appear in the challenge. They say nothing reliable about infrastructure, sophistication, or a real exfiltration path.

8. Reusable Tools, Scripts, and Artifacts

Encoded-content triage decision tree

1. Inventory the alphabet and field shape.
   Numeric fixed-width tokens -> test positional interpretations.
   Letters and spaces -> try simple, keyless substitutions.
   Base64-like or binary content -> validate that format before guessing intent.
2. For numeric tokens, keep leading zeros and note the largest digit.
   Test the smallest valid radix and plausible higher radices.
   Decode every token; examine full output and alternatives.
3. For letter text, try Atbash and ROT-N before keyed methods.
   Use frequency tests only on enough material to support them.
4. For high-entropy bytes, inspect headers and containers first.
   Entropy alone cannot distinguish compression from encryption.
5. Stop and reconsider whenever a rule needs exceptions or leaves a class
   of tokens unreachable. Keep rejected candidates in the analysis record.

For later triage, rough index-of-coincidence landmarks near 0.066 for English monoalphabetic text and 0.038 for a flatter polyalphabetic distribution can suggest what to examine next. Those are reference values, not decision thresholds for a 47-character fragment. Chi-square and entropy checks may help with byte-heavy input; neither was run here.

Reusable primitives

infer_radix(tokens) proposes the smallest base permitted by the observed digits. decode(tokens, radix) applies the positional rule. validate_blocks checks the output range. None turns a lower bound into a unique identification. The bounded content reviewer tests candidate bases, keeps decoded text out of its JSON report, and emits only review leads. Its synthetic messages, tests, and guide make the positive, false-positive, and near-miss behavior reproducible.

The rule-vs-table test

I now ask whether a recovered mapping can be generated by a short formula. In this case every token could be explained by positional arithmetic, so maintaining a 20-entry value table hid a simpler mechanism. A truly arbitrary codebook may not compress that way, but failing to find a formula is not proof that none exists. The test is a prompt to compare models, not an automatic classifier.

11b. Mitigation Realization

The proposed SI-4 implementation is a content review of numeric token runs. It needs actual body bytes. A connection log, NetFlow, or IPFIX record cannot supply those bytes. An email gateway, approved DLP export, application audit, or explicitly configured body-capture pipeline might. TLS also hides content from a passive network observer unless an authorized endpoint or inspection layer exposes it.

CIS 13.1 matters after the lead exists. A long digit run lacking 9 is common in benign data and does not merit a stand-alone incident. I would correlate it with an unexpected destination, unusual transfer volume, or a known sensitive workflow, then preserve the original content under the applicable access policy. No such pipeline was deployed for this challenge.

12. Indicators, Artifacts, and Detection Engineering

Detection maturity: local synthetic proof of concept. The reviewer and tests now exist. They have no production sensor, backend conversion, tuned threshold, or measured false-positive rate. This is a review aid for a very specific content shape, not an IOC or a general exfiltration detector.

Seed: non-decimal radix content detection

The challenge had a 42-token line of three-digit fields with 8 present and 9 absent. If N independent digits were uniformly sampled from 0-9, the probability that a preselected digit 9 never appears is 0.9^N. For 30, 60, 132, and 300 digits that works out to roughly 4.2e-2, 1.8e-3, 9.0e-7, and 1.9e-14. Real numeric data is rarely independent or uniform. Choosing which absent digit to highlight after seeing the sample also changes the inference. Those numbers illustrate one toy null model; they are not a calibrated alert false-positive rate.

The reviewer accepts an authorized local UTF-8 text export up to 1 MB, 1,000 lines, and 1,000 tokens per line. It looks for lines of at least ten three-digit tokens, computes the minimum possible radix, tests candidate bases up to ten, and checks for printable ASCII. Its JSON gives line number, token count, digit set, candidate bases, character counts, and a digest of the decoded text. It deliberately omits plaintext. The invented fixture produces one base-9-only lead and one decimal-ASCII line that is printable under both bases, an expected false positive. A third line containing 9 produces no printable candidate. Four tests passed those cases plus invalid-token and Atbash checks.

I would tune this only with a real collection source and its benign examples. Decimal ASCII, numeric telemetry, and product identifiers can match. Zeek conn.log summarizes connections and does not carry a message body. An appropriate body extraction or content sensor is required. Without authorized plaintext visibility, this idea has no detection coverage. No Sigma, SPL, or KQL rule can create content fields missing from the collection pipeline.
