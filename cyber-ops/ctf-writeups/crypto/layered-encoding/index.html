The One Letter Hidden Under Three Encodings

Four simple decodes taught me the shapes. The last two made me follow a single wrong character back through three layers.

Summary

The challenge. Identify and decode six supplied strings. The final pair used hex around Base64 around octal, with a one-character plaintext discrepancy.

What I did. I checked alphabets and group widths, decoded one layer at a time, and compared the last pair at the byte level.

The result. My notes say all six decoded and identify a 31-to-78 outer-hex difference behind cell versus call. The local synthetic lab verifies the stack using invented strings.

The limit. The six exact inputs, complete outputs, and submission receipts are absent from this account. I cannot independently replay or confirm challenge acceptance.

Attack Chain Overview

The final two exercises nested ordinary encodings. I read the hex pairs first. Those bytes spelled Base64 text; decoding that text produced space-separated octal values; the octal values spelled a sentence. The near-match in Challenge 5 made Challenge 6 more interesting than another mechanical decode. The direction matters: octal, then Base64, then hex to construct; hex, then Base64, then octal to read. 1. Problem Statement and Threat Scenario

Challenge Presentation

I worked through six strings with no keys or hints. The first four each used one representation: eight-bit binary groups, three-digit octal, hex pairs, and Base64. The last two wrapped octal text in Base64 and then represented those Base64 bytes as hex. My task was to recover the text, including a single-character discrepancy between the last pair. This account does not include the exact strings or complete answers. I can describe the steps and test the method with invented examples; I cannot replay the six challenge inputs.

Threat Model

I treated the supplied blobs as an exercise in obscuring text. A real operator might encode a command, configuration, or exfiltrated content so a plaintext string match misses it. That is an operational analogy, not an observed intrusion here. Common encoding also carries ordinary data every day. A Base64-looking string by itself says little about intent. The defender's useful question is whether the surrounding process, file, or message warrants decoding and investigation.

2. Techniques, Tooling, and Actions Taken

Initial Triage Methodology

I checked the character set and token width before choosing a decoder. Challenge 1 consisted of space-separated eight-character groups using 0 and 1, so I treated each as a byte. Challenge 2's three-digit groups could initially have been decimal. The recurring 040 at word boundaries made octal a stronger reading because octal 040 is an ASCII space. Challenge 3 used two-character hex groups; 20 at word boundaries was the same space in base 16. Challenge 4 was one dense string ending in ==, consistent with padded Base64. Those are clues to test, not proofs that an arbitrary string has only one possible interpretation.

Challenges 5 and 6 started as hex pairs. I decoded them to Base64 text, decoded that to octal groups, then read the octal bytes as ASCII. My Challenge 5 reading had cell where the expected sentence read call. I did not switch schemes because the intermediate shapes and the rest of the sentence still held together. My notes put outer hex pair 31 in one string and 78 in the other at position 36. Those pairs encode the Base64 characters 1 and x. The complete strings are absent here, so I cannot verify that position or the full sentence from the challenge data. The local lab shows the same kind of layered correction with invented words.

3. Tooling and Scripts

One-Liner Triage Probes

These small probes fit the single-layer cases. I inspect the bytes after each command before deciding what to try next:

printf '%s' '4d 54 49 30' | tr -d ' ' | xxd -r -p
python3 -c "print(''.join(chr(int(x, 2)) for x in '01001000 01101001'.split()))"
python3 -c "print(''.join(chr(int(x, 8)) for x in '110 151'.split()))"

The first line yields MTI0, which is another encoded-looking string. A printable result can still be an intermediate layer. I also tried base64 -d | strings as a quick probe. That pipeline may hide undecodable or nonprintable bytes, so I would keep the raw bytes for a forensic record and make decoding errors visible. An = suffix is a useful Base64 clue but not a validity check.

Single-Layer Decoders

My Python functions converted binary and octal tokens with int(group, base), used bytes.fromhex() for hex, and used base64.b64decode() for Base64. I added mirror encoders for lab validation. The bounded decoding aid keeps those four paths, requires an explicit scheme, checks group width and canonical Base64, and rejects malformed input. The examples 01001000 01101001, 110 151, 48 69, and SGk= all read Hi in the local tests. None came from the challenge strings.

Multi-Layer Decoder (Challenges 5 and 6)

The decisive order was:

base64_text = bytes.fromhex(hex_text.replace(' ', '')).decode('ascii')
octal_text = base64.b64decode(base64_text, validate=True).decode('ascii')
plaintext = ''.join(chr(int(token, 8)) for token in octal_text.split())

I inspect each intermediate value before moving on. My inspect_layers function printed raw and intermediate previews; encode_hex_b64_oct constructed a matching test string. The linked lab keeps a bounded decode_stack() and an encode_stack() for invented ASCII fixtures. It never evaluates, imports, or executes decoded text. A failed ASCII check stops instead of replacing a byte with ? and silently changing evidence.

Byte-Level Diff Utility

My diff_hex_ciphertexts compared space-delimited pairs, reported unequal lengths, and listed each differing position with hex and ASCII values. That is the right starting point for the 31 versus 78 difference. I would follow the changed Base64 character through its four-character group and compare the resulting octal bytes. An outer byte change need not always produce exactly one final character change. It can also make Base64 invalid or affect more than one decoded byte. This path is a particular case, not a general law.

4. Concept Explanation

Encoding vs. Encryption: A Critical Distinction

These exercises use public, keyless encodings. Reversing them needs the representation, not a secret. Encryption has a key-dependent security claim that encoding lacks. I kept this distinction in mind when assessing the threat model: a string hidden from a simple signature can still be read by anyone who recognizes its layers.

The Four Encoding Schemes

H is ASCII decimal 72, binary 01001000, octal 110, and hex 48. A space is decimal 32, octal 040, and hex 20. These repeated values made useful cross-checks in the first three exercises. Base64 packs input bytes into six-bit symbols using the alphabet A-Z, a-z, 0-9, +, and /. Padding depends on the input length: no = for a multiple of three bytes, == for one leftover byte, and = for two. The exact alphabet and padding rules are defined in RFC 4648.

Multi-Layer Stack Construction

For the last pair, the construction path was plaintext to octal groups, octal text to Base64, and Base64 text to hex pairs. I reversed that order. The intermediate text is part of the evidence: it tells me whether I have peeled off the intended layer or forced a plausible-looking result through a permissive decoder.

5. Exploit/Analysis Mechanics

Invariant Violated

There was no cryptographic secret to break. The exercise relied on the reader stopping at the outer representation. Once I recognized hex pairs, each next layer exposed another familiar shape. I had called these strings ciphertext in my notes. More precisely, they are encoded text.

Layer Identification Logic

My decision tree starts with grouping: eight-bit 0/1 tokens suggest binary, three-digit 0-7 tokens suggest octal, two-digit 0-9a-f pairs suggest hex, and a padded four-character-block alphabet suggests Base64. I test a candidate by decoding strictly and checking the result. A string can satisfy multiple surface patterns, especially a short hex string that also fits a Base64 alphabet. I do not let the first regex choose a final answer without inspecting the decoded bytes. My first auto-detector tried binary, octal, hex, Base64url, then Base64. Its permissive replacement decoding and automatic recursion could turn ambiguous or malformed input into a confident-looking answer. The linked aid makes me select each layer.

Single-Byte Error Propagation

I noted an outer difference of 31 (1) versus 78 (x) at pair 36 and traced it to octal 145 versus 141, or e versus a, yielding cell and call. This is plausible because a change in one Base64 symbol affects a bounded part of one decoded group. I cannot recheck the precise position and words without the exact challenge strings. I would retain both versions and a byte-level diff in a real evidence package rather than correcting the input in place.

6. Lessons Learned (Practitioner Perspective)

What the Exercise Validated

The first four strings gave me a quick vocabulary of shapes. On the last pair, that vocabulary let me notice that the hex output was still structured text. The 040 and 20 space values were good sanity checks. They did not replace strict decoding or a check of the final sentence.

Gaps and Inefficiencies Surfaced

I briefly considered decimal for the octal groups. Checking whether each token fell in the octal range and whether 040 aligned with spaces settled that. The multi-layer case needed deliberate intermediate inspection. An automatic decoder can be useful for triage, but it should expose every step and stop on malformed bytes rather than smoothing them away.

Transferable Principles

7. Extrapolation

Individual Practitioner Skill Development

The next things I would practice are Base64url, custom alphabets, compressed data before Base64, and encoded values inside JSON or scripts. XOR changes the problem because a key or key-recovery step enters the picture. The shared habit is to keep byte boundaries and record each transform.

Security Operations (SOC, IR, Threat Hunting)

A process command line, script block, file, or message body gives the encoding some context. I would start with a suspicious process or workflow, decode a bounded copy, and compare the result with known behavior. A PowerShell encoded command is one practical hunting entry point, but legitimate administration uses it too. The linked process-event triage script tests an invented JSONL event model. It returns a review marker without printing the decoded command. A SOC would need its own field mapping, access controls, baselines, and response process.

Intelligence Operations (SIGINT, IO/IW, OSINT, Attribution)

Encoding alone cannot tell me an actor's sophistication, identity, or purpose. I considered low-resource actors and commodity tooling as possible contexts, but these six strings did not establish either. If I collected a real artifact, I would preserve the outer form, document the decode chain, and attach the recovered bytes to the specific collection point and timestamp. That gives another analyst a way to test the claim.

8. Reusable Tools, Scripts, and Artifacts

Encoding Identification Decision Tree

My checklist covered token width, alphabet, Base64 padding, Base64url, compression, and custom alphabets. I keep it as a triage guide: inspect, choose a candidate, decode strictly, and stop when the output lacks a defensible next layer. A decoded string that happens to be printable is not automatically the final answer.

Auto-Detection and Decode Pipeline

I first sketched identify_encoding() and auto_decode() with a maximum depth of eight. The regex order can misclassify short strings, and errors='replace' discards byte evidence. Its Base64url branch repairs padding without confirming the format. I replaced that sketch with an explicit, bounded decoder for the four exercised schemes and at most four analyst-selected layers. The tests cover positive round trips and malformed near misses. The README states its input and output, limits, and how to adapt it.

CTF Encoding Triage Checklist

Before decoding, I note the character set, grouping, padding, and expected output type. During decoding, I save each intermediate value. Afterward, I check whether the result reads coherently and whether a second source or known format confirms it. For a near match, I compare the raw inputs before assuming a transcription error. That sequence preserves the mistake if the apparent typo turns out to be meaningful.

9. Framework Mapping

MITRE ATT&CK

I mapped the exercise to T1027, Obfuscated Files or Information and T1132.001, Standard Encoding as possible real-world applications. The six strings do not establish a malware file or encoded C2 traffic. T1132 specifically covers command-and-control information. T1140 describes adversary deobfuscation or decoding during execution; my analyst-side decode is not an observation of that technique. T1027.001, Binary Padding, did not appear. T1059.001, PowerShell, belongs to the defensive example below only if a PowerShell process is actually present.

MITRE D3FEND

I considered Dynamic Analysis, File Content Rules, and Script File Analysis. File or script inspection can help once the encoded text is located. Dynamic execution is unnecessary for these text exercises and should require a separate isolated analysis decision for an unknown real payload. No D3FEND technique was deployed or measured here.

CAPEC

I considered CAPEC-267, CAPEC-116, and CAPEC-86 as adjacent ideas. None is shown by these six decoding tasks: no executable was hidden in a non-executable file, no attack excavation behavior was observed, and there was no web query injection. I would map a real case only after the artifact and adversary action justify a pattern. I also considered OWASP, STRIDE, CACAO, and OpenC2; the six text decodes do not supply the application, architecture, or response workflow needed to apply them.

11. Controls Mapping and Mitigation Realization

11a. Standards Mapping

I considered NIST SP 800-53 SI-3, SI-7, AU-2, and AU-12, plus CIS Controls 8.2, 10.1, and 16.1. For this case they are planning references: collect the events needed to see the relevant process or script, inspect suspicious content safely, and keep audit records. I did not assess a system or collect implementation evidence. A policy that says "decode" is not a functioning detection pipeline.

11b. Mitigation Realization

For a PowerShell example, I would first verify process command-line collection and script logging on the actual host. Sysmon Event ID 1 and Windows Security Event ID 4688 can provide process creation context when configured, but their event fields and capture policy differ. PowerShell 4103/4104 data can help with script investigation; I would test what the environment actually records rather than assume every layer or every deobfuscated string appears in logs. AMSI may inspect script content through the host integration. That alone does not guarantee an encoded command will appear in the telemetry I have.

I sketched a Sysmon XML excerpt, a Sigma rule, and an SPL query. The XML's wildcard CommandLine condition would broaden collection beyond the stated encoded-command filter. The Sigma regex and SPL assumed field names and syntax without a tested backend; the SPL used urldecode() where Base64 and UTF-16LE decoding were required. I would keep the collection policy separate from the hunt and validate any backend query with local events. The linked JSONL process-event detector demonstrates the narrower predicate and its tests include a positive, a benign process, and malformed or absent arguments. It is a local proof of concept, not a deployed Sysmon, Sigma, or Splunk rule.

12. Indicators, Artifacts, and Detection Engineering

Indicators of Compromise (Illustrative / Sanitized)

I considered a powershell -enc pattern, long Base64 text in HTTP, a hypothetical registry path, and a hex-pair pattern. They are examples of places to look. No malicious file, registry value, host, domain, command line, or network transaction was retained as an IOC. A long Base64 string is common in benign material. I would require process ancestry, destination, decoded content, or other behavior before escalating.

YARA Rule

My proposed YARA looked for bytes 4D 20 54 20, a padded Base64 run, or repeated 040 tokens. Those bytes could match a particular spaced hex spelling of MT, but I did not test the rule against the six inputs or a benign sample set. Its mixed conditions do not establish the stated three-layer stack. I kept the detection idea and withheld a YARA file until actual representative file samples and negative controls support a rule.

Log Source and Telemetry Requirements

For the process hunt, I need image name, full command line, event identity, and a timestamp from a process-creation sensor. Script content requires an enabled PowerShell logging source and appropriate access controls. HTTP logs often contain URI and metadata but not a POST body; TLS can hide payload content from a network observer. I would not assume Zeek supplies body fields or that all email tenants share a retention period. I would document each sensor's actual fields, sampling, and retention before writing a query.

Detection Engineering Notes

The local detector selects PowerShell or pwsh with an encoded-command switch, checks strict Base64, and decodes UTF-16LE in memory. It emits only event ID, image, decoded length, and a review flag. The guide gives the event schema and tuning limits. A legitimate encoded administrative command remains a false positive for malicious activity. A renamed process, quoting variation, or different PowerShell abbreviation can evade this narrow predicate. The synthetic tests prove the code's behavior on those fixtures, not its field mapping or accuracy in a production SIEM.
