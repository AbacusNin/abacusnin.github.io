The Prefix That Gave Me the XOR Key

The archive opened without a password. The interesting part was the text file inside it: 44 hex characters hiding a 22-byte answer.

Summary

The challenge. Recover a flag from a hex-encoded blob transformed with an unknown one-byte XOR key.

What I did. I identified the hex representation, decoded it to bytes, XORed the stated flag prefix against the opening bytes, then tested the resulting key across the whole blob.

The result. Seven prefix positions yielded 0x42, and a full one-byte decode produced a printable, flag-shaped message consistent with the prompt. The answer value is withheld.

The limit. The original archive, ciphertext, answer, and platform receipt are unavailable for independent replay. The local tests use an invented example.

1. Problem Statement and Threat Scenario

The challenge archive was a normal ZIP containing one text file, cipher.txt. unzip -l showed a 45-byte member. The file held 44 hex characters plus a newline. The event supplied a flag-format prefix, so I had a candidate for the beginning of the plaintext even though the key was unknown.

My task was to identify the representation, recover the one-byte transform, and read the answer. This was a puzzle, with no compromised host or attacker activity. The operational parallel is still worth exploring: malware sometimes stores configuration strings under a simple XOR transform and decodes them at runtime. An analyst with the file can often recover those strings statically, then decide whether they are useful indicators. The puzzle itself provided no C2 address, mutex, persistence key, or real malware sample.

For that real-world parallel, the defender would have an authorized sample in an isolated analysis environment, perhaps with FLOSS, CAPA, YARA, and a hex viewer. Static recovery can save a detonation step. It does not establish that a recovered string was ever used on a network or host. The boundary here is between bytes stored in a file and behavior observed at runtime.

2. Techniques, Tooling, and Actions Taken

I started with the wrapper. unzip -l showed one 45-byte file, and extraction did not ask for a password. I did not spend time on ZIP password recovery. The text was 44 characters of [0-9a-f] followed by a newline. An even-length hex string was the plainest interpretation; bytes.fromhex gave 22 raw bytes.

Some of those bytes were below 0x20, so the raw decode was not directly readable ASCII. That made a printable-letter Caesar shift unlikely as the whole explanation. It did not mathematically rule out every alphabet transform or character encoding. The short length also gave me little basis for claims about EBCDIC, UTF-16, or UTF-32 from byte distribution alone. I kept the next test cheap.

The event's stated flag prefix gave me seven known plaintext bytes. I XORed them with the first seven ciphertext bytes and got 0x42 at every position. That is strong evidence for a one-byte key over that window. It does not exclude a longer key whose observed positions happen to be the same. I tested 0x42 across all 22 bytes. The resulting text was printable, began with the expected prefix, had the expected brace structure, and made sense with the prompt's welcome theme. Those checks reinforce one another; they are not four independent proofs of platform acceptance.

I had a 256-key brute-force fallback in mind, but the prefix made it unnecessary. I also left Hamming-distance period estimation and Kasiski-style analysis alone: 22 bytes are too little for a confident statistical result here. The archive had already opened, so zip2john and dictionary attacks had no role. The rejected detours matter because this challenge could have become harder through my own assumptions.

3. Tooling and Scripts

3.1 Hex decode and known-plaintext key recovery

The core operation was K[i] = C[i] XOR P[i] across the stated prefix. This runnable illustration uses the invented 17-byte hex fixture, not the original challenge bytes:

ct = bytes.fromhex("040e0305391a0d101d071a030f120e073f")
anchor = b"FLAG{"
key_window = bytes(c ^ p for c, p in zip(ct, anchor))
assert key_window == b"BBBBB"

The original solve used seven prefix bytes and found the same byte, 0x42, seven times. The illustration has a five-byte anchor, so its assertion proves only its own fixture. xor_anchor_scan.py exposes a strict hex reader and prefix-key function for local reuse. It rejects an empty anchor or one longer than the ciphertext.

3.2 Full decode

I then applied the candidate byte to the whole decoded blob:

plaintext = bytes(value ^ 0x42 for value in ct)
assert plaintext == b"FLAG{XOR_EXAMPLE}"

That line is a synthetic round trip. In the challenge, the full 22-byte decode yielded a flag-shaped printable message. I have not published the original ciphertext or answer. A full decode checks the single-byte hypothesis beyond the known prefix; it remains separate from a platform acceptance receipt.

3.3 Recon one-liners

The initial commands were short: unzip -l challenge.zip to see the member, unzip challenge.zip to extract it, wc -c cipher.txt to check the 45-byte count, and od -c or a hex viewer to inspect the characters and newline. A strict hex parser is more useful than a loose character-class check once the representation is suspected, because it also rejects odd-length input and non-hex characters. The linked tool implements that check locally.

3.4 Fallback path prepared but not executed

Without a trustworthy plaintext prefix, I would try all 256 one-byte keys and rank outputs by file magic, valid structure, or readable text. A printable-ASCII score alone can over-rank benign or meaningless strings, especially for a short blob. I did not execute that fallback in this solve. Multi-byte repeating XOR would require a different test, ideally more ciphertext or another anchored region; I would not force a key-length estimate from 22 bytes.

4. Concept Explanation

XOR is self-inverse: (A XOR K) XOR K = A. For a one-byte key, the same value transforms each byte. When I know one plaintext byte and its matching ciphertext byte, I can compute the key byte by XORing them. A longer known prefix lets me test whether the recovered key bytes repeat.

In this puzzle, all seven recovered prefix positions agreed on 0x42. The simplest working model was a constant one-byte key. I checked the model by decoding the rest of the blob, rather than declaring the period proven from seven matching positions. A repeating multi-byte key can share a constant opening run; an unknown transform could also mimic a short anchor by chance.

For an unknown malware string, I would first look for a reliable anchor such as a file header, protocol prefix, or known configuration field. If there is none, a bounded 256-key scan is cheap, but the output still needs review. FLOSS can help recover obfuscated strings; CAPA describes capabilities it finds in a sample. Neither tool turns a recovered http:// fragment into a verified C2 channel by itself.

5. Exploit/Analysis Mechanics

The weakness here is a fixed, tiny transform applied to a message whose opening bytes were disclosed by the challenge format. For ciphertext C and known plaintext prefix P, the candidate keystream bytes are K[i] = C[i] XOR P[i]. Seven equal bytes suggested K = 0x42. Applying that byte to every ciphertext position made the complete message readable.

44 hex characters + newline -> 22 ciphertext bytes
7 known prefix bytes       -> 7 candidate key bytes, each 0x42
22-byte one-key decode     -> printable, flag-shaped text

That is an obfuscation failure, not a general break of stream ciphers. A secure one-time pad requires unpredictable, non-reused key material at least as long as the message. A constant one-byte XOR key provides none of that protection. My formatting and theme checks made the candidate persuasive for this puzzle; the platform's final acceptance is not documented here.

6. Lessons Learned (Practitioner Perspective)

The fastest part of this solve was deciding what the bytes were before trying to read what they said. A 45-byte text member became 22 ciphertext bytes once I accounted for its newline and decoded the 44 hex characters. From there, the stated flag format was useful evidence, not merely a submission rule. It gave me a seven-byte anchor and a direct algebraic test.

I also learned how easily a short, successful decode can sound more conclusive than the record supports. Seven equal recovered key bytes support the one-byte model. The complete readable decode strengthens it. Neither observation proves that no longer key could have produced the same message, and the source record does not contain a platform acceptance receipt. I would retain the candidate and the checks in case notes, with the submission state labeled separately.

The original solve used inline one-liners. That was enough to finish a small puzzle, but it left no reusable harness for another analyst. I turned the primitive into a bounded local scanner with synthetic tests. That is a follow-on proof of concept, not a tool claimed to have run during the event.

What I did here What I would carry into an investigation
Checked the archive member and representation first Identify file type, length, encoding, and container structure before interpreting content
Used the supplied flag format as plaintext Look for trustworthy protocol headers, file magic, or configuration fields
Applied a candidate key to the whole blob Require full structural review and, where possible, independent behavioral corroboration
Skipped ZIP cracking and 256-key search Take the simple, evidence-backed test before expanding the search space
Recorded the rejected paths Give the next analyst enough context to avoid repeating them
7. Extrapolation

The next technical step for me would be a longer, messier sample. A repeating-key XOR blob may need key-length hypotheses, Hamming-distance comparison, and per-position analysis. XOR-wrapped PE, PNG, or ZIP content may reveal itself through magic bytes rather than a flag prefix. File carving and format validation become more important as the output grows. The same byte-level reasoning also helps with binary protocols and mistakes involving reused stream-cipher keystreams, although those are different cryptographic problems.

In a malware intake queue, I would use a bounded static pass to recover strings before spending sandbox time. FLOSS can expose candidate decoded strings, CAPA can add capability context, and YARA can find a known marker through one-byte XOR. A useful hunt question is whether a sample with sparse readable static strings also shows networking or persistence behavior elsewhere. That combination warrants review without being a malicious verdict on its own.

The recovered values could support threat intelligence only after verification. A decoded domain could be a dormant configuration value, decoy, test endpoint, or active destination. I would retain the sample hash, extraction method, byte offsets, key hypothesis, and confidence, then seek runtime telemetry or independent reporting before promoting it to an indicator. The same anchor technique can help examine shared blobs or embedded-device protocols, but it does not establish actor identity or intent.

8. Reusable Tools, Scripts, and Artifacts

These files are synthetic proofs of concept for applying this puzzle's method to a controlled intake workflow. The artifact README lists the commands, inputs, and limits. The invented hex fixture contains no challenge answer or live indicator. The scanner, its tests, YARA rule, Sigma rule, and STIX bundle are linked here and again where I discuss their use.

8.1 Triage decision tree for unknown obfuscated blobs

Unknown artifact
  |
  +-- Identify container, length, and file type
  |     ZIP member? Text representation? Binary magic?
  |
  +-- If text-like, decode a plausible representation with a strict parser
  |     Hex, base64, URL encoding, or another supported format
  |
  +-- Inspect raw bytes and available context
  |     Known prefix or file header? Try C[i] XOR P[i]
  |     No reliable anchor? Try a bounded 256-key scan and rank candidates
  |
  +-- If one-byte XOR fails, revisit the hypothesis
  |     Repeating key, compression, structured format, or another transform
  |
  +-- Validate the whole output
        Structure, length, expected fields, and independent evidence

This order keeps the original tree's representation, magic-byte, simple-transform, and validation branches. A printable-byte score is only a triage aid. An EBCDIC or UTF hypothesis needs contextual evidence; it does not become likely merely because raw bytes are awkward to read.

8.2 Reusable primitive: known-plaintext single-byte XOR recovery

The key-recovery primitive is small enough to audit:

def candidate_key(ciphertext: bytes, known_prefix: bytes) -> int | None:
    if not known_prefix or len(known_prefix) > len(ciphertext):
        raise ValueError("invalid known prefix")
    recovered = bytes(c ^ p for c, p in zip(ciphertext, known_prefix))
    return recovered[0] if len(set(recovered)) == 1 else None

def xor_decode(ciphertext: bytes, key: int) -> bytes:
    return bytes(value ^ key for value in ciphertext)

Equality in the anchor window returns a candidate one-byte key, not proof of the entire schedule. The runnable scanner adds strict hex decoding, input limits, an optional anchor scan, and bounded output. The tests include the synthetic example, positive and negative markers, a near miss, a wrong prefix, and malformed input. The tool is for authorized local samples; it performs no network lookups or sample execution.

8.3 Solve-pattern checklist for XOR-obfuscated content

  • [ ] Preserve the source bytes and record the container, size, and representation.
  • [ ] Decode hex, base64, or another representation with explicit error handling.
  • [ ] Inspect byte values and file magic without overclaiming what a short sample excludes.
  • [ ] Identify a reliable plaintext anchor and calculate the candidate key bytes.
  • [ ] If the window is constant, test the one-byte model against the entire blob.
  • [ ] If it differs, revisit the anchor or investigate a longer key with enough data.
  • [ ] If no anchor exists, run a bounded 256-key search and review the ranked outputs.
  • [ ] Check structure and context, then seek independent corroboration when available.
  • [ ] Record key hypothesis, offsets, output, failed routes, and submission or validation status.

10. Threat Intel and Standards Integration

The challenge supplied no domain, IP address, file hash for a live sample, or actor attribution. I therefore would not create a STIX indicator object that pretends one exists. The synthetic STIX 2.1 bundle instead records an attack-pattern, a course-of-action, and their relationship for a demonstration workflow. It is a representation of the method and response, not an IOC feed. A production STIX indicator would need an actual observable, a defensible pattern, provenance, confidence, and lifecycle handling before TAXII distribution. TAXII is a transport for sharing such content; this exercise did not use a TAXII server.

I would retain the decoded bytes as case evidence first. If later analysis finds a domain or URI, I would check whether it is a live endpoint, document the first and last observations, and record where the value came from. A syntactically valid decoded string alone is not enough to block a destination across an organization.

No STIG finding follows from this puzzle. A specific STIG requirement needs a named platform, benchmark version, observed configuration, and test result. CIS Benchmarks likewise apply to particular configurations. The CIS Controls offer a broader program mapping: Control 10 concerns malware defenses, while Control 13 concerns network monitoring. I do not claim that safeguard 10.2 (signature updates) or 10.5 (anti-exploitation features) mandates XOR deobfuscation.

11b. Mitigation Realization

For an authorized sample queue, I would make static deobfuscation a bounded analysis stage. The intake record would carry a sample identifier and hash, source and custody notes, tool versions, execution time, output location, and analyst review state. FLOSS, CAPA, and YARA could each contribute a different signal: recovered strings, inferred capabilities, and a match to a known marker. Their outputs should remain separate until an analyst adjudicates them.

Authorized sample intake
  -> hash and preserve the sample
  -> identify file type and enforce size/time limits
  -> run static string recovery and capability analysis
  -> scan for vetted content rules
  -> review candidate strings and record confidence
  -> escalate to dynamic analysis when the question requires behavior
  -> publish verified indicators with provenance and expiry

SI-3 and CIS Control 10 provide the malware-defense context. IR-4 provides the documented handoff and triage context. SI-4 and CIS Control 13 come into play when host or network telemetry can test a recovered indicator. A decoded string is not a substitute for runtime evidence, and a static pipeline is not a replacement for prevention controls. The small local scanner is deliberately offline, so it can be evaluated without contacting a suspicious endpoint.

12. Indicators, Artifacts, and Detection Engineering

12.1 IOCs (sanitized / illustrative)

There are no production IOCs in this challenge. The puzzle bytes yielded an answer, not an active C2 address, mutex, registry key, or malware hash. In a real case, possible outputs would include a decoded domain or URI, mutex, path, user-agent, or configuration marker. Each would need the sample hash, extraction offset, recovered key, validation method, and observation context. The synthetic STIX bundle intentionally contains no fabricated indicator.

12.2 YARA rule: detect single-byte XOR obfuscation of a known C2 indicator

The synthetic YARA rule uses an invented marker, lab-control.example, inside a PE-shaped file and searches keys 0x01 through 0xff. It demonstrates YARA's xor string modifier without naming an actual C2 endpoint. Before operational use, I would replace that marker with a vetted campaign-specific value and test known positive and benign corpora. The PE header condition narrows scope but does not make one string a high-confidence verdict.

The key range deliberately excludes 0x00, so plaintext occurrences of the marker are not covered by that string. If an analyst needs both plaintext and obfuscated variants, they should add a separate plaintext string or widen the design deliberately. YARA compilation and execution were unavailable in this local environment, so this rule is a reviewable proof of concept, not a tested detection release.

12.3 Sigma rule: detect static deobfuscation tooling execution

The Sigma process rule looks for floss.exe or capa.exe process creation on a Windows analyst workstation. I would use it as an informational measure of playbook activity: did static triage tooling run during intake? It does not indicate an attack, and I did not attach ATT&CK T1140 to an analyst's legitimate process. It also misses renamed binaries, non-Windows execution, and tools invoked through another wrapper. A meaningful compliance or coverage metric would correlate this signal with authorized intake records rather than count every tool launch as success.

12.4 SIEM query: surface samples with high obfuscated-string density (Splunk SPL)

This SPL assumes an intake pipeline has already normalized FLOSS output into one event per sample with numeric counts. It does not assume a particular nested FLOSS JSON path. Field names and thresholds must be adjusted to the deployed schema.

index=malware_intake sourcetype=sample:static_triage
| where isnotnull(sample_sha256) AND isnotnull(decoded_string_count) AND isnotnull(static_string_count)
| eval decoded=tonumber(decoded_string_count), static=tonumber(static_string_count)
| where decoded>=0 AND static>=0
| eval decoded_ratio=decoded/(decoded+static+1)
| where decoded>=5 AND decoded_ratio>=0.30
| table _time sample_sha256 decoded static decoded_ratio tool_version review_status
| sort -decoded_ratio

This is a review queue, not a maliciousness rule. Packers, benign software, and differences in tool output can all affect the ratio. I would validate the field extraction, establish a baseline from the actual intake population, and measure review yield before promoting a threshold.

12.5 Telemetry and data pipeline requirements

The static pipeline needs the sample hash, original file size and type, scan timestamp, tool version, recovered-string count, and rule matches. To measure analyst workflow with the Sigma rule, Windows process-creation telemetry needs an image path, command line when authorized, user, and parent process, along with an intake identifier to join against. To corroborate decoded network indicators, the environment needs relevant DNS, proxy, or endpoint network telemetry. None of those telemetry streams existed in the CTF file.

The sample should stay in an isolated, access-controlled workspace. Output that contains candidate domains or paths should retain provenance and handling labels. A vendor's custom-rule support cannot be inferred from this YARA proof of concept; deployment depends on the actual product and version.

12.6 Detection engineering notes

A single XOR-obfuscated marker can collide with benign content, and a PE header alone is a weak second condition. I would tune with longer or multiple independently useful markers, file section context where supported, and corroborating sample behavior. I would test both obfuscated positives and benign files, including the plaintext-marker case, before setting severity. The bounded scanner and tests are useful for checking recovered bytes, while the rule addresses detection of a known marker. They answer different questions.

The Sigma rule is deliberately low severity because it observes defender tooling. The SPL query should produce leads for analysis, not block files. A recovered URI should not enter an IOC feed until the analyst can explain why it is operationally relevant, when it was seen, and how to expire or retract it. That review loop is what turns an interesting static string into usable detection content.
