The Matrix Cipher That Became Linear

The code looked like a trip through a matrix group. I wrote down what happened to one character, and the elaborate part became a linear system.

Summary

The challenge. Recover a plaintext flag from a custom GL2(F67) stream cipher using its readable Haskell implementation and a known flag wrapper.

What I did. I traced the matrix schedule, probed the zero and unit keys, solved crib equations over GF(67), and ranked the remaining candidates by language.

The result. The case record reports a readable flag and exact ciphertext re-encryption. The retained materials support the structural break, while the intended flag and platform acceptance cannot be independently checked here.

The limit. The target ciphertext, original solver and ranking data, flag, and submission transcript are unavailable. The local proof of concept uses invented values and does not replay the historical solve.

1. Problem Statement and Threat Scenario

I had a Haskell file that called itself a symmetric stream cipher, a fixed ciphertext, and a familiar flag wrapper. I could read the implementation but had no secret key or live service to query. The task was to recover the plaintext. The matrix terminology initially made the cipher look more complicated than the input and output behavior it actually had.

This was an offline cryptanalysis puzzle. There was no defender, adversary infrastructure, log stream, or protected deployment in the case. The operational question it raises is narrower and useful: what happens if someone ships a custom transform like this to protect real data? I treat that as a proposed code-review scenario, separate from the puzzle result.

2. Techniques, Tooling, and Actions Taken

I read the Haskell arithmetic first. The field prime is 67, the key has 11 symbols, and each character is mapped from the printable range < through ~ into a field element. The seed matrices are upper triangular. The code enumerates group elements, extends the seed, and applies 12 rounds of adjacent matrix products before encrypting each character. The implementation's comment about its two generators commuting is misleading: the matrices do not commute, but that did not protect the cipher.

The case record says I built a Python reference implementation, checked an encrypt/decrypt round trip, and compared keystreams for multiple keys. The diagonal multiplier stayed fixed. I then used a zero key and eleven unit keys to measure how the upper-right matrix entry changed with each key symbol. The known flag prefix and closing brace gave seven independent equations. I solved them modulo 67 and ranked the remaining candidate decryptions with an English character-trigram model.

I first filtered for a lowercase body with underscores. That returned no readable answer. The reported flag contained mixed case and trailing punctuation, so I dropped the restrictive filter and let language ranking work over the wider candidate set. The case record reports an exact re-encryption of its selected plaintext. That is a useful check of the implementation, but Section 5 explains why it does not distinguish the intended plaintext from every other candidate under a different compatible key.

3. Tooling and Scripts

The bounded Python probe is a defensive proof of concept for this construction. It implements the matrix schedule, zero and unit-key probes, finite-field elimination, and synthetic encrypt/decrypt. The invented fixture contains an 11-symbol key and readable plaintext, and the test suite exercises full-rank recovery, seven-crib ambiguity, an inconsistent crib, and invalid inputs. The run guide gives the commands, input contract, and limits. These files do not contain the target ciphertext or the historical language-ranking solver.

The core of the reduction is short enough to keep visible:

K_i = ((d_i, a_i), (0, 1))
c_i = d_i * p_i - a_i                    mod 67
a_i = constant_i + sum_j M[i,j] * s_j   mod 67
sum_j M[i,j] * s_j = d_i*p_i - constant_i - c_i   mod 67

Here s_j is key symbol j. The probe obtains constant_i from the zero key and column j of M by subtracting that zero-key output from the output for unit key j. A row of known plaintext and ciphertext then becomes one equation in the key. I can run the local demonstration with python -B gl2_affine_probe.py from the artifacts folder. It reports full recovery with eleven independent synthetic crib positions and 20,151,121 possible keys with seven. That is a test of the reduction on invented data, not a replay of the challenge.

4. Concept Explanation

GL2(Fp) is the group of invertible two-by-two matrices over a prime field. This cipher uses a much smaller upper triangular form: ((d, a), (0, 1)), with nonzero d. Multiplying (d1, a1) by (d2, a2) gives (d1*d2, a1 + d1*a2) modulo 67. The matrices can be noncommutative while the key dependence of the upper-right term remains affine. Those facts can coexist.

The plaintext enters as (p_i, -1), so the retained first coordinate is d_i*p_i - a_i. For a fixed key, every position is a separate bijection of one plaintext symbol. Changing one symbol does not spread into later positions. The matrix schedule mixes the seed state, but it does not give plaintext diffusion across positions. Shannon's confusion and diffusion vocabulary is useful here: the diagonal sequence is independent of the key, and known plaintext makes the key-dependent addend solvable by linear algebra. Shannon's paper supplies the underlying vocabulary, not a security assessment of this puzzle.

Gaussian elimination over GF(67) works like ordinary elimination with all arithmetic modulo 67. If eleven unknown key symbols produce a rank-seven system, four independent values remain free. The solutions form an affine space with 67^4 = 20,151,121 members. More independent known positions can raise the rank; repeating dependent positions cannot.

5. Exploit / Analysis Mechanics

The preconditions were white-box cipher access, the target ciphertext, and known plaintext at fixed positions from the flag format. My first simplification was to stop treating the keystream as an opaque matrix. Every keystream element remained upper triangular. Its diagonal d_i came from powers of the public generator and position in the schedule, not from the key. The upper-right value a_i was a constant plus a weighted sum of the eleven key symbols. A zero-key run and eleven unit-key runs exposed those weights.

For each known position, I substituted the known p_i and observed c_i into the final equation shown in Section 3. The source account gives seven independent equations in eleven unknowns. That leaves four free symbols and about 20 million compatible keys. Direct search over all 67^11 keys would have been a different, much larger job. The linear reduction made candidate ranking plausible. The source reports that an English trigram model brought a readable, theme-related flag to the top after the lowercase-only filter failed.

There is a crucial distinction in the final check. For any one candidate key, decryption inverts its own per-symbol transform. Re-encrypting that resulting plaintext must reproduce the ciphertext. The synthetic ambiguity test deliberately produces two different plaintexts under two compatible keys; both re-encrypt exactly. A round trip can catch a broken port or transcription error. It does not prove which of the 20,151,121 candidates is the intended answer. Independent crib characters, an authenticated check, or actual challenge acceptance would make that claim stronger. The reported flag and submission evidence are unavailable here, so I retain the reported solve without presenting the round trip as proof of uniqueness.

6. Lessons Learned

Writing down the one-symbol map saved me from attacking the full matrix machinery. The useful habit was to ask which outputs actually depended on the key, then measure that dependence. This is also why my initial lowercase-and-underscore filter was a mistake: it imposed a flag style that the math had never promised. I would keep crib constraints, language scoring, and acceptance evidence as three separate layers next time.

The other lesson is about verification language. My algebra can establish a family of compatible keys exactly. A language model can make one candidate appealing. Re-encryption can show the candidate pair is internally consistent. None of those alone records what the event accepted. When the result matters outside a puzzle, I want an independent constraint before calling a secret recovered.

7. Operational Extrapolation

Individual Practitioner Development

The exercise gave me a practical sequence for unfamiliar crypto code: reduce the representation, probe key dependence, build equations over the right field, record rank, and keep the remaining uncertainty visible. A useful next lab would expose only an authorized encrypt/decrypt oracle and ask whether controlled probes can recover the same affine model without readable source. That lab has not been run here.

Security Operations

There was no SOC telemetry in this offline case. For a real application, I would begin with a source and architecture inventory: find the component, its callers, what data it protects, and where keys come from. A custom cipher in production would become a design-review finding, followed by migration planning with the owner. A SIEM rule about GL2 strings would have a weak connection to the actual risk and many benign matches. The review checklist turns the algebra into a proposed review and CI gate with explicit exceptions for teaching code and ordinary math libraries.

Intelligence Operations

The case has no campaign, actor, collection target, or infrastructure to attribute. Its useful intelligence-style product would be an internal technical assessment of a deployed component, supported by source revision, test vectors, key handling, and data exposure. I would not turn this puzzle into an IOC feed.

8. Reusable Tools, Scripts, and Artifacts

The reusable proof of concept is the affine probe. It accepts printable-domain key and text values up to 256 symbols, builds the zero/unit-key model, and returns a particular solution, nullspace basis, and rank for integer-indexed crib positions. It uses only Python's standard library and makes no network calls. The synthetic case, tests, guide, and custom-cipher review checklist provide a reproducible local exercise and a proposed route into authorized code review.

Eleven independent known positions recover the invented key exactly. Seven leave four free values, and the tests show two different candidates with matching round trips. A deliberately conflicting crib is rejected. No target ciphertext, original solver, wordlist, or full candidate ranking is packaged. A production review would need its own data classification, source revision, owner, policy, and independent acceptance test.

9. Framework Applicability and Mapping

MITRE ATT&CK does not describe the observed case: there was no intruder behavior on a defended system. CAPEC-97 Cryptanalysis is a useful method analogy for deriving information from a weak cipher, but this was my puzzle technique, not an observed adversary pattern. CAPEC-20 Encryption Brute Forcing describes the direct search I considered and set aside; I did not carry it out.

If this design protected real data, CWE-327 would be a reasonable weakness lens for using a broken or risky cryptographic algorithm, and CWE-1240 could guide review of its custom primitive. Those are deployment analogies, not vulnerability IDs assigned to an actual product here. STRIDE, D3FEND, and OWASP mappings need a specific system, boundary, and control to add value; this challenge supplies none.

10. Threat Intelligence and Standards Integration

There are no IP addresses, domains, hashes, malware, or actor behaviors to publish as indicators. STIX/TAXII would carry fabricated threat intelligence in this case. The useful portable output is a precise weakness description: a key-independent multiplier, a key-affine addend, and a rank-limited known-plaintext recovery. If a real product used the design, I would attach that assessment to its software inventory and review record, then connect any observed exploitation to separate evidence.

11. Controls Mapping and Mitigation Realization

NIST SP 800-53 Rev. 5 SC-13, Cryptographic Protection, is an illustrative control lens for an organization using cryptography to protect information. No control was assessed in this puzzle. For a deployed system, my proposed realization is to require a vetted, approved algorithm and maintained library, a reviewed key lifecycle, and a documented exception path for nonsecurity test fixtures. The owner would need to plan any migration and re-encryption before replacing a live format.

The review checklist states the evidence a reviewer should collect and the positive and benign cases a CI gate should distinguish. Its local tests validate the structural math only. They do not prove that a real organization's policy gate, library selection, or migration works.

12. Indicators, Artifacts, and Detection Engineering

The challenge leaves a Haskell implementation and ciphertext, with no runtime sensor or network trail. There is no defensible Sigma, KQL, SPL, YARA, or IOC rule to attach to this isolated solve. A code-search lead for custom encryption could be useful in a real repository, but a match would require human review of purpose and trust boundary. Ordinary linear algebra and training exercises are expected false positives. The checklist gives a proposed source-review workflow rather than pretending to be a production detector.
