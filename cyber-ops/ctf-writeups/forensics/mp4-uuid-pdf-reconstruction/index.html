Fifteen Videos, One Hidden PDF

The videos played normally. The document rode in extension boxes after the media data, one small slice per file.

Summary

The challenge. Fifteen short videos concealed a one-page PDF whose final line held the flag.

What I did. I walked the MP4 boxes, extracted the trailing uuid payloads, ordered readable PDF syntax, and tested the opaque compressed pieces by decompression.

The result. One fragment order produced a valid PDF with consistent object offsets and a readable memo containing the flag.

The limit. The puzzle supplied files rather than a live exfiltration path. The content-inspection ideas below are proposed and have no production false-positive baseline.

1. Problem Statement and Threat Scenario

I was given fifteen short video files and a hint about information moving through shared reels. Every video played normally. The task was to find the concealed data, rebuild its original artifact, and recover the five-word flag inside it. I had the files only, with no live target or network capture.

The prompt sounded like exfiltration, but the artifacts did not show an attacker, defender, or actual transfer. I treat that story as the puzzle's framing. Later sections use media-based data hiding as an operational analogy and propose a content-inspection exercise.

2. Techniques, Tooling, and Actions Taken

I hashed the fifteen carriers before analysis and preserved their bytes. ffprobe showed ordinary H.264 video and AAC audio. The useful difference was outside the playable streams: a walk of each top-level MP4 box tree ended in a uuid user-extension box after mdat. I extracted its payload and got fifteen slices of roughly 68 to 69 bytes each.

Several slices were readable PDF structure. I could see the header, numbered objects, a page and font description, a FlateDecode stream, the cross-reference table, and the trailer. I first followed the apparent order of the social-media short codes in the filenames. That concatenation did not start as a PDF and its compressed section would not inflate. I kept the failed order as a useful check: the carrier names were a clue to test, not an ordering rule.

The printable fragments joined at broken PDF tokens and object boundaries. I placed the header and trailer from the document grammar, then tried the tractable permutations of the opaque stream fragments. One order gave a zlib stream that decompressed. I checked the rebuilt PDF's cross-reference entries against the actual byte positions of its objects. The resulting one-page memo carried the flag on its final line.

3. Tooling and Scripts

Python's standard library did the box walk, extraction, ordering, decompression, and offset checks. ffprobe was a quick sanity check on the media streams. The core box parser read the declared size and type, honored a 64-bit extended size when present, and rejected a box that ran beyond the file:

import struct

size, kind = struct.unpack_from(">I4s", data, offset)
header = 8
if size == 1:
    size = struct.unpack_from(">Q", data, offset + 8)[0]
    header = 16
elif size == 0:
    size = len(data) - offset
if size < header or offset + size > len(data):
    raise ValueError("invalid box size")
if kind == b"uuid":
    if size < header + 16:
        raise ValueError("missing user UUID")
    fragment = data[offset + header + 16:offset + size]

The extra 16 bytes belong to the user UUID. For an ordinary box with an eight-byte size/type header, the hidden data begins 24 bytes into the box. An extended-size box has a longer header, so a fixed 24-byte skip would be wrong there. I kept each extracted fragment tied to its carrier during reconstruction, even though filenames did not decide the order.

For the compressed section I tried candidate orders with itertools.permutations, extracted the bytes bounded by stream and endstream, and called zlib.decompress. The parser also checked PDF object offsets after assembly. Those independent format checks mattered more than whether the output merely looked readable.

4. Concept Explanation

An MP4 uses length-prefixed boxes. The familiar types carry file identity, movie metadata, and media data. A uuid box adds a 16-byte user identifier and extension data. A player can ignore an unfamiliar extension and still play the video. That gave each carrier room for one piece of the document without affecting playback. ISO/IEC 14496-12 defines the container family.

A PDF has its own ordering clues. A header identifies the format, numbered objects refer to one another, and the xref table records object byte offsets. The trailer points to that table. Those byte offsets can check a reconstructed file, even when filenames are misleading.

The page-content stream used FlateDecode, a zlib-wrapped DEFLATE stream. A zlib wrapper includes an Adler-32 checksum, described in RFC 1950; RFC 1951 describes DEFLATE. The PDF stream's /Length describes the encoded bytes stored in the PDF. A separate length check would compare that number with the stored bytes before inflation. The decompressed text can have a different length.

5. Exploit / Analysis Mechanics

The hiding worked because each uuid box was a legal container extension after the media data. No single 68- or 69-byte fragment was the whole PDF. A viewer showed a normal video, and the readable pieces alone did not give me the correct order of the compressed stream.

The filename short codes suggested a chronological send order. That order failed the PDF header and zlib checks. I switched to constraints from the payload: %PDF at the start, object grammar through the body, and xref plus trailer at the end. A fragment ending in /F followed by one beginning ilter /FlateDecode, for example, completed a real PDF token. The compressed bytes had no such visible join, so I tried their small permutation space and kept the order that inflated.

The reconstructed file passed three checks I could apply without trusting its appearance: the zlib stream decompressed, PDF cross-reference offsets landed on their object definitions, and the page content read as one memo. The final line supplied the flag. This brute-force step was practical because only a few fragments lay inside the opaque stream. A much larger split would need additional ordering constraints.

6. Lessons Learned

The container tree gave me the hiding place before I spent time decoding the video or audio. I will check extension boxes early when media plays cleanly but still seems to carry data. The first filename order was attractive because it came with a story. The PDF header, object grammar, and checksum were better witnesses.

I also learned to build validation into the reassembler. The stream inflated and the cross-reference offsets landed on the expected objects. For a fuller PDF check, I would also compare /Length with the stored, encoded stream bytes. The same habit transfers to other checksummed or self-describing formats.

7. Operational Extrapolation

Individual Practitioner Development

This solve exercised ISO-BMFF parsing, file carving, PDF structure, and reconstruction from scattered fragments. I would repeat it on another extension mechanism, such as XMP metadata, to see which parts of the workflow generalize beyond MP4 uuid boxes.

Security Operations

I would test a content-inspection pipeline with a benign set of MP4s containing ordinary uuid metadata and a separate set with split document fragments. The blue team would parse whole containers and retain extension-box payloads. The purple team would vary fragment order and encoding. I would measure which files the pipeline surfaces and which reconstructed objects analysts can verify. I have not run this test against production media or a DLP gateway.

Intelligence Operations

These files gave me no actor, infrastructure, collection source, or attribution lead. Their concealment method is transferable to artifact analysis; this puzzle itself does not support an intelligence conclusion.

8. Reusable Tools, Scripts, and Artifacts

The reusable method is an MP4 uuid-box carver followed by a PDF reassembler. Its inputs are a set of MP4 carriers and an output path. It produces each extracted fragment, their recovered order, and the assembled PDF. Python's standard library is enough for the parser, permutations, and zlib checks. In the challenge run, the tool reproduced the target PDF byte for byte even after the carrier files were given generic names. Decompression and cross-reference offsets provided the structural checks.

The method assumes the carriers together hold one PDF with a small, reorderable compressed stream. It would need more constraints for a larger permutation space or multiple hidden documents. A parser used on untrusted uploads also needs strict box-size and file-size limits before allocating or trying combinations.

10. Threat Intelligence and Standards Integration

I have no host or network observable, adversary infrastructure, or campaign to share. The short codes, user UUID, and recovered flag belong to the challenge and do not become operational indicators. I would not create STIX objects or a TAXII exchange from this puzzle. The ISO, PDF, and zlib specifications are format references used to reconstruct the bytes, not threat-intelligence products.

11. Controls Mapping and Mitigation Realization

The challenge provided files, not a defended system with a stated content-inspection policy. I cannot claim a tested NIST, CIS, or STIG control result. The useful defensive work is a proposed parser and test set for media uploads or repositories. Section 12 describes what such a check would need before an organization could rely on it.

12. Indicators, Artifacts, and Detection Engineering

The file content suggests a detection question: which media objects carry substantial user-extension data, and can the pipeline find documents split across several related files? A whole-file %PDF- signature could identify only the fragment containing the PDF header. It could not match every carrier in this set. A rule requiring both uuid and %PDF- therefore cannot support a 15-of-15 detection claim.

Detection field Proposed design
Sensor Whole-file inspection at upload, repository, or DLP intake.
Parsing Walk top-level boxes with size bounds; extract and record uuid payloads.
Correlation Group related media and look for document fragments or a reconstructable embedded format.
First test set All fifteen challenge carriers plus benign MP4s with legitimate uuid metadata.
False positives XMP, vendor tags, and other normal extension data.
Limits Compression, encryption, file grouping, and large fragment counts can defeat simple signatures or brute force.
Validation status Proposed. I validated the reconstruction method on the puzzle; I have no production false-positive measurement or deployed rule.

I would keep a parser finding separate from an exfiltration alert. A uuid payload is a reason to inspect a file. A claim that data left an organization would require transfer evidence the puzzle never supplied.
