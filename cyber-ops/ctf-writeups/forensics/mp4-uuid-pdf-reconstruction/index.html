Fifteen Videos, One Hidden PDF

The videos played normally. The document was riding in extension boxes after the media data, one small slice per file.

Summary

The challenge. Fifteen short video files concealed a one-page PDF whose final line held the flag.

What I did. I walked the MP4 boxes, extracted the trailing uuid payloads, followed the readable PDF syntax, and tested the opaque compressed pieces by decompression.

The result. My solve record describes one reconstructed PDF with a readable memo and the recovered flag.

The limit. The ZIP contains the writeup but not the fifteen MP4 carriers or reassembler, so I cannot rerun the reconstruction from this archive.

The videos looked ordinary

I was given fifteen short MP4 files and a hint that something had moved through shared video. Each one played. ffprobe saw ordinary H.264 video and AAC audio. I recorded file hashes before taking anything apart, then looked at the container around the streams. Every file ended with a uuid box after its media data.

An MP4 is made of length-prefixed boxes. A uuid box gives a producer room for user-defined data, so a player can skip it and still play the video. These boxes held only about 68 to 69 bytes apiece. Extracted together, the pieces showed fragments of a PDF: a %PDF header in one, object and page syntax in others, and the cross-reference and trailer near the end. The videos were carriers. The document was the thing to rebuild.

The file names sent me the wrong way

The video names looked like social-media short codes. I tried their apparent order first. Concatenating the extracted bytes that way did not give me a PDF or a decompressible content stream. I had let the carriers tell me how to order the payload. The payload itself gave better clues.

Readable PDF pieces joined at broken tokens. A fragment ending in /F, for example, could be followed by the one beginning ilter /FlateDecode. I used those joins and the PDF object structure to place the header, objects, cross-reference table, and trailer. The page content stream was harder: its compressed bytes looked opaque, so I could not line those slices up by eye.

The compressed stream gave me a test. I tried the remaining short permutations and kept the order that zlib could decompress. A zlib stream includes an Adler-32 checksum, so a wrong byte order usually fails decisively. The recorded solve found one order that inflated. I then checked the rebuilt PDF's object offsets against its cross-reference table and read the one-page memo. Its final line held the flag, which I am leaving out of this page.

The source files are absent from this ZIP, so I cannot repeat the extraction here. There is also a limit to the brute-force step: it worked because only a small number of pieces belonged to the opaque stream. I would need a different ordering strategy for a much larger set.

The defender angle I would test

This was a file puzzle, with no observed network exfiltration or defender logs. A real content-inspection service could still learn from it. I would parse the full MP4 box tree, record unexpected extension payloads, and group related uploads for deeper inspection. Scanning only the playable video and audio streams would miss these bytes.

I would not ship a whole-file %PDF- signature as a detector for all fifteen carriers. The PDF header can appear only in the fragment that contains it. A useful test fixture would include all fifteen carriers plus legitimate MP4s with ordinary uuid metadata. The blue team could measure which files the parser surfaces; the purple team could change fragment order and payload encoding to find its limits. That validation has not been done on production media.

Framework and format notes

MITRE ATT&CK T1027.003, Steganography and CAPEC-636, Hiding Malicious Data or Code within Files are useful analogies for concealed data in a media container. The challenge did not show an intrusion or prove that these files crossed a real inspection boundary.

The ISO base media file format identifies the box-based container family. RFC 1950 describes the zlib wrapper and checksum that helped test the compressed piece order. If I validate a PDF stream's /Length value, I compare it with the encoded stream bytes in the file. It is not the size of the text after decompression, as Adobe's PDF stream documentation makes clear.

Reassembly method to reuse
  1. Hash the original carriers and walk their top-level boxes without changing the files.
  2. Extract extension-box payloads using the declared box sizes. Keep their source-file association.
  3. Let the embedded format supply the first ordering constraints. Treat file names as clues to test.
  4. For compressed pieces, try the tractable candidate orders against the format's own decoder and checksum.
  5. Validate the completed document structurally before trusting the message inside it.

That procedure is drawn from this solve. It is not a tested detector for arbitrary MP4 uploads.
