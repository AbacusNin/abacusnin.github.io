A Wi-Fi Probe Log, One Persistent Address, and Four Airports

One bit narrowed the probe log. Reading the names, including four airport networks, did the rest.

Summary

The challenge. A rogue access point had logged roughly 185,000 rows from roughly 39,000 source addresses. I needed the four airport codes associated with one address.

What I did. I checked the address assignment bit, read the directed probe names, rejected the highest-count noise source, and ordered the useful names by first appearance.

The result. One address was unique across the four airport SSIDs. Their order produced a flag the platform accepted.

The limit. The challenge uses a synthetic capture. An address bit cannot prove a device setting, and observed probe names cannot confirm a person's movements.

1. Problem Statement and Threat Scenario

I was handed one SQLite database. It held several days of probe requests logged by a rogue access point: roughly 185,000 rows from roughly 39,000 distinct source MAC addresses. A probe row tied an address to a network name, or SSID, plus timestamps and a duplicate count. The challenge wanted one source address whose observed names exposed four airport networks. I had to give those airport codes in collection order as CTF{AAA_BBB_CCC_DDD}. I keep the actual code sequence out of the public page.

The scenario has a collector and a person whose wireless traffic was collected. The collector can link repeated probes from a stable address and read any named networks in those probes. The person's location history is the sensitive part. My role was to reconstruct that exposure from the database. The capture is synthetic, and its network names suggest an itinerary; probes alone do not show that a person visited each place.

2. Techniques, Tooling, and Actions Taken

I checked the file's shape before chasing a device. The log table held about 185,000 rows, around 184,700 of them probe records. Its useful fields were mac, ssid, log_type, and created_at. The source count was about 39,000 distinct MAC addresses. Those are address counts, not a count of physical devices; one client can use several addresses.

The first-octet U/L bit gave me a cheap first cut. About 37,600 observed addresses had the locally administered bit set, while about 1,700 had it clear. I set the local-address group aside for this puzzle and looked at the universally administered group. That narrowed the work; it did not prove which device had randomization disabled. The IEEE address guidance defines the bit as local versus universal assignment. A locally administered address may be stable, and a universally administered value can be copied or spoofed.

I ranked the remaining addresses by distinct nonempty SSIDs. The highest count looked promising until I read the names: it was a stream of machine-like noise. Count had given me the wrong first lead. I opened the candidate lists and found one short, readable sequence. Its nine observed names looked like a residence, a local stop, a hotel, four airports, an in-flight network, and another hotel. The airport names did the decisive work. For each of the four airport SSIDs, I queried the MACs that had probed it. Each query returned the same single address.

I sorted that address's probe rows by collection time, used row order to break ties, and kept each SSID at its first appearance. The four airport names yielded the four codes in the flag. The failed shortcuts matter here: the U/L filter still left about 1,700 leads, and a pure count ranking promoted the wrong one.

3. Tooling and Scripts

I used read-only queries with Python's standard-library sqlite3. No network lookup or target interaction was needed to identify the address. The bit check was small:

def is_locally_administered(mac: str) -> bool:
    return bool(int(mac.split(":", 1)[0], 16) & 0x02)

The bit says how an address is administered. In this capture it was a useful candidate filter, not a device-configuration test. I first grouped probe rows by MAC and ranked the nonempty names. The local/universal filter was applied to those grouped addresses in Python:

SELECT mac,
       COUNT(DISTINCT CASE WHEN ssid <> '' THEN ssid END) AS n_ssid,
       COUNT(*) AS probe_rows
FROM log
WHERE log_type = 0
GROUP BY mac
ORDER BY n_ssid DESC;

Once the airport check settled the address, I read its named probe rows in collection order. The query did the sort; I removed repeated names on the first pass through its results:

SELECT ssid
FROM log
WHERE mac = ? AND log_type = 0 AND ssid <> ''
ORDER BY created_at, rowid;

seen = set()
for (ssid,) in rows:
    if ssid not in seen:
        seen.add(ssid)
        print(ssid)

I have kept the challenge MAC, network names, and flag out of these snippets. The reusable read-only triage script applies the same address check to a PineAP-style SQLite log, then prints several ranked candidates with their observed names. It leaves the semantic decision to the analyst. The tool guide documents the schema, outputs, limits, and test data. The supplied challenge database is not part of these files.

4. Concept Explanation

A client can send a directed probe when it looks for a network by name. Anyone collecting that frame nearby can see the source address and the SSID in the request. A list of observed directed probes can hint at networks a device knows, though a capture window may miss names and cannot prove that the list is complete.

The second least significant bit of the first MAC octet is the U/L bit, 0x02. Clear means universally administered; set means locally administered. Android's MAC randomization documentation gives one concrete implementation: its randomized address sets the local bit and clears the group bit. The IEEE bit definition is broader. Seeing a local address does not, by itself, prove it was randomly generated. Seeing a universal address does not prove a factory address, a disabled setting, or one physical device.

That distinction changes the claim I can make from the log. I can say the address used for the four airport probes had its U/L bit clear, stayed the same across those records, and was unique for those SSIDs in this dataset. The challenge framed that as a device that failed to randomize. The data did not show the device's settings screen.

5. Exploit / Analysis Mechanics

I needed three fields to make this work: source MAC, directed SSID, and collection time. The U/L bit partition reduced the search to about 1,700 universally administered address values. It was an exact test of address assignment. It was not an exact test of whether a handset had a privacy feature on.

The second step was reading the names. Some universal-address sources had only a few SSIDs, while the highest-count source emitted strings that looked like noise. The useful source had a coherent set of nine observed names and, more importantly, the airport names the challenge asked about. I checked the distinct MAC set for each airport SSID. All four checks came back to the same single value. That cross-check made the target selection stronger than a story built from recognizable names alone.

I then ordered that address's probe records by created_at and rowid, and kept the first sighting of each name. The target's recorded times progressed through the collection window without a conflicting order. The four airport SSIDs appeared in the sequence needed for the flag. I mapped those airport names to their standard three-letter codes, submitted the result, and the platform accepted it. That acceptance establishes the challenge answer. The nine names suggest a trip; they do not establish the owner's actual movements or the device's full saved-network list.

This method would lose its main handles if the capture held only broadcast probes or the target never reused a source address in the observed window. Collection coverage also matters: a sensor cannot report probes it did not hear.

6. Lessons Learned

The one-bit filter saved me work. It also tempted me to overstate what I had found. I had separated local from universal addresses, then still needed to inspect the names and verify the four airport matches. The biggest SSID count was noise. That wrong turn is why my reusable tool prints several candidates rather than naming the top row as the device. A privacy setting being available would not tell me whether it was active for the behavior I observed.

Next time I would keep the address test and the human reading step together. I would also describe the nine names as what the sensor observed, instead of calling them the whole saved-network list. A real device may have more saved networks than it probed during this collection window.

7. Operational Extrapolation

Individual Practitioner Development

This case made me read the 802 address format instead of guessing from vendor names. It also made me handle a large log with set-based queries and then return to the individual records. I would like to repeat the method on a consented monitor-mode capture. That would tell me how often current devices in that setting actually send named probes. I have not run that follow-on capture.

Security Operations

The defensive question is whether managed devices expose stable addresses and directed SSIDs where a wireless sensor can see them. I would start with a retrospective probe-log hunt, inspect the returned names, and check the device's platform-specific privacy settings separately. A live alert would need a sensor that preserves source MAC, SSID, timestamp, and frame type. I would test it against managed access points, older clients, and other legitimate sources before treating the output as an alert.

The triage script is a local starting point for that review. Its ranked output is an analyst queue. It has no visibility into a handset's settings, and it does not connect an address to a person.

Intelligence Operations

A stable RF address and a recognizable network name can help someone build a pattern-of-life hypothesis. That makes the exposure relevant to protective intelligence and travel hygiene. This challenge provided no real-world collection, actor, or attribution lead. I would not turn its MAC or SSIDs into intelligence indicators.

8. Reusable Tools, Scripts, and Artifacts

The PNL triage tool accepts a local SQLite capture and configurable table and column names. Its default mapping expects PineAP-style log_type, mac, ssid, and created_at fields. It opens the database read-only, checks address assignment, ranks universal-address candidates by distinct directed SSIDs, and prints their first-seen names as JSON. It never chooses a person or declares a device setting. --top and --max-ssids bound the output. The guide covers invocation, sensor mapping, false leads, and privacy limits.

I checked two synthetic databases. The baseline fixture contains 300 local-address sources and one universal-address source with six generic names. The tool returned that one candidate and its names in order. The stress fixture recreates my ranking mistake: a universal-address source with eight machine-like names sits above a coherent six-name source. It also includes a benign one-name source, a local-address near miss, duplicates, and a non-probe record. The tool displayed three universal candidates in order; the local address and non-probe name stayed out. The fixture generator rebuilds the stress case at a new path.

These checks validate the script against known local data. They do not replay the challenge database or measure production sensor accuracy. The challenge MAC, airport names, and flag are absent from the downloadable files.

The capture is a synthetic forensic dataset. Its MACs and SSIDs describe a potential victim's exposure, not a malware campaign or attacker infrastructure. 11. Controls Mapping and Mitigation Realization

Standards Mapping

I did not assess a particular enterprise environment against NIST SP 800-53, CIS Controls, CMMC, PCI DSS, or HIPAA. Numbered control claims would need that scope. The case supports a concrete endpoint privacy check and a way to look for exposure in wireless telemetry.

Mitigation Realization

For managed devices, I would verify the platform's scan-address behavior and its connection privacy settings on the air, then set the applicable MDM policy. A per-network private-address toggle is one setting to check; I would not assume that toggle alone explains every probe the sensor captured. I would also review automatic rejoin of open networks. These are proposed configuration steps, not controls I deployed during the challenge.

For staff who travel or handle sensitive work, I would suggest removing unused saved networks and keeping platform privacy features enabled. That is guidance, not a measured fix in this dataset. The detective step is the Section 8 script: it found the planted exposure in a local fixture. A real policy or alert still needs a managed-device inventory and live validation.

12. Indicators, Artifacts, and Detection Engineering

I would hunt for a source address with the U/L bit clear that repeatedly emits directed probes for several distinct SSIDs in one collection window. This is a review condition, not an atomic IOC. I withheld the challenge address and names because they identify the case's subject and will not generalize.

The read-only hunt script implements the retrospective first step over SQLite logs. It needs probe type, source MAC, SSID, and collection time. The baseline and stress test show its scope: one planted list is returned, but a noisy source can rank first. The script displays several leads and leaves coherence to an analyst. The local-address near miss and non-probe row in the stress test stay out of the universal-address list.

A streaming WIDS or SIEM rule is still Proposed, unvalidated. I would confirm the sensor preserves directed SSIDs before writing one. Then I would choose a time window, tune a distinct-SSID threshold, and compare hits with managed-device inventory. New or transient clients would deserve review ahead of fixed infrastructure. Older clients, access points, IoT gear, and legitimate stable addresses would need attention as false positives. A source can also spoof an address. I have no measured fidelity from a live feed, and a sensor that sees only broadcast probes cannot support this hunt. The tool guide records the field mapping and these limits.
