Deanonymizing a Non-Randomized Device from a Wi-Fi Probe-Request Capture

A rogue access point logged days of Wi-Fi probe requests. One device forgot to randomize its MAC and handed over its entire saved-network list, which read back as a travel itinerary. Finding it came down to a single bit.

Summary

The problem. A rogue access point sat in a shared space logging Wi-Fi probe requests for days. About 185,000 of them, from about 39,000 devices. One device never turned on MAC randomization, so it leaked its whole saved-network list. My job was to find it and read that list back in order.

What I did. I sorted the devices by a single bit. That bit says whether a MAC is randomized or real, and it dropped 39,000 devices to about 1,700 real ones. One of those stood out. Its saved-network list was short and readable, and it was the only device in the capture that had ever asked for an airport network. I put its list in the order it came in. It was a trip.

The result. The four airports, in order, gave the codes that made up the flag. The platform took it.

The honest limit. This is made-up data. A real phone today barely sends named probes at all, so you'd rarely find a leak this clean in the wild.

1. Problem Statement and Threat Scenario

I was handed one SQLite file: a rogue access point's probe-request log. A few days of it, about 185,000 rows from around 39,000 devices. Each row tied a MAC address to a network name that device was hunting for, plus a duplicate count and timestamps.

I had to find the one device that doesn't randomize its address, read back its saved-network list (its Preferred Network List, or PNL) in the order it was captured, and pull the four airport networks out of it. The answer was a flag shaped like CTF{AAA_BBB_CCC_DDD}, four three-letter airport codes. I'm keeping the real value out of this.

The roles underneath the puzzle are real ones:

  • Adversary: whoever is running the rogue access point, sitting quietly and logging whatever wireless traffic goes past.
  • Their goal: put a lasting identity on a device and follow where it goes, by tying a hardware ID that never changes to the networks that device keeps hunting for.
  • Me, the defender: the analyst piecing the exposure back together from the capture, after the fact.
  • What is at stake: the owner's movements, where they have been and where they travel.
  • The line that should hold: the open-air probe exchange is supposed to stay anonymous, because phones randomize their MAC. On one device, randomization was off, so it did not hold.
2. Techniques, Tooling, and Actions Taken

First I looked at what I was holding. A standard rogue-AP probe log. One log table, keyed on (mac, ssid, created_at). About 185,000 rows, 184,700 of them probe records, across 39,000 MACs. The counts lined up with the brief, so I trusted the schema and moved on.

One filter did most of the work. Modern phones randomize the MAC they probe with, and a randomized MAC sets one particular bit in its first octet: the locally-administered (U/L) bit. So I checked that bit on every MAC, and it split the crowd cleanly: most were randomized, roughly 37,600 of them, which left about 1,700 real ones. The randomized majority is doing exactly what it should, so I set it aside.

That left about 1,700 real devices. I ranked them by how many different networks each had asked for. That gave me candidates, but the count lied: the device on top was just spitting out random, machine-looking SSIDs no person ever typed, so sorting by count pointed me straight at the wrong device. The real question was simpler: did a device's list read like someone's actual saved networks? One device's did, and it was the only one in the whole capture that had ever asked for an airport network.

I read that device's list in the order it was captured and got a nine-stop trip: home, a local business, a city hotel, an airport, in-flight Wi-Fi, a second airport, a second-city hotel, then two more airports on the way home. The four airports, read in order, gave the codes for the flag.

Two wrong turns are worth writing down, because they're how I actually got there. I tried treating "has a real MAC" as the answer, but that leaves 1,700 devices to wade through. I tried ranking by SSID count alone, but that floats a noise device to the top. Either way, the bit only narrows the field. You still have to read the lists to spot the one that belongs to a person.

3. Tooling and Scripts
Show the queries

The whole solve is a handful of read-only SQL queries over the capture, run from Python's standard-library sqlite3. No third-party packages, no network, no talking to a target. The crux is the randomization test:

def is_randomized(mac: str):
    """True if the locally-administered (U/L) bit is set on the first octet."""
    # IEEE 802: bit 0x02 of octet 0 is the U/L flag.
    #   set   -> locally administered (randomized / software-set)
    #   clear -> universally administered (real vendor OUI)
    return (int(mac.split(":")[0], 16) & 0x02) == 0x02

The population split and the ranking are plain SQL:

-- Rank non-randomized devices by distinct directed SSIDs (PNL size).
-- The U/L-bit filter is applied in the caller; SQL supplies the ranking.
SELECT mac,
       COUNT(DISTINCT CASE WHEN ssid <> '' THEN ssid END) AS n_ssid,
       COUNT(*) AS probe_rows
FROM log
WHERE log_type = 0           -- probe records
GROUP BY mac
ORDER BY n_ssid DESC;

And the target's saved-network list, in collection order, de-duplicated to first appearance:

SELECT ssid
FROM log
WHERE mac = ?                 -- the non-randomized target device
ORDER BY created_at, rowid;   -- collection order

A generalized, sanitized version of this workflow is described in Section 8. Every query is read-only; only analyze captures you are authorized to handle.

4. Concept Explanation

Your phone keeps a list of the networks it has joined before. That's the Preferred Network List, the PNL. For years, phones advertised that list out loud. A phone would send a directed probe request for each saved network, a little frame that names the network and asks "are you around?" Anyone listening hears two things: the network name, and the MAC of the phone asking.

Two things make that a problem. A real MAC never changes, so if you see it in two places, it's the same phone in two places. And the set of networks someone has saved is usually particular to them. It quietly says where they've been.

Randomization is supposed to stop this. The 802 address format sets aside one bit of the first octet, the universal/local (U/L) bit, worth 0x02. A real vendor MAC leaves that bit at zero. A software-made, randomized one sets it to one. Phones now randomize the MAC they probe with, often a fresh one per network, so the address on the air no longer points back to the hardware. Reading that one bit is all it takes to tell a real MAC from a randomized one, and it's the whole pivot of this challenge.

But randomization only helps if it's turned on. Turn it off, say a phone where someone disabled the per-network "private address" toggle, and the phone goes back to broadcasting its real MAC right beside its saved-network list. That's the whole exposure randomization was meant to kill, and it's the device this challenge is built on.

5. Exploit / Analysis Mechanics

The whole thing leans on one fact about the address format and one fact about how the target behaves. The only thing I needed from the data was that each probe row carries a source MAC, the SSID it asked for, and a timestamp. It did.

First cut, the bit. octet0 & 0x02 is defined by the address format to mean "randomized or real," so reading it is exact, never a guess. A randomized MAC always sets that bit, so the check drops all ~37,600 randomized devices with nothing lost. One test takes 39,000 devices down to about 1,700.

Second cut, reading the lists. Most of the 1,700 real-MAC devices are access points, IoT things, or old hardware. They probe for a few networks or throw out junk names. The target was the one whose list read like a person's: a handful of real, recognizable networks in a sensible order. The airport SSIDs settled it. Only one device had ever asked for any airport network, and that same device had asked for all four. I checked each airport SSID against the MACs that had probed it, and it came back the same device every time.

Last step, order. The challenge wants the list the way it came in, so I sorted the device's rows by timestamp, with row order to break ties. For this device the timestamps run straight through the capture, no gaps, no reshuffling. In that order the rows line up into the same trip from Section 2. Read the four airport SSIDs in sequence and you have the codes, and the codes are the flag.

I can back every step. Each one is a plain query over the same fixed file. And the final pick doesn't rest on "this list looks right": the airport check settles it, coming back the same single device every time. The one bit of outside knowledge I needed was turning an airport network name into its code, which is standard. I submitted the flag, and it checked out.

Where it breaks: this only works if the target sends named probes and has randomization off. A phone that randomizes and only broadcasts gives you no stable identifier and no readable list, and the whole approach falls apart.

6. Lessons Learned

Big takeaway: try the dumb, exact thing first. One defined bit did more here than any clever ranking. If I'd reached for it sooner I'd have finished sooner. The trap is counting. The device with the most SSIDs was pure noise. The one I wanted had fewer, but they meant something. A count is easy to sort on, and it feels like progress. But it only stands in for the real question: does this list belong to a person? Mistake the two and the challenge makes you pay.

Next time I'd read the lists while I filter, rather than rank everything first and squint at it after. A few things here carry past the challenge. Tracking someone by a stable ID plus their behavior pattern is a real method; people do this. The same one-bit triage works on any Wi-Fi probe capture you're cleared to look at. And a privacy feature being available says nothing about whether it's switched on, which is a lesson that shows up all over endpoint security.

One caveat I want to be honest about: the itinerary is me inferring behavior from made-up data. On a real capture you'd see far less named probing, so a leak this complete would be rare.

7. Operational Extrapolation

Individual practitioner development

This one sharpened a few basics for me. Reading the 802.11 address format down at the bit level. Working a big capture with queries instead of by eye. And the one I keep relearning, holding what the data actually shows apart from what I'm guessing about it. The obvious next step is to run the same thing against a live monitor-mode capture and see for myself how little named probing phones really do now.

Security operations

This part is my own extrapolation; the challenge didn't show it. It does open a real defensive angle, though. A device sending named probes from a real, non-randomized MAC, especially one carrying a long saved-network list, is worth flagging, either to a wireless IDS or in a retro hunt over probe logs you already keep. Section 12 turns that into an actual hunt. The response side is different. Nobody broke in, so you're not chasing an incident. You're closing a gap in policy: enforce randomization and PNL hygiene.

Intelligence operations

Also my own extrapolation. The core move here, tying a stable RF identifier to a behavior pattern to build someone's pattern-of-life, is the same move that matters in collection and OSINT. It's a clean reminder of why randomization and travel-mode device hygiene matter for anyone whose movements are sensitive. I'm not claiming any real attribution or collection, just drawing the parallel.

8. Reusable Tools, Scripts, and Artifacts
Show the reusable abstraction

The part worth keeping is the triage routine, the thing that works on any probe capture. The exact queries above were specific to this one challenge.

  • Purpose: given a probe-request capture, classify MACs by the U/L bit, rank the non-randomized (real-OUI) devices by distinct directed SSIDs, and print the leading candidate's PNL in collection order.
  • Inputs: a SQLite capture with a probe table (the PineAP log schema by default; table and column names overridable for other tools).
  • Outputs: a ranked list of non-randomized devices and the top device's ordered saved-network list.
  • Dependencies: Python 3 standard library only (sqlite3, argparse).
  • Validation status: Validated. I sanitized it, then ran it against a synthetic fixture that plants one non-randomized device with a known list. It pulled that device out and reproduced the list in order.
  • Limits: the capture needs named probes and a timestamp to sort on. And the routine only hands you candidates; it can't tell a real saved-network list from noise, so you still read the top hit yourself. That's the trap from Section 2.

The airport list and the target MAC are left out on purpose. The routine ships with no challenge data baked in.

11. Controls Mapping and Mitigation Realization
Show the controls and mitigations

I'm not forcing a numbered-control mapping (800-53, CIS, CMMC, and the rest). This is a client-side configuration and behavior problem. It isn't a finding against an enterprise system under one of those catalogs, so any control number I cited would be a stretch. The control that does hold up is the plain one below.

The control is easy to say: keep client-side Wi-Fi identifiers and saved-network lists clean. In practice that's three things.

  • Configuration / MDM (Proposed): push MAC randomization onto managed devices (keep the per-network private-address setting on) and turn off auto-rejoin for open networks. This is the direct fix, and an org can actually roll it out through MDM.
  • Procedural (Proposed): tell people who travel or work somewhere sensitive to forget networks they don't use and leave randomization on. That's CAPEC-613's own advice, really.
  • Detective (Validated against fixture, see Section 12): go back through probe logs you already have and look for non-randomized devices leaking a list, so you find the out-of-policy phones instead of assuming there aren't any.

The first two are marked Proposed because I didn't deploy or test them in a real environment. Only the detective one was.

12. Indicators, Artifacts, and Detection Engineering
Show the detection work

You can actually detect this on real wireless telemetry, WIDS/WIPS logs, AP probe logs, or a monitor-mode capture, as long as the sensor keeps the source MAC and the SSID.

Behavioral indicator (Illustrative): a device whose MAC has the U/L bit clear (octet0 & 0x02 == 0) that sends named probes for N or more different SSIDs inside a window. It's a pattern to watch for, not a fixed indicator. The actual MAC and SSIDs from this challenge wouldn't help anyone, so I'm leaving them out.

Retro-hunt (Validated against fixture): the Section 8 routine is the hunt. Point it at probe logs you've collected and it ranks the non-randomized devices by how big a list they're leaking, which is the whole hypothesis: find endpoints leaking a saved-network list. I validated it against the fixture.

Live rule (Proposed): an equivalent WIDS/SIEM analytic over streaming probe-request events.

  • Required log source: 802.11 probe-request records (WIDS/WIPS, AP logs, or monitor-mode capture).
  • Required fields: source MAC, probed SSID, timestamp.
  • Expected fidelity: medium. The U/L-bit test is exact, but PNL-size thresholds need tuning.
  • False-positive surfaces: legacy and IoT devices that legitimately use real-OUI MACs with small PNLs; corporate devices probing a few managed SSIDs.
  • Tuning: threshold on distinct-SSID count and apply a coherence or allowlist filter for known managed SSIDs; alert on new or transient devices rather than fixed infrastructure.
  • Known limitation: ineffective against fully randomizing, broadcast-only clients.
