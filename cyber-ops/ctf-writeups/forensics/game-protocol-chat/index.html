Seven Chat Lines Inside a Game Session

The capture was mostly world data. The conversation I needed was seven small packets near the end.

Summary

The challenge. Reconstruct an adversary-themed exchange from one raw game-server packet capture and recover its staged secret.

What I did. I checked the flow, reassembled TCP in both directions, decoded VarInt frames for protocol 774, matched chat packets by structure and time, and swept for other payload channels.

The result. Seven broadcasts reconstruct the conversation. Three messages from one sender form the answer; its exact text is withheld.

The limit. The local capture confirms the packet counts, chat timing, and unsigned message fields. The challenge submission receipt and a real-world actor or exfiltration event are not established by this capture.

1. Problem Statement and Threat Scenario

I was given a capture from a game server and asked to reconstruct what two people exchanged. The story around it described adversaries using a familiar game protocol as cover for communication. The pcap was my only evidence: no endpoint log, server audit trail, or account record came with it. The analytical job was to read the application conversation and check whether anything else rode the same connection.

In the simulation, <player_b> passes a short staged secret to <player_a>. I can establish what the captured client and server sent; I cannot use a private-game username as proof of a real person's identity. Nor can this exercise, by itself, establish a malware command channel or an external incident. Its value is the method: a protocol that looks like normal game traffic can still carry a specific message, and a network team needs the right bytes and versioned decoder to see it.

2. Techniques, Tooling, and Actions Taken

2.1 Triage

I started with the shape of the capture rather than a string search:

capinfos game.pcap
tshark -r game.pcap -q -z conv,tcp
tshark -r game.pcap -q -z conv,udp
tshark -r game.pcap -q -z io,phs

There is one TCP conversation to port 25565. The capture contains 2,278 records over about 29.05 seconds. Including frame headers and control packets, roughly 17.30 MB travels from server to client and 74.6 KB in the other direction. The actual reassembled application payload is 17,220,896 server bytes and 2,740 client bytes. I keep those measures separate: packet size and TCP acknowledgments make the smaller wire total much larger than the client payload. The server's bulk is ordinary world and registry data. The small client payload does not rule out a short secret moving in either direction.

The available tshark pass identified Ethernet, IP, TCP, and mostly undecoded data. A few binary frames were heuristically labeled ESP; that label did not match the conversation or the later application framing. I treated the default port and strings like minecraft:brand as clues, then confirmed the protocol from its handshake.

2.2 Stream reassembly

Scapy had failed to import in my original analysis environment because of a route6 lookup error, so I switched to dpkt for offline packet reading. The first reassembler sorted segments by TCP sequence and filled a gap with zeroes. That is a bad general rule: a gap means missing evidence, and invented zero bytes can create a false application frame. My later offline capture tool rejects a gap or conflicting overlap instead. On this capture it found no duplicate payload segment or gap, and it rebuilt two complete byte streams.

This is the point where I stopped leaning on the port number. The parser had to account for each stream byte without manufacturing any. The invented pcap and test suite exercise the same rule, including a gap and a conflicting retransmission.

2.3 Identifying the protocol

The first client application frame is a handshake. Its packet ID is 0, its protocol-version VarInt decodes to 774, and next_state=2 selects Login. The declared port is 25565. Those fields fit the Java game protocol used by release 1.21.11; I used the negotiated number for packet decoding rather than assuming the default port meant a particular release. The first packets also contain normal brand and registry markers.

2.4 Custom protocol framing

For an uncompressed session, the shape is Length:VarInt | PacketID:VarInt | Data. The high bit of each VarInt byte says whether the value continues; seven low bits contribute to the integer. A 32-bit VarInt takes at most five bytes. I wrote a small framer and counted the resulting packets: 699 client-to-server and 17,799 server-to-client. The total consumption of both reassembled streams is a stronger check than a plausible-looking string at one offset.

Packet IDs are state and version dependent. A 0x3F in the right play-state table can mean Player Chat Message; that byte alone in an arbitrary protocol version cannot. The capture tool confines its partial chat decode to the known protocol-774 layout and reports that limit in its output.

2.5 Locating the data-bearing channel

The client stream mostly held position, rotation, on-ground, keep-alive, and small state updates. Only three 0x08 serverbound chat packets stood out as application messages. On the much larger server stream I searched for the two sender UUIDs, then decoded candidate Player Chat Message structures. Some UUID hits occurred inside NBT player-info data and failed the surrounding chat layout. I also checked that a candidate carried a plausible millisecond timestamp.

Seven server-to-client broadcasts survived that structural check, at seven distinct stream offsets, with clientbound packet ID 0x3F. The count includes messages from both players: three from <player_a> and four from <player_b>. All seven parsed with the signature-presence field clear. My independent pass reproduced the seven packet offsets, two-sender pattern, unsigned field, and time gaps without printing the message text.

2.6 Conversation reconstruction

The order by stream offset agreed with the embedded big-endian millisecond timestamps:

Relative time Sender Role in the exchange
0.000 s <player_a> Greeting
2.442 s <player_b> Reply
6.093 s <player_a> Pretext question
9.067 s <player_b> Answer piece 1
11.717 s <player_b> Answer piece 2
13.789 s <player_b> Answer piece 3
16.209 s <player_a> Acknowledgment

The three consecutive pieces from <player_b> concatenate into the challenge answer, shaped like SKY-AAAA-####. The final acknowledgment makes the intended completion clear in the conversation. I withhold the exact answer and player names. This ordering is supported twice, by byte offset and the chat timestamps, but neither field proves who operated the accounts.

2.7 Coverage sweep

After finding the chat, I checked the other clientbound and serverbound packet types for sign edits, book edits, command-block content, and plugin or custom-payload messages. The remaining client-to-server traffic in this capture parsed as routine movement and state telemetry. I found no second payload channel in the inspected material. That is a bounded conclusion about this one cleartext flow, not a claim that the protocol cannot carry messages elsewhere.

3. Tooling and Scripts

3.1 VarInt and frame extractor (reusable)

The capture triage script contains the complete reader and JSON report. This is the core of the frame walk:

length, next_offset = varint(stream, offset)
packet_id, body_offset = varint(stream, next_offset)
body = stream[body_offset:next_offset + length]
offset = next_offset + length

The real function bounds the capture, record count, frame length, and VarInt width. It rejects truncated frames and checks that the packet ID sits inside its declared frame. It reassembles both TCP directions strictly, which matters more than making a parser tolerant of missing bytes. The guide specifies the supported pcap shape and the cases it will refuse.

3.2 Player Chat Message decoder

For protocol 774, I read the global index, sender UUID, sender index, signature-presence field, length-prefixed UTF-8 text, and timestamp. The optional 256-byte signature area is skipped only when the presence flag says it exists. The packet continues with salt, previous-message acknowledgments, optional unsigned content, a filter field, and chat-type information. I do not claim to validate the signature, parse those trailing fields and their NBT, or decode other versions. The tool labels senders sender_1, sender_2 in the default report and hides text; --show-chat is an explicit local option for an authorized content review. That separation lets me test the structure without dumping the challenge answer into a report.

3.3 Offline-mode UUID derivation (verifier and detector)

The reference offline-name calculation hashes the UTF-8 bytes of OfflinePlayer: followed by the name, then sets UUID version and variant bits. I used it as a consistency check on the client login name and UUID; the captured pair matched exactly. My earlier work also reported a match for the second player's name, but I have not independently reconstructed that second mapping here. A matching name and UUID supports offline-style identity assignment. It cannot alone prove the full server configuration, the presence or absence of a proxy, or the human behind that name.

from hashlib import md5

digest = bytearray(md5(("OfflinePlayer:" + name).encode("utf-8")).digest())
digest[6] = (digest[6] & 0x0f) | 0x30
digest[8] = (digest[8] & 0x3f) | 0x80

The MD5 here reproduces a vendor naming convention. Password storage and authentication require different mechanisms. The cleartext stream and early login packets were the direct evidence I used for the capture's readable state.

3.4 Channel sweep helper (fallback path; was prepared, run, and produced negative)

I also enumerated plugin/custom-payload channel names and checked for unexpected bodies, while reviewing signs, books, and command-block related client packets. My first implementation keyed one plugin packet ID to this version; the broader technique is to use a versioned table and check the payload's own length-prefixed channel name. The sweep did not produce another answer. I have not packaged it as a generic detector because a wrong packet ID or state could turn normal world data into a false finding.

4. Concept Explanation

4.1 Why a game protocol is an attractive covert carrier

A public client and server give someone a ready-made conversation channel. Game sessions also have much more legitimate data than chat: registry information, world updates, position reports, and keep-alives. In this capture, seven meaningful lines sit inside over 17 MB of server application data. An analyst who stops at the port or byte totals will miss them. Whether an organization permits gaming traffic depends on its own users and policy; a familiar port is neither approval nor evidence of attack.

Chat, signs, books, command blocks, and plugin payloads offer distinct places to carry text or bytes. They are legitimate features. The investigative question is whether a particular session, endpoint, and message content fit the business context and the scenario's claimed behavior.

4.2 Protocol framing primer

The handshake chooses Status (next_state=1) or Login (next_state=2). Login can negotiate encryption and compression; Configuration exchanges registry and pack details; Play carries movement, world data, and chat. A packet number has meaning only inside its state and negotiated version. This session used cleartext, uncompressed framing, so I could read its packet lengths and IDs directly after TCP reassembly.

State What I looked for
Handshake Version VarInt, server address and port, next state
Status Server-list ping, not used in this session
Login Login start/success and any encryption or compression negotiation
Configuration Brand, registries, known packs, client information
Play Movement and world traffic plus 0x08 serverbound chat and 0x3F clientbound chat in version 774

The synthetic fixture builder constructs a small, valid classic pcap with a version-774 handshake and three invented broadcasts. Its expected report gives readers a safe way to check the framing before they examine an authorized capture.

4.3 Offline-mode UUIDs as a forensic signal

I saw no encryption transition before the readable application frames. The captured client login UUID also matched the deterministic offline-name calculation. That combination supports an offline-style session in this case. It says the in-protocol name is a weak attribution handle, since someone can choose a name that yields the corresponding offline UUID. A version-3 UUID by itself is not a server-mode detector, and a private proxy or server extension can change the picture. I would keep endpoint identity and account evidence separate from the captured chat label.

5. Exploit / Analysis Mechanics

The analysis works because the stream is readable and framed. I reassembled each TCP direction, decoded each length and ID, tracked the state transition, and used the version-774 chat layout to extract the message field. The signed presence field was false on all seven candidate broadcasts. That means the optional signature bytes are absent in these packets; it does not prove a sender's legal identity or validate an end-to-end trust chain. The message bytes were plain UTF-8.

The three answer pieces were short enough to fit in normal chat messages. A greeting and a final acknowledgment made them read like a small conversation. My parser returned seven ordered messages and the same 2.442, 6.093, 9.067, 11.717, 13.789, and 16.209 second offsets I saw in my first pass. I joined the three <player_b> pieces in order. The exact answer is withheld; the challenge was marked Solved, but a platform submission receipt is not in this record.

The capture demonstrates message recovery. It does not demonstrate that a compromised corporate host used this server, that the string was a real secret, or that an external actor exfiltrated it. Those claims would need host, identity, destination, and business-context evidence beyond a single CTF pcap.

6. Lessons Learned (Practitioner Perspective)

The first three commands gave me the conversation and protocol shape. The useful pivot was writing a minimal framer once the stock dissector failed. That got me from a 17 MB blob to a countable packet stream. The seven chat candidates then had to agree on structure, offsets, and timestamps; a raw UTF-8 search could have picked up incidental strings in registry or NBT data.

I also learned to carry a second packet library for offline analysis. Scapy's import issue did not change the evidence, but it could have stalled the work. dpkt got me through the first pass. The later strict reassembler fixed the more serious concern in my initial script: zero-padding gaps would have manufactured bytes. For this particular capture the streams are complete, so the correction does not change the result.

One tempting shortcut was to call every connection to port 25565 a game session, or every unsigned/offline-style chat suspicious. Both are too broad. Port, protocol handshake, asset role, approved use, and actual content answer different questions. I want a future detection to say which of those it really observed.

7. Extrapolation

7.1 Practitioner skill development

This case gave me practice reading a wire format rather than waiting for a dissector. The reusable skills are TCP reassembly, bounded VarInt decoding, per-version packet tables, state transitions, and cardinality checks. A next step would be a Wireshark or Zeek protocol analyzer tested against several versions, compressed sessions, packet loss, and benign captures. The current lab is deliberately narrower.

7.2 SOC, IR, and threat hunting

I would start a hunt with policy context: which assets have a reason to open game-server connections, which destinations are expected, and which sensors can verify the application handshake. The flow triage tool flags allowed TCP/25565 from an asset without an approved exception and labels whether protocol verification exists. Its invented events include a true policy lead, approved gaming, an unrelated port, and a port-only lead. That is a queue for review, not a C2 verdict.

If a case warrants content collection, I would preserve an authorized pcap and run a version-aware parser. NetFlow alone can show a connection but not the chat. I would then correlate endpoint process, owner, user activity, server reputation, and any sensitive-file access. After-hours timing and a self-hosted destination can sharpen a hypothesis; neither proves abuse. Blanket port blocks or TLS interception are policy decisions with user and protocol impact, not automatic outputs of this puzzle.

7.3 Intelligence operations

Protocol version, server address, destination history, timing, and path from a client process can be useful selectors across cases. A private-game username or offline-derived UUID is a poor identity anchor. A three-line split may be a useful behavioral description, but chat length limits and normal human conversation can produce the same shape. I would share a verified destination or message pattern only with provenance, scope, and expiration; this sanitized CTF case supplies no reusable external IP, domain, hash, or actor attribution.

8. Reusable Tools, Scripts, and Artifacts

8.1 Triage decision tree for unknown-protocol TCP pcaps

1. Measure capture duration, directions, bytes, and conversations.
2. Ask whether a dissector recognizes the application protocol.
3. Confirm a protocol hypothesis with both in-band structure and metadata.
4. Reassemble TCP strictly; stop on a gap or conflicting overlap.
5. Decode the negotiated version, state transitions, and frame lengths.
6. Count application packet IDs before interpreting content.
7. Decode candidate messages and cross-check order and timestamps.
8. Inspect other data-bearing packet types before closing the case.

The capture triage tool implements the bounded, cleartext portion of that tree. It reports packet/frame counts and chat metadata by default. The fixture builder, invented capture, expected report, and tests let another analyst reproduce the mechanics without the real conversation. The guide makes the byte, protocol, and privacy limits explicit.

8.2 Reusable parser primitives

The core reusable functions are strict TCP reassemble, five-byte varint, frames, handshake parsing, and the partial player_chat decoder in the tool. My offline-name UUID calculation in Section 3.3 is a separate identity-consistency check, not a dependency for extracting chat. A plugin-channel sweep remains a useful fallback after a version-specific packet table is confirmed; one packet ID cannot be assumed to apply to every release.

For the operational side, the flow checker and normalized event fixture identify allowed traffic to the default port from an asset without an approved game-use exception. The expected findings show a verified-handshake lead and a weaker port-only lead. It deliberately leaves approved gaming out of the result. The Sigma rule and SPL/KQL templates carry the same narrow hypothesis into a SIEM after schema mapping.

8.3 Solve-pattern checklist

[ ] Capture hash, format, duration, and original custody recorded
[ ] Every TCP direction reassembled without unexplained gaps
[ ] Protocol and version confirmed from an actual handshake
[ ] Compression/encryption state determined before payload decoding
[ ] Frame lengths consume the streams exactly
[ ] State/version table used for packet IDs
[ ] Chat and other likely message carriers checked
[ ] Sender labels separated from real-world identity claims
[ ] Conversation ordered by bytes and checked against timestamps
[ ] Answer derivation documented without exposing unrelated content
9. Framework Mapping

9.1 ATT&CK

ATT&CK T1071, Application Layer Protocol, is the useful analogy for the challenge's staged communication over a normal application protocol. Its current listed subtechniques cover web, file transfer, mail, DNS, and publish/subscribe; this game session belongs at the parent level. T1001, Data Obfuscation, is a weaker scenario analogy if the ordinary chat and surrounding world traffic were chosen to hide intent. The bytes show clear text. They do not show an obfuscation transform.

I also considered T1572 Protocol Tunneling and T1132.001 Standard Encoding. I leave both out of the finding. No second protocol is tunneled here, and UTF-8 is the ordinary text encoding of the game's chat field. Mapping every normal encoding to an adversary technique would erase the distinction between behavior and interpretation. The pcap is a simulated exchange, not proof of a deployed malicious C2 implant.

9.2 D3FEND

D3-NTA, Network Traffic Analysis, fits the capture review and proposed protocol-aware detection. D3-NTF, Network Traffic Filtering, and D3-OTF, Outbound Traffic Filtering, fit a policy-based egress control when the organization has decided which assets may game. These are defensive options, not controls observed in the pcap. I do not use D3-PA for protocol analysis: that identifier names Process Analysis in D3FEND.

9.3 CAPEC

I checked CAPEC-272, Protocol Manipulation, and CAPEC-292 Host Discovery against the capture. Neither describes the observed act precisely. The chat uses a legitimate feature without a demonstrated protocol bug or manipulation, and the capture shows no host-discovery step. I keep them here as reviewed, rejected mappings rather than filling the table with a loose match.

9.4 Frameworks intentionally omitted

OWASP Top 10 and ASVS would matter for a web application or a game-server security review, but this record is a network reconstruction. STRIDE could help design a new service; it does not add an observed technique to this solved pcap. OpenC2 could carry a future approved response action, but I did not create an orchestration command from a CTF flow. Those distinctions keep the framework section useful rather than decorative.

10. Threat Intel and Standards Integration

10.1 STIX SDOs

I considered a STIX attack-pattern, indicator, and course-of-action package. The only candidate indicator from this capture was traffic on the default game port. That would match many benign sessions, and this case has no verified external destination, malware family, campaign, or time-bounded atomic IOC for a STIX/TAXII feed. I therefore keep the observable and triage logic in the detector, Sigma candidate, and query templates. A shareable intelligence package would need scoped destination evidence and a validated STIX pattern.

The content here is also not proof of a C2 command. The challenge labels it adversary communication, while the packet evidence shows a staged chat exchange. That distinction matters when describing it to another team.

10.2 STIG references

I would look at the applicable firewall, router, application-layer gateway, and host operating-system guidance for a deployed environment. Egress rule ownership, documented exceptions, logs, and review are relevant themes. A pcap does not identify the organization's device product, STIG release, rule base, or assessment boundary, so I cannot make a finding or cite a vendor-specific requirement from this case alone.

10.3 CIS Benchmarks and Controls v8

No Minecraft-specific CIS Benchmark is implicated. CIS Controls v8 supplies the useful control language: Control 8 for audit logs; 12.4 for an architecture diagram that shows the egress boundary; 13.1 for centralized security event alerting; 13.6, Collect Network Traffic Flow Logs; and 13.10 for application-layer filtering where a suitable device can identify this protocol. Collection lets me review the flow; protocol-aware filtering is a separate control design.

11b. Mitigation realization

For a network where game traffic has no business purpose, I would document the source populations and destinations, make an egress decision at the firewall, log each allowed exception, and test the rule with an approved game client and an unrelated service on the same port. Port-only filtering is easy to evade and may block legitimate use. A protocol-aware gateway or sensor can improve identification, but it still cannot decide intent from a handshake alone.

For monitoring, the experimental Sigma rule flags an allowed TCP/25565 flow when asset policy says game use is unapproved. The SPL/KQL templates state their normalized fields instead of pretending a specific endpoint table contains byte totals or session duration. The offline checker is the runnable policy-lead equivalent. The guide describes source fields, tuning, and what the files have actually tested. A short Zeek signature that guesses at a handshake from a few bytes would be too brittle for this versioned, variable-length format, so I would use a tested protocol parser before relying on a Zeek alert. None of these flow examples claims to detect the three chat pieces from a firewall log.

An SOC playbook for a lead would enrich the asset owner and approved-use list, confirm protocol with a handshake if available, review destination history and process lineage, and request a preserved pcap only when the case warrants content inspection. If the parsed conversation shows a real unauthorized transfer, incident response can scope it and apply containment. OpenC2-style orchestration would require an approved action and target; there is no automatic block in this lab.

The private IPs in this pcap and the invented fixture addresses are not external indicators. The case provides no file hash, domain, or destination suitable for a feed.

12.2 YARA (file-side artifact)

I considered a YARA rule for brand and pack strings in stored pcaps. Those strings identify normal game traffic, not this staged conversation; a shortened handshake hex pattern is also too easy to match outside the correct packet boundary. I did not publish that as a malicious-content rule. The bounded parser is the more useful file-side triage proof of concept because it checks TCP continuity and VarInt framing before interpreting chat.

12.3 Sigma

The experimental firewall Sigma rule has one modest claim: an allowed flow to the game-server default port from an asset without an approved use exception deserves review. It requires enriched approved_game_use plus normalized dst_port, protocol, and action. pySigma parsed it locally. No backend conversion, production log trial, or measured false-positive rate was performed. The rule's low level reflects its port-based uncertainty; the packet parser is a separate tool for protocol and content verification.

12.4 SIEM queries

The KQL and SPL templates express the same review lead against explicitly described normalized flow schemas. They do not use a process file size as a byte-transfer estimate or subtract two different connection event times and call that one session's duration. A destination and source pair can have many connections. I have not run these templates in Sentinel or Splunk; they need field mapping, syntax checks in the target backend, and tuning on benign traffic.

12.5 Log source and data pipeline requirements

Question Needed source
Is this port allowed for the asset? Firewall or endpoint flow, asset role, owned exception list
Is it actually the game protocol? Handshake-capable sensor or preserved cleartext pcap
Is content visible? Full packet capture plus matching version/state decoder and content-review authority
Is a username tied to a person? Independent account, endpoint, or server identity records
Was data really lost? Content, destination, business sensitivity, and incident context

Flow records alone cannot reconstruct the chat. Conversely, a captured chat cannot prove business authorization. Time synchronization, retention, sensor placement, and protocol-version maintenance matter as much as the initial rule.

12.6 Detection engineering notes

The six local test groups cover a synthetic handshake/chat capture, opt-in text extraction, malformed VarInt and pcap, TCP gap/conflict, an unapproved flow, an approved gaming flow, a different port, and invalid policy input. The fixture generator, sample pcap, sample flows, expected capture report, and expected findings are all invented and linked. The capture parser also reproduced the real case's core structure in content-hidden mode: 2,278 records, 699 client frames, 17,799 server frames, three 0x08 client packets, and seven 0x3F chat broadcasts. That is a local parsing check, not a production detector evaluation.

I would tune the flow lead against known gaming populations, authorized tests, destination changes, and other applications on the port. I would measure both false positives and missed sessions before raising severity. Compression, encryption, other versions, other ports, and non-chat message carriers remain outside the packaged parser's coverage. Those are explicit gaps for any real deployment.
