The Image After the Image

The first picture opened normally. The bytes after its ending told the rest of the story.

Summary

The challenge. Recover a flag hidden in a single themed PNG supplied for a 500-point university CTF challenge.

What I did. I measured the data past the first PNG's logical end, identified a signature-stripped second image, restored its signature, rendered it, and checked ambiguous glyphs against submission feedback.

The result. The repaired image displayed the flag as drawn text. Two transcription guesses failed before the corrected answer was accepted; the value is withheld.

The limit. The carrier image and platform transcript are not displayed here. The local lab uses an invented PNG, so it tests the reusable carving method rather than replaying the accepted submission.

1. Problem Statement and Threat Scenario

The challenge handed me one themed PNG and asked for a flag. The prompt hinted at something "extra" in the picture. I took that literally and looked at the file beyond the pixels it showed. There was no service to query or account to compromise. This was a local file puzzle.

The flag format was familiar, but its exact characters mattered. I needed to find where the extra data lived, turn it into something I could view, and transcribe the drawn letters accurately. The exercise does not establish an attacker or a real victim. Its operational use comes later, when I apply the same file-boundary check to files moving through an organization.

2. Techniques, Tooling, and Actions Taken

I started with file and a SHA-256 hash, then checked the PNG's structure. The first valid IEND chunk ended the image a viewer displayed, but bytes remained after it. Counting markers in the challenge file showed one PNG signature and two IEND markers. The trailing region began with an IHDR chunk, the start of another PNG's chunk stream. It lacked the eight-byte PNG signature.

I carved that second stream from its IHDR through its own IEND, added the standard signature at the front, and opened the result. The second image drew the flag by hand. A text search would not read letters stored as pixels.

I considered a least-significant-bit sweep of the visible image. Once the trailing stream decoded into an image containing the answer, I left that route alone. The last part was less tidy: the drawn text used digit and letter look-alikes, and the leetspeak was inconsistent across repeated words. Two submissions failed because I read particular glyphs incorrectly. I rechecked those strokes and submitted the corrected transcription, which the platform accepted.

3. Tooling and Scripts

The first pass was deliberately small:

file carrier.png
sha256sum carrier.png

The important offset is the end of the first parsed IEND chunk. A raw search for the bytes IEND can land inside a chunk's data and produce the wrong offset. The offline scanner follows each chunk's declared length, checks its CRC, and stops at the structural IEND. It then tests any trailing IHDR candidate as a complete second PNG stream. It restores the fixed signature only when that stream passes its structural checks. The guide gives the input and output contract.

python artifacts/trailing_data_detector.py fixtures/sample_appended.png --out recovered

The carved image still needs to be opened and read. The script does not execute content inside it or decide which visually similar glyph is the flag character. The --out option writes recovered PNGs under the requested directory and refuses to overwrite an existing file.

4. Concept Explanation

A PNG begins with an eight-byte signature. After that come length-prefixed chunks with a type, data, and CRC. IHDR describes the image; one or more IDAT chunks carry compressed pixels; IEND closes the PNG datastream. The PNG specification requires IEND to be last and says no other content follows it in a conforming datastream.

That gave me a clean boundary. The visible image ended at its first structural IEND. The extra bytes were outside that image, even though many viewers still displayed the carrier normally. The appended stream began at IHDR and had its own chunks through IEND; its signature had been removed. Because the PNG signature is a fixed byte sequence, I could prepend it. That repair works only when the rest of the stream is intact enough to decode.

5. Exploit / Analysis Mechanics

The concealment used concatenation. One complete PNG came first. A second image's chunk stream sat after the first image's IEND, so the carrier still looked ordinary in a viewer. Removing the second signature reduced the chance that a simple signature scan would spot another PNG. The extra image could be reconstructed from the surviving IHDR, IDAT, and IEND chunks.

My path was: establish the first image's true end, measure the trailer, find the next IHDR boundary, restore the signature, render the second image, and read the lettering. The recovery proved where the answer was stored. Submission feedback resolved the last ambiguity in the hand-drawn glyphs. The first two rejected strings were transcription errors; they did not undo the file-structure finding.

The repaired image decoded to a fixed-size raster and its text fit the expected flag shape. The accepted submission is part of the case record. I do not have the carrier or submission transcript here for an independent replay. A damaged second stream would need more than signature repair, and a different kind of appended payload would need a different decoder.

6. Lessons Learned

The prompt's "extra" hint earned a byte-level check before I spent time on pixel steganography. Comparing the file's full length with its parsed PNG length was quick and decisive. It also spared me an LSB search that would not explain the second IHDR and IEND.

The wrong submissions taught a separate lesson. Rasterized text can make a technically correct carve look like a failed solve. Next time I would list possible readings for each 1/l, 0/o, 3/e, or 5/s shape before submitting. I would inspect each stroke at a larger scale and resist assuming that the writer applied leetspeak consistently.

7. Operational Extrapolation

Individual Practitioner Development

This was good practice in PNG internals, carving, and checking a file's declared end against its actual size. I would take the same question to JPEG, ZIP, and other formats, using each format's real structure rather than searching for a convenient marker string. A wider tool would need benign-file testing before I trusted its alert rate.

Security Operations

For a monitored file store, I would have a content-inspection job parse image boundaries and record trailing-byte counts. A positive file would go to review, not straight to an incident label. The reviewer could carve the trailer, determine whether it is a valid second format, and ask whether the producer legitimately appends data. The scanner demonstrates that structural step on local files. The test cases cover clean files, damaged candidates, and a misleading IEND string inside a valid chunk. No organization or production feed was assessed in this exercise.

Intelligence Operations

The challenge supplied no actor, infrastructure, or collection context. I would not turn a concealed puzzle image into an attribution claim or an IOC feed. If a real file appeared in an investigation, I would keep its hash, source, timestamps, parsed offsets, and carved bytes together so another analyst could reproduce the finding. That is an evidence-handling plan, not a claim about this challenge.

8. Reusable Tools, Scripts, and Artifacts

The scanner accepts a local PNG, reports the carrier's end offset and trailing-byte count, and tries to carve a signed or signature-stripped second PNG from the trailer. It checks chunk framing and CRCs, limits input to 16 MB, and never runs the extracted content. The guide lists the supported structure and the checks it does not make.

The invented appended PNG provides a safe example. Its first image ends at byte 973. The 1,155-byte trailer contains a stripped 180-by-64 PNG that reads SAMPLE TEXT, followed by an ASCII note. The expected report records the boundary, trailer length, and recovered image hash. The tests check that sample, a clean image with IEND text inside metadata, benign trailer text, a corrupt candidate, signed and stripped second images, and input bounds. Five local test groups passed. I also opened the carved sample image and checked its visible text.

The YARA rule is a narrower triage signal. It looks for a PNG signature, a fixed IEND byte sequence, and an immediately following stripped IHDR header. The Python scanner checks the chunk structure. The rule's engine compilation and performance on a file collection remain untested.

python -B -m unittest -v artifacts/test_trailing_data_detector.py
9. Framework Applicability and Mapping

The exercise does not show adversary behavior, so I do not assign it an observed MITRE ATT&CK technique. Hiding a second image inside a benign-looking file resembles T1027, Obfuscated Files or Information. Keeping data beyond the displayed image also resembles T1564, Hide Artifacts. Both are low-confidence analogies for how this method could be used in the wild. They say nothing about an actor in this puzzle.

D3FEND and STRIDE would require a defined defensive system or threat model to map precisely. OWASP web categories do not fit this local image task. I keep those labels off the case rather than giving a file carve the appearance of a web finding.

10. Threat Intelligence and Standards Integration

This file yielded no real infrastructure indicator, malware family, vulnerability, or campaign relationship. I have no case-specific STIX object to share and no TAXII exchange to report. The production-facing value is the inspection method: preserve the file, parse its real end, record the trailer, and review any recovered object with provenance. That method is described in the lab guide, including the limits that matter before operational use.

11. Controls Mapping and Mitigation Realization

The puzzle did not test an organization's controls, so it supports no NIST, CIS, STIG, or compliance finding. A real content-inspection control could place a structural PNG check in an upload or data-loss-prevention path. It would need a policy for benign trailers, retention for the original and carve, reviewer access, and a way to record the decision. The scanner supplies the parsing example; its 16 MB limit and incomplete PNG conformance checks would need deliberate changes for a production pipeline.

I would measure false positives on the files that pipeline actually sees before setting an alert threshold. A trailing region by itself proves a format anomaly. It does not prove malicious intent.

12. Indicators, Artifacts, and Detection Engineering

The main static-file signal is a valid PNG whose on-disk bytes continue after its structural IEND. A second valid IHDR-to-IEND stream in that trailer strengthens the finding. The scanner checks that sequence with chunk lengths and CRCs. The sample is a positive case; the tests include benign and damaged near misses. A file inspector needs access to the entire byte stream, not only the header or a rendered thumbnail.

The YARA candidate searches for an immediate stripped-image pattern. Its fixed-byte match can be fooled by coincidental bytes inside compressed data, and it misses a second image separated by text or one with its signature intact. It is for triage. The source-style count of two IHDR or IEND strings is weaker still: those letters may occur inside chunk data. I would verify a YARA hit with the structural parser before calling it an embedded image. No YARA engine or live collection was used to validate this rule.

A hunt could ask for stored PNGs whose file size exceeds their parsed image length, then group by producer and carve the uncommon trailers. Benign metadata appended by a producer is a likely false positive. Other payload types, corrupted PNGs, oversized files, and trailers hidden inside a different format fall outside this scanner. Sigma, KQL, and SPL event rules would need actual file-inspection telemetry; none was present in the challenge.
