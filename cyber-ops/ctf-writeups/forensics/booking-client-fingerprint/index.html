The Booking Client That Kept Its Rhythm

The first IP disappeared on day three. The sixty-second rhythm did not.

Summary

The challenge. Identify the suspected automated client in a three-day shared-equipment booking log and explain how it used the reservation workflow.

What I did. I ranked requests to the booking endpoints, checked intervals and paired POSTs, then searched day three for the behavior after both familiar identifiers disappeared.

The result. The available 1,290-line log independently reproduces the two source candidates, exact polling cadence, and same-second POST pairs described in the challenge record.

The limit. The log has no account identifier, request body, response body, or booking state. The two IPs are linked by behavior, not a verified account join; HTTP 200 does not prove a reservation was granted.

1. Problem Statement and Threat Scenario

A member-run facility shared equipment through a first-come reservation site. Staff suspected that one member had been taking an unfair share of available time over three days. My only artifact was the web server access log. It had 1,290 lines and 253 source IPs, with no account name in the ident or authuser fields. I needed to find a client that behaved like a booking script and explain the evidence without pretending the log could name the member.

The suspected abuse uses legitimate site functions. A client can poll for free equipment, then submit reservations as soon as a slot opens. No stolen credential, injection, or server compromise appears in this record. The affected resource is the booking opportunity. The site itself remained reachable.

I could see timestamps, paths, methods, statuses, IPs, and User-Agent strings. I could not see request bodies, response bodies, session tokens, booking IDs, or the resulting schedule. That missing application context matters all the way through this case. Two POSTs returning 200 are two accepted HTTP responses; they are not proof of two successful reservations.

2. Techniques, Tooling, and Actions Taken

My first instinct was to rank all requests by source IP. It would have sent me toward two ordinary sources with 24 requests each. The relevant source had 21 and ranked third. I changed the question from "who was busiest?" to "who kept using the equipment endpoint?" On the availability path, one source had 17 GETs, while the next highest had five. On the reservation path it had four POSTs, while the next highest had two. That endpoint-scoped view gave me a candidate worth reading line by line.

Day one was unusually clear. The candidate made six availability GETs one minute apart, then two reservation POSTs in the same second as the last poll. Its User-Agent was python-requests/2.32.5. That field was a useful lead, but a client can set it to any string. I used the full request set to look for behavior that would be harder to change accidentally: only the two booking paths, exact one-minute intervals, and a paired POST burst.

On day two, the same IP returned with an MSIE 7.0 / Windows CE User-Agent. For a moment, a different person behind a shared IP was a possible explanation. The new string did not come with new behavior. Eleven availability GETs still fell exactly sixty seconds apart. Two reservation POSTs again landed in the same second, one second after the last poll. The same narrow endpoint set remained. I treated a single client changing a header as the stronger explanation, while keeping shared-IP attribution as an unresolved possibility.

I then made the mistake that shaped the rest of the investigation. Searching day three for the first IP returned nothing. Searching for the Python User-Agent returned nothing either. I initially read those empty results as the activity stopping. Both searches depended on identifiers the client had already changed. I went back to the behavior: rank day-three availability GETs, then check intervals and POST timing. A second IP had five polls, compared with a next-highest day-three count of three, and it repeated the sixty-second rhythm and same-second two-POST burst.

Day Source label User-Agent shown Availability GETs Reservation POSTs
1 ACTOR-IP-A python-requests/2.32.5 6 2
2 ACTOR-IP-A MSIE 7.0 / Windows CE claim 11 2
3 ACTOR-IP-B Android 2.3.5 / Chrome 50 claim 5 2

The log establishes those source-level patterns. It does not establish that ACTOR-IP-A and ACTOR-IP-B belong to one authenticated member. The repeated combination makes that a strong investigative hypothesis, not a deterministic identity join. It also shows the order of the visible changes: User-Agent first, IP as well on day three. Why the client changed either field remains unknown.

3. Tooling and Scripts

The recorded solve used shell one-liners. The offline Python hunt was written afterward as a defensive proof of concept and replayed against the available log. I did not use it during the original challenge.

# The broad count put the useful source in third place.
awk '{print $1}' access.log | sort | uniq -c | sort -rn | head

# Scope the count to the function under review.
grep 'GET <AVAIL_ENDPOINT> ' access.log | awk '{print $1}' | sort | uniq -c | sort -rn
grep 'POST <RESERVE_ENDPOINT>' access.log | awk '{print $1}' | sort | uniq -c | sort -rn

# Read the candidate's whole request set and then its poll timestamps.
grep '<ACTOR-IP-A>' access.log
grep '<ACTOR-IP-A>' access.log | grep 'GET <AVAIL_ENDPOINT> ' | awk '{print $4}'

# Check whether the two identity fields can support an account join.
awk '{print $2, $3}' access.log | sort -u

The last command yields only - - in this log. In a real service I would ask for protected account and reservation-outcome logs before treating IP correlation as person-level attribution. The lab guide states the analyzer's input format, fields, bounds, and output. Its paths are illustrative so the public code does not expose the challenge's local endpoint names.

4. Concept Explanation

An availability poll asks the server whether a resource has become free. A script that sleeps for sixty seconds between checks can ask at a perfectly even pace. A person, a browser tab that auto-refreshes, or a legitimate partner integration can also create repeated requests. The timing alone is a lead. The same-second reservation pair after a long run of endpoint-only polling gives it more weight.

I measured the spread in the gaps between polls using the coefficient of variation: standard deviation divided by the mean interval. Each day-long candidate session had sixty-second gaps and a measured CV of 0.0. The session boundary is important. The first source had a 86,691-second overnight gap between days one and two. Treating that gap as a polling interval gives a CV near 3.96 and makes a plainly regular client look irregular. Split on idle gaps first; score the sessions second.

The two POSTs in one timestamp second leave an important question open. They may be two distinct reservations that the policy allows. They may be requests contending for the same item or racing a state check. The access log has no body or result details to separate those cases. A 200 response can even contain an application-level refusal. I would inspect booking IDs, account IDs, and application outcomes before calling this a race condition or claiming the equipment was actually reserved twice.

5. Exploit / Analysis Mechanics

The visible sequence is compact: poll the availability path, keep doing it at a machine-regular interval, then send two reservation requests close together. On day two the client presents a different User-Agent. On day three a different source IP presents yet another one while repeating the same request rhythm. Those are observations. The idea of a script using sleep(60) and changing headers or its route is a plausible mechanism, not recovered code.

The design risk is that a member might exercise an allowed booking function more often or in more parallel than the service intends. CWE-799 describes inadequate control of interaction frequency. CWE-770 describes allocations without adequate limits. Both are useful review questions here; this log alone cannot prove the application's actual limits or whether allocations completed. I would test the policy in application state before filing either as a confirmed vulnerability.

The client did not have to flood the server to gain an advantage. Even one poll a minute may be early enough to reach a newly free slot before a person browsing manually. A crude "one request per minute" limit would let a request spaced at exactly sixty seconds through at its nominal boundary. A per-account booking policy and an atomic reservation operation address the allocation itself, regardless of where the traffic originates.

6. Lessons Learned (Practitioner Perspective)

The useful part of this solve was changing my unit of analysis. Total volume told me who generated the most lines. Endpoint-scoped counts told me who was unusually focused on the booking workflow. Then timing and request order let me keep looking after the User-Agent and IP changed.

I also have to keep the failed turns in view. The empty day-three IP search was a real dead end. I almost filled it with a story about the client stopping after noticing scrutiny. The log did not contain that motive. It contained no matches for one IP. Repeating the same search with the User-Agent family failed for the same reason. The behavior-based pivot found the day-three candidate.

The first defensive analyzer written for this case had a more embarrassing problem: it was described as working before anyone ran it. On replay, it missed ACTOR-IP-A. Its seventeen polls produced fifteen sixty-second intervals and one overnight gap. That gap inflated the aggregate CV to about 3.96. Splitting sessions after an idle gap fixed the local test. I have kept that failure in the published tests, because a detector that misses the very case it explains should not be presented as ready to use.

This exercise gives me a short checklist for the next access-log case: rank the affected function, inspect complete candidate traffic, split sessions before timing analysis, and treat an empty search on a mutable identifier as a reason to try another discriminant. I would still verify the application outcome before writing an incident conclusion about a person or a successful booking.

7. Extrapolation

For a SOC hunt, I would start with a question that a different booking, ticketing, or inventory service can answer: which accounts poll an availability-like endpoint with low timing variance and then issue tightly clustered state-changing requests? That demands web and application telemetry at the same time. IP-only logs can generate candidates, as they did here, but cannot resolve shared IPs or rotations to a member.

For the response team, the immediate work is to preserve the access log, obtain reservation outcomes and account identifiers, then check whether the suspected periods actually crowded out other members. A ban on the two source IPs would be fragile when the client already appears under a second one. The service should enforce fair-use limits on the authenticated principal and keep its own audit trail of granted, rejected, and canceled bookings.

The visible sequence of User-Agent and IP changes might suggest someone adjusted the client over time. It does not reveal intent, awareness of detection, a particular tool author, or a wider campaign. The transferable lesson is narrower and useful: request timing and workflow choice can persist after self-reported fields change. I would test that hypothesis against local baselines before promoting it to an alert.

8. Reusable Tools, Scripts, and Artifacts

Triage decision tree

I use this order for an authorized booking-service review:

Access log
  -> scope to availability GET and reservation POST paths
  -> rank sources or accounts on those paths
  -> inspect full request sets, including navigation and outcomes
  -> split polls into sessions after a measured idle gap
  -> score timing regularity inside each session
  -> seek a same-second or near-second reservation pair
  -> compare other days by behavior when IP or User-Agent stops matching
  -> verify account, item, and booking result in application records

That last line is the gate between a traffic candidate and a member-level finding. With the present log, the analysis stops before it.

Cadence primitive (sessionized)

The offline analyzer implements the session split, CV test, and POST-pair check. It reads bounded Apache Combined logs and prints JSON candidate summaries. Its four local test groups cover the positive rotation case, a benign auto-refresh client without booking, a near miss with irregular polls and spaced POSTs, and malformed input. The README documents the parser and the expected fields.

The lab defaults are a ten-minute idle gap, at least four polls, CV < 0.05, and POSTs no more than one second apart within five seconds after the final qualifying poll. A three-poll floor is mathematically possible but gives only two intervals, a weak basis for a variance judgment. The public implementation uses four as a modest minimum. These numbers came from a small synthetic exercise, not a measured production baseline. The tool groups by source IP because the exercise lacks accounts; a deployed version should group by authenticated account and preserve IP as context.

10. Threat Intel and Standards Integration

I would not publish the two source IPs or the three User-Agent strings as a transferable intelligence feed. The source labels changed inside a three-day exercise, and the User-Agent field is easy to forge. A STIX indicator that matches only an availability GET would hit normal users. The durable part is a timing-plus-workflow hypothesis, and that requires local correlation logic and a baseline. There is no outside infrastructure, malware family, actor identity, or campaign here to share through TAXII.

I also leave STIG requirement IDs out of this case. I have an access-log visibility gap and a booking-policy question, not evidence of a reviewed STIG benchmark or its applicable findings. The controls below name the audit and monitoring ideas I can actually connect to this record. They are review mappings, not a compliance determination.

11b. Mitigation Realization

An IP-keyed reverse-proxy limit can reduce casual polling, but it cannot enforce member fairness when IPs are shared or rotated. A one-request-per-minute setting may even admit a client that lands exactly on sixty-second boundaries. I would set the actual limits from service policy and expected browser behavior, then enforce a per-account reservation cap in the application.

The reservation decision should lock a stable account or quota row and the selected item inside one transaction, count active holdings under that lock, and commit the item transition atomically. Locking only existing reservation rows is insufficient when the member currently has none: two concurrent requests can both see an empty set. The quota cap answers the permitted-by-design case; the item transaction answers a race on the same slot. Neither weakness is proven by the access log, so both need an application test.

Finally, I would add a protected account identifier, item identifier, and application outcome to the audit event. That would let an analyst join activity across source IPs and tell a successful booking from a 200 response carrying a rejection message. Keep those fields access-controlled and minimize personal data. The hunt templates describe how to use the resulting telemetry.

12. Indicators, Artifacts, and Detection Engineering

The offline candidate detector was run against the available exercise log. The Sigma and SIEM files are starting points, with no backend or production validation. I keep those maturity levels separate.

Validation run

The first, unsessionized CV check missed the main source. Its seventeen polls produce fifteen sixty-second gaps and one 86,691-second overnight gap. The combined mean was about 5,474 seconds and CV about 3.96, far above the 0.05 candidate threshold. Once I split on idle gaps, the offline hunt returned exactly two sources in the 1,290-event, 253-source log:

Source label Total polls Best session Mean gap CV Paired POST bursts
ACTOR-IP-A 17 11 polls 60 seconds 0.0 2
ACTOR-IP-B 5 5 polls 60 seconds 0.0 1

Against the challenge's labeled candidates, that is two of two found and no other source returned. It is a result for this one synthetic log, not a production false-positive rate. The invented test cases add a positive rotation case, a benign auto-refresh case, and an irregular near miss. They test code behavior, not live traffic.

IOCs (sanitized / illustrative)

Signal Value in this case How I would use it

Sigma

The Sigma selector matches an availability GET in normalized webserver fields and is labeled informational. A single matching request is ordinary. This rule cannot calculate cadence or join reservation outcomes. It feeds a correlation pipeline that can do both. The selector parsed locally, but its backend mapping still needs validation.

Splunk SPL - cadence plus burst correlation

The SPL and KQL templates join endpoint-scoped polling with a same-second POST pair, then calculate interval variation by source and day. Their day partition prevents the overnight gap that broke the first Python attempt. It is an approximation: a real session can cross midnight, and production code should assign an idle-gap session ID. The queries have not been executed in Splunk or Sentinel. Their normalized field names and time handling must be mapped and tested against the actual environment before alerting.

Telemetry requirements

I need method, path, timestamp with at least one-second precision, source, and a protected account ID. I also want reservation item and application outcome. Standard Combined logs gave me the first four but no account or outcome. If a pipeline rounds timestamps to a minute, it destroys both the exact cadence and same-second burst signals. If a reverse proxy masks the client IP, I need a trusted forwarded-address configuration or an application-level principal instead of treating the proxy as the actor.

Tuning

The lab uses at least four polls, a ten-minute idle-gap split, CV < 0.05, and a POST pair no more than one second apart within five seconds after the final poll. Those values separated the two labeled sources in this exercise. They are not universal bot thresholds. Auto-refresh pages, monitoring probes, and approved integrations can be regular. A human double-click can create nearby POSTs. Review the account, item, and result before escalation. A same-second pair after regular polling is a stronger combination, but still a triage signal.
