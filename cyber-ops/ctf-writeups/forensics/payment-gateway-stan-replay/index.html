The Transaction Number That Came Back Twice

I started with bytes that looked encrypted. The byte counts told a different story: the gateway was speaking EBCDIC.

Summary

The challenge. Identify the protocol and version, count repeated account numbers, and identify the repeated transaction number in an unusual payment-gateway capture.

What I did. I characterized the bytes, decoded cp037, parsed the message bitmap and LLVAR account field, then compared message types, accounts, transaction numbers, and ports.

The result. The recorded solve identifies ISO 8583:1987, four repeated account numbers, and repeated STAN 918939. The later reversal is suspicious, but the capture summary does not establish settlement or fraud outcome.

The limit. Packet counts and decoded fields come from the recorded packet review. Gateway decisions and settlement are not shown; linked defensive examples use invented events without account numbers.

1. Problem Statement and Threat Scenario

The case began with an 18.7 KB Ethernet capture from an internal payment gateway. The recorded analysis counted 89 packets. The payloads looked opaque in an ASCII view: no readable strings, obvious protocol header, or TLS handshake. I needed to identify the protocol and version, count accounts that appeared more than once, and find the repeated transaction number.

The scenario invites a fraud hypothesis: a terminal or process with gateway access could replay an authorization and then request a reversal. My evidence boundary was narrower. The record contains packet analysis, without gateway state, application logs, settlement records, or proof of terminal compromise. A real gateway should check transaction identity and the original authorization state before acting on a reversal. I cannot tell from this packet summary whether that check existed or failed.

ISO 8583 Session Analyzer

#!/usr/bin/env python3
"""
iso8583_analyzer.py - Case-specific ISO 8583 review for EBCDIC-encoded TCP payloads.
Requires: dpkt (pip install dpkt)
Usage:    python3 iso8583_analyzer.py <capture.pcap> [--verbose]
"""
import sys, dpkt
from collections import Counter, defaultdict

MTI_NAMES = {
    '0100': 'Auth Request',     '0110': 'Auth Response',
    '0400': 'Reversal Request', '0410': 'Reversal Response',
    '0800': 'Netmgmt Request',  '0810': 'Netmgmt Response',
}

def e(b):
    return b.decode('cp037')

def bit(bmap, n):
    return bool((bmap >> (64 - n)) & 1)

def parse(payload):
    """
    ISO 8583:1987 EBCDIC message parser.
    Layout: [MTI: 4B EBCDIC][Bitmap: 8B binary][Data Elements...]
    Variable-length fields (LLVAR) carry a 2-byte EBCDIC decimal length prefix;
    consuming this prefix before reading the value is mandatory.
    """
    if len(payload) < 12: raise ValueError('short message')
    mti  = e(payload[0:4])
    if len(mti) != 4 or not mti.isdigit(): raise ValueError('invalid MTI')
    bmap = int.from_bytes(payload[4:12], 'big')  # 8-byte big-endian bitmap
    supported = {2, 3, 4, 7, 11, 12, 13, 14, 41, 42, 49}
    present = {n for n in range(1, 65) if bit(bmap, n)}
    if present - supported: raise ValueError('unsupported bitmap field; use gateway profile')
    pos  = 12
    f    = {'mti': mti, '_name': MTI_NAMES.get(mti, 'Unknown')}

    def fixed(n, key):
        nonlocal pos
        if pos + n > len(payload): raise ValueError('truncated fixed field')
        f[key] = e(payload[pos:pos+n]); pos += n

    def llvar(key):
        """Consume 2-byte EBCDIC length prefix, then read that many bytes."""
        nonlocal pos
        if pos + 2 > len(payload): raise ValueError('truncated LLVAR length')
        digits = e(payload[pos:pos+2]); pos += 2
        if not digits.isdigit(): raise ValueError('nondecimal LLVAR length')
        length = int(digits)
        if length > 19 or pos + length > len(payload): raise ValueError('invalid PAN length')
        f[key]  = e(payload[pos:pos+length]); pos += length

    if bit(bmap,  2): llvar('pan')             # F2:  PAN (LLVAR, max 19)
    if bit(bmap,  3): fixed(6,  'proc_code')   # F3:  Processing Code
    if bit(bmap,  4):                          # F4:  Transaction Amount
        raw = e(payload[pos:pos+12]); pos += 12
        if not raw.isdigit(): raise ValueError('invalid amount')
        f['amount_minor'] = int(raw)  # currency and exponent require profile context
    if bit(bmap,  7): fixed(10, 'tx_dt')       # F7:  Transmission DateTime
    if bit(bmap, 11): fixed(6,  'stan')         # F11: STAN (scope/retry rules vary by profile)
    if bit(bmap, 12): fixed(6,  'local_time')   # F12: Local Time
    if bit(bmap, 13): fixed(4,  'local_date')   # F13: Local Date
    if bit(bmap, 14): fixed(4,  'expiry')       # F14: Expiry
    if bit(bmap, 41): fixed(8,  'terminal_id')  # F41: Terminal ID
    if bit(bmap, 42): fixed(15, 'merchant_id')  # F42: Merchant ID
    if bit(bmap, 49): fixed(3,  'currency')     # F49: ISO 4217 currency code
    return f

def main(path, verbose=False):
    pan_log = defaultdict(list)   # pan  -> [(pkt, sport, mti, stan, amount)]
    stan_log = defaultdict(list)  # stan -> [(pkt, sport, pan)]
    mti_cnt = Counter()
    req_p, res_p = set(), set()

    if __import__('os').path.getsize(path) > 10_000_000:
        raise ValueError('capture exceeds this example limit')
    with open(path, 'rb') as fh:
        pkts = list(dpkt.pcap.Reader(fh))

    parse_errors = 0
    for i, (_, buf) in enumerate(pkts):
        try:
            seg = dpkt.ethernet.Ethernet(buf).data.data
            fld = parse(seg.data)
            mti = fld.get('mti', '')
            if mti not in MTI_NAMES: raise ValueError('unexpected MTI')
            mti_cnt[mti] += 1
            if mti == '0100': req_p.add(seg.sport)
            if mti == '0110': res_p.add(seg.dport)
            pan, stan, amt = fld.get('pan'), fld.get('stan'), fld.get('amount_minor', '?')
            if mti in ('0100', '0400') and pan:
                if stan: stan_log[stan].append((i, seg.sport, pan))
                pan_log[pan].append((i, seg.sport, mti, stan, amt))
            if verbose:
                print(f"\n[{i:3d}] {mti} - {fld.get('_name','')}")
                for k, v in fld.items():
                    if k not in ('mti', '_name'):
                        print(f"  {k:<16}: {v[-4:] if k == 'pan' else v}")
        except (ValueError, AttributeError, dpkt.UnpackError):
            parse_errors += 1

    print(f"Packets skipped by this case parser: {parse_errors}")

    print(f"\n{'='*52}\nMTI SESSION SUMMARY\n{'='*52}")
    for mti, cnt in sorted(mti_cnt.items()):
        print(f"  {mti}  {MTI_NAMES.get(mti,'Unknown'):<22}  {cnt:>3}")

    print(f"\nSESSION BALANCE CHECK")
    for req, res in [('0100','0110'),('0400','0410'),('0800','0810')]:
        r, s = mti_cnt.get(req,0), mti_cnt.get(res,0)
        print(f"  {req}/{res}: {r} req / {s} res{'  <- MISMATCH' if r!=s else ''}")
    orphaned = req_p - res_p
    if orphaned: print(f"  Orphaned ports: {sorted(orphaned)}")

    print(f"\nDUPLICATE PAN ANALYSIS")
    dups = {p:t for p,t in pan_log.items() if len(t)>1}
    print(f"  PANs appearing more than once: {len(dups)}")
    for pan, txns in dups.items():
        print(f"  PAN ending: {pan[-4:]}")
        for pkt,port,mti,stan,amt in txns: print(f"    Pkt {pkt:3d} | Port {port} | {mti} | STAN {stan} | {amt}")

    print(f"\nREPEATED STAN REVIEW (retry or replay candidate)")
    dup_stans = {s:t for s,t in stan_log.items() if len(t)>1}
    if dup_stans:
        for stan, txns in dup_stans.items():
            print(f"  STAN: {stan}  <- REVIEW REQUIRED")
            for pkt,port,pan in txns: print(f"    Pkt {pkt:3d} | Port {port} | PAN ending {pan[-4:]}")
    else: print("  None detected.")

if __name__ == '__main__': main(sys.argv[1], verbose='--verbose' in sys.argv)
4. Concept Explanation

EBCDIC (IBM Code Page 037). Once I counted the byte values, cp037 became a useful hypothesis. Its digits occupy 0xF0-0xF9, and space is 0x40; many letters land in high-byte ranges that look odd in an ASCII view. Decoding produced readable terminal and merchant strings and plausible message types. The histogram and entropy were clues, not a proof that encryption was absent. Small or structured encrypted records can also have nonuniform bytes. The decoded field layout was the stronger confirmation.

ISO 8583 message structure. The recorded payload layout was four EBCDIC MTI bytes, an eight-byte primary bitmap, then data elements in field order. In this profile, the leading 0 in the MTI fits the 1987 version convention. The next digits distinguish authorization (1), reversal (4), and network management (8), then request (0) from response (1). Field 2, the PAN, had a two-character EBCDIC LLVAR length prefix. I had to consume that length before moving the cursor to the other fields. Field 11 is the six-digit STAN. Its uniqueness and retry scope depend on the gateway profile and processing day, so a repeated value calls for review rather than an automatic fraud verdict.

5. Exploit / Analysis Mechanics

The repeated transaction number (ST.8). The recorded parse places a JCB account on port 40010, packet 20, in a 0100 with a response. Port 40043, packet 86, carries the same STAN 918939, account, and stated amount $187.85 in another 0100. The record reports no matching 0110 in this capture for the later request. It does not show that the entire message bytes were identical, that the terminal deliberately suppressed a response, or that the gateway did not respond outside the capture.

The reversal sequence (ST.5, ST.9). A 0400 request and 0410 response followed near the end, after the request with no response observed on port 40043. A timeout or error can legitimately lead to a reversal under a gateway's rules. This ordering also fits a replay-and-reversal hypothesis. I cannot choose between those explanations from message types and ports alone. I would need the reversal's original-data reference, terminal logs, gateway decision, and settlement state.

Gateway decision boundary. I initially read the reversal response as approval, but the parser above does not read the response code or original-data reference field. A 0410 says a reversal response exists; it does not by itself prove approval, funds returned, or a missing gateway check. I treat that control failure as a testable hypothesis.

The parsing mistake (ST.5a). I first read fields from a fixed offset after the bitmap. Field 2 begins with an EBCDIC length, for example \xF1\xF6 for 16. Treating those two bytes as part of the PAN shifted later reads and produced implausible 18-digit "amounts." I stopped trusting the fixed offsets and advanced a cursor through the bitmap's declared fields.

6. Lessons Learned (Practitioner Perspective)

What helped. A byte histogram gave me a fast cp037 lead, and decoding checked it against readable fields. Looking at MTIs, ports, account repeats, and STAN together gave me a stronger investigative lead than the reversal alone. The four repeated accounts answered one challenge question; the STAN repeat answered another. Neither count establishes criminal intent.

What I got wrong. I initially treated opaque bytes as possible encryption. Then I parsed a variable-length field at a fixed offset. Both mistakes were cheap to catch once I checked the byte distribution and read the bitmap order. The larger gap is the jump from a suspicious packet sequence to a gateway failure claim. I need response codes, original-data references, and financial state before making it.

7. Extrapolation

Individual. I want to get faster at reading financial and other length-delimited protocols. The cursor mistake here translates directly to TLV and other variable-length formats. I would not assume the field set or encoding from ISO 8583 alone; the processor profile still matters.

Security operations. A parsed gateway log could surface repeated STANs within a terminal and processing day. Retries may legitimately reuse identifiers, so I would compare session IDs and the gateway's retry rules before escalating. Request/response imbalance is another review cue; capture loss, timeouts, and log gaps can cause it. Field 41 can help map a message to a configured terminal, but asset inventory must confirm the physical device before containment.

Intelligence operations. I would keep EBCDIC among the candidate decoders for an authorized payment-traffic collection pipeline. A four-digit MTI followed by a plausible bitmap is a useful protocol lead even when the port is unfamiliar. It still needs framing, field-order, and environment checks; a four-digit string alone is too weak a fingerprint.

Universal encoding probe

import math
from collections import Counter

def probe_encoding(payload, threshold=0.62):
    """Suggest a codec for inspection; do not classify encryption from entropy."""
    if not payload: return None, 'Empty payload'
    c = Counter(payload); t = len(payload)
    ent = -sum((v/t)*math.log2(v/t) for v in c.values() if v)
    for codec in ['cp037', 'cp500', 'utf-8']:
        try:
            decoded = payload.decode(codec, errors='strict')
            if (decoded[:4].isdigit() and len(decoded[:4]) == 4 and
                    sum(1 for ch in decoded if ch.isprintable()) / len(decoded) >= threshold):
                return codec, decoded
        except Exception: continue
    return None, f'No candidate confirmed (entropy={ent:.2f})'

ISO 8583 bitmap decoder

def decode_bitmap(bitmap_bytes):
    """Return declared fields; require a secondary bitmap when field 1 is set."""
    if len(bitmap_bytes) < 8: raise ValueError('short primary bitmap')
    bmap   = int.from_bytes(bitmap_bytes[:8], 'big')
    fields = [n for n in range(1, 65) if (bmap >> (64 - n)) & 1]
    if 1 in fields:
        if len(bitmap_bytes) < 16: raise ValueError('secondary bitmap missing')
        bmap2   = int.from_bytes(bitmap_bytes[8:16], 'big')
        fields += [n for n in range(65, 129) if (bmap2 >> (128 - n)) & 1]
    return fields

10. Threat Intel and Standards Integration

The useful shareable idea is a review pattern: repeated F11/STAN within a terminal's processing-day scope, a later authorization request with no response visible in the available telemetry, and a nearby reversal. Each part needs context. Retries can repeat identifiers, a capture can miss a response, and a reversal can be legitimate. I would share the pattern with those qualifiers, its normalized field definitions, observation window, and data source, without PAN data or an allegation about this gateway.

For a corroborated case, a STIX 2.1 attack-pattern could describe confirmed behavior and a course-of-action could describe duplicate handling and reversal-reference checks. A mitigates relationship could connect them. An indicator requires a pattern language and observable fields that actually represent the parsed gateway events; the local terminal_id and stan fields are not automatically portable STIX cyber observables. I have not created STIX objects or published over TAXII because I have no independently replayable capture, gateway decision record, or confirmed malicious infrastructure to package as intelligence.

Splunk SPL - session balance and reversal correlation

The session-balance SPL counts all four relevant MTIs by terminal, processing date, and session. It preserves first and last event times before the final table. The companion repeated-STAN SPL searches across sessions. Both require a complete enough event stream to interpret missing responses.

index=payment_gateway sourcetype=iso8583_parsed mti IN ("0100","0110","0400","0410")
| stats count(eval(mti="0100")) AS auth_requests count(eval(mti="0110")) AS auth_responses count(eval(mti="0400")) AS reversal_requests count(eval(mti="0410")) AS reversal_responses earliest(_time) AS first_seen latest(_time) AS last_seen BY terminal_id processing_date session_id
| eval unmatched_auth=auth_requests-auth_responses
| where unmatched_auth>0 AND reversal_requests>0
| table first_seen last_seen terminal_id processing_date session_id auth_requests auth_responses reversal_requests reversal_responses unmatched_auth
