The Merchant Name Was a Dead End

The merchant column looked like the obvious place to start. It gave me an empty result and an incorrect answer.

Summary

The challenge. Answer five questions about a synthetic transaction table with unreliable merchant display names.

What I did. I profiled the fields, checked the card-network category mapping, and used the right operation for each question.

The result. The corrected hotel-code count was four; the other questions resolved through category filtering, frequency, summation, and a strict amount threshold.

The limit. The five answers were recorded during the challenge. The linked tool and tests use invented transactions to demonstrate the method.

The zero was the useful part of the story. It was my first answer, and it was wrong. The merchant labels in this dataset were synthetic; I had exhausted variants of the name before checking whether the category code offered a better route.

1. Problem Statement and Threat Scenario

Challenge Presentation

The exercise gave me 1,000 synthetic credit-card transaction rows with four fields: timestamp, merchant, mcc, and amount. I had five questions: count transactions for a named hotel, find the sole merchant in a named retail category, identify the most frequent MCC, total spend for a medical-services category, and count amounts strictly greater than a specified threshold. The case record says all five flags were captured. It preserves the numerical outcomes for four questions; the merchant name from Question 2 is not printed here.

The data was built to make display names a poor starting point. An MCC describes a merchant's business type. Some card-network codes, including the branded hotel code used in Question 1, are more specific. Most codes are shared by many merchants. That distinction matters: a category filter can recover the right row set in this puzzle, but it does not normally prove which legal entity made a transaction.

Threat Model

This was an analytical puzzle, not evidence of payment fraud, money laundering, or compromised accounts. The scenario imagined a financially motivated actor blending into transaction noise, but the dataset only establishes synthetic naming and five questions. For an operational analogue, I would be an authorized investigator working with a normalized extract. I would ask whether a weak display-name match had hidden relevant transactions, then require a merchant identifier, acquiring context, and transaction provenance before attributing those rows to a real business.

2. Techniques, Tooling, and Actions Taken

Phase 1: Dataset Profiling

I profiled the four columns before settling on the query strategy: types, nulls, cardinality, amount range, and time coverage. The merchant names looked programmatically generated. The MCC column was complete and integer-typed. That made it useful for category filtering, although completeness alone says nothing about whether a code was assigned correctly. In pandas, the first pass was df.dtypes, df.describe(include="all"), df.isnull().sum(), and distinct counts for mcc and merchant.

Phase 2: Field Trust Classification

I treated mcc as a reference-backed category, amount as a value to validate, timestamp as contextual time data, and merchant as an unreliable display label in this particular extract. I would not call any one column ground truth in a production financial system. MCCs can be miscoded, amounts need currency and reversal context, timestamps need a time zone, and legal entity matching needs identifiers beyond a display string. In this challenge, the code was the more stable pivot because the names were intentionally unhelpful.

Phase 3: Question 1 - Initial Dead End and Pivot (Instructive)

I searched the merchant field for the named hotel, parent-brand forms, and abbreviations. Every query returned an empty DataFrame. I reported zero and the answer was marked incorrect. My mistake was turning "no string match" into "no transactions" without testing another identifier.

I then looked up the brand-specific hotel code in a card-network reference. Visa's Merchant Data Standards Manual lists MCC 3795 as Paris Las Vegas Hotel. Filtering the case table by 3795 gave four rows. That is the corrected Q1 count in the record. The code's specificity made this pivot plausible here; I would still verify merchant-account IDs before making a real-world entity claim.

hotel_rows = df[df["mcc"] == 3795]
len(hotel_rows)  # 4

Phase 4: Questions 2-5 - Systematic Execution

The remaining questions used four small operations. For Q2, I filtered MCC 5311 (department stores in the Visa list) and found one merchant name; I am leaving that name out of this public account. For Q3, value_counts().idxmax() returned MCC 3023. For Q4, I summed amount for MCC 8011 and got $198.26. For Q5, the count of amount > 50.00 was 504; equality to 50 did not qualify. I kept frequency ties and missing values in mind for reusable code even though this case had one top code.

3. Tooling and Scripts

3.1 Environment and Data Ingest

I used pandas to read the CSV, strip column-name whitespace, parse timestamps and amounts, and make MCC nullable integer data. That is enough for quick puzzle queries, but malformed currency values or a missing column can silently change an aggregate if a parser coerces them to null. The offline transaction reviewer uses only the Python standard library, rejects malformed MCCs and non-finite or negative amounts, and bounds the local input. Its six-row fixture is invented and intentionally gives different counts from the challenge.

3.2 Challenge-Specific Solves

Here is the full set of operations I needed. The runnable tool implements them with decimal amounts and reports an ambiguous merchant category instead of forcing a single name.

q1 = len(df[df["mcc"] == 3795])
q2 = df[df["mcc"] == 5311]["merchant"].dropna().unique()
q3 = df["mcc"].value_counts().idxmax()
q4 = df[df["mcc"] == 8011]["amount"].sum()
q5 = (df["amount"] > 50.00).sum()

The synthetic tests cover all five operations, a zero name hit with a nonzero MCC count, an ambiguous category, and malformed input. They exercise the proof of concept, not the historical answer sheet.

3.3 Fallback: Negative Space Validation Protocol

I should have run this check before submitting Q1 as zero. A failed name search tells me about the search expression and the field it used. I would then inspect the known category code, any stable merchant/account ID, date and amount filters, spelling or DBA variants, and the completeness of the extract. A zero across those documented routes is still bounded by the records and identifiers available. My later validate_null() sketch checked name patterns, candidate MCCs, and date range. Its "confirmed absence" string was too strong because those paths cannot prove global absence.

4. Concept Explanation

ISO 18245 Merchant Category Codes

ISO 18245:2023 defines codes for classifying merchants by the business, trade, or services they supply. A code is a category signal, not a universal merchant ID or proof of activity type for an individual transaction. Card-network manuals can add practical detail. Visa's list makes 3795 a branded hotel code, while 5311 and 8011 describe broader department-store and physician categories. The small lookup excerpt and search CLI show those distinctions without posing as a complete or permanently current catalog.

Signal Trust as an Analytical Framework

The label/code split here resembles other investigations: an account name can change while a SID remains stable, or a process name can be spoofed while other execution context remains. None of those fields is infallible. I rank a field by who assigns it, how it can change, what it actually identifies, and whether another source can corroborate it. For these five questions, MCC was the better category filter. I used merchant text afterward as a value to report for Q2, not as the first filter for Q1.

MCC Range Structure

I can group code ranges into agriculture, contracted services, travel, retail, professional services, and government as a memory aid. The boundaries and branded codes vary across network reference lists. I would use a dated network manual for a consequential lookup. The distinction that mattered here was simple: 3795 is branded in the Visa list; 5311 and 8011 are general categories. A range guess would not have justified the hotel count.

5. Exploit and Analysis Mechanics

Invariant Violated by the Dataset Design

The puzzle broke my assumption that a named hotel must appear in the merchant display field. The MCC values remained useful for the exercise even though the names did not. That is an analytical failure mode, not a software exploit.

Derivation of the MCC-Based Entity Resolution Method

My first path was name -> string match -> zero rows. The corrected path was name -> dated card-network reference -> branded MCC -> row filter -> count. For generic categories, that path stops at category membership. It cannot uniquely resolve a merchant without more identifiers. The case's Q2 worked because its filtered subset happened to contain one displayed name.

Operational Steps

I made a separate operation out of each question: count Q1's branded code; list Q2's unique names after filtering department stores; count all codes and handle a possible tie for Q3; sum Q4 with decimal arithmetic; and apply a strict greater-than test for Q5. I would record the filter, row count, and reference used for each answer. The test fixture is small enough to check by hand, and the tool prints the operations separately.

Why Null Validation Is a Separate Step

The rejected Q1 answer came from a perfectly executed query against the wrong field. A clean zero can look authoritative. Before closing a case on one, I now write down the field searched, alternate identifiers, reference mapping, date coverage, and known data gaps. If the dataset lacks a stable merchant identifier, I label the conclusion as a bounded search result rather than a verified absence.

6. Lessons Learned (Practitioner Perspective)

What the Exercise Validated

The useful habit was field profiling before question solving. The five operations were ordinary pandas work: count, unique, frequency, sum, and a Boolean filter. The judgment was choosing a field that answered the question I actually had. After I stopped treating a display name as an identity key, the queries became short.

What the Exercise Surfaced as Gaps

I did not validate the empty Q1 result before reporting it. The incorrect-answer feedback forced me back through the assumptions behind that query. I also should have made the initial profile explicit: type checks, null counts, and merchant/MCC cardinality would have made the synthetic names harder to overlook. A prepared null-check function can remind me to test another field, but it cannot certify an entity's absence by itself.

7. Extrapolation

Individual Practitioner Skill Development

This case is a good drill in structured-data triage. I can carry its small operations into SQL, SPL, KQL, and ES|QL. The next step is harder: join a merchant reference table, keep code-list versions, handle currency and refunds, and preserve account or merchant identifiers. Time-series baselines, entity linkage, and anomaly models need those inputs. A cluster of MCC values alone is too coarse for attribution.

Security Operations (SOC / IR / Threat Hunting)

Financial transaction logs can enter an enterprise investigation when the organization operates or protects a payment service. An analyst might look for a first-seen category for an account, sudden velocity, or a mismatch between a vetted merchant record and its display label. Each requires permissions and data beyond this four-column puzzle. A code such as 7995 selects a category for review; it cannot be called a fraud indicator without account history and other evidence.

I considered hunting for gambling, money-transfer, and quasi-cash patterns and repeated amounts just below a cutoff. I would treat those as hypotheses. The $45-$50 interval used for the teaching example is arbitrary and is not a legal reporting threshold or a validated structuring detector. A useful workflow starts with an approved policy, an account-level baseline, a defined time window, and a review process for ordinary customers who trigger the same filter.

Intelligence Operations (SIGINT / FININT / Attribution)

A category distribution can describe part of a spending pattern. In a lawful financial-intelligence review, it can help choose which records to inspect next or compare a customer's own history over time. It cannot establish that two accounts belong to one actor, that a merchant is a front company, or that a name is deliberately deceptive. I would require identifiers, provenance, location and time context, and independent reporting before making those claims. The puzzle taught me to pivot away from bad labels; it did not prove any real-world laundering behavior.

8. Reusable Tools, Scripts, and Artifacts

The artifact README explains the inputs, output, and testing boundary for the offline reviewer, invented CSV, transaction tests, limited MCC reference, lookup CLI, Sigma selection, synthetic Sigma events, Sigma test, and synthetic STIX object. These are defensive proofs of concept. They do not contain the challenge's transaction table or a production risk model.

8.1 Full Modular Analysis Engine

I sketched a broader engine around profiling, category frequency, aggregations, threshold filters, anomaly scoring, rule-driven review, and clustering. Those are useful modules to design, but the last three need a much richer dataset and validation plan. A fixed MCC "high risk" weight, a round-number rule, or KMeans cluster can produce a chart without producing a defensible investigation finding. The available challenge table has no account history, merchant ID, case labels, or confirmed fraud outcomes.

I kept the implemented proof of concept to the five operations the exercise actually used. transaction_review.py reads a bounded CSV, preserves cents with Decimal, and returns category and amount results. It reports all tied top MCCs rather than silently picking one. Its q2_unique_merchant field becomes null when more than one distinct name appears in the chosen category. That is an intentional guard against pretending a general MCC identifies one merchant.

python -B transaction_review.py synthetic_transactions.csv \
  --entity-mcc 3795 --category-mcc 5311 \
  --spend-mcc 8011 --threshold 50 --name-hint hotel

The invented fixture has six rows. It returns two 3795 rows and zero matches for the word hotel, so the negative-name/positive-code failure is visible without exposing financial data. The tests also cover a category with multiple merchants, a bad amount, and a missing required field. Production enrichment would need a reviewed reference table, currencies, reversals, account/merchant keys, privacy controls, and model evaluation.

8.2 Field Trust Triage Flowchart

Read transaction extract
  -> Check columns, types, nulls, code-list version, and date coverage
  -> Classify each field by who assigns it and what it identifies
  -> Match the question to count / unique / frequency / sum / threshold
  -> Choose a reference-backed filter where the name is unreliable
  -> Keep merchant IDs and names for corroboration and reporting
  -> If result is zero or ambiguous, test alternate identifiers and scope
  -> Record the query, row count, reference, and remaining uncertainty

The trust-tier idea needs one qualification: an MCC can be a useful category key and still be wrong or too broad. The time, amount, and display-name fields also need their own checks.

8.3 MCC Quick-Lookup CLI

The lookup script searches a four-row reference excerpt checked against the Visa manual: 3795, 5311, 7011, and 8011. It is deliberately incomplete. For another case, I would use the network's current dated manual or an approved institutional table, then record the exact version. A search miss in this tiny excerpt means only that I did not include the code.

8.4 Solve Pattern Checklist

  • [ ] Count rows and check column types, nulls, ranges, and duplicates.
  • [ ] Record what each field identifies and where its value came from.
  • [ ] Match the question to the correct operation and comparison boundary.
  • [ ] Verify MCC meaning against a dated network reference.
  • [ ] Keep category membership separate from merchant identity.
  • [ ] Check zero and ambiguous results through another identifier or reference.
  • [ ] Show count alongside sum; retain currency and reversal context.
  • [ ] Save the query and output before reporting the answer.
9. Framework Mapping

9.1 MITRE ATT&CK

No observed event in this puzzle establishes an ATT&CK technique. Synthetic merchant names were a challenge-design feature, not evidence of cyber masquerading. T1036 and T1036.005 concern adversary masquerading in computer systems; T1078 concerns use of valid accounts. The dataset did not show account compromise, cloud-account abuse, staged data, or acquired web infrastructure, so I would not tag it with T1078.004, T1074.001, T1530, or T1583.006 either. Those IDs can guide a separate cyber investigation if its evidence supports them. They do not explain these five CSV questions.

9.2 MITRE D3FEND

D3-DAM and D3-OAM can suggest data analysis and operational mapping, but D3-SBV and D3-NTA describe different defensive work. This review is financial tabular analysis, not service-binary verification or network traffic analysis. I use the concrete field and query requirements here instead of assigning a D3FEND label merely by analogy. D3FEND becomes useful when a cyber defensive technique, its digital artifact, and its deployment are actually specified.

9.3 CAPEC

CAPEC-167 (catching an exception thrown by a subsystem) and CAPEC-117 (interception) do not describe a failed display-name search or the five questions. I leave CAPEC unmapped. STRIDE, OWASP Top 10, CACAO, and OpenC2 would also need a different system-design, application, or orchestration question to add value.

10. Threat Intel and Standards Integration

10.1 STIX 2.1 Sample Objects

This case has no actor, malware, infrastructure, or confirmed malicious transaction to publish as an IOC. The synthetic STIX 2.1 bundle contains a textual course of action: check the category mapping and provenance before closing a name-search null. It does not invent a financial-transaction cyber observable or claim that a category is malicious. The OASIS specification allows a course of action to carry such procedural guidance, but this file is an illustrative representation. No TAXII exchange occurred.

10.2 STIGs

No STIG finding follows from the table or my pandas queries. STIGs assess configurations of particular systems against named benchmarks. A real payment platform could have applicable STIGs, but this dataset does not identify its stack or show a tested configuration.

10.3 CIS Benchmarks

CIS Benchmarks also require a specific product and configuration. The organizational CIS Controls can help frame log collection and review if transaction events are in the organization's security-monitoring scope. A completed category filter does not establish that those safeguards are implemented.

I do not map SI-4(4) to financial inflow/outflow, RA-3 directly to a toy score, or CIS 13.6 to transaction "flow logs." Those controls have specific cybersecurity scopes. The case can teach the analyst's query discipline without turning a CSV exercise into compliance evidence.

11b. Mitigation Realization

For an authorized production review, I would preserve incoming records, validate schema and reference version, run a category filter, join stable identifiers, and send review leads to an analyst queue. The queue should show why a row appeared, the relevant baseline, and the source system. A daily job could automate the first steps after data classification and access controls are in place. I would not schedule a prototype over real transactions without privacy review and a defined owner.

The Sigma rule supplies one low-severity category selection. The offline tool supplies the Q1-Q5 operations for a local CSV. Neither implements arbitrary risk weights, the $45-$50 "structuring" rule, or unsupervised clustering. Those ideas need labeled outcomes, account-level history, a regulatory context, and false-positive evaluation before deployment.

12. Indicators, Artifacts, and Detection Engineering

12.1 Indicators of Concern (Sanitized / Illustrative)

The MCC list {4829, 6011, 6051, 7995} is a category review set, not an IOC list. I also considered repeated $45-$49.99 amounts, synthetic-looking merchant names, and concentration in selected categories. Each is context-dependent and can describe normal behavior. I would record these as leads only after defining an account or merchant baseline, a time window, and a reason the values matter in that environment. The five solved CTF answers do not identify a real suspicious account.

12.2 Sigma Rule - High-Risk MCC Transaction Detection

The informational Sigma rule selects normalized transaction events whose string mcc is one of four chosen codes. It needs a mapping from the platform's actual event schema. It has no ATT&CK tag, no unsupported Sigma threshold block, and no claim that a single matching event is fraud. I parsed the rule locally with pySigma and checked a selected category, ordinary category, and near miss using a local test. Backend conversion and live telemetry were outside this proof of concept. For a useful alert, I would correlate with account history, transaction velocity, identity, and analyst-confirmed outcomes in a supported SIEM query or correlation rule.

12.3 SIEM Queries

The first query is a Splunk review queue for a chosen category set. It assumes normalized mcc, amount, account_id, and currency fields. The threshold is a local triage parameter, not an AML rule:

index=financial_transactions sourcetype=normalized:transaction
| where mcc IN ("4829", "6011", "6051", "7995")
| stats count AS transactions sum(amount) AS total BY account_id, mcc, currency
| where transactions >= 3
| sort -transactions

This KQL version asks for the same grouped review. It needs a verified TransactionLogs table and field mapping before use:

TransactionLogs
| where mcc in ("4829", "6011", "6051", "7995")
| summarize transactions=count(), total=sum(amount)
    by account_id, mcc, currency, bin(timestamp, 1d)
| where transactions >= 3
| order by transactions desc

For a baseline, ES|QL can count by MCC. The query shape is FROM financial_transactions | STATS transactions = COUNT(*) BY mcc | SORT transactions DESC | LIMIT 10. Before calling a code unusually frequent, I would compare the same population across time, account type, and transaction volume. The $45-$50 SPL example is best kept as a teaching filter; it lacks the account grouping and regulatory context needed for a structuring finding.

12.4 YARA

YARA can match bytes in files, but the useful detection question here is about fields in transaction events. Parsing CSV records and querying mcc, amount, account, and time is more precise than searching raw file bytes. I did not make a YARA rule for this case.

12.5 Detection Engineering Notes

The minimum operational event needs timestamp with zone, stable account and merchant IDs, MCC, amount, currency, transaction state, and source. Reversals and duplicate events must be handled before summing. Access controls and retention matter because financial records can be sensitive. A 30- to 90-day history might help establish a baseline, but the right window depends on the population and seasonality.

Legitimate customers use all four selected categories. A generic-name pattern and a small amount interval are weak signals. I would test a positive lead, an ordinary customer in the same category, and a near miss with realistic field mappings. Then I would measure the analyst yield and adjust thresholds. The local tests cover query mechanics and malformed records; they do not measure production false-positive rate or prove an AML typology.
