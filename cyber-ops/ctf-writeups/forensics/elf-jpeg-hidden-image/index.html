The Image Appended to a Package Manager

The altered binary kept the same BuildID. Its size gave me a better first question: where did those extra 79,117 bytes go?

Summary

The challenge. Compare a known-good executable with a recovered copy, find the modification, and recover the concealed information.

What I did. I checked file size and structure, compared the baseline bytes, carved the appended JPEG, inspected the visual decoy, then used steghide with an empty passphrase and OCR on the extracted image.

The result. The recorded solve recovered a 7,552-byte inner JPEG and read the flag from it. The changed file was an exact baseline prefix plus a 79,117-byte tail.

The limit. The executable pair, carved images, flag, and acceptance receipt are not reproduced here. Case measurements and extraction are from the recorded solve; the linked tool uses invented ELF fixtures.

1. Problem Statement and Threat Scenario

I was given two extensionless files: a known-good executable and a copy recovered from a suspect device. Both identified as 64-bit PIE ELF binaries. Strings connected them to apt, the Debian and Ubuntu package tool. The job was to determine whether the second file had changed and recover anything hidden in it.

The case narrative treats the recovered copy as adversary-controlled. What I could actually compare was narrower. The files had the same BuildID and the same first 18,752 bytes, but the recovered copy was 79,117 bytes larger. Those added bytes began with a JFIF image. No package repository compromise, software update, persistence mechanism, or execution of the appended data was shown. For a real endpoint, I would investigate those possibilities separately.

I also had a useful baseline. An exact byte comparison between two files can establish an append-only difference even when a general-purpose ELF trailer heuristic cannot decide whether extra bytes are malicious. The trustworthiness of that baseline would still matter outside the challenge.

2. Techniques, Tooling, and Actions Taken

Solve Trace

ST.1 file and stat identified two ELF64 PIE files of 18,752 and 97,869 bytes. The BuildID matched; the size delta was 79,117 bytes.
ST.2 readelf -S and objdump -d showed matching section tables and disassembly. I calculated the section-table end at 0x4940. That equaled the baseline file size in this case.
ST.3 A Python byte comparison found zero differences in the first 18,752 bytes. That was the strongest support for an append-only change relative to this baseline.
ST.4 The first trailer bytes at offset 18,752 were FF D8 FF E0 00 10 4A 46 49 46, the JPEG SOI, APP0 marker, length, and JFIF identifier.
ST.5 Carving from that offset yielded a 79,117-byte, 2464 by 1874 JFIF image.
ST.6 Pillow and NumPy measured a near-white canvas: mean channel value 254.98; 3,125 zero LSBs and 13,849,483 one LSBs.

3. Tooling and Scripts

Binary Triage and Trailer Detection

My first triage script computed e_shoff + e_shentsize * e_shnum, labeled anything after it a trailer, and wrote the remainder to disk. That formula happened to land at the end of this baseline. It cannot serve as a general ELF boundary: file-backed segments or sections can appear after the section header table, and some ELFs have no table. A tool also needs to reject malformed offsets and unsupported extended counts.

The linked read-only ELF reviewer computes the greatest end offset across the header, program and section tables, file-backed segments, and file-backed sections for little-endian ELF64. It checks whether the entire baseline is a prefix of the suspect and reports a JFIF header lead. Its guide lists the supported input and limits; tests include a JPEG-like marker inside a legitimate section after the section table.

file baseline suspect
stat -c '%n %s' baseline suspect
sha256sum baseline suspect
readelf -h -l -S suspect
python elf_trailer_review.py baseline suspect

The script does not carve by default. I would preserve the original, record a full-file hash, and carve only after reviewing the offset and output destination. The case's exact append-only result came from comparing the baseline bytes, not from a portable BuildID rule.

steghide Passphrase Bruteforcer

My helper tried an empty passphrase before a short built-in wordlist, then suggested a larger cracking tool. The empty candidate was enough here. The decisive command was:

steghide extract -sf carrier.jpg -p "" -xf payload.jpg
file payload.jpg
sha256sum payload.jpg

I would check the process exit code and the extracted file rather than search stdout or stderr for the words "wrote" or "extracted." A command can print an unexpected message, be localized, or leave an older output file in place. Use a fresh evidence directory and avoid -f unless replacing a known disposable output. The passphrase search is an authorized forensic step here; an incident team would record each attempt and preserve the carrier unchanged.

Full Triage-to-Flag Pipeline

I also chained ELF parsing, byte comparison, carving, steghide, and OCR. The chain is useful as a map, but my first code assumed 64-bit little-endian ELF, wrote outputs next to the suspect, treated message text as success, and printed OCR output that could contain a secret. I would fix those limits before relying on it in a live investigation.

I would run the phases separately in a real case. First prove the file relationship. Then carve to a controlled output directory and validate the JPEG. Only after that would I run steghide and inspect the inner image. This leaves a record of where each conclusion came from, and it keeps the flag or a real credential out of routine triage logs.

4. Concept Explanation

ELF Binary Structure and the Loader Boundary

An ELF executable has headers that describe file-backed program segments and, when present, sections. The loader primarily follows program headers. An appended tail may therefore leave ordinary execution unchanged. The ELF header specification also allows an ELF with no section header table. The section specification says SHT_NOBITS consumes no file bytes. I use those distinctions in the linked reviewer.

Here the recorded e_shoff = 0x41c0, e_shentsize = 64, and e_shnum = 30 give 0x4940, or 18,752 decimal. That equals the baseline's entire length, and the suspect begins with an exact copy of those bytes. The case therefore supports an append-only modification without needing the section-table formula as a universal parser.

The BuildID is an ELF note, not a fresh full-file hash calculated when a monitoring tool opens the file. Appending bytes leaves the note unchanged. A preserved BuildID is unsurprising in this case and cannot substitute for a trusted full-file digest.

JPEG Steganography: DCT Coefficients vs. Pixel LSBs

JPEG encodes quantized frequency coefficients, while a decoded RGB pixel array is a rendered result. Re-encoding can change pixel least-significant bits, so a naive decoded-pixel LSB extraction is a poor first assumption for this carrier. The failed all-0xFF output and the heavily white image told me that particular path was unproductive. They did not establish zero capacity or exclude every crafted JPEG LSB method.

steghide works with JPEG coefficient data rather than simply reading decoded RGB LSBs. A valid JPEG signature or a white appearance cannot prove steghide content exists. The extraction with the empty passphrase and the resulting inner JPEG are the stronger observations.

5. Exploit / Analysis Mechanics

Layer 1: Locating the ELF Boundary and Identifying the Trailer

The baseline was exactly 18,752 bytes. The suspect was 97,869 bytes. Subtraction gives the 79,117-byte addition. The first 18,752 bytes compared equal, and the next bytes were FF D8 FF E0 00 10 4A 46 49 46. I carved the remainder at offset 0x4940 and treated the signature as a JFIF lead. The reported image dimensions and successful steghide operation support that the carrier decoded in the original solve. The raw files are not available here for a fresh decode.

The recorded readelf and objdump matches support unchanged sections and disassembly, but the byte comparison is more direct for this pair. It does not tell me who appended the image or whether another program ever read it.

Layer 2: Ruling Out LSB and Identifying the Steganography Class

The 2464 by 1874 image has 13,852,608 RGB channel samples. The recorded LSB counts add to exactly that total: 13,849,483 ones plus 3,125 zeros. A decoded-pixel extraction yielded only 0xFF bytes. I treated it as a dead end and turned to the file format and steghide instead.

OCR found the phrase "no flag here! or is there?" in the nonwhite region. It was a decoy in this challenge. I did not treat its words as an instruction to stop, and I did not infer anything about a real adversary from the joke.

Layer 3: steghide Extraction

The empty passphrase worked. The tool wrote a second JPEG of 7,552 bytes and 1130 by 290 pixels. OCR gave the flag value. The important validation sequence was extraction success, inner file type and dimensions, then readable content. An OCR transcript alone can misread characters, so I would also inspect the image visually and check the exact submission result. I have no separate acceptance receipt to show here.

There were two environment detours: xxd was missing, so od supplied the byte view, and a subprocess wrapper encountered an encoding issue with steghide output. Calling steghide directly or reading subprocess output as bytes avoids depending on the terminal's text encoding.

6. Lessons Learned (Practitioner Perspective)

What the Exercise Validated

The first useful finding was 79,117 extra bytes, not a flashy stego result. Once the baseline prefix compared exactly, the investigation became a file-carving problem. The same BuildID could have reassured me too early if I had mistaken it for a whole-file integrity check.

What the Exercise Surfaced as Gaps

I spent time on decoded-pixel LSBs because the carrier was an image. The all-0xFF output and the JPEG format pushed me away from that route. I would phrase the lesson narrowly: pick a method that fits the encoded format, then test it. My first tool choice did not work on this artifact.

The missing xxd and steghide subprocess encoding snag were small but real. I had three helper scripts, but I had not separately validated them against the challenge files. The linked reviewer now has synthetic positive, benign, near-miss, and malformed-input checks, but it still has no run against this pair.

7. Extrapolation

Individual Practitioner Skill Development

This case joins ELF parsing, byte comparison, carving, image interpretation, and steghide extraction. I would extend it by building a format-aware scanner that handles both ELF classes and byte orders, extended header counts, and package-specific overlays. The limited offline reviewer makes its ELF64 little-endian scope explicit so it does not silently misparse another executable.

Security Operations (SOC / IR / Threat Hunting)

The operational question is whether an installed executable still matches a trusted package artifact. Compare its full-file digest and size with an independently trusted baseline, then inspect an unexplained tail. A package manifest on the same compromised host is useful but may have been changed too. debsums can help on Debian systems where package checksums exist; AIDE or another FIM system can supply an independently protected baseline. Package upgrade timing and local wrapper formats need triage before alerting.

An investigation should preserve file hashes, inode metadata, package version, installation logs, and the recovered image as separate evidence. The trailer may be a data carrier, but this record does not show it being executed, loaded, or transmitted.

Intelligence Operations (SIGINT / IO / Attribution)

A legitimate-looking executable, a JPEG tail, and steghide form layers of concealment in this exercise. They do not identify an actor, a delivery route, or a covert network channel. If similar files appear elsewhere, compare full-file hashes, tail offsets, carrier structure, and package versions before linking cases. The visible decoy text is weak attribution evidence.

8. Reusable Tools, Scripts, and Artifacts

ELF Trailer Triage Decision Tree

I start with file type, full-file size and hash, and package provenance. For an ELF, I inspect program and section extents. If a suspect has bytes beyond those extents, I check whether the tail is expected for that product. With a known-good file, I compare the entire prefix and size before carving. A JPEG signature prompts validation; it does not prove steganography. Only a controlled extraction and verified inner file support that finding.

The ELF trailer reviewer implements the first comparison, and its tests make a key near miss explicit: a JPEG-like marker inside a real section after the section table must not be called an appended trailer.

Tier 2 - Applied Where Material

The original mapping proposed D3FEND file integrity monitoring, executable allowlisting, and binary hardening. File integrity monitoring and allowlisting are relevant design choices, but a label alone does not tell me whether the baseline is trusted or enforced. I would verify the exact D3FEND term before treating an ID as a control requirement.

CAPEC concealment patterns can describe the scenario, but a JPEG payload is data here. No executable second stage is shown, so a code-execution CAPEC or CWE-506 "Embedded Malicious Code" would overstate the finding. CWE-345 is a possible design weakness only if an actual monitoring system relied on BuildID alone. The file comparison did not examine a real monitoring system.

For STRIDE, tampering is visible as a file modification. Information disclosure and privilege escalation are not evidenced by the static pair. Runtime behavior that appears unchanged in disassembly was not exercised here, and no attacker's route to root privileges is established.

10. Threat Intel and Standards Integration

I have behavior to describe but no real indicator bundle to share. The exact hash values are withheld; the file sizes and JFIF bytes are case observations, not global block rules. A STIX representation would need valid object IDs, concrete evidence, confidence, and clear distinction between observed file structure and inferred adversary intent. No TAXII sharing occurred.

That states what another analyst could verify if given the evidence.

11. Controls Mapping and Mitigation Realization

11a. Standards Mapping (Abbreviated - T2)

NIST SP 800-53 SI-7 and SI-7(1) are the clearest control references for software integrity checking and automated checks. AU-2 applies if file changes and package operations are logged. SI-3 can support malware analysis, but an antivirus signature is not required to notice a full-file hash mismatch. CIS software inventory and malware-defense controls are relevant after checking the organization's current version and implementation group. These are design mappings, not a compliance assessment.

11b. Mitigation Realization

I would record a trusted full-file digest, size, package identity, and source of the baseline. On Debian systems, debsums -c can triage package-managed files with recorded checksums. AIDE or another FIM system can watch high-value executable paths, with its baseline kept outside the host's writable trust boundary. I would alert on an unexpected content change, then correlate it with an authorized upgrade, reinstall, or local build before declaring compromise.

The illustrative Splunk and Elastic searches I drafted look for debsums failure messages. They depend on exact ingestion fields and message format, so they remain proposals. The more durable normalized event would include host, path, package/version, trusted baseline hash, observed hash and size, check time, baseline source, and whether the change belongs to an approved package transaction.

For a purple-team check, append an invented JFIF-like tail to a synthetic ELF fixture and confirm the offline reviewer flags it. Then test an unchanged binary and a marker stored inside a legitimate file-backed section. The test file covers those local cases. A production trial would additionally measure how often legitimate overlays and package updates trigger review.

12. Indicators, Artifacts, and Detection Engineering

The work here is a tested local review aid plus detection proposals. It has no deployed sensor or measured production accuracy.

IOCs (Sanitized / Illustrative)

The concrete file sizes are 18,752 and 97,869 bytes, with a 79,117-byte difference. The case's JFIF start bytes are a structure clue. Placeholder MD5 values and an unchanged BuildID are not useful block indicators. A whole-file SHA-256 value would be useful for evidence comparison if tied to a trusted source, but none is published here.

YARA Rule - ELF Trailer Detection

I drafted a YARA rule using uint64(40) and uint16(58) * uint16(60). Apart from supported-class and byte-order questions, it ignored file-backed extents after the section table. I would use YARA to find candidate ELF files or a JFIF marker at a known offset, then hand structural analysis to a parser. The linked reviewer performs that limited structural check. I did not carry the rule forward because it could mislabel legitimate file extents as trailers.

YARA Rule - JPEG steghide Carrier (Heuristic)

My second rule matched a normal JFIF header and a size under 50 MB. That identifies many ordinary JPEGs and has no steghide-specific evidence. I keep the idea as a file-type triage step, without calling it a steghide detector. An analyst would validate the JPEG, inspect provenance, and run steghide only when the case context justifies it.

Sigma Rule - Binary Size Anomaly vs. Package Manifest (Linux FIM)

My Sigma selection looked for changed files under system binary paths and filtered an IntegrityStatus of ok. Despite its title, the rule never compared a file size with a trusted manifest. A usable rule needs a real FIM event carrying observed and expected hash or size, or a SIEM join to a protected package baseline. Field names and thresholds depend on the sensor. The local review guide states exactly what the offline script accepts; no Sigma backend conversion was tested.

Log Sources Required

The minimum telemetry is a protected package or FIM baseline plus observed full-file hashes and sizes. Package transaction logs help separate legitimate upgrades from unexplained replacement. File-write telemetry adds timing and process context, but Sysmon FileCreate and FileCreationTimeChanged events alone cannot prove a size mismatch or capture a whole-file digest. The triage result should retain the raw file and provenance for offline examination.

13. Visual Artifact

The solve process flow above tracks the investigative layers: baseline comparison, JFIF tail, unproductive LSB attempt, decoy text, and successful extraction. For defense, I would put three controls alongside it: a trusted full-file baseline, an ELF-aware tail review, and careful handling of the carved image. The case supports those steps without assuming package-distribution compromise or execution of the hidden content.
