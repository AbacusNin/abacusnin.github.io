The Plot That Became a Protected Track

The scope did not ask whether a plot came from its radar. It asked whether three fields matched a track it already knew.

Summary

The challenge. Make one protected track enter the required classification and release the scope's sealed export by sending a CAT048 block to its ingest.

What I did. I decoded the sample feed, read the correlation and release rules, patched a known-good record, checked its fields offline, then timed the submitted block against the live refresh.

The result. The case record reports that the corrected plot was accepted, the classification latched, and the export released after a short burst.

The limit. The retained capture verifies the fixed record layout. It contains no TCP peer identity or post-merge state; the live submission and export transcript were not available for replay.

1. Problem Statement and Threat Scenario

The exercise put a protected corridor track on a radar scope and gave me a plain TCP ingest that accepted ASTERIX Category 048 plots. I had sample records, a scope map, the ingest's correlation rules, and a small client showing how to send one framed block. I needed to change that track's state so the scope would release a sealed export. The answer was a state transition, then the export, rather than a number to calculate locally.

The simulated attacker was any network peer that could reach the listener. The operator trusted the fused display. The protected assets were the corridor track's identity and the export gate tied to its classification. The trust boundary ran from an unauthenticated TCP connection into the track store. The store merged a plot on (SAC, SIC, track number) without tying those claimed fields to a verified sensor. This is the adversarial behavior the challenge modeled; no real aircraft or operational radar was involved.

2. Techniques, Tooling, and Actions Taken

I started with the sample feed. CAT048 blocks announced Category 48 with byte 0x30, then a two-byte big-endian block length. I walked those lengths and decoded records under their FSPEC, the bitmap that says which fields follow. The sample contained four 177-byte blocks, six 29-byte records in each. All 24 records used FD D2 as their FSPEC and the same SAC/SIC. This gave me a concrete, accepted-looking layout to work from. The protected track number came from the scope map; the source identifiers came from the sample and ingest description. The binary capture alone did not identify the TCP sender or prove how the scope merged a later plot.

The ingest rules were the turning point. A plot with the same (SAC, SIC, track number) replaced the latest Mode-S address, callsign, Mode-3/A code, position, SPI, and status fields shown for that track. I considered a shorter record, then kept the full sample FSPEC because the case record says the ingest rejected nonconforming blocks. I cloned a known-good shape and changed only the correlation tuple and the fields the release gate checked. I decoded the result again before sending it.

My first read of the release rule was too narrow. I had focused on one identity field. The export endpoint's response spelled out a combined condition: Mode-S address, Mode-3/A code, and the SPI bit all had to match the gate's required state. I corrected the record and used the reference client's one-block-per-connection framing. A live feed kept refreshing the track, so the forged plot needed to be the latest observation when the export evaluated it. The case record reports that a short burst just before reading the export won that timing race, latched the state, and released the export. I can verify the sample format offline; I cannot replay that operator interaction from the retained capture.

3. Tooling and Scripts

My small decoder followed the FSPEC's User Application Profile order, then printed SAC, SIC, track number, Mode-3/A, Mode-S address, callsign, and SPI. The offline subset builder and decoder preserves the useful part of that method. It handles the exact FD D2 layout observed in the sample and rejects a different FSPEC or malformed block length. The invented benign block and invented changed block show the same correlation tuple with different identity and SPI fields. The tool guide explains its inputs, output, and scope.

Two encodings were worth checking by hand before I trusted a record:

# Four octal digits, three bits per digit; upper flag bits stay zero.
mode3a = int("7500", 8).to_bytes(2, "big")

# Eight identification characters, six bits each.
code = (ord(ch) - 64) if "A" <= ch <= "Z" else ord(ch)

The source's sender used socket.create_connection and sendall with an already framed block, one connection per block. I keep the host and port out of this article. The linked proof of concept does not send anything; it builds or decodes local bytes. Running python -B cat048_subset.py from the artifacts folder prints a synthetic two-record block. The fixed-layout parser also decoded all 24 records of the challenge sample. That supports the wire-format analysis, while service acceptance and export release remain reported outcomes.

4. Concept Explanation

EUROCONTROL's CAT048 specification defines Monoradar Target Reports. A block carries a category byte, its total length, and one or more records. Each record starts with FSPEC. A set bit says a data item is present; the User Application Profile supplies its order and size. The low FX bit extends FSPEC to another octet. In this sample, FD D2 selected source identifier I048/010, time I048/140, target descriptor I048/020, position I048/040, Mode-3/A I048/070, flight level I048/090, Mode-S address I048/220, aircraft identification I048/240, track number I048/161, and track status I048/170.

Mode-3/A is four octal digits packed into 12 bits. Treating 7500 as decimal would make the wrong bytes. The aircraft identification item packs eight six-bit characters into six bytes. Letters use codes 1 through 26; digits retain codes 48 through 57; spaces use 32. The SPI bit is in the first target-report descriptor octet. These details matter because a valid-looking FSPEC does not rescue a field encoded at the wrong offset or in the wrong base.

The scope's correlation rule was separate from CAT048 itself. It joined on (SAC, SIC, track number) and treated a matching report as a fresh observation. A tuple can be a useful join key when the source is already trusted. Here, a peer could claim the tuple and choose the new identity fields. The source claim did the work that authentication should have done. The sample capture proved the record shape and common source codes; the map identified the protected track. Neither artifact recorded an authenticated peer for the received plot.

5. Exploit / Analysis Mechanics

I needed five fields to line up. I048/010 carried the claimed SAC/SIC, and I048/161 carried the protected track number, so the store would join the plot to the existing track. I048/220 carried the Mode-S sentinel used by the classifier. I048/070 carried the required Mode-3/A squawk. The SPI bit in I048/020 completed the release condition. Other fields stayed in the known-good layout to keep offsets and lengths stable. The invented benign block and changed example show the field-level difference without publishing a challenge target value.

The ingest accepted whichever plot most recently matched the correlation key. That made timing part of the exploit. A genuine sensor continued to refresh the protected track, and its next plot could replace my changed fields on the display. The case record says I sent a short burst immediately before requesting the export. It reports that the corrected combination latched the compromise classification and released the sealed export. I do not infer a permanent track takeover from that result. The exact reply and transport log are not present in the retained case materials.

The offline decode was an important but bounded check. It showed that the patched record had the intended tuple, Mode-S address, Mode-3/A code, and SPI bit under the same parser used for the sample. Its FSPEC remained FD D2; its record stayed 29 bytes. Those observations reduce encoding mistakes. They cannot guarantee that an independent ingest accepts a packet or that its business logic releases an export. The source-reported operator result supplies that separate end-to-end outcome.

6. Lessons Learned

The export response was more useful than my first guess. I initially changed too little because I read the classifications separately and assumed one value would trip the gate. Once the endpoint stated the combined requirement, I had a precise target for the record. I would read that response before patching bytes next time.

Cloning a record that already parsed gave me a safer starting point than inventing a minimal FSPEC. Decoding my changed bytes before sending caught field placement errors without using a live attempt. The last wrinkle was time: a latest-plot decision is a race against the ordinary feed. A short, well-timed burst explained why a single valid plot could appear to work and then vanish. The general failure mode is source identity inferred from an easily repeated correlation key.

7. Operational Extrapolation

Individual Practitioner Development

This case exercised binary framing, bit fields, octal encoding, and offline checks against a service with its own acceptance rules. I would extend the lab by decoding more UAP layouts and measuring how the parser responds to malformed FSPECs. That is a proposed next exercise. The published subset tool deliberately stops at the one observed layout rather than claiming full CAT048 coverage.

Security Operations

The defensive question is whether a protected track's identity changed and whether the plot came from a source authorized to make that change. A production ingest would need to log the authenticated peer, claimed SAC/SIC, track number, raw pre-merge fields, merge decision, and resulting committed state. I would compare those events with a protected-track registry and route mismatches to an operator before downstream actions. The offline track check exercises that idea on invented normalized events. It needs a trusted peer field from the transport gateway; an attacker-supplied label is not provenance.

Intelligence Operations

The same fusion problem can arise in other telemetry systems, but this record contains no campaign or actor to attribute. Distinguishing an injected plot from a sensor fault would require per-source raw data, authenticated source identity, and timing around the merge. The challenge's sample binary lacks those observations. I would preserve them in a real investigation before making an attribution claim.

8. Reusable Tools, Scripts, and Artifacts

The CAT048 subset tool builds and decodes one fixed 29-byte record shape under FSPEC FD D2. It accepts a source tuple, track number, Mode-S address, Mode-3/A code, callsign, and SPI; it fills unrelated time, position, and flight-level fields with invented values. Its output is a framed byte block or a decoded field dictionary. It needs only Python 3 and has no network feature. The benign fixture and changed fixture are synthetic. The parser accepts local captures up to 1 MiB and rejects unsupported layouts.

The track-integrity checker reads a protected-track registry and normalized ingest events. It emits reasons for unexpected authenticated peers, Mode-S mismatches, suspect classifications, and missing provenance. The expected output, tests, and guide make the proposed detection logic reproducible. The three tests cover a changed protected plot, an ordinary authorized plot, a same-number plot under a different source tuple, a provenance gap, and malformed records. These are defensive proofs of concept; no production feed or SIEM backend has been tested.

10. Threat Intelligence and Standards Integration

This single lab has no campaign, malicious infrastructure, or indicator-sharing context for STIX/TAXII. The sentinel Mode-S value was a classifier input for this particular scope. Its invented stand-in, 0BADFF, appears only in the synthetic fixture and is not a real-world IOC. A protected-track identity change or untrusted peer is a better behavior to monitor than a hard-coded address string. EUROCONTROL's CAT048 specification supplies the wire-format reference. It does not define this scope's correlation or release policy.

Mitigation Realization

No production control was implemented or assessed in the challenge. Network allowlisting reduces exposure but cannot substitute for message-origin checks at the merge boundary. A real deployment would also need sensor credential ownership, rotation, replay handling, and a safe fail-closed path when origin verification fails. The synthetic hunt demonstrates only one monitoring layer.

12. Indicators, Artifacts, and Detection Engineering

The useful detection point is before the merge. A normalized event needs the transport-authenticated peer, claimed SAC/SIC, track number, Mode-S address, classification, and a protected-track registry. The checker flags a protected plot from an unexpected peer, a Mode-S address that differs from the registry, or an application classification of spoof, hijack, or compromised. If the peer was never authenticated, it reports a provenance gap. The four invented events include a positive, a benign event, a same-number near miss under another SAC/SIC, and the missing-peer case. The expected findings show two records, with reasons rather than a claim of confirmed attack.

An operator would compare the raw plot, channel identity, pre-merge and post-merge fields, authorized maintenance activity, and neighboring sensor observations. A legitimate aircraft identity update, multi-sensor handoff, stale registry, or bench replay can trigger review. The sample capture contains no authenticated TCP peer or merge log, so this proposed hunt has no measured production fidelity. I did not publish a Sigma rule or SIEM query for an ingest schema that the case does not establish. A YARA rule has no useful file behavior to match here.
