The Passwords in the PNG Comment

The image looked like the evidence. Its comment held the actual puzzle.

Summary

The challenge. Recover three wedding-site passwords from one PNG and assemble them in the required flag order.

What I did. I inspected image metadata, found three 128-character values in XMP, tested candidate hash algorithms, and searched wedding words with three-digit suffixes.

The result. The challenge record reports three matching BLAKE2b preimages and manual flag acceptance. I independently confirmed the PNG and its three-value metadata pattern.

The limit. The original passwords and flag are withheld. I did not independently rerun the original recovery or witness the platform submission.

1. Problem Statement and Threat Scenario

I had one PNG and a short story about three passwords from wedding-planning sites. The challenge said they had been "stored and encrypted in an unorthodox manner." I needed all three passwords, in order, to form FLAG{password1-password2-password3}. The useful hint was unusually specific: each password had one wedding-related word followed by three digits. ceremony042 is an illustrative example of the shape, not a disclosed challenge password.

There was no site to log into and no live target to probe. This was an offline puzzle about a supplied file. The security problem it resembles is real, though: if an application stores password verifiers as fast, unsalted hashes, someone who obtains those values can try guesses locally. I use that connection in the later sections as an operational analogy. The challenge did not show an intrusion, an attacker, or production telemetry.

2. Techniques, Tooling, and Actions Taken

I started with the file itself. The challenge record lists a SHA-256 baseline and file-type check, then a metadata pass. That was a sensible first move for a PNG described as an unusual storage location. It also saved me from treating the pixels as a steganography puzzle without evidence.

exiftool was unavailable during the solve, so I used strings to inspect readable data. The useful text came from an Adobe XMP packet. Its exif:UserComment field held three hexadecimal values separated by hyphens. The count lined up with the three passwords I was looking for. In a later structural check, I parsed the local PNG rather than relying on printable strings: all nine chunk CRCs passed, and the XMP comment held exactly three values of 128 hex characters each. That check confirms the location and shape of the data. It does not identify the hash function or reveal the passwords.

The 128-character length means 64 bytes, or 512 bits, if the field is a hex-encoded digest. The challenge's name suggested BLAKE2b. I still needed a matching input to test that guess. The recorded trial covered SHA-512, SHA3-512, SHA-256, SHA-384, BLAKE2s, and BLAKE2b. A short wedding-word list yielded one preimage under BLAKE2b and none under the alternatives. That first match earned the algorithm choice.

The first list did not get all three. I expanded the hand-built wedding vocabulary, still without another hit, then moved to a broad English wordlist. The source record reports that this recovered the other two passwords. Each recovered candidate reproduced its stored digest, and the flag was assembled in the order of the metadata values. The record also says the flag was submitted manually and accepted. I have the recorded result, not a separate submission transcript or an independent replay of the three original passwords.

3. Tooling and Scripts

My triage used a hash baseline, a type check, and a text pass through the image. strings -n 6 exposed the XMP UserComment after exiftool proved unavailable. This is the useful command sequence, with the local image name generalized:

sha256sum authorized-image.png
file authorized-image.png
strings -n 6 authorized-image.png | grep -A2 UserComment

The digest-length check was small but necessary. I counted 128 hexadecimal characters in each of the three values. That gave me candidate 512-bit output, not a unique algorithm. RFC 7693 allows BLAKE2b outputs from 1 to 64 bytes; Python's default hashlib.blake2b() output is 64 bytes.

For the reusable check, I wrote a bounded PNG/XMP scanner. It validates chunk CRCs, parses the Adobe XMP iTXt packet, and looks inside exif:UserComment. By default it reports counts and a file SHA-256 without printing the embedded values. I ran that scanner against the local challenge image: one XMP packet, one UserComment, three candidate 512-bit values, and the expected hyphenated pattern. A match is a review lead, not an algorithm verdict.

The offline suffix recovery tool takes a wordlist and a separate digest file. It tries each alphabetic word with zero-padded numeric suffixes and compares every candidate with all targets. It hashes the word prefix once, copies the hash state, and adds each suffix. That is the same optimization described in the challenge record, using Python's documented hashlib copy() behavior.

python artifacts/png_xmp_audit.py authorized-image.png
python artifacts/suffix_crack.py fixtures/sample_words.txt fixtures/sample_hashes.txt --algorithm blake2b --suffix-width 3

The second command uses invented data. The sample words and sample hashes recover ceremony042, vows173, and bouquet999; they are not the challenge values. I tested the linked implementation and fixtures locally. They do not constitute a replay of the password recovery. The tool guide gives inputs, limits, exit codes, and validation scope.

4. Concept Explanation

The image rendered normally, but PNG can carry text metadata outside the visible pixels. This file used an iTXt chunk with Adobe XMP XML. The exif:UserComment field was a convenient place to hide three long strings from casual viewing. Anyone who checks the file's metadata can read them. The word "encrypted" in the prompt did not describe what I found: the field contained one-way digest values, not ciphertext that could be decrypted with a key.

Digest length helped me choose tests. A 128-character hex string represents 64 bytes, but several algorithms can produce that length. BLAKE2b itself permits different output lengths. Only a candidate password that hashes to the stored value can validate the algorithm for that value. The first small-list hit served that purpose in the source account; the remaining two were checked the same way after the wordlist expanded.

The password-storage lesson has two parts. A random, per-password salt prevents precomputed tables and stops the same candidate hash from being reused across several accounts. A suitable password hashing function adds deliberate cost to every guess. A fast general-purpose hash such as one pass of BLAKE2b supplies neither property by itself. NIST SP 800-63B-4 addresses salted, costed storage of memorized secrets. CWE-759 and CWE-916 describe the two weakness classes illustrated here.

5. Exploit / Analysis Mechanics

The hint turned an open-ended search into word + NNN. A list of 370,000 words would produce up to 370 million candidate strings across all 000-999 suffixes. With three unsalted digests, a single candidate hash can be compared with all three targets. That is 370 million candidate evaluations for the set, assuming the full list is searched, rather than three separate full passes. The actual search can stop as soon as all targets are found. I have no benchmark for the full list, so I do not assign a runtime.

For each word, the tool normalizes case according to its option, hashes the word as a prefix, copies that state, and feeds each three-digit suffix. The resulting hexadecimal digest is compared with the stored values. Equality verifies that the candidate is a preimage of that digest under the selected algorithm. It does not, by itself, prove who chose the password or where else it was used.

The first curated list made the BLAKE2b hypothesis testable. The unsuccessful expanded hand list mattered too: it showed that a narrow wedding vocabulary could miss ordinary words that still fit the challenge's theme. A comprehensive dictionary gave the remaining matches in the source record. The unsalted design allowed one hash computation to serve all three targets. A salt would prevent that cross-target reuse and precomputation, while a properly configured password KDF would raise the cost of each guess. Neither measure can make weak passwords magically strong; parameters, hardware, and the actual candidate space determine the work.

I kept the recovered strings and final flag out of this page. The evidence I can publish is the method, the file structure, and the source-reported outcome.

6. Lessons Learned

Metadata was the shortest route to the answer. I would still inspect a suspicious image's type and integrity first, but the prompt's "unorthodox storage" clue made a metadata check much cheaper than diving into pixel analysis.

Length was a filter, not an algorithm identifier. The first matching preimage settled a question that the 512-bit appearance could not settle. The wordlist progression also deserves to stay in the record: a fast, small list found one answer; a larger hand list stalled; a general English list found the rest.

7. Operational Extrapolation

Individual Practitioner Development

This case let me practice the handoff between file forensics and password analysis. The image structure told me where to look. The grammar told me how to search. A matching digest kept me from declaring the algorithm based on a title or a byte count alone. A good follow-up lab would compare the same invented passwords under fast BLAKE2b and a configured password KDF, measuring both cost and resource use rather than repeating an assumed speed figure. Hashcat or John could also reproduce the word-plus-suffix rule on an authorized fixture.

Security Operations

The operational lead is a file that carries long, unexplained values in comment metadata. An upload scanner or DLP process could parse XMP, record the specific field, and send a review event. An analyst would then ask whether the value is a harmless content hash, an application identifier, a test fixture, or an exposed credential verifier. The PNG scanner demonstrates that first extraction step. It needs an authorized file feed and context from the real environment before it could support alerting.

Intelligence Operations

This puzzle gave me no infrastructure, actor behavior, victim environment, or collection trail. I cannot turn three metadata values into attribution or a threat-intelligence report. If a real investigation found the same pattern, intelligence value would depend on surrounding evidence: where the file traveled, who could access it, and whether a known campaign used the technique. Those facts are absent here.

11. Controls Mapping and Mitigation Realization

Standards Mapping

The control issue is storage of memorized secrets. NIST SP 800-63B-4 calls for salted password hashing with a suitable cost factor. CWE-759 addresses an absent salt, and CWE-916 addresses too little computational effort. Those are relevant to the design the puzzle models. They are not findings against a named production service.

Guidance Concrete check suggested by this case Status here
NIST SP 800-63B-4, memorized-secret verifiers Confirm per-record salts and a costed password hashing scheme Proposed application review
CWE-759 Check that identical passwords do not share reusable unsalted digests Illustrated by puzzle storage
CWE-916 Measure the configured per-guess cost against current hardware No production benchmark performed

Mitigation Realization

For an application I control, I would replace a bare BLAKE2b password digest with a maintained password hashing library. Argon2id is one suitable option when its parameters are chosen for the service's hardware and load. A library should generate a fresh random salt for each stored password, retain the parameters needed for verification, and provide a verification method. The application still needs rate limits and appropriate credential-reset handling if an old unsalted database was exposed.

# Illustrative application design; not executed against a challenge service.
from argon2 import PasswordHasher

hasher = PasswordHasher()
stored = hasher.hash(password)
hasher.verify(stored, candidate_password)

This is a proposed remediation example using argon2-cffi, not a deployed control or a tested configuration. I would select and load-test the memory, time, and parallelism settings before using it in production, then keep a process to review those settings as hardware changes. A salt stops reuse and precomputation across records. The costed function slows each individual guess.

12. Indicators, Artifacts, and Detection Engineering

My first YARA sketch looked for exif:UserComment somewhere in a file and a run of at least 64 hex characters somewhere else. That could pair unrelated strings and could not prove either string was inside the parsed comment. I had no YARA-engine or benign-corpus validation for that sketch. I kept the hunt idea and made the field boundary testable with the PNG XMP scanner.

The scanner validates PNG chunk framing and CRCs, finds Adobe XMP iTXt, parses XML, then counts 128-hex values inside exif:UserComment. It reports whether the specific three-value pattern from this case appears. A defender could run it over authorized image uploads or attachments and join the result with owner, path, source, and collection-time fields from the file sensor. The rule is a file-content triage signal. This challenge supplied no event schema or backend on which I could test a Sigma, KQL, or SPL rule.

The test suite observed the expected positive result on seeded XMP, no result when the long hex string sat in another metadata field, no result for a 127-character near miss, and rejection of a bad CRC. It also covered compressed XMP. The local challenge PNG produced three candidate values and the exact hyphenated pattern. No production image corpus was labeled or scored, so sensitivity, false-positive rate, and alert load are unknown. Legitimate software may put long hex in comments. Encoded, split, altered-length, or stripped metadata can evade this exact rule. The proposed review checklist tells an analyst how to preserve context and resolve a lead before escalation.
