The Drawing Hidden in the Deltas

The file had no picture in it. It had the movements that made the picture.

Summary

The challenge. Recover a message from a CSV of time, dx, dy, and pen state, without an image or absolute coordinates.

What I did. Check the fields, sum each delta in order, gate line segments by pen state, and inspect the result with equal axis scale.

The result. The path rendered a legible flag-shaped message; the recorded submission was accepted by the platform.

The limit. I recorded an accepted submission but did not keep a platform screenshot. The flag-bearing image and CSV stay private; the linked files use invented fixtures.

At-a-Glance Mental Model

I started with a log, not a drawing. Each row said how far the pointer moved, and one bit said whether the airbrush was on. I added the movements in order. Then I drew a line only for rows with pen_down=1. The path resolved into readable text without another decoding layer. The flow above shows the entire solve.

1. Problem Statement and Threat Scenario

The challenge gave me a CSV from a virtual airbrush trail. Its fields were time_ms, dx, dy, and pen_down. I had no screenshot or absolute position channel. I needed to recover what the user had drawn from the movements alone.

This was a reconstruction puzzle. I had no evidence of an attacker, a stolen file, or a diagnostic uploader in the challenge. The security question it raises is still useful: a log of input movements can retain content even when it never stores an image. The drawing here depended on a complete, ordered stream and a pen-state bit. I would check those assumptions before making the same claim about another device.

2. Techniques, Tooling, and Actions Taken

I inspected the header and early rows before plotting anything. The two signed decimal columns were small movements; the last column held zeros and ones. Most sample intervals were 16 ms, which is about 62.5 samples per second, close to the rough 60 Hz impression from the first inspection. The first record moved the cursor while the pen was up. That mattered: the cursor still travels during a pen-up row, even though I draw no ink for it.

I treated dx and dy as relative changes and kept running x and y totals. Then I joined the previous and current point only when the current row had pen_down=1. A continuous path through the pen-up rows would have drawn transit lines across the letters. The math-space plot was legible. An inverted Y view is a quick orientation check if a reconstruction looks mirrored, but this drawing needed no additional transform or cipher.

The CSV has 782 data rows, 756 active rows, and 26 stroke segments. The accumulated bounds are about x=-0.002..174.529 and y=0..15.936 when the arbitrary origin is included. Those numbers establish the reconstruction's shape and scale. They do not spell out the message by themselves. The visible drawing supplied the reading. I recorded an accepted submission, although I did not retain the platform screen.

3. Tooling and Scripts

The first pass can be as simple as head -n 20 trackpad_deltas.csv and a numeric range check. I use the standard csv reader rather than splitting on commas by hand. This is the decisive transform:

x = y = 0.0
previous = (x, y)
segments = []
for row in rows_in_time_order:
    x += float(row["dx"])
    y += float(row["dy"])
    current = (x, y)
    if int(row["pen_down"]) == 1:
        segments.append((previous, current))
    previous = current

The previous point must update on every row, including pen-up moves. Otherwise a new stroke reconnects to the end of the old one. My earlier plotting code used Matplotlib, equal aspect ratio, and no axes. It rendered the accepted path with the ordinary math-space Y convention.

For reuse, I wrote a bounded motion CSV reviewer. Its default output is a numeric summary, so a quick triage run does not print the recovered content. An analyst can explicitly request an SVG in either Y convention. The neutral motion fixture and tests exercise stroke gating and axis choice. Any SVG produced from real user input is content-bearing and needs the same handling as the source data.

I had a fallback in mind for a non-legible plot: verify row order and units, then check whether the fields were polar movement, scaled deltas, or a different coordinate frame. Quaternion and IMU traces would need a different model. I did not need that fallback for this CSV.

4. Concept Explanation

The CSV stored differences. If a point moves by d_i = p_i - p_(i-1), adding the differences gives p_k = p_0 + sum(d_i) through row k. I can set the starting point to (0,0) because moving the entire drawing across a page does not change the shapes of its letters.

That statement depends on the data. Missing rows, clipping, quantization, changing units, or a reset in the device frame can spoil the path. An IMU's acceleration is also different from a cursor-position delta; getting position from acceleration takes additional integration and drift handling. I would not call every motion log lossless.

The pen-state bit carries its own information. It marks where a line ends and another begins. In this file, I still add pen-up movement to the cursor position, but I hide those transit segments in the drawing. Plot axes add another choice: screen coordinates often put positive Y downward, while a math plot puts it upward. Equal scale on both axes matters as much as orientation; stretching one axis can turn a readable letter into a poor clue.

5. Exploit/Analysis Mechanics

I parsed four typed fields, verified increasing time, accumulated each axis, and segmented strokes on pen_down. The current row's state controls the movement from the previous point to the new one. That convention is explicit in the reviewer's code, since other devices may timestamp the state differently.

The result was a wide path, roughly 174.5 by 15.9 motion units. Rendering the 26 active segments at equal aspect produced readable characters. I read the answer from the image and checked its flag shape. I recorded that the submitted answer was accepted, though I did not keep a platform screenshot. Repeating the calculation against the retained CSV confirmed the counts, bounds, and legible drawing. I keep that drawing private because the pixels reveal the answer.

6. Lessons Learned (Practitioner Perspective)

The schema gave me the right first question. The numbers were too small and too regular to be a finished drawing, but they made sense as changes in position. I could test that idea with one running sum. I also learned to keep the gesture bit in the first plot. If I had drawn every move, the pen-up travel would have made the message harder to read.

Orientation was a cheap check. A path can be mathematically right and look wrong because a screen and a plotting library disagree about Y. I now set equal axis scale and compare conventions before changing the reconstruction logic. In this case the retained math-space view was already readable.

The useful operational lesson is about retention. A motion log may need the same review as the content it can reconstruct. That depends on what fields it stores, whether the stream is complete, and who can retrieve it. I would not classify every device diagnostic file as an input-capture incident from its name alone.

7. Extrapolation

For my own work, this is a compact exercise in discrete integration, segmentation, sampling, and coordinate frames. The same shape of reasoning helps with deltas in event logs or drawing tools. A mouse or stylus path is a closer match than an IMU acceleration trace, which needs more modeling and can drift.

In a SOC or incident response case, I would start with the data path: which process received the input, whether it wrote reconstructible deltas, where the file went, and whether an upload occurred. Accessibility tools, game controllers, design software, and vendor diagnostics may all have legitimate reasons to touch these sensors. A hunt needs device-access telemetry and process identity, followed by review of file content and destination policy. A file name such as motion.csv is only a lead.

For intelligence work, repeated collection of precise motion traces could reveal sensitive drawings or timing habits. This puzzle gives no basis for biometric attribution or a real SIGINT claim. Those would need consent, multiple comparable samples, and error measurements that the challenge never supplied.

8. Reusable Tools, Scripts, and Artifacts

Triage flowchart for unknown CSV-shaped telemetry

I inspect the schema, row count, numeric ranges, and time order first. If signed fields cluster near zero, I try a cumulative plot. If a column instead appears to be absolute position, I plot it directly. A categorical field may be a state gate. When the geometry is plausible but mirrored, I compare Y conventions; when the geometry itself fails, I return to units, dropped samples, and encoding.

Reusable primitive: state-gated trajectory integrator

The offline reviewer implements the running sum and pen-state gate with bounded input, finite-number checks, and explicit SVG output. Its invented CSV makes two short strokes without a hidden answer. The README gives inputs, commands, output sensitivity, and parser limits. This tool reviews a motion file; it does not prove why that file was collected.

I also built an event-sequence hunt for the defender side. It correlates a direct input-access event, a telemetry-file write, and a network connection under one stable process identity. The invented event fixture includes a positive lead, a benign two-event case, and a process mismatch. The tests include an expected false positive: legitimate software can complete all three steps.

Solve-pattern checklist

I save and hash the file, check field meanings and time order, accumulate the deltas, gate active strokes, render at equal scale, compare axes, and read the result against the challenge's expected answer form. For a real investigation, I keep the content-bearing render in a controlled evidence location and document any missing samples or coordinate assumptions.

9. Framework Mapping

ATT&CK

T1056, Input Capture is a useful analogy if an adversary deliberately records a user's input stream. The puzzle did not show that behavior. T1056.002, GUI Input Capture emphasizes deceptive GUI prompts for credentials, which makes it a poor match for this motion file. T1005, Data from Local System would require an adversary collecting the local log, and T1119, Automated Collection would require an automated collector. Neither happened here. T1041 specifically requires an existing command-and-control channel; an ordinary diagnostic upload would not establish it. A real web-service theft might fit T1567 after the transfer is observed.

D3FEND

D3-IDA, Input Device Analysis fits the question of how input is observed and controlled. D3-FA, File Analysis fits inspection of retained motion files. I would choose additional D3FEND techniques only after defining a deployed sensor or countermeasure. The lab has no endpoint authorization mechanism.

CAPEC

CAPEC-569, Collect Data as Provided by Users could describe an attacker planting a collection mechanism for genuine input. CAPEC-117, Interception would need an intercepted channel. This CSV alone supports neither attack finding. OWASP application risks and a full STRIDE model would need an actual product boundary to assess.

10. Threat Intel and Standards Integration

STIX 2.1 sample SDOs

I would not share this puzzle's CSV schema as a threat indicator. It is a normal-looking data format, and no actor, campaign, malicious hash, or destination was observed. A real incident could justify a STIX 2.1 attack pattern and course of action after the behavior and confidence are documented. An indicator should describe an observed, discriminating pattern, with valid IDs and timestamps. I did not create a TAXII collection or publish the redacted placeholder objects as usable intelligence.

STIG and CIS Benchmarks

An organization handling controlled drawings should review the applicable host baseline, audit settings, device access policy, and diagnostic retention. I cannot name a STIG finding or a CIS Benchmark failure without the OS, version, benchmark revision, and configuration evidence. The general CIS Controls themes are data handling, logging, and network monitoring. They are design inputs here, not assessed compliance results.

11. Controls Mapping and Mitigation Realization

11a. Standards Mapping

The most relevant NIST SP 800-53 Rev. 5 families are AC-20 for use of external systems, SI-4 for monitoring, AU-2 for selecting events, CM-7 for limiting unnecessary services, and SC-7 for network boundaries. In a real environment I would map these to a named host, logging pipeline, and approved diagnostic destination. A generic 90-day retention number or blanket service-disable instruction would need the organization's policy and legal requirements. PE-19 concerns information leakage, but this case is a stored telemetry-content question; I would not assign that control without a system-specific assessment.

11b. Mitigation Realization

The practical control starts before the SIEM: avoid retaining raw motion traces when the product only needs a summary. If raw data is necessary, define access, encryption, retention, and an approved upload path. At the endpoint, log actual sensor or device access with a stable process identity, file creation, and network connections. Compare destination and process against an approved diagnostic workflow. No control was deployed in this challenge.

On Windows, Sysmon Event 1 is process creation, Event 7 is a DLL image load, Event 11 is file creation, and Event 3 is a network connection. Loading hid.dll or user32.dll does not prove a process subscribed to raw input. A host firewall, proxy, or MDM rule also cannot be assumed to enforce binary-signature and user-agent identity; I would verify the actual product capability before claiming it. The event-sequence hunt therefore expects a distinct input_open event from an appropriate EDR or OS audit source.

12. Indicators, Artifacts, and Detection Engineering

Indicators (sanitized / illustrative)

The CSV header and four numeric columns are useful triage clues. The challenge supplies no malware hash, host path, domain, cloud bucket, or actor IOC. A file named for motion, a renderer process, or a network connection alone would be noisy. I would preserve file provenance, schema, process identity, and destination policy with any alert.

YARA: on-disk HID delta CSV signature

A YARA rule matching time_ms,dx,dy can find candidate text files. It cannot establish that the values are relative motion, that a drawing is recoverable, or that the file is malicious. The CSV reviewer checks the fields and time order more deeply and can count active strokes without writing the image. It still needs analyst interpretation. I did not claim a YARA engine run or a production precision rate.

Sigma: HID-API consumer with disk write and outbound connection

A single Sigma event selection cannot make a three-event temporal correlation merely by combining Event 7, 11, and 3 fields. Event 7 also lacks the direct device-access evidence this hunt needs. I kept the intended sequence in the normalized event hunt and event fixture. A production implementation needs a trustworthy input-access sensor and a backend capable of joining by stable process identity and time. This local script is a review lead generator, not a shipped Sigma detector.

Splunk SPL: anomalous HID consumers writing telemetry

The useful SPL plan is to normalize three event kinds, then join input_open -> telemetry_write -> network_connection by host and process GUID within a measured window. A raw ProcessId can be reused, and fields such as TargetFilename do not exist on every Sysmon event. An implementation must preserve event order, source names, and the absence of any direct upload proof. The README defines the small normalized schema that I tested. I did not run an SPL backend.

KQL: equivalent for Microsoft Sentinel / Defender

The same evidence requirement applies to KQL. Defender file and network events may support two legs of a hunt, but a DeviceImageLoadEvents row for user32.dll is not an HID-subscription row. I would map the input-open event first, then verify the process identifier and time fields in the tenant's actual schema before writing the join. No Sentinel or Defender tenant was available for query validation.

Log source and data-pipeline requirements

The file-analysis path needs the actual CSV bytes. The behavioral path needs direct input or sensor-access events, file writes, network connections, clock normalization, and stable host/process identity. Sysmon 3 and 11 can supply two legs on Windows; an additional sensor must supply the input-access leg. Zeek or proxy logs can help with destination context, but without endpoint attribution they cannot prove which process sent the file. Cloud object logs matter only if an upload destination is part of a real case.

Detection engineering notes

The five local tests cover a positive correlation, a benign partial sequence, a process mismatch, bad ordering, and a legitimate full sequence that alerts anyway. The motion parser tests cover a neutral drawing, axis choice, invalid pen state, non-increasing time, and a nonfinite delta. The real challenge CSV replay produced the expected counts and readable path. None of this measures production false positives or proves exfiltration. I would tune on approved diagnostic clients and destinations, review the content and transfer evidence, then decide whether an alert is warranted.
