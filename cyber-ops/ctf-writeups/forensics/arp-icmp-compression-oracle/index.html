The Relay That Gave Away a Secret One Byte at a Time

I first picked the host at the center of the traffic graph. That answer was wrong. The useful clue was where the secret-bearing requests began.

Summary

The challenge. Identify the compromised server, the information taken, and the techniques used in a short network capture with TLS key material.

What I did. I mapped protocol and host conversations, inspected ARP and ICMP, decoded the POST bodies, then used the key log to examine the HTTPS response bodies and compare sizes.

The result. The case record identifies the victim as the source of the repeated flag guesses and reports an accepted CRIME answer. The HTTP response compression mechanism is more precisely BREACH-class.

The limit. The capture, key log, exact secret, and submission receipts are not reproduced here. Packet counts and acceptance are from the recorded solve; the linked defensive tools use invented events.

1. Problem Statement and Threat Scenario

I had a roughly 4.7 MB Ethernet capture covering about 45 seconds, plus a TLS session key log. The task was to find the compromised server, say what left it, identify the attack techniques, and explain how to stop a similar incident. I could inspect packets and decrypt the TLS leg with the supplied keys. I had no endpoint image or process telemetry.

Three roles emerged: a victim that generated secret-bearing requests, a host that handled both legs of the conversation, and a remote endpoint that returned compressed responses. The case uses a flag as the secret. In an application, the corresponding risk would be a token or another value placed beside reflected attacker input in a compressed response. The capture begins after any initial access. It can show traffic behavior, but it cannot establish how the attacker first controlled a host.

The story describes an ARP and ICMP assisted relay plus a length oracle. I treat each part separately. A packet proves a packet was sent; it does not prove the receiving kernel installed a route or that every observed size difference came from one compressor decision. Those require cache or route state and controlled comparisons.

Methodology notes

The wrong host answer was useful. The relay had the busiest conversations, so it looked important, and it was. It was still the wrong answer to "which server was compromised?" I went back to the POST bodies and asked which machine generated the secret-bearing guesses. That moved the answer to the victim. I kept the relay as a separate suspect for traffic interception and forwarding.

I also kept two kinds of visibility apart. The analyst with the key log could read the response token. Someone observing only ciphertext could see lengths and timing, but recovering the same token from size alone would need enough controlled guesses, stable framing, and verified response pairing.

3. Tooling and Scripts

3.1 tshark Reconnaissance One-Liners

These are the core pivots I would repeat against the capture. I would preserve the original PCAP and key log, work from copies, and restrict access to decrypted payload exports.

tshark -r capture.pcap -q -z io,phs
tshark -r capture.pcap -q -z conv,ip
tshark -r capture.pcap -Y 'arp' -T fields \
  -e frame.time_epoch -e arp.opcode -e arp.src.hw_mac -e arp.src.proto_ipv4
tshark -r capture.pcap -Y 'icmp.type == 5' -T fields \
  -e frame.time_epoch -e ip.src -e ip.dst -e icmp.code -e icmp.gateway
tshark -r capture.pcap -Y 'http.request.method == "POST"' -T fields \
  -e frame.number -e ip.src -e ip.dst -e http.request.uri -e http.file_data
tshark -r capture.pcap -o 'tls.keylog_file:tls_keys.log' \
  -Y 'http.response.code == 200' -T fields \
  -e frame.number -e tcp.stream -e frame.len -e http.content_encoding

The last command is for triage, not an oracle verdict. An HTTP message may span frames, and a frame can contain overhead or multiple records. I would compare complete, paired responses with equal-length guesses and a stable server path before attributing one byte to gzip.

3.2 Bulk HTTP Body Decoder

The recorded decoder converted http.file_data from hex, grouped by source and destination, and counted unique bodies. That is how the 288 distinct prefixes became readable. A practical revision also retains the frame number and order; sorting a set hides the sequence that matters to the prefix tree. Raw decoded bodies can contain secrets, so I would summarize shape and counts in ordinary logs and put any full-body export in restricted evidence storage.

import sys

for row in sys.stdin:
    frame, src, dst, raw = row.rstrip("\n").split("\t", 3)
    try:
        body = bytes.fromhex(raw).decode("utf-8")
    except (ValueError, UnicodeDecodeError):
        continue
    print(frame, src, dst, len(body), body.startswith("FLAG:"), sep="\t")

3.3 ARP Poisoning Detector

The recorded helper grouped ARP replies by MAC and declared poisoning when one MAC claimed more than one IP. I would keep the grouping but change the conclusion to a review signal. Virtual IPs, routers, and load balancers can use one MAC for several IPs. The detector also needs requests and replies with timestamps, authorized bindings, switch port, and the victim's neighbor cache to distinguish a suspicious claim from a successful poisoning event.

The linked offline network hunt implements the bounded multi-IP claim signal. Its guide states the normalized fields and its tests include a benign multi-address example that still triggers review.

3.4 CRIME Oracle Response Length Analyzer

The recorded analyzer grouped response frame lengths and intersected whitespace tokens in decrypted short responses. That can surface a candidate secret, but repeated headers or ordinary words can also survive the intersection. More importantly, a short frame does not automatically mean a correct guess. I would pair each request with its response, compare candidates of equal byte length, and repeat a known incorrect control after each candidate. I would avoid printing the token in a routine alert.

The linked hunt emits a length-oracle hypothesis only after a burst has two adjacent response sizes. That deliberately stops short of claiming extraction. It accepts normalized response byte counts; it does not decode TLS records or prove same-body compression.

4. Concept Explanation

4.1 ARP Cache Poisoning

ARP resolves an IPv4 address to a link-layer address on a local segment. It does not authenticate that binding. A forged reply can therefore induce a host to send frames toward an attacker-controlled interface. The recorded 128 reply frames and shared MAC claim fit that hypothesis. Whether the victim actually changed its cache is a separate observation. I would compare the claimed bindings to switch, DHCP-snooping, and endpoint neighbor records. MITRE's ARP cache poisoning entry describes both solicited and gratuitous reply paths.

4.2 ICMP Redirect Injection

ICMP Type 5 tells a host that another gateway is a better route; Code 1 is a host redirect. The five packets here advertised the relay. Modern host configuration and router-origin checks affect whether a host accepts them, so I cannot infer an installed route from their presence alone. For an incident, I would collect the route table and relevant kernel settings before and after containment. RFC 792 defines the message; local host policy decides whether to honor it.

4.3 CRIME and BREACH: Compression Ratio Side-Channel Attacks

The distinction changed how I explained the answer. CRIME originally exploited TLS-level compression of secret and attacker-controlled material. BREACH applies the same family of length inference to HTTP response compression. The case record says the challenge accepted "CRIME," and the recorded response header says Content-Encoding: gzip. The observed mechanism therefore belongs to the HTTP compression side of the family. The BREACH project describes that setting, and the Wireshark TLS guide explains what the key log changes for a forensic analyst.

4.4 The gzip / LZ77 Compression Oracle Mechanism

DEFLATE can encode repeated substrings compactly. When attacker-controlled text and a secret appear in the same compression context, a better match can shorten output. A remote or on-path observer may then infer a guess from response length. The exact output is affected by Huffman coding, headers, TLS record layout, TCP segmentation, and application variation. A one-byte frame difference is consistent with the idea; it does not, by itself, prove an LZ77 back-reference or leak exactly eight bits of secret.

The attack model is adaptive: hold the request shape steady, vary one candidate character, and compare response distributions against controls. The recorded 288 distinct guesses and prefix expansion support an automated search pattern. They do not supply, in this public account, a complete request-response pairing that independently proves every character was learned from ciphertext lengths.

5. Exploit/Analysis Mechanics

5.1 Establishing the MITM Position (ST.3, ST.4)

The ARP stream lasted through the short capture, and the five redirects appeared early. The two mechanisms could have steered traffic through the relay. The flow graph then showed plaintext POSTs on the victim-to-relay leg and TLS sessions from relay to the remote endpoint. That combination is stronger than the ARP count alone. I still cannot see the victim's ARP cache, accepted route, or the operator's installation actions.

The relay's recorded Werkzeug/Python banner is a triage lead. Werkzeug can also belong to a legitimate service, and a banner cannot establish persistence. I would identify the owning process, deployment record, and listening socket before calling it attacker tooling.

5.2 Decrypting the Relay Leg (ST.6)

The TLS key log was decisive for my forensic view. Tshark can use session secrets supplied in NSS key-log format to decrypt matching TLS traffic. The case record says that exposed the forwarded POST guesses and response bodies. I would not publish the key log: it is secret material for these sessions. Nor would I assume all enterprise TLS can be decrypted this way; collection must be deliberately enabled, protected, and lawful. Wireshark's guide covers the decryption prerequisite.

5.3 The Oracle in Detail: LZ77 Back-Reference Arithmetic (ST.7)

The recorded 342- and 343-byte buckets made me look for a length oracle. They were reported for 200 responses on the TLS leg. To confirm the mechanism, I would map each prefix guess to one complete response, normalize the variable fields, and repeat equal-length correct and incorrect candidates. Then I would compare compressed body lengths and ciphertext record lengths separately. Without that controlled pairing, packet length can be a confounder.

This is also why I would avoid calling the delta "eight bits leaked." A one-byte difference in output length can signal a yes/no comparison, with noise and false positives. The signal does not disclose eight secret bits directly.

5.4 Flag Recovery (ST.9)

The recorded decrypted bodies contained a constant second token holding the flag. That gave the analyst a direct recovery path. The changing submitted prefixes, including the branch that matched, are consistent with a character search. The case record says guesses continued beyond the matching suffix, so the search may have exhausted a character set before moving on. I cannot prove the attacker's exact loop from that fact.

I withheld the actual secret. The meaningful result is the distinction between direct decryption during analysis and an on-path compression oracle as an attack capability. The former is documented in the solve. The latter is a credible mechanism that needs the controls described above to reproduce confidently.

6. Lessons Learned (Practitioner Perspective)

What the Exercise Validated

Starting with protocol hierarchy and IP conversations kept me from getting lost in thousands of frames. The small ICMP count was worth inspecting, and the key log opened a view that ciphertext alone could not provide. The POST bodies gave the answer to the host question because they showed where the secret-bearing guesses began.

What the Exercise Surfaced as Gaps

My first host submission was wrong. I had treated the relay's central position as proof that it was the compromised server. The rejection pushed me to trace data origin instead of traffic volume. In a real response, I would investigate both hosts: one may hold the sensitive data, and another may be the forwarding foothold. I would not infer the initial intrusion path from these packets.

The source's detector ideas also needed more careful boundaries. A multi-IP MAC is a review signal, an ICMP redirect is a message rather than a confirmed route change, and two response lengths do not prove secret recovery. I kept those signals but attached the extra checks they require.

Transferable Principles

7. Extrapolation

7.1 Individual Practitioner Skill Development

This case made me practice four separate jobs: mapping a capture, reconstructing a relay, handling TLS session secrets, and judging a side-channel claim. The last job required the most restraint. A pattern can point me toward a mechanism while leaving the mechanism unproven. I would next run a controlled application test that toggles compression and compares paired responses without placing a real secret in the fixture.

7.2 Security Operations (SOC, IR, Threat Hunting)

I would hunt for the sequence, not one magic threshold: repeated unauthorized ARP claims on a switch port, redirects from a host that is not an approved gateway, a server generating many similarly shaped POSTs, and a relay making outbound TLS connections. The offline hunt models those four signals from normalized events. Its results are review queues, not incident verdicts.

For containment, I would preserve volatile host and switch state as the situation allows, isolate the suspected relay and victim, and repair the binding or route condition. Flushing caches alone would be temporary if the source kept sending forged replies. The order of imaging and isolation depends on live risk and collection capability; I would not keep an active exfiltration path open just to preserve memory.

7.3 Intelligence Operations (SIGINT, IO, Attribution)

Size and timing remain visible around encrypted sessions, which makes this case useful for traffic-analysis thinking. They do not identify an actor. Werkzeug, nginx, and a relay-shaped topology are common technology choices, so I would use them to pivot across local evidence, not to attribute a campaign. A production intelligence report would need infrastructure history, repeated tooling fingerprints, and independent corroboration.

8. Reusable Tools, Scripts, and Artifacts

8.1 PCAP Triage Decision Tree

My sequence is: map protocols and conversations; inspect ARP sender claims and ICMP redirect senders; identify request origin; apply available TLS keys under evidence controls; pair guesses and responses; compare sizes with equal-length controls. At each stage I keep a separate column for observed packets and inferred host behavior. The tool guide defines a small normalized schema for the post-capture hunt.

8.2 CRIME / Compression Oracle Assessment Checklist

For an authorized application review, I would check whether a secret and attacker-controlled input enter one compressed response; whether a client can generate many chosen requests; whether an observer can measure a stable response length; and whether equal-length candidate and control guesses produce repeatable differences. Disabling compression on the affected secret-bearing response or separating the secret from reflected input removes the central condition. Random padding may add noise but should not be the primary fix. HTTP/2 is not a generic cure for HTTP response compression.

10. Threat Intel and Standards Integration

10a. STIX 2.1 Sample SDOs

I would represent the observed behavior as an attack pattern or incident note with a source reference and confidence, then keep sanitized IP and MAC placeholders out of machine-actionable indicators. The source included illustrative STIX objects, but their redacted UUIDs and timestamps are not valid deployable STIX IDs, and a network-traffic pattern on a generic byte count would not capture "two response buckets across a burst." A real bundle needs valid IDs, SCO relationships, indicator semantics, and schema validation before TAXII sharing. No TAXII exchange occurred.

For a sample machine-readable case that a team could adapt, I would start from an internal normalized event record: arp_reply_claim, icmp_redirect, post_burst, and response_length_pair, each with source sensor, timestamp, host role, and confidence. That is the same boundary the offline hunt uses. A detection hypothesis is not an IOC until a concrete, reliable value is established.

10b. STIG References

The source named specific STIG V-IDs for redirect acceptance and switch inspection. I would verify those identifiers against the exact platform and benchmark revision before a compliance ticket. The technically relevant checks are whether hosts accept redirects, whether switches inspect ARP on the affected VLAN, and whether exceptions for static bindings are documented. A packet capture cannot establish STIG compliance.

10c. CIS Controls v8

CIS Controls for protecting data in transit, securing network architecture, and monitoring network infrastructure are pertinent to the path. The source's safeguard numbers are useful search leads, but I would verify the current text and implementation group before claiming a formal mapping. The case tests behavior, not an organization's CIS conformance.

11. Controls Mapping and Mitigation Realization

11a. Standards Mapping

Control Design question this case raises
NIST SC-8 Is the victim's service traffic protected across its real trust boundary?
NIST SC-23 Does the client authenticate the intended service, and does the service authenticate authorized clients?
NIST SC-7 Can an untrusted relay host share the L2 segment or reach the remote endpoint?
NIST SI-4 Can the team see ARP claims, redirect attempts, and repeated application requests?
NIST IA-3 Are device identity and switch-port bindings available for this environment?

These are proposed applications of controls. I did not assess a deployed system.

11b. Mitigation Realization

I would start at the application: avoid placing a secret beside reflected attacker input in a compressed response. Disable response compression for that endpoint if the response must carry a secret. I would test the actual deployed route and verify the response headers and body sizes after the change.

Next I would protect the path: authenticated TLS or mTLS where service identities are controlled, segmentation and explicit egress policy, Dynamic ARP Inspection where the switch and binding source support it, and host policies that reject unneeded ICMP redirects. The source included illustrative nginx, Cisco, firewall, and sysctl snippets. I would adapt each to the actual platform and verify the effect, including static-IP binding exceptions. A standalone add_header Content-Encoding "" is not a reliable way to undo upstream compression, and random spaces appended to a response are not an adequate padding control.

The test I would ask a purple team to run is bounded: generate invented prefix guesses against a nonsecret fixture, collect raw and normalized network events, confirm the hunt raises the expected hypotheses, then turn off compression and check that the size distinction disappears while the app still functions. Re-run with a legitimate multi-IP MAC and an authorized redirect to measure expected false positives.

12. Indicators, Artifacts, and Detection Engineering

The detection work here is scaffolding. It has synthetic tests but no deployed sensor, SIEM conversion, or production false-positive rate.

12a. IOCs (Sanitized / Illustrative)

The source identifies a MAC that claimed two IPs, a relay address, a remote address and port, /ping, and a Werkzeug banner. Their values are placeholders here, not deployable block indicators. A URI or banner is weak alone. I would preserve exact values in the incident record, then decide whether any is stable and specific enough for sharing.

12b. Sigma Rules

The source drafted Sigma-like rules for a multi-IP ARP MAC, unauthorized ICMP redirect, and high POST rate. The aggregate group-by, having, and timeframe blocks in those examples are not portable Sigma detection syntax; zeek_arp and zeek_icmp are not guaranteed standard Zeek logs. I would normalize packet or switch telemetry first, convert simple event selections with a supported backend, and implement the cross-event count in the SIEM. The local tests exercise that count logic on invented records, including a benign multi-address MAC.

12c. Splunk SPL Detection Queries

An SPL translation needs a real data model. The source's ARP query grouped by exact _time, which would often separate the claims it wanted to correlate. A starting pattern after mapping fields is:

index=network event_type=arp_reply
| bin _time span=1m
| stats dc(claimed_ip) as ip_count values(claimed_ip) as ips by _time, src_mac, switch_port
| where ip_count > 1

That is a review queue and needs an authorized-binding lookup. For redirects, compare sender IP against an approved gateway lookup. For POST bursts, group by source, destination, URI, and minute. For a suspected oracle, retain per-response sizes and pair them with the corresponding request before testing a two-bucket distribution. These are query designs; I have not run them against a Splunk backend.

12d. Log Source and Data Pipeline Requirements

ARP needs L2 packet capture, switch inspection events, or endpoint neighbor state. ICMP needs packet or host telemetry that retains type, code, sender, and advertised gateway. HTTP requests need method, endpoint, timestamp, and source identity. The length hunt needs a response-size measurement that is consistent across the same leg and a reliable request-response key. A TLS key log adds plaintext for authorized forensics, but it is sensitive evidence and is not required to observe outer packet lengths. Zeek's current standard log list does not promise arp.log or icmp.log; those would require a known local package or custom pipeline.
