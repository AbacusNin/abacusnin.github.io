The Source Line I Could Not See

The line looked ordinary in the editor. Its bytes told a different story.

Summary

The challenge. Find an unseen change in a note-taking application's source history, decode it, and recover the embedded flag-format value.

What I did. I compared raw bytes with rendered text, identified Unicode Tags, decoded their ASCII content, isolated the XOR arithmetic, and counted Tags across commits.

The result. The case record reports a recovered flag-format value and a mid-history insertion; the network-bearing tail was not executed.

The limit. The repository, commit hash, original payload bytes, and flag are withheld, so the linked defensive lab uses synthetic fixtures.

1. Problem Statement and Threat Scenario

The developer of a small Python note-taking app believed someone had changed the repository before a commit. The odd part was that the altered line still looked harmless during review. I had the source tree and Git history, and I needed to find the change, decode what it carried, and recover the hidden flag-format value. I did not need to run the app.

This was an adversarial CTF story with a concrete source-integrity problem. A malicious contributor could put extra bytes into a file that a reviewer sees as ordinary text. The protected boundary was the source-to-commit review, and the downstream risk belonged to anyone who later built or ran compromised code. The decoded content described an outbound request and a second-stage fetch. That gave me a reason to treat it as hostile content during analysis.

The page makes a narrower claim than a full compromise story. I found and decoded the hidden content and traced its appearance in history. I did not execute the decoded network code or observe a victim system making either connection. A hidden comment or string does not run by itself; a separate loader or execution path would have to use it.

2. Techniques, Tooling, and Actions Taken

I started with the simplest question: which tracked file had bytes that the editor might hide? I cloned the repository, inventoried tracked files, and checked size, line count, and SHA-256. A raw scan found non-ASCII bytes in exactly one file, the app entrypoint. That brought a repository-wide mystery down to one line.

The first count was misleading. My byte scan treated each UTF-8 byte outside ASCII as a separate mark. These characters live outside the Basic Multilingual Plane and take four UTF-8 bytes each, so the count was about four times the number of hidden code points. I switched to a Unicode-aware read and listed the code points. They fell in the Tags block around U+E0020 through U+E007E.

Those Tag characters can carry printable ASCII by subtracting 0xE0000 from each code point. I decoded them in order and got Python source text. I read that text. I did not execute it. For the flag, I lifted only the byte-array and repeating-key XOR arithmetic into an isolated calculation. That produced the flag-format value without touching the code that built an outbound URL or fetched another binary.

I then checked Git history for the affected file, counting Tag characters in each committed version. The first increase identified a mid-history insertion. The available account does not include the commit ID or the original file bytes, so I cannot reproduce that attribution here. The method and the synthetic detection lab below show exactly what I would preserve in a real review.

3. Tooling and Scripts

My first pass looked for bytes outside ASCII. A byte count is a quick locator, while the next step needs a character count. A shell loop that splits filenames on spaces can also miss files. This small Python fragment shows the safer code-point step after I have identified a suspect file:

from pathlib import Path

data = Path("app.py").read_text(encoding="utf-8")
tagged_ascii = "".join(
    chr(ord(char) - 0xE0000)
    for char in data
    if 0xE0020 <= ord(char) <= 0xE007E
)
print(tagged_ascii)  # inspect the recovered text; do not execute it

That range is deliberate. U+E0001 is LANGUAGE TAG and U+E007F is CANCEL TAG. I count them as Tag characters, but I do not convert them into printable payload bytes. The read-only scanner reports code points, file hash, location, and decoded Tag runs. Its guide gives the directory and CI usage.

The redacted payload's flag calculation used a short XOR key more than once. A faithful generic form is:

def repeating_xor(ciphertext: bytes, key: bytes) -> bytes:
    if not key:
        raise ValueError("empty key")
    return bytes(value ^ key[index % len(key)] for index, value in enumerate(ciphertext))

I ran the equivalent arithmetic on the embedded values alone. The source text's network-bearing statements stayed inert. For attribution, I reviewed committed versions of app.py and compared Tag counts; git log --format=%H -- app.py identifies revisions to examine, and git show <commit>:app.py retrieves a committed blob for byte-aware inspection. I did not use commit authorship as proof of a person's identity.

4. Concept Explanation

Unicode gives each character a code point; UTF-8 encodes that code point as bytes. A printable ASCII Tag component at U+E0020 through U+E007E corresponds to an ASCII character at 0x20 through 0x7E. The arithmetic is simple: tag_codepoint - 0xE0000 = ascii_codepoint. The Tags block also contains special characters, including LANGUAGE TAG and CANCEL TAG. They are part of the block, but they are not ordinary printable payload characters.

These characters can be hard to see in editors. Twenty Tag characters occupy eighty UTF-8 bytes in the synthetic carrier, yet its line renders much shorter. That same fixture decodes to the harmless text print("review only"). It sits in a Python comment and has no effect when the file is interpreted. A real attack needs a code path that reads, decodes, and uses the hidden content. The recovered source in this case described such hostile actions, but I did not observe them run.

Tag sequences also have benign uses, including subdivision-flag emoji. The emoji fixture is an expected detection hit, not malicious code. The distinction matters when this becomes a pre-commit check. I cannot label every Tag character an intrusion.

This is related to Trojan Source, which used bidirectional controls and confusable characters to make reviewed text differ from program behavior. My case carried hidden ASCII source in Tag characters. The shared review problem is that a rendered line does not reveal every byte it contains. The mechanisms are different.

The second decoding step was repeating-key XOR. I XORed each ciphertext byte with the matching key byte, wrapping the key index with % len(key). XORing again with the same key recovers the original bytes. The key and ciphertext were embedded together, so this was an obfuscation layer over the flag, not a claim of strong encryption.

5. Exploit / Analysis Mechanics

The first boundary crossed was visual review. The file's bytes included a run of Tag characters that the editor did not make obvious. I located them through a repository-wide byte scan, decoded the printable Tag components to ASCII, and got source text. The content included an XOR-protected flag value, an outbound URL-building path, and a curl second-stage fetch. Only the decode and isolated XOR calculation were needed to solve the challenge.

My local proof of the flag did not depend on a network connection. I decoded the embedded bytes with the repeating key and checked that the result had the expected flag structure. A separate decoding route reproduced it according to the case record. The raw flag remains withheld. The record does not provide an organizer acceptance transcript, so I make no platform-acceptance claim.

Counting Tags in each committed blob showed when the invisible content entered the history. That establishes insertion timing within the repository. It does not by itself identify the actor, prove that the app executed the hidden text, or prove a download or exfiltration occurred. Those would require loader analysis, build provenance, and runtime evidence.

6. Lessons Learned

The prompt said the developer could not see the change. I treated that as a representation problem before looking for a subtle logic bug. One raw-byte pass put me on the right file. The four-to-one count mistake was useful: it forced me to separate UTF-8 bytes from Unicode code points, which made the hiding method clear.

Static decoding gave me the flag without letting the recovered source do anything on my machine. That separation is worth keeping. A decoded line can describe a dangerous command while remaining only text in the analyst's workspace.

Git history was the last step, not a substitute for the byte work. I could date the insertion by looking for the first committed version with Tag characters. I would still preserve the parent and child blobs and review any build or loader path before telling a team what ran.

7. Operational Extrapolation

Individual Practitioner Development

This case sharpened my source-integrity workflow: inventory, compare raw bytes and rendering, classify code points, decode in a read-only path, and then use Git history for timing. The next step would be to run the scanner in a real review pipeline with a controlled allowlist and measured false-positive rate. I have not deployed it there.

Security Operations

At commit or CI time, the relevant sensor is the repository content itself. A hit on invisible characters deserves a focused review of the line, the decoded text, the commit, and any code path that consumes it. The YARA rule gives a fast byte-level lead; the Python scanner gives code-point counts and locations. The review checklist walks from preservation to a scoped response.

For runtime hunting, MITRE's DET0920 describes correlating hidden Unicode in a script with decode or evaluation behavior and later process or network events. That is a proposed extension here. I would need file hash or script identity, execution telemetry, child-process events, and network connections tied to the same process or time window. None of those live events were collected in this exercise.

Intelligence Operations

The decoded code's fetch and outbound URL are leads for a real investigation, where I would preserve the exact destination and compare it with network logs and other samples. The sanitized case gives me no shareable infrastructure IOC or actor attribution. I would not connect it to a campaign from the hiding method alone.

8. Reusable Tools, Scripts, and Artifacts

The Unicode scanner reads a file or source directory without importing or executing it. It reports Tag, zero-width, bidi, joiner, and embedded-BOM code points, a SHA-256 hash, byte size, line and column, and Tag-run length. --show-decoded emits at most 500 ASCII characters per run in JSON; default output does not print hidden text. Exit codes distinguish clean input, a finding, and incomplete scanning. The guide lists its suffix filters, file and count caps, and CI boundary.

The separate YARA rule looks for UTF-8 byte prefixes of Tags and selected controls. It compiled under yara-python 4.5.4 and matched the synthetic carrier. It left the ASCII control and visible-accented control clear. Both scanner and rule also flag the legitimate emoji Tag sequence, an expected false positive. The test file checks those cases, special Tags that must not decode to ASCII, and a bidi control.

The review checklist gives a human workflow for preserving the blob, decoding in isolation, checking a loader, and tracing a commit. The behavior bundle is an illustrative STIX 2.1 Attack Pattern, Course of Action, and relationship. It has no Indicator or challenge IOC. These are new, synthetic defensive assets. They do not replay the original repository or validate a production pipeline.

9. Framework Applicability and Mapping

The strongest fit is ATT&CK T1027.018, Invisible Unicode. The case's Tag bytes concealed source content from ordinary visual review. MITRE's GlassWorm example uses private-use characters rather than this case's Tags block; it supports the broader family, not a claim that these are the same sample.

10. Threat Intelligence and Standards Integration

The illustrative STIX bundle has an Attack Pattern for the hidden-Unicode method and a proposed Course of Action for source review. The relationship says the review can mitigate that pattern. It contains no IP, domain, hash Indicator, actor, or campaign. Its JSON and internal object references passed local checks; I did not run a full STIX schema validator or publish it through TAXII.

A filename-only pattern such as [file:name MATCHES '.*\\.py$'] would match ordinary Python files. It cannot assert that a file contains Tag characters, so it would be a misleading Indicator for this case. The scanner and YARA rule express the content test more directly. A future real incident could add file hashes and observed infrastructure with their own provenance and expiry.

Mitigation Realization

I would place the scanner at a review or CI boundary and require an explicit decision on each hit. The YARA rule can quickly identify files for deeper code-point inspection. Both were validated against synthetic files. Neither has been wired to a production repository, tested at scale, or given a production allowlist.

The checklist makes the human step concrete: preserve the raw blob and commit, decode without execution, inspect the loader path, and distinguish legitimate Unicode uses. Protected branches and signed commits can improve provenance and gate changes, but a signed commit can still contain hidden bytes. Those repository controls are proposals here, not proof that the code is safe.

12. Indicators, Artifacts, and Detection Engineering

The primary observable is the raw source file. Tag code points in the U+E0000 to U+E007F area, selected zero-width and bidi controls, and an unusual gap between byte length and visible line length can justify inspection. These are structural leads, not malicious IOCs by themselves. A legitimate emoji Tag sequence is the clearest counterexample in the fixtures.

The scanner takes files or a directory and emits JSON findings and errors. For each hit it records path, SHA-256, byte count, code-point category and count, and up to 100 positions. The YARA rule checks a smaller byte-pattern set. A commit/CI implementation needs raw file access, repository and commit identifiers, the scanner version, a protected result log, and a path-specific allowlist review. Scan errors must fail the gate or route to manual review; they cannot count as clean files.

On the synthetic carrier, the scanner reports 20 Tag characters and 80 corresponding UTF-8 bytes. It decodes the placeholder only when asked. The clean file and visible Unicode file produce no findings. The emoji fixture is a deliberate benign hit. The tests check these cases and the special Tag boundary. YARA compiled and matched the same positive and negative files, including the benign emoji hit. This establishes local behavior, not a measured field false-positive rate.

The runtime hypothesis is separate. DET0920 looks for hidden Unicode associated with decoding or evaluation and later process or network behavior. A real hunt would join file hash or script identity to process creation, child processes, and outbound connections. I have no such telemetry from this exercise, so that hunt remains Proposed. I would not treat the decoded curl text as a network event.
