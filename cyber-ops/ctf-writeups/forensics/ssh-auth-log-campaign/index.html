The 618 Lines My First Regex Missed

My first service count looked tidy: one daemon, 1,782,247 lines. The file had 1,782,865 lines. Those missing 618 were the important part.

Summary

The challenge. Triage one month of Linux authentication logs for exposed services, targeted accounts, unusual protocol traffic, dominant sources, and infrastructure ownership.

What I did. I counted the file, tested the service parser against that total, ranked password failures and connection closures, examined HTTP-like SSH banners, and traced the dominant address to a published prefix listing.

The result. The corrected service inventory included sshd and an FTP daemon. Root led password failures; one address led closure volume. The ASN finding remained secondary-source enrichment.

The limit. The recorded solve did not test accepted logins, cross-service source overlap, or hourly behavior. The linked defensive tools are tested on synthetic records only.

1. Problem Statement and Threat Scenario

I had one artifact: a roughly 180 MB /var/log/secure file from an internet-facing, RHEL-like Linux host. It covered about 30 days and contained 1,782,865 lines. There was no SIEM view, packet capture, host configuration, or live target. The questions were practical: which services wrote to this file, which accounts were hit hardest, what odd traffic reached SSH, which address dominated, and whose network that address belonged to.

The shape of the traffic suggested automated password guessing from outside the host. That is a working hypothesis, not a claim that an actor got in. A log of failed attempts can tell me who tried; it takes success records and more context to establish whether the authentication boundary was crossed. The FTP daemon mattered for the same reason. Its presence was observed, but this record did not determine whether it was authorized, whether its users were attacked, or whether its source addresses overlapped the SSH activity.

2. Techniques, Tooling, and Actions Taken

I worked offline. The one outbound step was the later ASN lookup. I kept each attempted route because the two failed regular expressions explain how an ordinary triage query can turn into a confident wrong answer.

Step What I did What came back
ST.1 Extracted secure_log.zip, counted lines, checked the ends of the file. 1,782,865 lines over about 30 days.
ST.2a Extracted a service only when its name was followed by [pid]. sshd looked like the only service, but the count was 618 short. Rejected.
ST.2 Ended the service name at either [ or :. sshd 1,782,247 plus FTP daemon 618, exactly the file total.
ST.3 Captured names after both for user and for invalid user. root had 184,393 failed-password lines; the leading non-root name had 4,208.
ST.4 Searched for http, then read the actual SSH diagnostic and request bytes. HTTP-like methods appeared in a protocol-version error.
ST.5a Looked for closure addresses after from. Empty result. Wrong message template. Rejected.
ST.5 Read addresses after Connection closed by. Top address 150,314 closures; second 32,174, about 4.67 times lower.
ST.6a/b Tried local whois, then an HTTP lookup service. whois was absent; egress policy blocked the API.
ST.6 Compared published prefix listings for the redacted address. A covering /16 was attributed to the same redacted AS in several listings. This was secondary-source enrichment.

The closure count is a count of log messages, not 150,314 distinct attempts. I never saw a transcript establishing successful authentication for the address. The AS identifies infrastructure associated with a prefix at a point in time; it cannot identify the person operating a cloud instance.

Methodology note: ST.2a, the failure that looked like a success

The first service expression required a process name immediately followed by a PID bracket. It ran without error and produced 1,782,247 sshd. That result looked reasonable in an SSH-heavy log. I only caught the omission because I had already counted every line. The subtraction was simple: 1,782,865 minus 1,782,247 equals 618. The FTP daemon used a bare colon after its process name, so the lookahead never matched it.

I changed the terminator to accept [ or : and recounted. This time the service buckets summed to the file total. That check made the negative claim, "nothing else is here," defensible. The separate ST.5a error was easier to spot because it returned nothing at all. A parser that returns plausible but incomplete output is the more dangerous failure.

Methodology note: enumerate before you query

I needed to learn which services were present. Grepping for sshd would only confirm the service I already knew to ask about. Extracting the process token from each line let an unknown service appear in the result. The coverage sum then tested whether the extractor was complete. A third service, if present, could have surfaced without a new guess.

Methodology note: know your enrichment provenance

I would have preferred a direct, current routing or registry source for the AS answer. My local environment lacked whois; the lookup API was beyond its egress allowlist. Published prefix tables agreed on a /16, but their update time and routing view were not established in this record. The containment calculation was straightforward. The underlying source was the weak point, so I kept the ASN conclusion qualified. A provider AS is also a poor stand-in for an attacker identity.

3. Tooling and Scripts

The solve used shell pipelines. I did not run a purpose-built parser during the challenge. These are the decisive commands, with the case's host and addresses withheld:

unzip -p secure_log.zip > secure.log
wc -l secure.log
head -1 secure.log; tail -1 secure.log

# ST.2a, rejected: loses a service whose name ends at a colon.
grep -oP '<target-host> \K\S+(?=\[)' secure.log | sort | uniq -c | sort -rn

# ST.2: capture the process token before either delimiter.
grep -oP '<target-host> \K[^\[:]+' secure.log | sort | uniq -c | sort -rn

# ST.3: valid and invalid-user SSH templates.
grep 'Failed password' secure.log \
  | grep -oP 'for (invalid user )?\K\S+(?= from)' \
  | sort | uniq -c | sort -rn | head -20

# ST.4: inspect the messages before naming the invariant text.
grep -i 'http' secure.log | head -20

# ST.5: sshd says 'Connection closed by', not 'from'.
grep 'Connection closed by' secure.log \
  | grep -oP 'by \K[\d.]+' | sort | uniq -c | sort -rn | head -10

The first ST.5a query had used from \K[\d.]+ after filtering closure lines and returned no address. I retained that miss because Failed password ... from <IP> and Connection closed by <IP> are different templates. For the ASN fallback, the attempted paths were whois <address>, an HTTPS lookup, and then the published prefix listings. The first two did not complete here:

whois <REDACTED_IP> | grep -iE '^(origin|aut-num)'
curl -s 'https://api.hackertarget.com/aslookup/?q=<REDACTED_IP>'

A Team Cymru reverse-octet DNS query or current BGP route view would be useful independent follow-up, but neither was performed in this solve. For an address a.b.c.d, the proposed DNS form was dig +short d.c.b.a.origin.asn.cymru.com TXT. The returned route and observation time would still need interpretation before I called the AS confirmed.

The offline auth-log triage script, invented log fixture, and tests are later defensive examples. Their usage notes state the input, output, and limits. They were not used to produce the counts above.

4. Concept Explanation

/var/log/secure is a shared authentication log on this RHEL-like host. Its familiar header looks like <time> <host> <process>[pid]: <message>, but the FTP service showed that a PID bracket is not universal. The message body is free text emitted by each process. That is why I first counted process tokens and only then parsed event-specific wording.

A single SSH session can emit multiple lines: a reverse-name warning, a PAM failure, a Failed password result, and a closure. Total lines therefore are neither unique sessions nor unique guesses. They are still useful as a coverage denominator, provided I do not turn them into attempt counts. The username parser has to handle both Failed password for root from ... and Failed password for invalid user guest from ...; the optional phrase changes the location of the account token.

The HTTP-looking traffic has a different boundary. RFC 4253, Section 4.2 describes the SSH identification string beginning SSH-. A request starting GET, POST, HEAD, CONNECT, or the HTTP/2 PRI preface does not satisfy that exchange. In this log, sshd wrote a Bad protocol version identification message and included the quoted bytes it received. That is evidence of protocol mismatch at an SSH listener. It does not, from this one host, establish a scan of whole IP blocks or the scanner's intent.

For the network lookup, an IP-to-AS answer depends on routing data and time. A more-specific BGP route can supersede a broad covering prefix, and a prefix may have multiple origins. A published /16 match is therefore a lead to check against a current routing view. Even a confirmed origin AS would identify a network, not the user of a rented server.

5. Analysis Mechanics

The strongest measurement in the case is the service-coverage invariant: the first extraction accounted for 1,782,247 of 1,782,865 lines; the corrected extraction accounted for all of them, including 618 from an FTP daemon. In a real ingest pipeline I would keep an explicit unparsed bucket rather than silently drop messages and call the remaining sum complete. The triage script does exactly that for classic syslog headers.

For ST.3, the optional invalid user group captures both SSH failure templates without removing root. I ranked all names first. Root's 184,393 failures are part of the evidence; excluding it before counting would hide how strongly generic scanners target it. The top non-root name had 4,208 failures. Neither number alone tells me how many passwords were tried, because passwords are absent from the log.

ST.4 required reading across several matching messages. The fixed leading words were Bad protocol version identification; the quoted request and trailing address varied. I separated that diagnostic from its argument instead of treating a request path as the error text. ST.5 required the same care with one preposition. The top closure source's 150,314 messages compared with 32,174 for second place give me a clear investigative priority. A misconfigured authorized client could also be noisy, so I would review account names, timing, successes, and asset ownership before calling that address malicious. A distributed, low-rate campaign could evade a top-IP sort entirely.

The enrichment step was weaker than the log parsing. Agreement among republished prefix listings made the redacted AS plausible. I did not obtain a time-specific RIR or BGP confirmation. That uncertainty stays with the conclusion.

6. Lessons Learned

The 618-line discrepancy is the result I would remember from this exercise. An empty query asks for a fix. A nearly complete query can end an investigation too early. Counting the source file gave me a cheap way to challenge the service parser before I used its answer.

The solve also stopped short of the most consequential host question. I did not check Accepted messages. A failure-to-success sequence from the same address would raise the priority sharply, but even an Accepted line would need account, timing, and session context before I called it a compromise. I did not correlate the FTP source addresses with SSH, bucket the traffic by hour, or establish whether the FTP service was intended. Those are open investigative steps, not findings.

One other lesson is about names on a framework chart. A technique ID can look as polished and as wrong as my first regex. I checked the ATT&CK and D3FEND definitions before using them below. I left the narrow Scanning IP Blocks claim out because a few HTTP-like requests to one host do not show an address-range scan.

What failed or worked here What I would carry into operations
Service counts reconciled to raw lines. Compare normalized event coverage with raw ingest and retain an unparsed bucket.
Enumerating all process names exposed FTP. Inventory every authentication-bearing service before scoping collection or rules.
The closure parser assumed from and found nothing. Test each daemon template with positive and near-miss samples.
The AS lookup fell back to republished data. Record source, timestamp, prefix, and whether routing was verified.
No success or time correlation was run. Hunt for success after failure, cross-service overlap, and rate changes.
7. Extrapolation

For a host-response team, I would start with the auth log, then join any successful SSH authentications to the ranked failure sources and affected accounts. I would inspect whether those accounts received sessions and what they did next. I would review the FTP records separately and compare their source set with the SSH set. A shared IP would be a lead, not proof of one operator. Hourly rates, source-to-account cardinality, and authorized scanner inventories would help distinguish bursts, stale automation, and deliberate guessing.

For a security-operations pipeline, the important design choice is to collect all authentication services and measure parser coverage. A rule that sees only sshd can look healthy while missing the 618 FTP records. Success correlation and an unmapped-event alert belong beside the volume detector. The HTTP-to-SSH diagnostic is useful for service-discovery context, but I would not page an analyst on a single HTTP banner.

For intelligence work, an origin AS can group infrastructure and suggest which provider to contact. It cannot attribute the campaign. I would preserve the lookup date and source and check a current route view before using the AS in a report or block decision. Broad cloud-AS blocking would need its own impact review.

8. Reusable Artifacts

Triage checklist: internet-exposed Linux host, auth log only

[ ] Preserve the log and record size, total lines, and time window.
[ ] Enumerate all process names, including services without PID brackets.
[ ] Reconcile service counts plus unparsed headers to the raw line count.
[ ] Rank failed passwords by account and source; retain root in the count.
[ ] Count connection closures separately; do not call them unique attempts.
[ ] Read quoted protocol-mismatch bytes for scanner context.
[ ] Check Accepted events and join by source, account, host, and time.
[ ] Review FTP failures and compare FTP and SSH source sets.
[ ] Bucket rates over time and check authorized automation or scanners.
[ ] Record the route/ASN source, timestamp, prefix, and uncertainty.

Reusable primitive: sshd template patterns + the coverage assertion

The reusable part is a small template map plus an accounting rule. A service parser must accept either [pid]: or a bare :. A failed-password parser must allow invalid user; closure extraction must look after by. For each line, either assign a service or increment an explicit unparsed count. Check sum(service_counts) + unparsed == total_lines before trusting the ranking.

I put those checks in the offline parser with an invented nine-line fixture, an unparsed-header fixture, and three parser tests. The tests cover a non-PID FTP header, two failed-password forms, a closure, an HTTP-like SSH banner, a failure followed by success, a benign success without a preceding failure, a bad address, an unparsed header, and a line-length rejection. These results test the example logic. They do not reproduce this case's 1,782,865-line analysis or establish detection accuracy on a real environment. The artifact guide describes field assumptions and sensitive output.

10. Threat Intel and Standards Integration

The source IP, prefix, ASN, and reverse-mapping domain are withheld here. The useful intelligence is behavioral: repeated SSH password failures, unusually high closure volume, and HTTP-like bytes at an SSH listener. An ASN is infrastructure context that can age as routing changes. The domain in a reverse-mapping warning can be a failed lookup or untrusted client-controlled string; I would verify it before treating it as an indicator.

I did not create a shareable STIX indicator from a redacted placeholder or claim a TAXII feed received one. In a live case I would package a verified address with valid_from, confidence, source, and expiry appropriate to the indicator's lifetime; I would keep the behavior and analytic context alongside it. The exercise did not supply that verified, current IOC set.

I also do not assign a STIG finding. The log shows that root was targeted, not that root login was permitted. It shows FTP records, not that FTP was unauthorized. Those are configuration questions to inspect on the host. The concrete hardening and logging intent appears in Section 11.

11b. Mitigation realization

I would first confirm how SSH is really configured, which auth methods are active, and whether keys or another approved method work for every authorized user. For a host that can safely require keys, PasswordAuthentication no, KbdInteractiveAuthentication no, and PermitRootLogin no are candidate settings. Check effective settings with sshd -T, test a second live session, and reload only after that check. Disabling one password path while PAM or another interactive path remains active does not prove password guessing has been eliminated. MaxAuthTries 3 limits attempts per connection, not across new connections.

A fail2ban SSH jail can use maxretry = 5, findtime = 600, and bantime = 3600 as starting values if the daemon, filter, log path, and firewall action are verified on the actual distribution. Test the parser and a permitted recovery path before enforcement. A short ban slows a high-rate source; it can also be abused to lock out legitimate users. For the FTP service, inspect ownership and business need before disabling it or removing its firewall exposure. The 618 records alone do not warrant a production shutdown.

# Candidate /etc/fail2ban/jail.d/sshd-custom.conf; verify log path and action.
[sshd]
enabled = true
port = ssh
filter = sshd
logpath = /var/log/secure
maxretry = 5
findtime = 600
bantime = 3600

The SSH settings below express the intended authentication posture, not a drop-in change for an uninspected host. ChallengeResponseAuthentication no appears in older configurations; check the installed OpenSSH version and effective KbdInteractiveAuthentication setting before relying on either name.

PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
MaxAuthTries 3

If the FTP daemon is unneeded, the recorded response pattern was systemctl disable <ftp-daemon> --now followed by firewall-cmd --remove-service=ftp --permanent and firewall-cmd --reload. Check the actual unit and firewall zone first. Disabling a service merely because its log appeared would be an unjustified outage.

Centralize auth logs off-host with authenticated, protected transport and retention controls suited to the environment. Include SSH and FTP events and watch the unparsed count. A forwarder selecting only sshd would recreate the 618-line blind spot. A simple unencrypted TCP 514 rule is not a sufficient production design.

The minimal selection idea in the case used an rsyslog rule for both $programname == 'sshd' and $programname == '<ftp-daemon>', forwarded with @@<siem-host>:514. That @@ example is plain TCP and leaves transport protection unspecified. In a real deployment I would configure a supported authenticated TLS forwarding action, validate both program names against actual records, and compare received counts with the source log. The second process is the point of this control.

12. Indicators, Artifacts, and Detection Engineering

The case supports detection designs, not a measured production detector. The linked parser passed synthetic local checks. The Sigma files below have not been converted for a SIEM backend or exercised on live telemetry. Any threshold needs a baseline and an authorized-scanner inventory.

IOCs (sanitized / illustrative)

Item What the case actually establishes
Source address Withheld; top address appeared in 150,314 closure lines. Treat as a triage lead.
Prefix and AS Withheld; published /16 listings agreed, but no time-specific route verification was recorded.
Reverse-mapping domain Withheld; its relationship to an operator was not established.
Portable behavior SSH failures by source and account, closure volume, HTTP-like protocol errors, and possible SSH/FTP source overlap. The last overlap was proposed, not tested.

The original 1,000-failures-per-day and 10,000-closures-per-day examples are candidate hunt thresholds, not baselines. The 50-failures-in-ten-minutes detector below is also a starting value. Closure counts can include benign or repetitive session handling, so I would pair them with failure, account, and success evidence.

Sigma - SSH brute force by volume

The Sigma event and correlation rule separates a single Failed password selection from event_count by src_ip and host over ten minutes. The threshold is greater than 50. The older pipe-aggregation form is obsolete in the Sigma correlation specification. The synthetic rule checks cover the 50/51 boundary and an expected authorized-test false positive. The rule needs a backend that supports correlation and a normalizer that supplies src_ip and host; otherwise it must fail closed at deployment, not silently group on missing fields. Stale automation, an approved test, and a struggling user can produce false positives. A low-rate distributed campaign is a false negative for this threshold.

Sigma - HTTP to the SSH port

The HTTP-to-SSH selection looks for Bad protocol version identification plus a quoted HTTP-like method. A conforming SSH identification string starts SSH-; this event therefore marks a mismatch. The sender could still be an authorized network scanner or a misdirected health check. I keep the level informational. A different daemon message, truncation, or an unusual HTTP method could evade this selection.

Splunk SPL - failure counts by source and account

This hunt extracts both account forms and keeps the time, host, source, and account dimensions. index and sourcetype are deployment placeholders, and _raw must contain the intact SSH line.

index=linux_auth sourcetype=linux_secure "Failed password for "
| rex field=_raw "Failed password for (?:invalid user )?(?<username>\S+) from (?<src_ip>\S+)"
| where isnotnull(src_ip) AND isnotnull(username)
| bin _time span=10m
| stats count AS failures dc(username) AS account_count BY _time host src_ip
| where failures > 50
| sort - failures

I would run a separate join or transaction review for Accepted from the same address and account. A shared IP without ordered timing does not prove a successful guess. The offline parser reports the address intersection for triage; it does not implement time-window or account-aware attribution.

Detection engineering notes

My first operational test would be a parser-coverage assertion, because a perfect threshold on incomplete ingestion still misses the FTP service. Next I would replay an approved synthetic failure burst, a stale automation case, and an HTTP-like banner. I would verify the backend grouping fields and rule conversion before treating Sigma as deployed. The artifact guide records what the local examples do and what they have not proven. An ASN-level block needs current route evidence and an impact review; a broad cloud-provider block could cut legitimate traffic.
