The One 200 in Ten Thousand Requests

I went looking for a hidden payload. The useful clue was one ordinary HTTP status code.

Summary

The challenge. Identify what a brute-force web capture disclosed and use that lead to recover the challenge answer.

What I did. I counted responses, paired the lone 200 with its request, checked the empty body, and tested the endpoint with the right session after several unnecessary detours.

The result. The capture reveals one endpoint. A later authenticated request reportedly returned the answer; the answer itself is withheld.

The limit. The packet findings were checked again against the capture. The later live-service response was described during the solve but was not independently replayed. No platform submission transcript is shown.

Defensive proofs of concept for applying this pattern to web telemetry: browse the tools and detections on GitHub and the invented fixtures. These operational examples use synthetic fixtures, not the challenge's raw capture.

1. Problem Statement and Threat Scenario

I received a packet capture and a prompt asking whether an automated brute-force against a web application leaked anything. The capture showed a client trying a sequential family of paths, /<resource>_0 through /<resource>_9999. My job was to find what the traffic revealed and recover the challenge answer.

The simulated actor wanted to discover a path that was not advertised in the application. I was the analyst with the capture. The important boundary was between learning that a resource exists and being allowed to read its content. A discovered path is useful intelligence. The capture alone cannot show that the application gave content to an unauthorized client.

2. Techniques, Tooling, and Actions Taken

I first checked the capture format and shape. It is a classic little-endian pcap with 100,004 packets over roughly 15.08 seconds. The IP traffic in it is loopback. It records 10,000 HTTP GET requests to one numeric path family, each index from 0 to 9999 exactly once and in order. My independent packet pass found 9,999 404 responses and one 200, with all 10,000 requests paired to responses. Every response declared Content-Length: 0; the successful response also had no body bytes in its first packet. In this capture, the answer was a pointer to a path, not a string in the successful response.

That should have ended the capture search. Instead, I treated the empty body as a hint that a more elaborate encoding must be present. My investigation notes count roughly 133 sandbox command executions and around 100 distinct techniques. The tooling inventory records approximately 240 tshark references, 180 Python references, 70 Scapy references, 29 tcpflow references, 31 strings references, 20 editcap/capinfos references, 16 live curl references, two nmap runs, one Suricata 7.0.3 run, and hash comparisons. Those are rough activity notes, not a benchmark or counts of unique executions per tool. bulk_extractor and Zeek were unavailable in that environment, so I approximated their functions with Python.

2a. Complete Technique Register

I keep the negative work because it explains the bad hypothesis I was carrying. The packet counts and path pairing above were the parts I checked again; the other family outcomes come from my investigation notes.

Family A, structure and integrity. I compared tshark, Scapy, and tcpflow views; checked capinfos, protocol hierarchy, the classic-pcap magic bytes, record boundaries, captured versus wire lengths, checksums, and file tail. My notes show no length mismatch or embedded pcapng comment block. The two downloaded copies matched by SHA-256. My later byte comparison also found the two available copies identical.

Family B, HTTP application data. I listed methods, URIs, hosts, response codes, streams, headers, cookies, authorization fields, query strings, request bodies, and possible exportable objects. I found no useful alternate content location or exported object. The URI range was complete and ascending with no gap or duplicate. I counted 17 distinct response strings and found the 200 versus 404 status text to be the useful discriminator.

Family C, statistics. I tried chi-square, Benford, run-length, Kolmogorov-Smirnov, compression ratio, per-field variation, and mutual-information checks. None gave a reproducible message. Random-looking metadata alone cannot prove there is no encoding, but these tests supplied no reason to continue treating the fields as a carrier.

Family D, timing. I measured request spacing and response latency, tried bimodality and modulus-2-through-600 ANOVA variants, a continuous-frequency transform, TCP timestamp deltas, and microsecond bit extraction. A period near 44.21 appeared in the analysis but did not decode useful content; one out-of-order packet was noise, not a message.

Family E, protocol-field covert channels. I swept IP IDs, TCP initial sequence numbers, ephemeral ports, windows, reserved and urgent bits, eight fields' low bytes, high bytes, nibbles and bit planes, and response-arrival order. My notes show zero values for the relevant reserved-bit and urgent-pointer checks. The single success occurred in its matching request slot, so permutation/order did not provide a second channel.

Family F, cryptographic transforms. I tried single-byte XOR, repeating-key XOR for periods 1 through 8, additive and subtractive transforms, bit rotations, Base32/Base64-like alphabets, Caesar shifts, 168 pairwise field combinations, index-selection sets, and 5/6/7-bit symbol framings. Apparent XOR hits were TCP timestamp artifacts. I also used the successful index as a possible offset, stride, key, modulus, or selector. None produced a verified answer. I did not submit the hash-derived guesses.

Family G, carving and strings. I searched for ZIP, gzip, PNG, JPEG, PDF, RAR, 7z, PEM, SQLite, xz, and bzip2 signatures; decoded narrow and UTF-16 strings; swept reconstructed flows; and approximated URL, email, Base64, hex, host, and account extractors. I found no useful embedded payload.

Family H, independent parsers. Suricata reportedly produced zero alerts or anomalies and agreed that the HTTP response lengths were zero. Python-derived equivalents of Zeek http.log, files.log, conn.log, and notice/weird views also gave no hidden-content lead. A zero-alert result is a property of that run and rule set, not evidence that the browsing behavior was safe.

Family I, visual encodings. I rendered 100 by 100 field bitmaps, low-byte strips, a Hilbert curve over 70,000 low bytes, and raw field-byte grayscale. No readable glyph emerged.

Family J, other services. I tried object-store listings and keys, a GCS bucket, CDN-origin clues, prior-year flag conventions, a full and a fast host port scan, and probes of high ports. The object-store checks yielded anonymous deny or a missing bucket. The high ports served unrelated interactive challenges, not this HTTP answer. These were dead ends, and the prior-year flag-format assumption was particularly misleading.

The useful pivot was a request to the discovered path on the live platform from a valid authenticated browser session. My anonymous requests had returned 404; the valid session received content. The differential is consistent with access gating, but a 404 does not reveal the server's exact authorization decision or route logic.

3. Tooling and Scripts

The compact triage I wish I had used first is a status tally followed by inspection of the rare response's TCP stream:

tshark -r capture.pcap -Y 'http.response' -T fields -e http.response.code | sort | uniq -c
tshark -r capture.pcap -Y 'http.response.code == 200' -T fields -e frame.number -e tcp.stream -e http.content_length

I pair the response to its request in the same TCP stream. I do not rely on a version-specific convenience field to report the request URI. The offline capture triage script makes that pairing for this simple cleartext pcap and reports the URI, status counts, numeric range, and declared body length as JSON. Its guide states the packet-local parser's limits. For a different capture with segmentation, retransmission, TLS, or HTTP/2, I would use full stream reassembly and verify the output manually.

python -B artifacts/http_capture_triage.py capture.pcap

I also used capinfos, editcap, Scapy, tcpflow, strings, Python statistical libraries, and a Suricata pass. I prepared a Zeek http.log route: inspect uri, status_code, and response_body_len for the rare success. The XOR and entropy scripts belong to my failed-path register, not to the minimum solution.

My final request used the discovered URI and an authenticated platform session. I would keep a session credential out of shell history and published notes. The capture's loopback address was never a useful remote destination. I did not repeat live scans or account requests for this page.

4. Concept Explanation

Forced browsing means requesting guessed resources without navigating to them through links. A run of numeric paths can reveal the shape of an application's namespace. In this capture the code distribution is unusually clean: 9,999 misses and one success. The success identifies a specific path. It does not mean that the HTTP response contained a secret, because the successful response declared zero content length.

RFC 9110 also makes the anonymous 404 worth treating carefully: a server can return 404 when it is unwilling to disclose a resource's existence. The valid-session result suggests an authentication-sensitive difference, but I cannot infer the exact server policy from a status code. Discoverability, authentication, and authorization are three separate questions.

The path index has a theoretical maximum of about log2(10,000), or 13.3 bits, if a uniformly selected one-of-10,000 index is the only unknown. That is a way to describe the namespace choice, not a measurement of all information in the pcap or of secret entropy.

5. Exploit/Analysis Mechanics

The successful route can be identified deterministically: enumerate HTTP transactions, isolate the one 200, and pair it with the matching request. A body check then determines whether the capture itself has content to recover. Here all declared body lengths are zero, and the successful response's packet had no body bytes. My earlier full-stream review reached the same conclusion.

The captured traffic uses loopback, so it cannot directly name a public service endpoint. The record's last step used the corresponding path on the live challenge platform with a valid session. It reports that this request returned the answer and that anonymous probing had returned 404. I keep the answer value out of this page. I can independently verify the pcap-side lead; I cannot independently verify the historical live transaction or submission from the capture alone.

In three actions: count codes, extract the successful path, request it in the authorized challenge session. The failed analyses in Section 2a happened between the second and third actions.

6. Lessons Learned (Practitioner Perspective)

I overworked this case. Once I had one successful path and a zero-length response, the next cheap test was to follow that pointer in the intended environment. Instead I looked for ciphertext, metadata bits, carved files, and timing channels. Those checks were technically interesting, but they were answers to a question the evidence had stopped asking.

Two assumptions kept me there. First, I carried a flag-format convention from earlier challenges into this one as though it were a rule. Second, I treated the anonymous 404 as conclusive absence and did not vary session state. The later authenticated request exposed that mistake. In future HTTP triage I will write down both the resource I found and the identity making the request.

The portable habit is to use status and path metadata to find the anomaly, inspect the response body, then run the cheapest authorized test of the lead. I still preserve the negative work because it shows how an investigation can be thorough yet poorly directed. The actual challenge difficulty is Easy despite my detour.

7. Extrapolation

For my own practice, this is a stopping-rule exercise as much as a network-forensics exercise. I can apply the same first pass to access logs, Zeek http.log, WAF records, or a cleartext capture: count statuses by client, host, path family, and time; pair any rare success with the preceding misses; then examine the route and requester context.

For a SOC or incident-response team, the useful hypothesis is a client discovering a numbered endpoint after many misses. I would preserve the raw request/response records, check proxy attribution, identify the account or session if present, inspect response bytes and route sensitivity, and ask the application owner whether the path was intended to be accessible. Secret rotation follows only if exposure is confirmed. Authorized discovery scans, broken links, and health checks are expected false positives to tune around.

For threat intelligence, the cadence, path pattern, and User-Agent could help cluster activity, but they are weak selectors. A single CTF loopback capture does not establish a real actor, campaign, external IOC, or exfiltration. For a purple-team exercise, I would generate a controlled series of numbered-path misses followed by a success on a test host, verify the sensor records all five necessary fields, and check that the alert points to the exact requests without claiming sensitive-data loss.

8. Reusable Tools, Scripts, and Artifacts

My reusable decision pattern is: establish the protocol; tally status codes; pair rare success with its request; check whether the response actually carries content; then follow any discovered pointer under the permitted account context. Deeper carving or covert-channel work begins only if those checks fail.

The capture triage tool and its synthetic pcap reproduce the basic request/response shape without publishing the challenge endpoint. The expected capture report makes the output checkable. The normalized web-log detector runs the operational hypothesis on invented web events, with an expected finding. The regression checks include a positive case and near misses. The lab guide explains inputs, limits, and tuning.

My early generic triage idea chose whichever status was rarest and treated a missing content length as an empty body. I changed that logic: this tool explicitly reports 200 responses and calls a body declared_empty only when the response says Content-Length: 0 without transfer coding. It remains a packet-local helper, so I still require a real stream review before using it to rule out content in a new capture.

10. Threat Intel and Standards Integration

The strongest indicator here is behavioral: many distinct 404 paths in one numbered family, followed by a 200 for the same client and host within a short period. The challenge's loopback address and route name are not reusable external IOCs. A default client User-Agent, if present, is too weak on its own. There is no evidence of a TAXII feed or a production intelligence exchange.

I sketched a STIX 2.1 bundle with an attack-pattern, indicator, and course-of-action object. The indicator pattern matched one HTTP request path, but that single observable cannot express the aggregate and temporal 404-then-200 behavior. I therefore keep the multi-event logic in the web-log detector and the Sigma candidate. A STIX producer could describe the pattern in prose with references, but it should not claim an equivalent executable STIX pattern without a valid representation and consumer test.

For standards implementation, I would select the current STIG and CIS Benchmark for the actual server product, then check its route authorization and access-log requirements. The capture does not identify that product or establish a compliance finding. NIST SP 800-92 offers general log-management context; it does not certify this detection.

11b. Mitigation Realization

I would make the application's authorization check explicit on sensitive routes and test anonymous, normal-user, and privileged-user outcomes. I would remove unnecessary production routes, enable detailed access logging, and use proxy or WAF rate limits as a brake on bulk enumeration. A discovered route returning 200 to a valid account might be correct behavior, so the deciding test is the route's intended audience and the response actually delivered. If an unauthorized account obtained a secret, I would contain access and rotate the affected value; the capture by itself does not establish that condition.

The offline detector is the concrete monitoring proof of concept. The query templates and Sigma correlation candidate show how to move it toward SIEM processing, with backend and field-mapping work still required.

12. Indicators, Artifacts, and Detection Engineering

The packet-level facts I can stand behind are the 10,000 numbered requests, 9,999 404s, one 200, and declared zero-length responses. The useful production signal is a distinct-path 404 run followed by a 200 for the same client, host, and numeric path family. No challenge-specific IP, domain, route, flag wrapper, or file hash is a responsible general-purpose IOC.

The web-log detector implements a sliding five-minute window with a default threshold of 100 distinct misses. It requires sorted JSONL events with timestamp, real client IP, host, path, and status. Its synthetic events, expected output, and tests show one hit and near misses for the wrong source, host, family, order, duplicate paths, or time window. The SPL and KQL templates use fixed bins and need local schema mapping and runtime validation. The Sigma correlation parsed with pySigma, but no backend conversion or production log trial was performed. The guide gives the sensor and tuning assumptions.

An alert is a lead. I would inspect account state, authenticated response size, route ownership, and authorization policy before calling it exposure. I would also suppress known testing sources with care, so those exceptions do not conceal an actual discovery attempt. I had considered a generic YARA FLAG{...} pattern, but a puzzle wrapper is neither the observed network behavior nor a useful organization secret format. A real DLP rule needs that organization's secret grammar and a measured false-positive test.
