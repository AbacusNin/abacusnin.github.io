The Portrait Was a Crop of a Crop

The face in the infobox was easy to find. The account behind the photograph took a few more clicks.

Summary

The challenge. Identify the platform account that uploaded a new portrait connected to a public figure's biography.

What I did. I disambiguated the subject, set aside an older portrait, followed two crop links to a base file, and read its upload history.

The result. The challenge record reports that the account from the base file's upload history was accepted in the required flag format.

The limit. The subject, file titles, account, and submission transcript are not retained here. I cannot independently replay the case attribution or verify the claimed family relationship.

1. Problem Statement and Threat Scenario

The prompt was a riddle about a public figure's portrait. It said a relative had uploaded a more flattering photograph for the figure's encyclopedia biography, and the change had caused an editorial misunderstanding. My job was to find the platform account used for that upload and wrap it in the event's flag format. The answer was an account name, not a person's legal name.

Everything I needed was public: the biography, Wikimedia Commons, the article's revision and talk pages, and the media files' upload histories. I did not need to log in or touch a private system. The puzzle itself showed no intruder or protected network. A real investigator might use the same public records to attribute a posted image to an account, but that would be a separate case with its own evidence.

2. Techniques, Tooling, and Actions Taken

I began by sorting out the subject. The name in the riddle fit more than one notable person. One namesake, though, had a long-running argument over the photograph at the top of the biography. That lead-image dispute was the clue that picked the right article.

Then I made the obvious wrong turn. The older, familiar portrait seemed like the photograph everyone had argued about. Its Commons page credited a third-party photographer, so it did not fit the relative in the prompt. I went back to the biography and looked at the more recently added lead image. That was the useful pivot.

The newer displayed file was a crop of a crop. I followed the first Commons source link to its parent, then the next source link to the base file. On that base file's File history, the oldest visible upload named the account that had introduced that file to Commons. The intermediate crop accounts described edits to the image; using either of them as the answer would have answered a different question.

I also looked at the article's talk and conflict-of-interest discussion for context around the claimed relationship. Those discussions can provide a second source when they contain a specific disclosure. A general COI notice alone cannot prove who controls a Commons account. My case notes report that the base-file account, put in the required flag syntax, was accepted by the scoring platform. I do not have the file titles, a retained talk-page citation, or a submission transcript to replay that result now. The account and flag remain withheld.

3. Tooling and Scripts

I solved the case in a browser. The useful sequence was to open the lead image from the biography, choose its Commons file page, follow each recorded parent link, and read the base file's upload history. I used a general web search to disambiguate the subject and the article's public discussion to check the story around the image. No exploit or custom code was part of the original solve.

Biography at the relevant revision
  -> displayed lead image
  -> Commons derivative file
  -> parent crop
  -> base file
  -> File history: oldest visible upload account

The MediaWiki Imageinfo API offers an auditable way to repeat the last step. iiprop=user|timestamp|comment requests the uploader, upload time, and comment for each visible version. iilimit=max requests the largest page of results; it does not guarantee that a long history fits in one response. A continuation token means more versions remain. The Parse API's wikitext property can show source links recorded in a derivative's description. I did not execute those API calls in the challenge solve.

For a reusable check, I made an offline upload-history reviewer. It reads one saved imageinfo JSON response for a base file, refuses a continuation token, sorts timestamps, and reports the oldest visible account. The guide shows a curl request that URL-encodes a file title and saves the response. I tested the reviewer against invented upload history, not the withheld challenge chain. The synthetic tests cover a newer replacement, shuffled API order, a hidden oldest account, missing and nonlocal files, and incomplete pagination.

4. Concept Explanation

Commons keeps visible upload versions for a file name. Each version can have an uploader account, timestamp, and comment. That history answers a narrow question: who uploaded the oldest visible version of this Commons file name? It may not reveal the photographer, the real person behind the account, or the first appearance of the image elsewhere. MediaWiki's Imageinfo documentation also notes that a user field can be hidden and that a request can require continuation.

A crop uploaded under a new file name has its own history. The person who made that crop can differ from the person who uploaded the image it came from. Commons descriptions can record a parent through a Derived from or Extracted from link. I followed the recorded links in this case. I would not infer a parent from a similar file name alone; a derivative description can be missing or wrong.

The conflict-of-interest discussion was useful for the riddle's family claim, but it has a different evidentiary role. The base file's history attributes an upload to a platform account. A specific, preserved self-disclosure could support a relationship between that account and the subject. A broad policy page only explains why such discussions occur. It does not authenticate a person.

5. Exploit / Analysis Mechanics

I kept two chains separate. The media chain was the displayed portrait, the first crop's source, the second crop's source, and the base image. The account chain began only when I reached the base file's upload history. That distinction was the whole solve: the newest, visible portrait pointed me to the right file family, but the base upload identified the account the prompt wanted.

The old portrait was a useful negative check. Its named photographer did not match the riddle's relative. It would have been easy to stop at the most famous photograph and invent a connection. The newer lead image and the two recorded crop links gave me a path I could inspect instead.

On the base file, I read the earliest visible upload rather than the latest replacement. The public upload record supports the account attribution for that file name. The reported accepted flag supports that the account satisfied the puzzle. Neither proves that the account holder was a relative. The relationship claim needs a specific independent record, such as an identifiable disclosure in the article discussion, which I cannot cite here.

This method has limits. A bot may import an image from another wiki, a revision may be suppressed, or the file description may omit its parent. A biography may point to media outside Commons. A lead portrait can change after the solve. Those cases call for a narrower conclusion or more digging; the checklist records the article revision, every parent link, and any earlier source before naming an account.

6. Lessons Learned

I lost a little time on the old portrait because it was the famous one. Checking the file page stopped that line of thought quickly. The challenge asked who introduced the newer image, so I needed the image in the relevant article revision and the oldest visible upload of its base file.

The two crops mattered. If I had read the uploader of the displayed crop, I would have credited the person who edited the framing. Following the parent links prevented that mistake. I would use the API earlier next time to save the visible history and timestamps in one record, while still checking the file descriptions by eye.

7. Operational Extrapolation

Individual Practitioner Development

This case sharpened a habit I want in OSINT work: follow the object's history before making a story from its appearance. I practiced separating the biography, displayed crop, base media file, and uploader account. A useful follow-up is to run the history reviewer on several public multi-crop examples and compare the output with the Commons page. That would test the workflow across different import and revision patterns; I have not done that broader trial here.

Security Operations

The puzzle did not supply host logs, network events, or a compromised service. I cannot turn this browse path into a credible Sigma rule or SIEM query. For a public-facing organization, a narrower defensive use is possible: an editorial team can watch changes to its own biography or organizational pages, record the exact lead-image file at each revision, and review unexpected replacements through Commons provenance. That is a proposed media-integrity process. It would need a maintained page list, revision feed, expected-image baseline, and human review before it could become an alert.

Intelligence Operations

This is the strongest real-world fit. A collector tracing an image posted in a public corpus can find the account that introduced its visible base file, then compare that with other public records. I would keep the account-level finding separate from identity, intent, and affiliation. The case gave no SIGINT collection or information-operation campaign to map. A crop chain and a username can start an attribution lead; they cannot finish an actor assessment.

8. Reusable Tools, Scripts, and Artifacts

The provenance checklist is the main reusable asset. It tells me to capture the article revision, each derivative link, the base-file upload history, any transfer or hidden revision, and the exact talk-page statement if I make a relationship claim. It is a proposed process for public-source review, not a record of an investigation run against a client.

The offline history reviewer handles one narrow part of that process. It accepts a saved Commons imageinfo response and returns the oldest visible account, upload time, and version count with a scope warning. It refuses incomplete pagination rather than quietly calling a partial record complete. The README documents the API request, inputs, outputs, exit codes, and limits. The sample JSON and five synthetic tests exercise the tool without exposing the challenge account. The browser-led puzzle result was reported as accepted; these new files do not independently replay it.

9. Framework Applicability and Mapping

I checked ATT&CK rather than treating every OSINT task as an adversary technique. T1593, Search Open Websites/Domains, does model adversaries searching public sites during reconnaissance. The browsing here resembles that collection method, but the challenge had no adversary, victim-targeting objective, or later intrusion. I use T1593 only as an analogy for an operational case that might involve targeting. I do not label my puzzle solve as observed ATT&CK behavior.

10. Threat Intelligence and Standards Integration

The account was the puzzle answer. I have no indicator of compromise, attack pattern, malware, infrastructure, or vulnerability to express as STIX, and no TAXII exchange to report. Treating a public username as a threat indicator would imply malicious conduct that the evidence does not show. I would preserve it privately in an authorized case record if it were relevant to a real investigation, with its source URL, timestamp, and account-level scope.

The useful standard interface is MediaWiki's public API. The Imageinfo endpoint returns visible upload history; the Parse endpoint can return the derivative page's wikitext. Both support repeatable collection. Neither verifies a claimed family relationship for me.

11. Controls Mapping and Mitigation Realization

Commons publishes upload history as part of its normal transparency model. Reading that history did not expose a vulnerability or misconfiguration. I therefore cannot claim a failed NIST or CIS security control, nor a mitigation deployed for the challenge.

The practical privacy and publishing lesson is simpler. Anyone contributing media through a public account should expect the account and revision trail to be visible. An organization managing its public biography can review proposed image changes, preserve the relevant revision IDs, and understand who uploaded each file before accepting a portrait. I would propose and test that editorial practice with the organization's actual workflow. This puzzle provides no validation of a product control.

12. Indicators, Artifacts, and Detection Engineering

The case artifacts were public article revisions, derivative file descriptions, the base file's history, and talk-page discussion. They are provenance evidence, not IOCs. No host or network telemetry came with the puzzle, so I have no honest KQL, SPL, Sigma, or YARA detection to publish for it.

If a team needs to watch its own public page, the behavior to notice is a changed lead-image file. A monitoring process would need page revision IDs, edit timestamps and accounts, the prior and new image titles, and a baseline of approved images. It could then route an unexpected change to an editor who follows the provenance checklist. I have not built a revision-feed collector, connected a backend, measured false positives, or run this against production pages. Ordinary editorial improvements would be expected review cases, not incidents by default.
