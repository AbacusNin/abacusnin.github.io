The Chat Named the Target

The IP addresses looked like the obvious lead. A quick range check sent me back to the conversation.

Summary

The challenge. Identify the intended next target from five screenshots of a private group chat.

What I did. I inventoried the images, checked metadata, reconstructed their timeline, translated the target discussion, and classified every reported IP against its address range.

The result. The single entity named with both a brand and a city matched the requested answer format. The case record reports that the submitted answer was accepted.

The limit. The screenshots, target, and submission transcript are withheld. The translation and accepted answer cannot be independently reviewed from this public page.

1. Problem Statement and Threat Scenario

I had five phone screenshots from a private group chat. An outside account had been added by mistake, captured the conversation, and was removed. The messages were in Simplified Chinese. My job was to name the next intended target as a brand and city pair. I had no host to examine, no credentials, and no live network task.

The chat described two people discussing tooling from an outside supplier and a script that had supposedly found vulnerable hosts. That made the IP addresses tempting. The exercise still hinged on reading what the speakers said. Their messages showed claimed intent. I had no evidence that anyone scanned or attacked a real organization.

2. Techniques, Tooling, and Actions Taken

I began by hashing and inventorying the images. All five were portrait screenshots. The EXIF check came up empty, so I had no device or location metadata to work with. I then used the timestamps inside the screenshots. The filenames were out of order; the visible times put the exchange into a conversation of about 27 minutes on one morning. I did not infer a timezone from the pictures.

I translated the discussion and tracked who named which prospective target. One speaker said an outside supplier had delivered tooling and a script had produced a list of vulnerable IPs. The speakers attached organization stories to those addresses and debated which target to pick. I kept their claims separate from verified ownership of the addresses.

Before I tried to geolocate any IP, I checked its range. The address set reported in this case fell within the three documentation blocks and the benchmarking block described in Section 4. That ended the IP-to-organization path. I went back to the conversation and asked which candidate met the required brand-plus-city format. One did. The speakers also preferred that target over a larger unnamed alternative.

The first dead end was EXIF. The more important one was apparent IP attribution. Both were cheap to close, and neither required a lookup against a live third-party service. The exact address list and answer-bearing chat bubbles are withheld here, so the range classification and translation are case-recorded observations rather than independently reproducible results on this page.

3. Tooling and Scripts

I used file hashing, an image viewer, a metadata check, and Python's ipaddress module. I enlarged the relevant chat bubbles and read the words in the images. I also noted the gap between two screenshots where one speaker's confirmation was missing.

My image inventory followed this pattern. It recorded each file's hash, dimensions, and EXIF tag count. In the challenge, the five images were portrait-oriented and every EXIF count was zero.

from hashlib import sha256
from pathlib import Path
from PIL import Image

for path in sorted(Path("imgs").glob("*.jpg")):
    with Image.open(path) as image:
        print(path.name, sha256(path.read_bytes()).hexdigest(), image.size, len(image.getexif()))

Here is the core of the address test, using invented values from the offline fixture:

from ipaddress import ip_address, ip_network

blocks = [ip_network(cidr) for cidr in (
    "192.0.2.0/24", "198.51.100.0/24", "203.0.113.0/24", "198.18.0.0/15"
)]
print(any(ip_address("203.0.113.9") in block for block in blocks))  # True

The linked IPv4 intake filter turns that one-off test into a bounded offline tool. It reads one address per line and labels documentation, benchmark, private, shared, link-local, and loopback values. The guide defines its input and output. It makes no network requests and does not say an unclassified address is safe, malicious, or currently routed.

4. Concept Explanation

An IP can be syntactically valid and still be useless for identifying a public victim. RFC 5737 sets aside 192.0.2.0/24, 198.51.100.0/24, and 203.0.113.0/24 for examples. IANA's IPv4 special-purpose registry lists those blocks and 198.18.0.0/15, used for benchmarking, as not globally reachable. A geolocation result for one of these example values would not establish the organization named in a chat.

I do not apply that conclusion to every special-purpose address. The same IANA registry includes globally reachable special-purpose entries, including 192.0.0.9. A private address can also matter greatly inside a local network. The category and the source context determine how an analyst should handle a value. My narrow filter marks known examples and benchmark values before public enrichment; it keeps the source record intact.

The other concept is source order. The screenshots had to be read by their visible timestamps, then translated as a conversation. A cropped image, a missing message, or an ambiguous character can change who a pronoun refers to. The translation review worksheet records the visible wording, timestamp, interpretation, and gap separately for exactly that reason.

5. Exploit / Analysis Mechanics

I solved this by analyzing the five screenshots. Roughly a dozen distinct IPs appeared as supposed scan findings. The case record says every extracted address landed in a documentation or benchmark range. Membership in those exact CIDR blocks is a deterministic check once the address has been transcribed correctly. It says nothing about whether the speakers actually ran a scan.

With those addresses set aside as public attribution leads, I compared the entities the speakers described. An unnamed restaurant, an unnamed hospital, and an unnamed large foreign company could not supply both fields the flag required. One entity had a brand and a city. A later message named that preferred brand, although a confirming message from the other speaker fell between captures. I could still select the single pair that fit the requested shape without inventing the missing bubble.

The case record reports that the formatted answer was submitted and accepted. I do not print the pair or the screenshots here. Acceptance supports the challenge answer, but it does not turn the invented address attributions into facts about real hosts or verify a real threat actor's intent.

6. Lessons Learned

The quick checks mattered more than a big OSINT search. EXIF gave me nothing. The range test kept me from building a story around example addresses. The useful evidence was the sequence of statements in the chat, and I only saw that sequence after putting the images in time order.

I would keep two separate notes in a live investigation: what the speaker claimed, and what independent evidence supports. Here, the speakers' target preference was useful for the puzzle. It was not an incident report. The missing screenshot gap also mattered; I marked it instead of smoothing it into a complete conversation.

7. Operational Extrapolation

Individual Practitioner Development

This case practiced two skills together: reading a foreign-language source and testing whether the technical-looking details deserved attention. A next exercise would add IPv6 and the rest of the IANA special-purpose registry to the intake policy, then have a second reader review the decisive translation. The current filter is deliberately an IPv4 subset.

Security Operations

A threat-intelligence intake queue could run a range check before it sends IPs to public enrichment or creates block actions. It should retain known documentation and benchmark values as source text and keep them out of external victim or attacker IOC lists. Private and shared addresses need local context. The testable filter demonstrates those decisions with positive, benign, boundary, and invalid examples. It has no live feed connection, SIEM field mapping, or production accuracy claim.

Intelligence Operations

I would preserve each screenshot, its hash, visible time, language, and any uncertain translation. The review worksheet is a small way to keep source wording apart from the analyst's interpretation. A stated preference can inform an intent assessment. Attribution or warning to a real organization would require independent corroboration. This puzzle supplies none.

The invented list and expected output show the data contract. 9. Framework Applicability and Mapping

The chat says a script found vulnerable hosts. That claim resembles MITRE ATT&CK T1595, Active Scanning at a narrative level. No scan trace or target system was available, so I cannot mark the technique as observed. The speakers also said an outside supplier delivered tooling. T1588, Obtain Capabilities is a loose narrative fit. The source description does not establish that the item was malware, so the more specific T1588.001 mapping would overstate it.

The challenge gave no defended system or web application to assess. I did not assign OWASP, STRIDE, D3FEND, or a control identifier to the pictured conversation. My operational proposal is an indicator-intake check, described on its own terms in Sections 11 and 12.

10. Threat Intelligence and Standards Integration

I have no real IOC set to package as STIX or distribute by TAXII. Turning the documentation and benchmark examples into STIX Indicators would falsely present them as actionable infrastructure. The exercise supplies no campaign evidence. The useful standard here is the current IANA special-purpose registry for address classification. It should be checked again when an operational policy is updated.

11. Controls Mapping and Mitigation Realization

The screenshots do not show an organization's controls or a system configuration. I cannot rate a NIST, CIS, STIG, or sector-specific requirement from them. I can describe a practical control proposal: at IOC intake, keep the raw source mention, classify the address, and stop known example or benchmark values before external enrichment and automated blocking. Send private or shared values to a local-context review. Log the decision and policy version so an analyst can reverse it.

The offline filter supplies only the classification step. A real deployment would need a maintained registry, an owner, IPv6 rules, source-field mapping, audit logs, and a way to handle exceptions. None of those were implemented in this challenge.

12. Indicators, Artifacts, and Detection Engineering

The five screenshots contain no endpoint, DNS, firewall, or EDR telemetry from a victim. A Sigma rule, KQL query, or SPL search for an attack would require invented event fields. The defensible analytic is an indicator-quality gate: classify extracted IPs before enrichment, preserve the surrounding text, and queue uncertain cases for review. The fixture exercises example and benchmark positives, ordinary unclassified addresses, 192.0.0.9 as a special-purpose near miss, and an invalid value. The expected result makes the decision inspectable.

The gate has a known limit. Its explicit list stops at common IPv4 categories. An unclassified result is not evidence of routability or maliciousness. Production validation would require a current registry snapshot, real intake schemas, an exception workflow, and tests that prove no analyst evidence is silently discarded. The local tests verify only the script and invented fixture.
