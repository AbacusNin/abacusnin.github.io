The ELF That Would Not Load

I could make the loader recognize the file, but that was not enough to make it run.

Summary

The challenge. Recover the intended stdout of a deliberately corrupted x86_64 PIE executable without relying on execution.

What I did. Compare the first bytes and byte distribution, test a repair, then use surviving symbols, segment mapping, raw code, and call order.

The result. I reached the intended output by static reconstruction after the loader path failed; the exact stdout and an acceptance receipt are not retained.

The limit. The binary and final stdout are not available for independent replay here. The linked defensive proof of concept uses invented bytes and tests file-triage logic only.

At-a-Glance Mental Model

The first four bytes looked like an ELF signature with its final letter changed. I expected a simple header repair until I counted the whole file: the roughly 17 KB image had no zero bytes and about 14,100 spaces. A global 0x00 to 0x20 change explained that pattern, but it destroyed information. Some of those spaces had been real spaces all along. My attempt to turn every space back into a zero made the file recognizable and got it past the kernel, then the dynamic linker aborted. I moved to static recovery: find the surviving functions, read low bytes of character immediates, check format strings and call targets, and assemble output in call order. The flow above follows those pivots.

1. Problem Statement and Threat Scenario

I was given a single on-disk binary and asked what it was meant to print. file called it data, even though the challenge hint pointed toward ELF. I had no source code and no service to query. The file was an x86_64 position-independent executable after enough of its header was repaired to classify it, but executing that broad repair did not reach its own code.

The challenge models a useful forensic problem: an executable-shaped file may fail ordinary typing or loading, yet still hold enough structure to analyze. A real incident could involve a damaged transfer, an adversarially altered file, or a staged payload that another component repairs. This exercise alone does not establish a real adversary, a repair loader, or a host compromise.

2. Techniques, Tooling, and Actions Taken

I began with the first 64 bytes using od -A x -t x1z -v. The signature was 7f 45 4c 4b, spelling ELK where an ELF file should begin 7f 45 4c 46. At that point I suspected one magic-byte change. Before patching it, I counted every byte with Python's Counter. In approximately 17 KB, there were zero 0x00 bytes and roughly 14,100 0x20 bytes. Those are reported rounded figures; I do not have the image to remeasure them.

That distribution changed the question. The evidence suggested two visible alterations: the F-to-K magic change and a file-wide 0x00-to-0x20 substitution. I tried the tempting broad inverse, changing all spaces to zero and restoring the magic. file then identified an x86_64 PIE and the kernel accepted it, but the dynamic linker stopped at elf_get_dynamic_info before main. Recognition was not recovery. A genuine 0x20 in a string, instruction, or offset is indistinguishable from a substituted zero without context.

I changed course to raw-byte analysis. readelf -s and nm were the symbol-inspection tools; readelf -s exposed main, flag, and flag1 through flag4. The text LOAD segment had both file offset and virtual address 0x1000, so within that segment its symbol virtual addresses matched file offsets. I used that mapping, Capstone disassembly, mov immediates, format-string references, and the call chain to reconstruct the printed characters. I reached the intended output statically. I did not retain the exact output or an accepted submission, so I cannot replay or display either result here.

3. Tooling and Scripts

3.1 Byte-distribution triage

I counted values before changing the file. Counter(data) exposed the missing NULs and dominant spaces more quickly than repeated hex dumps. The defensive read-only ELF substitution reviewer applies a bounded version of this check to a supplied file and returns JSON. Its usage and limits matter: a match is a review lead, not a malicious verdict.

3.2 ELF magic / header sanity check

The first four bytes were 7f 45 4c 4b. I checked EI_CLASS, EI_DATA, and EI_VERSION before treating the prefix as ELF-like. In an ELF64 little-endian header, e_type begins at offset 0x10 and e_machine at 0x12. Their upper bytes can reveal a substitution when otherwise small values have become 0x20xx. This is a clue, not a safe automatic correction: endianness and file class must be checked first.

3.3 Static recovery via Capstone

The useful raw-code pattern was bf 6d 00 00 00 for mov edi, 0x6d, which becomes bf 6d 20 20 20. The low byte 0x6d, or m, survives. I traced putchar arguments from edi, %c arguments from esi, and RIP-relative lea references to format strings. I had to inspect string boundaries and small displacements in context, since every 0x20 could be an original space. I then walked the short flag function chain in execution order. A general simulator would need the actual symbol ranges and PLT targets, so this method is not a ready-to-run tool for another ELF.

3.4 Fallback: surgical patch + execute under strace

I prepared a narrower fallback: repair only structural fields needed for loading, then capture writes in an isolated environment with strace -e trace=write. I did not complete that path. It would require checking dynamic entries and relocations one at a time; a broad replacement would simply repeat the failure. I kept static recovery as the recorded route to the output.

4. Concept Explanation

4.1 ELF header at a glance

An ELF file starts with the 16-byte e_ident array. The first four bytes are \x7fELF; class, data encoding, and version follow. Elf64_Ehdr then contains type, machine, entry point, and offsets to program and section headers. The program headers describe what the loader maps. The section and symbol information helped me navigate this image, while the dynamic section still had to satisfy the linker's rules. Fixing a signature does not fix all of those fields.

4.2 Why the substitution is so destructive

Changing every zero byte to 0x20 damages small multibyte fields, padding, NUL-terminated names and strings, and instruction operands. For example, 0x00000003 in little-endian storage becomes bytes ending in three spaces when the zero positions change. A call displacement can point somewhere entirely different after that. The transformation is many-to-one: original zero and original space both appear as space. That is why my wholesale inverse could create a recognizable but still broken executable.

4.3 What survives

Nonzero bytes other than 0x20 survive this rule. In the character-immediate example, the low 0x6d survives even though the higher zeros do not. Some opcodes, symbol-name letters, and relative structural relationships remain useful. None is universally safe: an intended literal space is ambiguous, and an opcode or displacement containing an original zero changes. I checked each candidate against its instruction form, segment bounds, adjacent calls, and expected output behavior.

5. Exploit / Analysis Mechanics

5.1 The invariant that was violated

The loader needs the on-disk header and dynamic records to contain their actual encoded values. Here the magic was wrong, and the substituted zeros damaged fields throughout the image. The magic change explains the initial type and kernel rejection. The broad inverse repaired that gate while corrupting legitimate spaces; the subsequent linker assertion showed that a file that passes the first gate can still be unusable. It does not by itself identify which dynamic record was wrong.

5.2 The reconstruction recipe

I kept the original bytes intact, mapped a symbol virtual address to a file offset with p_offset + (VA - p_vaddr), and disassembled only within the mapped segment and known function sizes. The text segment's offset and VA were both 0x1000 in this case; that equality must never be assumed for another ELF. For each candidate mov reg32, imm32 feeding putchar or printf, I retained the low byte only when the encoding and surrounding call supported it. I identified 0x1030 and 0x1040 as PLT call targets in this image; those addresses cannot be generalized. I treated each RIP-relative displacement and rodata terminator as a hypothesis to check, then followed the actual call order.

This also exposed a mistake: I first trusted a disassembler-resolved call target and got an off-by-one result. Recomputing from the raw instruction address, length, and signed displacement was the right check. I assembled the intended stdout, but I cannot reproduce its exact bytes here.

6. Lessons Learned (Practitioner Perspective)

6.1 What the exercise validated

The cheapest useful pivot was a byte count. It showed the corruption was wider than the header before I spent time on loaders. Symbols and raw code still offered a foothold when normal file parsing was unreliable. Capstone could disassemble a supplied byte buffer without successfully loading the ELF.

6.2 Gaps and inefficiencies surfaced

I spent about ten minutes on the blanket inverse even though the map was noninvertible. I also trusted a resolved target once without checking raw displacement arithmetic. Both errors came from treating a plausible tool output as if it had already restored the original bytes. I would establish the many-to-one property and the segment mapping first next time.

6.3 Transferable principles

I now put hashes, magic, byte counts, and a small header dump at the start of unfamiliar-file triage. I document the transform rule and its ambiguity before attempting repair. If a loader refuses a file, static analysis can still recover limited behavior; I keep that analysis separate from claims about actual execution.

6.4 Exercise-to-operations mapping

7. Extrapolation

7.1 Individual practitioner skill development

This exercise made me practice e_ident, ELF header fields, program headers, symbol addresses, the dynamic section, little-endian immediates, RIP-relative addressing, and call sequencing together. The next useful drills would be a stripped ELF, a nonidentity VA-to-offset mapping, and a literal space in the target output; each removes a convenience this case had.

7.2 Security operations (SOC, IR, threat hunting)

For an endpoint collection, I would preserve the original file and hash, inspect its first bytes, and calculate distribution features before any repair. A near-ELF prefix plus zero NULs and dominant spaces is a narrow lead for file review. An execve format failure can help prioritize that review, but the syscall event does not carry file bytes or prove this substitution. I would correlate by a reliable path or file identity, host, and time, then compare with build pipelines and transfers that may have altered encoding accidentally.

7.3 Intelligence operations (SIGINT, IO/IW, OSINT, attribution)

If several collected samples share a corruption rule, I would record it as a low-confidence clustering feature alongside hashes, provenance, compiler traits, and any actual repair code. A shared rule alone cannot identify an actor; independent text conversion could produce it. A real loader that repairs the bytes would strengthen an adversary-behavior hypothesis, but none was observed in this case.

8. Reusable Tools, Scripts, and Artifacts

8.1 Triage decision tree for unfamiliar binaries

I use this order: preserve and hash; inspect magic; count bytes; check class/endianness and header fields; decide whether a transform is plausible and reversible in specific positions; map symbols and segments; then analyze raw code. A dynamic run belongs in a controlled lab after I understand what was changed. The artifact guide states what the local triage proof of concept can and cannot tell me.

8.2 Reusable: byte-distribution probe (abstracted from 3.1)

The Python reviewer returns file size, prefix, zero count, space count and ratio, contributing signals, and a boolean review_lead. It reads at most 32 MiB and never writes to the input. Its positive condition mirrors the reported pattern; those thresholds have not been tuned on a production corpus.

8.3 Reusable: x86_64 immediate harvester

A character harvester can start with Capstone's x86_64 mode and emit the address, register, raw immediate bytes, and candidate low byte for mov reg32, imm32. I would require a nearby relevant output call and record uncertainty around original 0x20 values. Merely masking every decoded immediate with 0xff will produce false characters from unrelated instructions. A five-function replay needs actual symbol ranges, PLT targets, format strings, and call validation; I have not packaged one as a runnable recovery utility.

8.4 Solve-pattern checklist for tampered-header artifacts

Record the original hash; dump the header; count all bytes; identify a plausible rule; mark ambiguous positions; map VA through program headers; cross-check symbols and instruction bytes; reconstruct output in call order; and state exactly what was verified. The synthetic tests include a positive, a valid-header benign case, a magic-only near miss, and a direct demonstration that zero and space collapse to the same byte.

9. Framework Mapping

The closest ATT&CK analogy is T1027, Obfuscated Files or Information, if a real adversary deliberately altered a payload to make analysis harder. This CTF does not prove such activity. I would apply T1140, Deobfuscate/Decode Files or Information only after observing an adversary's loader or script restoring the bytes, not to my own analysis. T1027.001, Binary Padding describes added junk data and does not fit a zero-to-space substitution. The magic mismatch also does not, by itself, show impersonation required for Masquerading. I do not assign those two labels to the case.

On the defensive side, D3-FCR, File Content Rules fits a tested content signature, and D3-FA, File Analysis fits the static review. These describe proposed defensive practice here. CAPEC-636 concerns hiding code in file features and is too specific for this substitution; CAPEC-572 was not needed to explain the mechanism. OWASP and STRIDE add little to a single damaged binary with no application design to assess.

10. Threat Intel and Standards Integration

10.1 STIX sample

I would share this as an analytic description first: ELF-like prefix 7f 45 4c ??, altered fourth byte, valid class/data/version, no NULs in a file of at least 4096 bytes, and spaces over half the bytes. It is a heuristic, not a known malicious sample. A STIX 2.1 Indicator with a YARA pattern would require a valid rule, stable ID and timestamps, defined producer, confidence, and test evidence. I do not have those prerequisites or an exchange destination, so there is no publishable STIX object or TAXII feed for this case.

10.2 STIG applicability

There is no STIG check for this particular CTF byte pattern. In an actual deployment I would inspect the applicable operating-system and endpoint-protection STIG for configured malware protection and logging, then record the exact product and version. I would not claim a configuration finding from this sample alone.

10.3 CIS Controls v8

CIS Controls v8 places endpoint malware software under Safeguard 10.1, audit-log collection under 8.2, centralized alerting under 13.1, and host-based intrusion prevention under 13.7 where appropriate. A tested file-content rule could support 10.1 through a product that actually accepts it. A reliable event join could support 13.1. Network-flow collection under 13.6 is not the sensor needed for this on-disk byte pattern. None of these controls was deployed in the challenge.

11b. Mitigation Realization

I would integrate file-byte scanning with an agent capable of on-write or scheduled inspection, route leads to an analyst queue, and collect execve failure events separately. The collector would attach host, path or file ID, timestamp, and SHA-256. Tuning would compare known converters, build outputs, and test fixtures. I would not auto-quarantine on this heuristic alone. FIM or IMA becomes useful where a trusted binary baseline exists; it does not reconstruct unknown bytes. These are implementation requirements, not controls proven active by this exercise.

12. Indicators, Artifacts, and Detection Engineering

12.1 IOCs (illustrative, sanitized)

There is no retained hash, host, path, actor, or network indicator to share. The reported artifact traits are 7f 45 4c 4b, zero NULs, roughly 14,100 spaces, and approximately 17 KB total. Only the first trait is an exact recorded byte sequence; the counts are rounded. I treat the combination as a file-triage signature, not an IOC tied to a campaign.

12.2 YARA rule

A YARA rule could combine ELF-like identification with math.count thresholds. I have not validated that form with a YARA engine or measured false positives. The Python implementation is the tested local form of the narrow hypothesis. Its result should feed manual review before any YARA port is deployed.

12.3 Sigma rule

A Linux auditd Sigma rule for execve returning -8 could flag an ENOEXEC event, provided the log pipeline maps syscall and exit fields as assumed. Such an event cannot assert ELF-like magic because audit events do not contain the file's first bytes. I would title that rule "Linux exec format failure," keep it low severity, and enrich it with a separate file scan. I have not shipped it as a standalone detector because the event alone does not answer the file-content question.

12.4 SIEM queries

The useful join is file_scan(host, stable_file_id_or_path, scan_time, verdict) to exec_failure(host, attempted_path, exec_time, errno) within a short, ordered window. An auditd exe field can name the calling executable rather than the failed target, so I would normalize the target from appropriate PATH records and verify an event adapter against real logs. A file-create event joined to an unrelated process-create event by device alone does not establish failed execution. There is no validated SPL or KQL query to publish for this particular sensor schema.

12.5 Telemetry requirements

The byte signature requires access to the file image, or counts calculated by a trusted collector. For correlation, I need host ID, stable file identity or canonical path, collection time, hash, scan result, attempted execution target, syscall return, and synchronized clocks. I would document retention and permissions for binary collection. Sysmon for Linux process-creation records can provide useful process context, but cannot substitute for a missing file-byte scan or prove a failed attempt by themselves.

12.6 Detection-engineering notes

I tested the invented positive, benign, and near-miss fixtures locally. The positive reproduces the hypothesized substitution; the near miss changes only the magic; the benign retains a standard ELF-like header. Those tests establish only the Python branch logic. Real ELF corpora, build pipelines, anti-malware scanning, YARA conversion, audit schemas, false-positive rates, and real attacker samples remain untested. A hit should be triaged with provenance and file content, not treated as proof of intent.
