Three Code Objects in One Python Function

The checker seemed to have one function doing all the work. Its body changed three times while the program ran.

Summary

The challenge. A self-contained Python script accepted or rejected a candidate flag. Its visible source hid the check inside serialized code objects.

What I did. I split the embedded blob, inspected each code object, found a compatible CPython version, and read the RC4 data flow from the disassembly.

The result. The recovered input passed the format gate, reproduced the stored ciphertext, and was accepted by the checker.

The limit. This local puzzle produced no production telemetry. The blue/purple exercise and detection ideas below are proposed.

The script and the first clue

I was given one Python script. It asked for a flag and told me whether I had the right one. The challenge hint talked about getting more behavior from fewer named functions. I took a closer look at the call path and found the trick: the script split an embedded byte blob into three serialized code objects, assigned each one to the same function's __code__ attribute, and called that function after each swap.

The function's name stayed the same. Its instructions did not. That made the visible definition a poor guide to what the checker actually did. I needed to recover the three bodies, then follow the last one through to the comparison. The intended answer had a fixed flag prefix and length; I withhold the challenge-specific bytes and the flag itself here.

This was a local reversing puzzle. I did not have an incident, production system, or attacker telemetry to analyze. The blue/purple exercise later in this article is my proposed way to test the technique in an operational setting.

I pulled apart the hidden bodies

I isolated the blob without running the interactive entry point and split it at the delimiter used in the source. The three pieces began with a code-object marshal marker. I deserialized them with marshal and looked first at their constants, names, and local variables. That quick pass gave me a map of the checker: one body read input, one enforced the prefix and exact length, and one validated the bytes. Locals such as S, key_length, and keystream_byte made RC4 likely. They did not prove the roles of the embedded constants.

The inspection itself was short. The variable functions held the embedded blob; the delimiter separated its three bodies.

import marshal

segments = functions.split(delimiter)
codes = [marshal.loads(segment) for segment in segments]
for code in codes:
    print(code.co_varnames, code.co_names, code.co_consts)

I neutralized the interactive entry point before loading the script to obtain that blob. That edit depended on an exact text match and still executed the rest of the script. I would isolate an untrusted sample and extract its literal without executing it. Python's marshal documentation warns against deserializing untrusted data.

I inspected each segment on its own. That kept the visible source, the serialized objects, and the behavior of the running function from blurring together. The functions variable was a container for three bodies. It did not give me three ordinary definitions to read in place.

The output let me identify the RC4-shaped stage before I could trust its instructions. It did not give me a valid solution by itself. A constant pool can contain the right key and ciphertext while leaving their use, byte order, and repeated values unclear.

The bytecode looked wrong until I changed interpreters

The first disassembly was incoherent. marshal.loads had produced objects I could inspect, but my host interpreter did not assign the same meanings to their opcode bytes. I tried two CPython minor versions that were wrong before finding the version that gave a coherent listing. The successful listing agreed with the surrounding script and the local-name clues.

That distinction cost me time. A code object's outer structure can be readable while its co_code bytes are being interpreted under the wrong opcode table. CPython changes bytecode between releases; the Python dis documentation says so directly. I installed candidate minor versions and used dis.dis on the validator under each one. Only one gave a listing whose control flow agreed with the script. An opening RESUME opcode can help identify a mismatch in versions that use it, but I required a coherent listing before relying on any operand flow.

The mechanical reason is specific to CPython. A function's __code__ points to a code object containing bytecode, constants, names, and local-variable metadata. Reassigning that attribute can give a compatible function a new body at runtime. marshal can serialize code objects, but it is tied to Python's internal formats. Reading the wrapper and reading the opcodes are separate checks. The challenge worked because the script kept its three real bodies inside serialized data and swapped them into one callable when needed.

My first RC4 attempt was backwards

The constant pool contained the material I needed, but it did not tell me how the validator used it. I initially reversed the key and ciphertext roles. I also under-counted an embedded byte list after treating repeated values as duplicates. The output was garbage. That was a useful failure because it exposed exactly what I had assumed: a pool of constants is a collection of values, not an ordered account of how the code constructs its inputs.

I went back to the native disassembly, followed the assignments, and kept repeated bytes in their original order. The validator used a 128-byte key and compared against 40 bytes of stored ciphertext. Its logic was RC4(key, candidate) == ciphertext, after the earlier gate had accepted the candidate's format.

RC4 builds a 256-byte state from the key, then generates a byte stream and XORs it with the data. XORing the same stream twice returns the original bytes. That meant I could run the validator's RC4 routine over its stored ciphertext to obtain the input it expected:

candidate = rc4(key, ciphertext)
assert rc4(key, candidate) == ciphertext

I did not need a brute-force search. The equality check gave me an inverse operation. For background on why RC4 is unsuitable for modern TLS, RFC 7465 prohibits its cipher suites there. This checker did not use TLS.

I checked the RC4 identification against the instruction sequence, not only the variable names. The code built a 256-entry permutation S, mixed it with the key, advanced two indices while producing a keystream byte, and XORed each input byte with that stream. Those are the key-scheduling and output phases of standard RC4. The stored 40-byte value was the comparison target. Its length also matched the input gate, which gave me another way to catch the earlier under-counted byte list.

How I checked the recovered input

I checked the recovered input at three points. It had the required prefix and exact length. Feeding it back through RC4 reproduced the stored 40-byte comparison value. The unmodified checker then accepted it under the matching CPython version. That last run checked the whole path, including conditions around the RC4 call.

What I would bring into a blue/purple exercise

I would use this technique to test analysis and visibility. A purple team could build a benign three-stage Python sample: one blob containing serialized code objects, a gate, and a harmless comparison. The sample would swap __code__ at runtime. The blue team would receive the file plus whatever process and script telemetry its actual environment collects.

I would ask the blue team to answer four concrete questions. Did its collection show that the Python process loaded serialized code? Could an analyst identify which function body actually ran? Could they find the matching CPython version and reproduce the disassembly? Could they tell the difference between this sample and legitimate software that uses dynamic code? The last question needs real baseline data before anyone writes an alert.

For the purple pass, I would vary the packaging while keeping the three-stage behavior: reorder benign constants, change the delimiter, or put the blob in a different source location. A brittle string rule should break. An analysis procedure that follows the data into marshal.loads and the assignment to __code__ should still explain the sample. I would record whether the relevant telemetry exists, how analysts recovered the behavior, and the false positives found in ordinary Python tooling. These are exercise objectives and proposed checks. I have not run this drill or measured a detection rate.

The exercise would produce a small set of usable artifacts: a benign sample and its source, the three serialized segments, a known-good disassembly under the matching interpreter, and a worksheet for the blue team's observations. I would put the expected stage order and the RC4 comparison in the answer key. During replay I would change one variable at a time, so a miss has an explainable cause. If endpoint logging never exposes the code swap, the outcome is a visibility gap to document. If it does, I can test whether an analyst can reconstruct the behavior from that evidence. Either result is more useful than writing a rule against the string marshal and calling the exercise done.

A hunting hypothesis remains useful if an organization has the right evidence: Python code that deserializes an embedded code object and then assigns it to __code__ deserves inspection in the right context. I would first check whether endpoint telemetry captures either operation at all. Next I would test against legitimate dynamic-code packages, tune scope, and measure misses on varied samples. Until that work is done, the idea is proposed and unvalidated. It is not a production detection.

I found no basis here for STIX/TAXII objects, intelligence attribution, or a deployable YARA, Sigma, or SIEM rule. A rule needs a real data source and tests against both benign and suspicious behavior.

Reusable tools and my next reversing checklist

I came away with two reusable methods: a standard-RC4 routine that takes a key and bytes, and a bytecode-triage procedure. The routine performs the same XOR operation for encryption and decryption; it does not cover RC4 variants. The procedure moves from blob isolation through marshal inspection, interpreter matching, and a trustworthy disassembly.

For the next checker like this, I would:

  1. Save the embedded bytes and their order before executing any part of the sample.
  2. Identify every code-object segment and inspect its names, constants, and signature.
  3. Treat a garbled listing as a possible version mismatch. Match the CPython minor version and require a coherent control flow.
  4. Follow assignments and byte construction in the disassembly. Repeated constants still count when the code uses them twice.
  5. Write the validator's exact equation, including its format gate. Invert a symmetric transform only after the operand roles are clear.
  6. Check the candidate against the gate, a cryptographic round trip, and the original program when the artifact is available.

I would keep the extraction and execution steps in an isolated environment for untrusted code. marshal is an internal Python serialization format, not a safe interchange format for hostile inputs.
