Three Code Objects in One Python Function

The checker seemed to have one function doing all the work. Its body changed three times while the program ran.

Summary

The challenge. An interactive Python checker accepted or rejected a candidate flag. Its visible source hid three stages inside serialized code objects.

What I did. I split the embedded blob, inspected each code object, matched its CPython version, and inverted the final RC4 comparison.

The result. The recovered input passed the format gate, reproduced the stored ciphertext, and was accepted by the checker.

The limit. This was a local reversing puzzle. The operational exercise and detection ideas below are proposed and unvalidated.

1. Problem Statement and Threat Scenario

I was given one Python script that asked for a flag and answered yes or no. The hint talked about doing more with fewer named functions. In the source, I found an embedded byte blob split into three serialized code objects. The script assigned each object to one function's __code__ attribute and called that function after each swap. The name stayed put while its instructions changed.

My job was to recover the input that survived a format gate and the final validator. The expected answer had a fixed prefix and length. I withhold the flag and the embedded key and ciphertext values here, while keeping the mechanism and checks that established the result.

This was a self-contained reversing puzzle. It supplied no attacker, victim system, or production telemetry. I treat the operational comparisons later in the article as proposed tests of the technique.

2. Techniques, Tooling, and Actions Taken

I read the script's call path first. The visible function definition was only the starting body; I needed the code objects it would execute later. I isolated the embedded blob, split it on the script's delimiter, and inspected the three serialized objects. Their names and constants pointed to an input reader, a prefix-and-length gate, and a validator. Local names such as S, key_length, and keystream_byte suggested RC4 in the third stage.

My first disassembly was incoherent. I had used the Python interpreter already on my machine. I tried two other CPython minor versions before one produced instructions that agreed with the script and the local-name clues. That was the point where I could follow the assignments instead of guessing from constants.

I did guess too early once. I reversed the roles of the key and stored ciphertext, then under-counted a byte sequence after collapsing repeated values. The output was nonsense. I returned to the working disassembly, kept the byte sequence in order, and traced which value fed the RC4 key schedule and which value the checker compared with its output. From there I ran RC4 over the stored ciphertext, checked the gate, checked the round trip, and ran the recovered input through the unmodified checker.

3. Tooling and Scripts

I used Python's marshal to inspect the code objects and dis under the matching interpreter to read their instructions. The important extraction step was the split and inspection:

import marshal

segments = functions.split(delimiter)
codes = [marshal.loads(segment) for segment in segments]
for code in codes:
    print(code.co_varnames, code.co_names, code.co_consts)

Here, functions is the script's embedded blob and delimiter is the byte sequence it used to separate the bodies. I neutralized the interactive entry point before loading the script to obtain that blob. This worked for the challenge, but that exact text edit still executed the rest of the script. I would parse out the literal or use an isolated analysis environment for an untrusted sample. Python warns that marshal is unsafe for untrusted data.

I fetched candidate CPython builds and disassembled the validator with each interpreter's dis module. The first two listings made no sense; the matching version exposed the gate and RC4 data flow. I used the ordered byte construction from that listing because the constant pool alone did not preserve the roles I needed.

The recovery operation was small:

candidate = rc4(key, ciphertext)
assert rc4(key, candidate) == ciphertext

The helper accepted bytes for both arguments. I checked its standard-RC4 behavior against known-answer vectors, then used the challenge's 128-byte key and 40-byte comparison value. The table separates what each tool produced from what I concluded from it.

4. Concept Explanation

A Python function can run a different compatible code object after an assignment to function.__code__. That object carries bytecode along with constants, names, and local-variable metadata. In this checker, one callable acquired three bodies in sequence. Counting named functions in the visible source would have missed most of the behavior.

marshal serialized those bodies. I could inspect their structure on my first interpreter, but its dis module interpreted the raw opcode bytes under the wrong CPython minor version. CPython bytecode changes across releases, as the Python dis documentation notes. A readable constant pool did not make the disassembly trustworthy. I needed a coherent listing under the producing interpreter before relying on operand order.

RC4 starts with a 256-entry permutation, mixes it with the key, then advances two indices to produce a keystream byte for each data byte. XOR combines that stream with the input. Applying the same stream twice returns the original bytes. RFC 7465 prohibits RC4 cipher suites in TLS; this challenge used the old primitive inside a local checker, not TLS.

5. Exploit / Analysis Mechanics

The second body required a fixed prefix and exact length. The third body took the candidate as bytes, used the 128-byte key in RC4's key schedule, and compared the transformed candidate with a stored 40-byte value. The native disassembly settled those roles. My earlier key/ciphertext swap had come from looking at the constants without following their assignments.

The validator's condition was RC4(key, candidate) == ciphertext. The same operation on the stored ciphertext recovered the candidate. That is why this solve did not need brute force or a guessed keystream. I kept repeated bytes in the order the instructions constructed them; dropping a duplicate changed the length and broke the check.

I verified the result at three levels. The candidate met the prefix and length gate. RC4 over that candidate reproduced the stored comparison bytes. The original checker accepted it under the matching CPython version. The last run covered the surrounding input handling as well as the cipher equation.

6. Lessons Learned

I now separate code-object structure from instruction meaning when I triage Python bytecode. Names and constants can point me toward the algorithm, but I do not trust an opcode listing until I have matched the interpreter. An opening RESUME opcode can be a quick version clue where that opcode applies. I still require the whole listing to make sense.

The failed RC4 attempt was my own avoidable error. I had inferred data roles from a pool of values and removed repeated bytes as though I were deduplicating a set. Next time I will trace store targets and byte construction before writing a decoder. Once those roles were clear, RC4's symmetry reduced the recovery to one call and a round-trip check.

7. Operational Extrapolation

Individual Practitioner Development

This exercise made me work across CPython code objects, serialized bytecode, interpreter versions, and a stream-cipher validator. I would repeat the method on a sample that also encrypts or reorders its embedded code objects. That would test whether I can still recover the behavior when the easy constant-pool clues disappear.

Security Operations

I would build a benign three-stage sample with the same __code__ swap and give the blue team the sample plus its ordinary endpoint and script telemetry. The first question is whether its collection reveals the dynamic load at all. Then I would ask an analyst to recover the actual bodies and identify the right CPython version. I would vary the delimiter and placement of the embedded blob during replay to see whether the process depends on a brittle string match.

I would record the collected evidence, time to recover the stage sequence, legitimate dynamic-code examples that look similar, and misses from the varied samples. If telemetry cannot show the behavior, the exercise documents a visibility gap. If it can, I can evaluate an analyst workflow. I have not run this drill or measured a production detection rate.

Intelligence Operations

This checker gave me no actor, infrastructure, collection source, or attribution lead. I would not turn the puzzle into an intelligence finding. The transferable skill is unpacking an obfuscated Python sample when a real collection provides one.

8. Reusable Tools, Scripts, and Artifacts

The two reusable pieces are a standard-RC4 byte routine and a bytecode-triage procedure. The RC4 routine takes key and data bytes and returns their keystream XOR. I used it for the inverse and the round trip; it does not cover RC4 variants. Known-answer vectors checked the primitive, while the checker run tested the whole challenge path.

My bytecode procedure starts by saving the embedded bytes in order. I split the segments, inspect each code object's constants and locals, and match the CPython minor version before reading instructions. I then follow assignments, recover the validator equation, and test the candidate against every earlier gate. A large version gap may make marshal loading fail outright. Even when loading succeeds, I do not assume the opcodes mean the same thing.

These methods need an isolated environment when the input is untrusted. The challenge's entry-point edit was tailored to its script and is not my general extraction procedure.

12. Indicators, Artifacts, and Detection Engineering

The local checker produced no production host or network events and no IOC. I would not publish a YARA, Sigma, or SIEM rule from it. My proposed hunting hypothesis is narrower: inspect Python processes that deserialize embedded code and assign a new function __code__ where the environment can capture that behavior.

I would validate the data source before writing a query, then test the hypothesis against benign dynamic-code use and variants of the sample. The status remains Proposed, unvalidated. A string hit on marshal alone would neither prove a malicious load nor cover other ways to hide code.
