Three Code Objects in One Python Function

The source showed one checking function, but it behaved like three. The trick was in the code objects it loaded at runtime.

Summary

The challenge. A self-contained Python script accepted or rejected a flag. Its visible source hid the check behind serialized bytecode.

What I did. I split the embedded blob into three code objects, found the Python version that disassembled them cleanly, and inverted the final RC4 comparison.

The result. My solve record says the recovered input passed the format gate, reproduced the stored ciphertext, and was accepted by the original checker.

The limit. The ZIP contains this writeup but not the challenge script or recovery artifacts, so the exact bytes cannot be replayed from this public page.

The script I was handed

The challenge gave me a Python script that asked for a flag and answered yes or no. Its hint talked about doing more with fewer functions. I initially read that as flavor text. Then I found the part of the source that mattered: a byte blob split into three serialized code objects, each assigned in turn to the same function's __code__ attribute. The function's name stayed put while its body changed.

That changed how I approached the checker. Reading the visible function definition would tell me little about the code that actually ran. I needed the three hidden bodies and, especially, the last one that decided whether my input was right.

Getting the hidden bodies into view

I separated the blob at its delimiter and inspected the code objects with Python's marshal module. Their constants and local names gave me a rough map: the first stage read input, the second checked its prefix and exact length, and the last performed the comparison. Names such as S, key_length, and keystream_byte pointed toward RC4, but names alone were not enough to tell me which embedded bytes were the key and which were the target ciphertext.

My first disassembly was a mess. I had used the Python interpreter on my machine, and its opcode meanings did not match the serialized code. I tried other minor versions until the instructions made sense alongside the surrounding source. Python's dis documentation is blunt about this: CPython bytecode can change between releases. Successful deserialization was not proof that I was reading the instructions correctly.

Stage What I could establish Why it mattered
Input The script took a candidate string. I could trace the value that reached the checker.
Gate It required a fixed prefix and exact length. A plausible decryption result still had to satisfy the program's format check.
Validator It ran RC4 with an embedded key and compared the output with stored bytes. The comparison could be reversed without searching candidate flags.

The guess that cost me time

I tried to rebuild RC4 before I had the operand roles straight. I swapped the key and ciphertext in my first attempt and counted a repeated byte only once while copying an embedded list. The result looked nothing like a flag. That failure was useful: it sent me back to the instruction stream to follow the assignments and the ordered byte construction instead of trusting the constant pool as a recipe.

Once the native disassembly showed the data flow, the check was simple. It computed RC4(key, candidate) and compared those bytes with the embedded ciphertext. RC4 generates a keystream from the key and XORs it with the input. Applying the same operation to the ciphertext yields the candidate that produces it: RC4(key, ciphertext). I used the 128-byte key and 40-byte comparison value recorded in the checker. I am leaving both constants out of this public page.

My notes record three checks on the recovered string. It had the required prefix and length. Running it back through RC4 reproduced the comparison bytes. The original, unmodified program accepted it under the matching interpreter. Those checks were stronger than a flag-shaped output alone. The ZIP did not include the original script or the companion RC4 utility, so I cannot rerun them from this archive.

Taking it into defensive work

This was a local reversing puzzle. It did not give me an incident, an attacker, or host telemetry. I still see a useful exercise for a blue and purple team: give the blue team a benign Python sample that deserializes embedded code and swaps __code__ at runtime. Have the purple team vary the packaging while keeping the behavior the same. The blue team can test whether its collection actually shows the loaded code and whether its analysts can recover the behavior under the right interpreter.

I would start with process and script evidence, then decide whether a hunt is practical. A rule that fires on marshal alone would catch legitimate tooling and miss other loaders. The CTF provides no false-positive rate or production log sample, so this is a proposed exercise rather than a detection I tested. I would also handle unknown serialized code in an isolated environment: Python warns that marshal is not secure against maliciously constructed data.

Framework fit and references

MITRE ATT&CK T1027, Obfuscated Files or Information, gives me a vocabulary for the hidden code. T1140, Deobfuscate/Decode Files or Information, describes a possible step in real malicious code execution. I use both as analogies. The challenge itself showed a checker I reversed; it did not show an adversary using either technique in an environment.

I do not have an operational asset or a measured control failure to map to NIST or CIS controls here. The practical control lesson is narrower: collect enough evidence to see dynamic code loading, analyze it with the matching runtime, and test any proposed alert against legitimate use. RFC 7465 prohibits RC4 cipher suites in TLS; that standards point is background on RC4, not a claim that this puzzle used TLS.

Reusable reversing checklist
  1. Find the data that becomes executable code. Save the serialized bytes and their order before running the sample.
  2. Inspect code-object constants and names, then match the CPython minor version before trusting dis output.
  3. Follow assignments in the instructions. A constant pool does not tell you which byte sequence is a key or a comparison target.
  4. If a stream cipher checks transformed input against stored bytes, test whether the same transform recovers the input.
  5. Confirm the recovered bytes against every gate and, where the original artifact is available, the unmodified checker.

This list comes from the recorded solve. It is a method to try on similar puzzles, not a claim that every serialized Python checker uses RC4.
