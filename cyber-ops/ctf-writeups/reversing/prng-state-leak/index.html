The Shuffle Gave Away the Groups

The salt looked like the wall. The board order turned out to be the way around it.

Summary

The challenge. Partition ten 16-item boards into four groups of four under an 800 ms timer, with the last six boards showing salted hashes instead of words.

What I did. I followed the state leak through the server's shuffle, recovered 16 missing bits from a plaintext board, and used original positions to group the hashed boards.

The result. My test notes record 80 consecutive successful local replica runs after two fixes. The live service was not reached from that environment, so I have no live acceptance record.

The limit. The local test logs and compiled replica are unavailable now. The Java source and a synthetic protocol simulation support the method; the 80-run trial has not been repeated here.

1. Problem Statement and Threat Scenario

I had ten rounds of a Connections-style game. Each board contained sixteen items, and I had to submit four correct groups of four before an 800 ms round timer expired. The first four rounds showed words. From round five onward, the service showed twelve-character hex prefixes of SHA-256 digests computed from a normalized word, a separator, and a fresh eight-byte salt. A wrong group ended the run.

The salt made a dictionary lookup unattractive. The client never saw it, and the server generated a new one for each hashed board. I had the server's Java code, its word database, the message schema, and a container recipe. That white-box view changed the question I asked: could I learn where each token came from without learning its word?

The authorized client could register, log in, request one fragment, start the challenge, and submit proposals over TCP. The asset was the integrity of the server's grouping decision. The broken boundary was the fragment response: it returned part of the same per-user state later used to shuffle boards. My notes show local-replica success. I have no live flag acceptance receipt.

2. Techniques, Tooling, and Actions Taken

I read the server before trying to beat the timer. Three details lined up. getFragment advanced a 48-bit per-user state and returned its high 32 bits. applySecureShuffle advanced that same state once more, passed it to new Random(seed), and ran Fisher-Yates. Game.getAllWords() sorted words inside each group, sorted the groups, then concatenated them. That last step meant each original block of four positions belonged to one group.

Step What I tried or learned Recorded result
ST.1 Read the game loader, session handler, PRNG path, and protocol fields. Identified the leak, shuffle, and ordered group layout.
ST.2 Considered direct salt recovery, hash matching, and guessing one of 1,820 first groups. Rejected them. The salt was fresh and a wrong guess reset the run.
ST.3 Ported Java Random and its bounded nextInt behavior to Python. The implementation reproduced the shuffle in my local tests.
ST.4 Called getFragment after login. Received the high 32 state bits, leaving 16 unknown bits.
ST.5 Matched candidate states against the first plaintext board's observed permutation. One full state remained; my notes give 25 ms median over 40 runs, with a 50 ms maximum.
ST.6 Ran the ten-board solver against a local replica. Failed as the fifth board arrived hashed.
ST.7 Changed the plaintext branch from step <= 5 to step <= 4. Reached the end in single local runs.
ST.8 Repeated 25 local runs. Twenty passed; five failed on hyphenated words.
ST.9 Normalized incoming board words for database lookup and checked sort behavior across 3,648 groups. My notes give zero sort-order mismatches and 80 subsequent passes across 30 plus 50 runs.
ST.10 Packaged the client and word data for execution where the live host was reachable. Live submission was deferred; I have no acceptance receipt.

The threshold mistake was my first useful interruption. The server had already printed [HASHED MODE] after step four, but I had read the constant name as if step five would still be plaintext. The hyphen issue took longer: the server normalized words on submission while its board output retained their original spelling. Five failures in 25 runs were enough to expose the mismatch. A single clean run would have hidden it.

The rough timing is also part of the method. The client sends four independent proposals together and then reads their responses, collapsing four sequential network waits. My recorded seed search fit well inside the local 800 ms round budget. I did not measure it against the live service.

3. Tooling and Scripts

The challenge solver contains the complete standard-library Python client: registration, login, fragment request, game identification, Java-compatible shuffle, 65,536-state search, and grouped submissions. It expects the game database from the challenge beside it or as its third argument. It does not carry the database or any flag. The multiplier below comes from the server's GameManager code.

The critical state transition is short:

MASK48 = (1 << 48) - 1
STEP_MULT = (0x5DEECE66D ^ 0xABCDEF123) + 0xB
STEP_INCR = 11

def lcg_step(seed):
    return (STEP_MULT * seed + STEP_INCR) & MASK48

The leak is the high 32 bits of a state I call S2. The first challenge board uses S3 = lcg_step(S2) as the seed passed to Random. The client tries each possible low 16-bit suffix of S2 and stops when the predicted first-board permutation matches the observed one. On later hashed boards it uses the predicted permutation to put each displayed token in original_position // 4. I tested that model with a synthetic state and a ten-round in-memory protocol simulation in the local test suite. Those checks do not replay the original Java server or establish the recorded 80-run rate.

The lab guide describes the input data, how to run the solver in an authorized challenge environment, and what the defensive sequence test can and cannot show. The normalized event reviewer is separate from the solver; it is for exploring a production-style logging hypothesis, not for playing the challenge.

4. Concept Explanation

A linear congruential generator advances a state with next = (a * state + c) mod m. In this server, m is 2^48. Once the high 32 bits of one state were exposed, only 65,536 full states remained. The first plaintext board supplied a strong check on each candidate because I knew the original word order from the 912-game database and could compare a predicted sixteen-position shuffle with the board I actually received.

Fisher-Yates swaps from the end of an array toward the front. Its choices are entirely determined by the generator's output. Java's Random also has specified seed mixing and bounded nextInt behavior, including rejection sampling for bounds that are not powers of two. I reproduced those details rather than relying on Python's unrelated shuffle. Oracle's Java Random documentation specifies the 48-bit behavior and warns against security use.

Each hashed board still began as sixteen words in four contiguous groups. The server hashed the words and then shuffled those sixteen tokens. The salt concealed which hash named which word, but it did not conceal the original position once I could predict the shuffle. Four positions from each original block made a valid group. This is why the attack could pass the server's group check without recovering the salt or reversing SHA-256. The Java code uses two containsAll calls after a length check; that is set-like containment, not a general multiset-equality implementation when duplicate tokens exist. The solve did not rely on duplicate hashes.

5. Exploit / Analysis Mechanics

The state leak and the grouping rule each did a different job. The fragment call reduced a 48-bit search to sixteen unknown bits. The known first board let me distinguish candidates. Predicting later shuffles then gave each displayed hash a group index, even though I could not name the underlying word.

In symbols, if P[shuffled_position] = original_position, the proposed bucket is P[shuffled_position] // 4. The server built those original positions as four consecutive groups. The code did not have to crack a digest or guess one of the 1,820 possible four-item subsets. It submitted the actual hash strings already on the board in the arrangement the server would accept.

The first board is the observation that makes the state search practical. A bare high-32-bit fragment still leaves 65,536 states, and a later hashed board alone would not reveal which candidate's shuffle was right. This attack also assumes the database and its ordering match the running service, and that no unseen operation advances the user's state between the fragment and the boards. Those are real dependencies, not generic properties of salted hashes.

6. Lessons Learned (Practitioner Perspective)

Reading all of the server code before implementing the client saved me from spending the whole exercise on the salt. The useful chain ran through three files and two interfaces: the client-visible fragment, the stateful shuffle, and the word layout. I would have missed it if I had stopped at the first cryptographic-looking function.

The local tests were worth the time. My threshold assumption failed on the first hashed board. Then the stress run found the hyphen boundary that ordinary boards did not exercise. The server's own mode message made the first failure easy to diagnose; the 25-run distribution made the second one visible. I still cannot claim live success from that. A correct model and a local streak are strong preparation, while live acceptance remains a separate observation.

For an operational team, the parallel is straightforward. Inventory every client-visible state value, trace each random generator's consumers, and test protocol normalization on both the send and receive sides. Fast automated sessions may be a useful hunt lead, but fast play alone is weak evidence of abuse. The state read followed by machine-speed proposals is the tighter sequence.

7. Extrapolation

The practitioner exercise is a compact way to rehearse cross-language PRNG modeling: port the exact arithmetic, preserve the order of calls, compare a known output, and only then forecast later outputs. It also rehearses a useful change of viewpoint. If a defender protects item identities but validates a structural relation among items, ask whether the relation leaks through order, indexing, or timing.

For a SOC, the promising observable is a same-session sequence: a state-revealing read and four or more dependent submissions inside a short window. The event reviewer and invented event fixture make that hypothesis inspectable. A benign optimized client in the fixture also triggers it. A defender would need to add source identity, endpoint context, expected client behavior, and allowlisted testing before using the result as an alert.

For intelligence work, a confirmed implementation detail such as java.util.Random in a security path can help compare products or protocol versions, but a few timing samples do not attribute an operator or prove a generator family. I would look for an exposed value and a known output before making a state-recovery claim. No campaign, actor, or real-world IOC is established by this challenge.

8. Reusable Tools, Scripts, and Artifacts

The solver is a complete example of the state and shuffle calculation. Its java_shuffle_perm function includes the non-power-of-two rejection branch; its crack_seed function compares predicted positions early to avoid fully shuffling most bad candidates. The generic idea can be lifted into another review: enumerate the unknown state suffix and supply a target-specific verify(candidate) function. The 16-bit search size belongs to this particular leak and must be recalculated for a different system.

I also keep a short white-box triage checklist in the lab guide: list client-callable operations, mark internal state in each response, follow every PRNG use, write down data ordering before and after encryption or hashing, and inspect exactly what the validator checks. For timed protocols, measure computation and network trips separately. The proposed runtime reviewer, its fixture, and tests are defensive proofs of concept built around those observations. They use invented events and contain no challenge transcript.

10. Threat Intel and Standards Integration

An intelligence note could describe this as a technique pattern: partial PRNG state returned by an auxiliary API, a known-output check, and prediction of a downstream shuffle. That is more useful than an indicator containing the game's operation names. The names are challenge-specific, and there is no campaign infrastructure to share.

If another team had an affected product, I would put the pattern into a STIX 2.1 attack-pattern object and attach the exact product/version evidence, observed endpoint, and confidence there. I would use a course-of-action object for removing state disclosure and replacing security-sensitive randomness. I have no TAXII feed or exchanged STIX bundle here. The lab guide gives the small field list a defender would need before sharing: affected build, endpoint behavior, logging coverage, and tested reproduction. Any application STIG or CIS safeguard mapping should be checked against the current baseline for the actual product; a challenge source tree alone does not establish a compliance finding.

11b. Mitigation Realization

I would start by removing getFragment or making its response independent of shuffle state. I would also separate any client-visible telemetry generator from the generator used to order security-relevant items. Replacing Random with SecureRandom in that path makes forecasting harder, but I would still review the protocol: when the decision is "which supplied tokens form a group," a predictable or leaked ordering defeats a hidden word-to-hash mapping. The validator should use a design whose acceptance cannot be reconstructed from a client-visible permutation alone.

A code review gate can flag new Random(...) where the result controls authorization, nonce selection, challenge assignment, or any other security decision. A simple text search is only a lead; data-flow review must establish the actual use. A regression test should expose the fragment to a test client, gather a known board, attempt prediction, and fail when the client can recover the next partition. Repeat with hyphenated words because the original client failed there. The synthetic test suite checks only the attack model. A defender regression test still needs to be built.

12. Indicators, Artifacts, and Detection Engineering

Indicators

I have no campaign IOC, malicious domain, or production packet trace. The case-level pattern is a fragment read followed by multiple submitProposal calls at machine speed in the same session. Repeated short registrations may strengthen that lead, but legitimate test clients can look similar. Source IP and generated usernames alone would be weak selectors.

YARA - static-side artifact

A static source search for new Random(seed) near a shuffle is useful during review, but a YARA hit would not prove that the seed is exposed or that the shuffle gates a security decision. A YARA expression for these strings would be a triage lead, not a validated finding. Reviewers should trace getFragment, applySecureShuffle, and getAllWords together. A grep-style pattern can find candidate files; the data-flow argument is the finding.

Splunk SPL - runtime indicator

The following template expects normalized session_id, source_ip, operation, and _time fields. It selects submissions within five seconds after the first fragment read. Map fields and index names to an actual deployment before use.

index=application_logs earliest=-1h
| eval read_epoch=if(operation="getFragment",_time,null())
| eventstats min(read_epoch) as first_read by session_id source_ip
| where isnotnull(first_read) AND _time>first_read AND _time<=first_read+5 AND operation="submitProposal"
| stats count as submissions by session_id source_ip first_read
| where submissions>=4

Microsoft Sentinel KQL

This template assumes a normalized ApplicationLogs table. It keeps the read time and submission time separate, so event order is explicit. Multiple reads in one session may produce duplicate joins and need a product-specific deduplication rule.

let reads = ApplicationLogs
| where TimeGenerated > ago(1h) and Operation == "getFragment"
| project SessionId, SourceIP, ReadTime=TimeGenerated;
let submissions = ApplicationLogs
| where TimeGenerated > ago(1h) and Operation == "submitProposal"
| project SessionId, SourceIP, SubmitTime=TimeGenerated;
reads
| join kind=inner submissions on SessionId, SourceIP
| where SubmitTime > ReadTime and SubmitTime <= ReadTime + 5s
| summarize Submissions=count() by SessionId, SourceIP, ReadTime
| where Submissions >= 4

Log source and pipeline requirements

The useful sensor is the application operation log. It needs a stable session identifier, event time with enough precision for sub-second work, operation name, and source identifier. A reverse proxy without operation names cannot support this sequence. The JSONL reviewer accepts those four normalized fields and is bounded to a 2 MB, 20,000-line local file. Its fixture and test suite are linked here so the input and expected result can be inspected together.

Detection engineering notes

The local test finds a case-like session and a deliberately benign fast client. It leaves a delayed near miss clear. That is an honest result: the sequence has some recall in a toy event stream and poor specificity without endpoint and client context. The SPL and KQL are query templates; neither was run in a SIEM or tuned against production telemetry. Ordinary Sigma selectors cannot express this complete timed sequence. A formal Sigma correlation would need the specification's ordered event and count semantics, backend support, and a mapped application log source. I would validate the query and investigate known automation before promotion.
