The Message Packed Eight Bytes at a Time

The numbers looked imposing until I stopped reading them as numbers. Eight bytes at a time, they were a sentence.

Summary

The challenge. Recover a location-and-time message from eight decimal integers and submit its words in the required flag format.

What I did. I checked integer widths and hex bytes, unpacked each value as an eight-byte block, compared byte orders, and stopped at the null terminator.

The result. The recovered words produced an accepted flag, as recorded in the challenge result.

The limit. The eight challenge integers and answer are withheld; the linked decoder and triage lab run on a separate synthetic sample.

1. Problem Statement and Threat Scenario

I was given eight large decimal integers and a flag format. The task was to recover a short message naming a place and a time, then join its content words with underscores inside the flag wrapper. There was no service to interrogate and no binary to reverse. The integers were the whole puzzle.

The values sat around 10^18, which made them look more like cryptographic material than text at first glance. Their size was the clue. An unsigned 64-bit word can hold eight bytes, and eight bytes can hold eight ASCII characters. If the puzzle had packed a sentence into those words, I could reverse it without guessing a key.

The challenge was offline and non-adversarial. It showed no attacker, vulnerable service, or event stream. Later sections describe how I would reuse the decoding habit when examining an acquired suspicious file. That is a proposed analyst workflow, not an event that occurred in this challenge. I leave the actual place, time, integers, and flag out of this public page.

2. Techniques, Tooling, and Actions Taken

I began with width, using Python's bit_length() on the eight values. My notes put each at 63 bits. An ASCII character uses at most seven bits, so the first byte of a big-endian eight-character block keeps its high bit clear. That puts the packed value below 2^63. The width did not prove the interpretation, but it gave me a cheap test to run next.

I printed the numbers as hexadecimal and looked at the bytes rather than the decimal spellings. The leading byte in one block was 0x4D, or M in ASCII, and the others looked like printable text. I then converted every value to exactly eight bytes in big-endian order and joined the blocks. The result read as an English message.

I checked little-endian too. That version reversed the characters within each eight-byte block and gave me garbled text. It was an instructive dead end: the same numbers can become very different byte streams when I choose the wrong order. I kept the byte-order check in the method because a readable output is much better evidence than the width alone.

At the end of the big-endian buffer I found a null byte followed by two padding bytes. I cut the message at the first null, kept the content words, and placed them in the required underscore-separated flag format. The platform accepted the submission. The case can be understood and retested with a placeholder sample without publishing that answer.

3. Tooling and Scripts

This short Python example uses five synthetic integers. They decode to a placeholder sentence with the same kind of final block:

sample = [
    6008203707511283821, 7306373966651138160, 7809632514823253604,
    2338610025081104239, 2335227948786798938,
]
raw = b"".join(value.to_bytes(8, "big") for value in sample)
message = raw.split(b"\x00", 1)[0].decode("ascii")
print(message)  # Sample meeting place and time go here

The sample integer file holds those same five values. The generalized decoder accepts a file or positional integers, checks the selected unsigned width, and prints both byte orders with --auto:

python -B artifacts/int_unpack_decode.py --file fixtures/sample_packed_ints.txt --auto

Its big-endian view reads Sample meeting place and time go here. The little-endian view begins m elpmaS and stays readable as individual characters but makes no coherent sentence. The synthetic final block contains 0x00 followed by QZ; those are filler bytes, not part of the message. In the challenge, my notes describe a null followed by two non-text padding bytes. The two sets of values serve different purposes.

The decoder uses Python's standard library. It can keep bytes after the null for inspection, change the block width, and emit the raw hex view. The run guide describes the bounds and output. I did not need an automated submission tool for this offline task.

4. Concept Explanation

Each integer is a base-256 number. Its eight bytes are eight base-256 digits. In big-endian order, the first byte carries the most weight:

value = b0*256^7 + b1*256^6 + ... + b6*256 + b7

int.to_bytes(8, "big") performs the inverse conversion. The explicit width matters. An integer can begin with a zero byte, and a minimal-length conversion would silently drop that byte and shift every following character out of place. I used eight bytes for every value, then concatenated the results in their given order.

ASCII fits in seven bits, so an eight-byte block of ASCII has a leading byte below 0x80. Its big-endian integer is therefore at most 63 bits. It need not be exactly 63. The synthetic sample's five integers have bit lengths 63, 63, 63, 62, 62; blocks beginning with a space use fewer. This is why I treated the 63-bit observation as a clue and checked the actual bytes.

The null byte marks the end of this particular string. Fixed-width packing still fills the last eight-byte block, so bytes after the null are padding for this exercise. I discarded them only after identifying the terminator. In a different format, a null may be valid data, and truncating there would be a mistake. The producer's format decides that boundary.

5. Exploit / Analysis Mechanics

The transformation was reversible because the producer had preserved the byte values in order. For each integer, I used an unsigned eight-byte big-endian conversion. I joined the blocks, stopped at the first 0x00, and decoded the prefix as ASCII. I had no cipher key to recover and no search space to explore.

The sample gives me a useful round trip. int.from_bytes(block, "big") on each of its five original blocks returns the exact integers shown in Section 3. The same sample read in little-endian order produces garbled blockwise reversals. Those checks validate the conversion and make the byte-order choice visible. Grammatical text and the challenge's accepted submission are the independent checks on the original result.

The method assumes a consistent block width, byte order, and character encoding. An out-of-range integer should be rejected instead of being truncated. I also need to keep the null and the trailing bytes visible during triage before deciding what counts as padding. The decoder exposes a --keep-null option for that inspection.

6. Lessons Learned

I nearly gave the numbers more mystery than they deserved. Printing a few hex bytes took less effort than testing a homemade cipher idea, and 0x4D gave me a letter I could recognize. Once I saw printable bytes across the blocks, I had a concrete hypothesis to test.

Width helped, but it was a fingerprint with limits. All-ASCII eight-byte blocks stay below 2^63; they do not all have a 63-bit length. The little-endian view reminded me that printable characters alone are weak evidence too. Both views of the sample are printable. Only one reads as the kind of phrase the challenge asked for.

The last few bytes were easy to overlook. Keeping the whole padded block would have polluted the flag. Cutting at the null matched this format and gave me the clean place-and-time phrase.

7. Operational Extrapolation

Individual Practitioner Development

I can reuse this small sequence of checks whenever data has been stored as words instead of bytes: count the width, inspect hex, unpack both orders, and round-trip the conversion. The next useful practice case would use another block width or UTF-16, where zeros appear inside the text and this null-trimming shortcut fails.

Security Operations

The puzzle itself produced no host or network activity for a SOC to detect. A related real-world job begins only after an analyst has collected a suspicious Python file. Literal arrays of large integers can hide readable strings from a quick source review. I built a static triage script that parses a Python file without executing it and flags arrays whose eight-byte views are mostly printable. It gives the analyst a line number and both plausible byte orders, then leaves the meaning and risk decision to human review.

I would use that result as one lead in a file investigation, alongside the file's origin, hash, execution evidence, and the code that consumes the array. A readable string might be a harmless label, test data, or something operationally important. The array alone does not tell me which. The triage guide lists the input limits, false positives, and collection fields I would need in a real case.

Intelligence Operations

No source, infrastructure, or actor in this challenge supports an intelligence finding. Representation fluency could help decode a collected artifact in a future investigation, but that investigation would need its own provenance and corroboration. I would not attach an attribution or campaign label to these integers.

8. Reusable Tools, Scripts, and Artifacts

The challenge primitive is the fixed-width integer decoder. It accepts decimal values or the synthetic integer fixture, a block width of 1-16 bytes, a selected byte order, and an option to show both orders. It returns JSON with ASCII text when valid and the raw hex bytes. It bounds the file to 1 MB and the list to 4096 values. The guide gives the command and expected sample output.

For defensive reuse I added a separate read-only Python source triage tool. It examines literal lists and tuples in a collected .py file through the syntax tree. It does not import or execute the file. The positive source fixture contains the placeholder integers; benign numeric metrics and a UTF-16 near miss give it two negative cases. The local tests check the decoded phrase, round trip, byte-order contrast, positive detection, both negatives, and malformed or out-of-range inputs.

This scanner deliberately misses computed arrays, changed widths, compressed material, and non-Python carriers. Both orders of the positive sample pass its printable test, so it reports both for analyst review. No production file set or endpoint sensor has been tested. The decoder is a working analyst aid; the scanner is a synthetic triage proof of concept.

9. Framework Applicability and Mapping

I do not assign an ATT&CK, CAPEC, D3FEND, STRIDE, or OWASP technique to the challenge. It was an offline representation puzzle with no adversary behavior or vulnerable application to classify.

The proposed file-triage use has a conditional ATT&CK connection. If a malicious script intentionally packs strings into integers to hide its content, T1027 Obfuscated Files or Information may describe that separate observed behavior. A matching array alone does not establish malice or an ATT&CK technique. I would first inspect how the file uses the data and what execution or delivery evidence exists. I do not assign a finer subtechnique to the synthetic fixtures.

10. Threat Intelligence and Standards Integration

The challenge has no IOC, actor, malware, infrastructure, or victim. A STIX Indicator, TAXII exchange, or threat report would have nothing evidence-backed to say about it. The placeholder phrase is a test string, not an indicator.

If a real investigation surfaced an encoded array, I would preserve the file hash, acquisition time, source system, exact array bytes, decoding parameters, and the code path that consumes them. Those fields let another analyst reproduce the decode and judge whether the content belongs in a larger case. Any structured intelligence object would follow from that case's evidence, not from the packing method by itself.

11. Controls Mapping and Mitigation Realization

I found no vulnerability or misconfiguration in the challenge, so I do not claim a NIST, CIS, STIG, CMMC, PCI DSS, or HIPAA control failure. There is no challenge system to patch.

For the proposed static-analysis use, the practical control is an intake process: collect suspect source without running it, keep the original bytes and hash, analyze in an isolated workspace, and review decoded strings in their code context. That process is a handling recommendation, not a tested mitigation for a known incident. A numeric-array match should start examination; it should not trigger automatic blocking.

12. Indicators, Artifacts, and Detection Engineering

The challenge supplied no runtime telemetry and no IOC. A Sigma or SIEM rule would need an event source that this offline puzzle never produced. I chose a file-level triage proof of concept instead of inventing one.

The static scanner requires a collected UTF-8 Python source file. It reports literal arrays of 3-4096 unsigned 64-bit integers when an eight-byte interpretation yields at least 16 bytes with a printable ratio of 0.95 or more and at least one letter. It records file name, line, array size, candidate byte orders, ratio, and null presence. It omits decoded text by default. Those are leads for an analyst, not IOCs. The required sensor is access to the file itself, with origin and case metadata maintained outside the tool.

The positive fixture produces one candidate. The benign and near-miss fixtures produce none; the test file checks these expectations. Benign packed text can still match, and an actual malicious file may use a form the scanner misses. There is no precision or recall estimate and no deployed rule. If I found a candidate in a real case, I would decode it with the separate decoder, check the consuming code, and correlate it with acquisition and execution evidence before calling it security relevant.
