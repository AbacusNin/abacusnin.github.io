The Password Filter That Carried Its Own Answer

The program wanted me to perform a syscall ritual. Its own data gave me a shorter path.

Summary

The challenge. Recover the flag gated by a userspace loader and an embedded eBPF syscall-tracepoint program.

What I did. I inspected the outer ELF, located the embedded EM_BPF object, reconstructed the counter and emit formula, parsed its rodata tables, and tested the diagonal layout with a forward calculation.

The result. The 40 diagonal bytes form a printable flag shape, and the inferred 4x4 grid regenerates all 160 value-table entries exactly.

The limit. The binary and tables were replayed offline. The BPF program was not loaded or run, and no challenge-platform acceptance receipt was available.

1. Problem Statement and Threat Scenario

What was presented

I had a stripped, roughly 350 KB x86-64 PIE ELF and a prompt about writing a password with the whole system at my disposal. The loader imports libbpf, libelf, and libz, asks for a PID, attaches a BPF tracepoint program, and prints characters received through a ring buffer. There was no source, debug build for the outer userspace code, remote service, or required runtime proof. A single flag-shaped string was the deliverable.

Realistic scenario it simulates

The interesting design is a gate: a userspace process loads kernel-side BPF code that watches syscalls and releases output only after a particular sequence. A real investigation might encounter a custom observability agent, hidden trigger, or BPF-based implant with similar components. This supplied binary is a challenge artifact. Its structure alone does not establish a rootkit, exfiltration, or a compromised host.

Assets and access provided

The host ELF was readable offline. Its embedded BPF object kept enough section and BTF information to name maps, tables, and the tracepoint section, even though the outer loader was stripped. I did not need a privileged Linux host to answer the challenge. I kept execution out of the recovery path because static inspection exposed the data I needed.

Analytical objective

I needed to recover the flag and explain why the answer was correct. A syntactically plausible string alone would have been thin evidence. I wanted the table layout, emit formula, grid selection, and regeneration check to agree.

Threat model

From the challenge author's side, the target PID and 160 matching syscalls seem to protect the answer. From my side, I could read the file and its embedded object. The gate controls when the program emits bytes; it does not keep the bytes' derivation out of the shipped file. In a real product, embedding a sensitive static value behind an execution gate would expose it to anyone who can inspect the binary, regardless of how awkward the runtime ceremony is.

2. Techniques, Tooling, and Actions Taken

Recon

I began with file, dynamic imports, and strings -n 8. The outer file was an ELF64 PIE for x86-64. The recorded imports included bpf_object__open_mem, bpf_program__attach_tracepoint, ring_buffer__poll, and bpf_map__update_elem. Strings such as Enter a PID to monitor, Received value number %d: %c, Failed to set whoami PID, and password_checker_bpf connected the prompt, a loader-self marker, and bytewise output. The %c format made a four-byte ringbuf record worth examining: its low byte could be displayed as a character.

Embedded object discovery

I searched past the host ELF header for a second 7f 45 4c 46 signature. One valid inner ELF begins at file offset 250,296 (0x3d1b8), and its machine type is EM_BPF (247). Its section table ends at 9,464 bytes from that inner header. A simple carve-to-EOF method would also include later host-file bytes, so I used the inner ELF section bounds to describe its minimum structural length. The object has tracepoint/raw_syscalls/sys_enter, .maps, an eight-byte .bss, an 800-byte .rodata, .BTF, and .BTF.ext. The offline inventory tool checks this structure and reports it without executing the file.

BPF disassembly and state-machine reconstruction

My disassembly notes describe a 155-instruction tracepoint function called track_syscalls; the 1,240-byte section size is consistent with 155 eight-byte BPF instructions. The first stretch identifies the loader through whoami and latches my_pid, then checks target_pid_map[0]. The counter range check stops work after index 159. For each allowed event, R = counter / 40 chooses one of four value tables and idx = counter % 40 chooses the position. A jitter_p[idx] comparison gates emission. Depending on the ten-position sub-row, the program adds +1, +2, -1, or -2, XORs the syscall number, writes four bytes to the ring buffer, and advances the counter. The wrong-syscall branch resets the counter and emits the failing number.

Approximate instruction span Role in the recorded disassembly

I checked the ELF sections and replayed the table arithmetic against the binary. I did not reload or execute the BPF instructions during this check. The disassembly supports the control-flow account; runtime claims about races and side channels below remain hypotheses.

Rodata parsing

Five little-endian u32[40] arrays fill the 800-byte section. The first is jitter_p at 0x000; value_0, value_1, value_2, and value_3 begin at 0x0a0, 0x140, 0x1e0, and 0x280. The jitter schedule is the ten-number cycle 257, 0, 1, 262, 3, 8, 9, 5, 87, 88, repeated four times. This gives 200 rodata entries in total, of which 160 are value-table entries. I checked the section length and cycle directly.

First-pass static decode

My first calculation followed the reported emit formula across all four rounds and all 40 positions. It gave 160 output values: some were recognizable flag characters, while the others looked like clutter. That is where I nearly spent time chasing an arithmetic mistake. The better question was why 160 values had been arranged as four rounds of 40.

The arithmetic has to stay 32-bit until after the XOR. Some jitter values are greater than 0xff. Masking value + row_off down to one byte before XOR can invent a high byte. For the selected diagonal cells, I computed ((value + offset) & 0xffffffff) ^ jitter, then checked that the result fit a byte. All 40 selected values did.

The pivot that unlocked the layout

Four rounds times four ten-byte sub-rows suggested a 4 x 4 grid. I tried the same tables with zero offset away from the diagonal. The 12 off-diagonal cells yielded 120 bytes of recognizable cover text, including three line breaks. I do not need to reproduce the copyrighted text to show its role: a coherent alternate reading confirmed that the apparently noisy cells were deliberately arranged. The four diagonal cells each held ten characters of the answer.

Diagonal extraction

I selected cell (R, R) for rounds R=0..3, ten bytes per cell. The 40 resulting values were printable ASCII, had the recorded prefix shape and balanced braces, and ended at the expected closing brace. I keep the actual answer out of the public page. The cover-text reading under the alternate offset and the forward check below are stronger support than flag formatting alone. No grader receipt was available to confirm challenge-platform acceptance.

Dynamic verification considered, not needed

I considered driving the 40-syscall schedule four times and watching the ring buffer. I sketched a ctypes syscall harness with deliberately bad arguments, but did not run it. Those calls would require an isolated test environment; I cannot assume every argument template is free of side effects. The static calculation answered the question, so I did not load the BPF program. The disassembly suggests the counter stops after 160 matches; that runtime lockout remains untested.

3. Tooling and Scripts

Embedded ELF carve

A magic-byte search was enough to find a candidate at 0x3d1b8, but I required a complete ELF64 little-endian section table and e_machine=247 before calling it BPF. My first blob.find(ELF_MAGIC, 4) carve-to-EOF approach would have written all 112,624 bytes after the inner header. The defensive inventory tool reports the validated minimum object length of 9,464 bytes and leaves the host file untouched.

BPF disassembly driver

The instruction pass used llvm-objdump -d -r --no-show-raw-insn on the inner ELF, followed by readelf -S and readelf -s to connect code, relocations, maps, BTF, and rodata names. I later used a bounded ELF parser to verify the section structure and replayed the tables. I did not load or attach the program to validate its runtime behavior.

Rodata parser and static decoder

The useful compact form of the decoder is below. Each value_R is a 40-entry little-endian array; jitter is the neighboring 40-entry array. I keep the full-width XOR and check for a byte only afterward, because eight jitter values exceed 0xff.

row_offsets = (1, 2, -1, -2)
answer = []
for round_no in range(4):
    for within_cell in range(10):
        index = 10 * round_no + within_cell
        value = value_tables[round_no][index]
        output = ((value + row_offsets[round_no]) & 0xffffffff) ^ jitter[index]
        if not 0 <= output <= 255:
            raise ValueError("diagonal value is not one byte")
        answer.append(output)
assert len(answer) == 40

Forward generator (verification harness)

I also inverted that relationship. Put four ten-byte answer pieces on the grid diagonal, place 12 ten-byte cover pieces off diagonal, then calculate each value-table entry as ((jitter[idx] ^ intended_byte) - offset) & 0xffffffff. The offset is the sub-row value on the diagonal and zero elsewhere. The cover-order rule reads rounds 1 through 3; when a round reaches its own diagonal slot, it substitutes the matching off-diagonal cell from round 0. With that placement, all 160 value-table entries regenerated exactly.

This is an internal consistency check of the recovered layout and formula, not an independent grading result. I kept the answer and cover text out of the diagnostic output.

Optional dynamic harness (not needed for solve)

My unused ctypes sketch listed the ten jitter numbers and repeated them through four rounds. One entry is syscall 1, which is exit in i386 compat mode; a naive all-compat driver would terminate its own producer. The loader's permissions, kernel support, and effects of each argument template would need isolated testing. Nothing about the static answer required taking that risk.

4. Concept Explanation

eBPF tracepoint programs at a glance

The raw_syscalls/sys_enter tracepoint observes a syscall entry before dispatch. A BPF program attached there can inspect the raw syscall number and other context, subject to kernel verifier and helper restrictions. Raw numbering depends on ABI, which matters if someone tries to feed the sequence dynamically. The verifier's job is program safety and allowed access; a successful load would not mean the program's authentication design is secure. No verifier result was observed in this offline solve.

Maps used in this challenge

The map inventory names three maps: whoami, a hash-like bootstrap at key 0, gives the loader a way to identify itself; target_pid_map, an array, stores the monitored PID at key 0; and event_map, a ring buffer, carries output to the userspace poller. The .bss holds the four-byte my_pid and counter globals. The BPF object exposes these names for inspection. A map name is a useful local pivot but too generic to serve as a malicious indicator.

The challenge's emit formula

At position counter, the reported logic takes R = counter // 40 and idx = counter % 40, checks syscall_nr == jitter_p[idx], then emits

out_u32 = ((value_R[idx] + row_off(idx)) mod 2^32) XOR syscall_nr
row_off(idx) = [1, 2, -1, -2][idx // 10]

The four-byte ringbuf value is displayed as a character by the loader. For the diagonal positions, the full-width arithmetic yields one-byte values. The mismatch path reportedly emits the failing syscall number and resets the counter. I distinguish that described runtime path from the static arithmetic I replayed.

Why the four value tables are not independent

Each table entry is derived from an intended grid character, the jitter number at that position, and either a sub-row offset or zero. Inverting the XOR and addition recovers a character for every grid cell. There are four tables because there are four rounds, not four independent secrets. The 800-byte rodata still contains five distinct 40-entry arrays; the structural claim concerns how the 160 value entries were generated.

The diagonal/substitution selection rule

The answer occupies (0,0), (1,1), (2,2), (3,3), ten characters in each cell. To read the 120-character cover message, I walk rounds 1, 2, and 3 across four cells. At each round's diagonal hole, I use (0,j) instead. That makes round 0's three off-diagonal cells useful rather than leftovers. One character appears to have been trimmed to fit the 120-byte budget. The cover text includes three line breaks, so "printable" means ordinary text controls as well as visible characters.

State machine summary

The disassembly describes one counter from 0 through 159, with a reset on a mismatch and an exit once it reaches 160. A correctly matched syscall produces a deterministic output from its position, the table, and the syscall number. This accounts for the apparent 160-event ritual. Shared mutable state could introduce races if multiple tasks drive it, but I did not run a concurrency experiment; one counter alone does not serialize multiple producers.

5. Exploit/Analysis Mechanics

The invariant the encoding violates

The intended gate asks the analyst to provide runtime observations before receiving bytes. But every input to the answer calculation is in the file: the 40 jitter numbers, 160 value entries, and four offsets in the program logic. Addition and XOR can be reversed. Anyone who can read the object can recover the answer without satisfying the gate. That is the design failure this puzzle demonstrates.

Operational steps to realize the recovery

I located the secondary ELF, verified its BPF machine type and sections, used the reported instruction flow to write the emit equation, parsed the five arrays, and tested two readings of the output. The all-position reading looked noisy. Grouping by ten-character cells exposed the diagonal. I selected those 40 bytes, checked the flag shape, then regenerated the value entries from the answer and cover grid. The inventory tool handles only the defensive first step: identifying a valid embedded object for review.

Why the diagonal layout works as a stego carrier

Each of four rounds visits 40 positions, but only one ten-position sub-row in that round is answer-bearing. The other 30 positions create a second readable layer when interpreted without the diagonal offset. Someone who watched only live ringbuf characters would see many non-answer characters and still need a layout hypothesis. Reading the static tables made that geometry visible.

Concurrency, ABI, side-channels - auxiliary findings

My static audit raised several runtime questions. The x32 ABI marks syscall numbers with bit 30, so its raw values would miss the small jitter numbers if the tracepoint sees them unchanged. An i386 compat stream shares some raw numbers, but syscall 1 is exit; switching modes after that slot was one possible workaround. The counter-at-160 check appears to prevent replay without reload. A failed syscall reportedly goes to the ring buffer, which could leak information to a reader with access to that channel. None of those routes was dynamically tested here, and I would not claim a three-to-five-byte leak without a trace.

I found no familiar ptrace, prctl, seccomp, or common BPF anti-analysis helper clues in the inspected paths. That bounded search does not prove every form of anti-analysis is absent. The static route did not require bypassing a runtime check.

6. Lessons Learned (Practitioner Perspective)

What the exercise validated

I was tempted to make the machine perform the syscall sequence because the binary offered that path so prominently. Looking at what was shipped paid off faster. The embedded object had the tables, the expected sequence, and the output arithmetic. Treating it as its own reverse target made the loader's prompt much less intimidating.

What the exercise surfaced as gaps

I spent too long thinking instruction by instruction before writing down the one-sentence state model: a counter advances on the expected syscall, chooses a round and position, and emits a table-derived value. I also tried to repair the noisy 160-byte output as if the formula were wrong. The four-by-forty shape should have pushed me toward a grid sooner.

Comparison: exercise vs. operational behavior

In the exercise In a real investigation
Inspect imports and strings before running Establish what the file contains and who supplied it
Validate the inner ELF separately Preserve both outer and embedded layers with offsets and hashes
Parse rodata and derive a static result Check whether protected material is actually outside the artifact
Consider a runtime syscall driver Use an isolated, authorized test host only when static work leaves a question
See a structural BPF hit Correlate with approved observability software before escalating

Transferable principles

I ask whether a gate contributes secret information or merely controls when already-shipped data is released. I also check layouts before assuming a flat byte stream. A failed first decode can be evidence of a second arrangement, particularly when the dimensions divide cleanly into meaningful cells.

7. Extrapolation

Individual practitioner skill development

This case exercised nested ELF validation, BPF section reading, instruction-to-state-machine reasoning, and byte-grid recovery. The next useful practice is to compare static claims with an isolated bpftool inventory on a system I control. That would test loaded program identity and map behavior without confusing a challenge file with a real incident.

Security operations (SOC, IR, threat hunting)

A hunt can inventory loaded BPF programs, attach points, loader provenance, and map names. A second pass can scan binaries in approved collection scope for embedded EM_BPF objects. The offline inventory proof of concept and its Sigma selection cover only that second pass. They do not observe a live bpf() call or attach operation. Legitimate libbpf, tracing, and network tools often embed BPF objects, so the structural hit is a review lead.

For response, I would preserve the host binary, loader identity, loaded-program metadata, program instructions, and map state before detaching anything, subject to local authority and the kernel/tooling available. A bpftool prog show -j or map show -j snapshot is a starting point; names alone are insufficient, and runtime state can disappear when objects unload. I would not promise that .bss state survives a detach or that one snapshot captures every transient event.

Intelligence operations (SIGINT, IO/IW, OSINT, attribution)

The cover-text choice and table schedule are possible clustering features if multiple independently collected samples share them. One puzzle cannot attribute an operator. A real intelligence note would separate the observed file structure from a proposed BPF-gated-channel pattern and would avoid presenting the challenge's lyrics, map names, or hash as broad threat IOCs.

8. Reusable Tools, Scripts, and Artifacts

Decision flow: when to static-extract a BPF-gated secret

I first ask whether the host embeds a structurally valid BPF object. If it does, I inspect sections and the code path that uses rodata. A pure function of shipped tables is a static-recovery candidate; a function that genuinely depends on a runtime secret needs a different plan. I then test grid, permutation, and offset hypotheses before calling a noisy output random. The last check is to regenerate the parsed tables or compare with a truly independent observation.

Reusable primitives

The Python inventory tool validates both ELF section tables, checks the inner machine type, reports the minimum object length, and identifies raw_syscalls tracepoint sections. Its tests generate a synthetic positive host, benign host, wrong-architecture inner object, allowlisted positive, and truncated header. The guide gives the input limits, fields, sensor assumptions, and false-positive boundary. For static math, the reusable primitives are a bounds-checked u32 table parser, the full-width emit equation, and diagonal-cell selection; the challenge answer is deliberately absent from the defensive tool.

Triage checklist for an unknown libbpf-based binary

I record file provenance and digest, inspect imports and strings, scan for a second ELF, validate EM_BPF, enumerate .maps, .bss, .rodata, BTF and attach sections, then disassemble the BPF function and trace the emit call. I write a state-machine summary before trying to drive it. If a static hypothesis works, I check the inverse and its limits. Only then do I consider a runtime experiment on an authorized host. A section name or libbpf import by itself does not make a file malicious.

9. Framework Mapping

The closest ATT&CK analogy is T1027.009, Embedded Payloads when an adversary hides an operational payload inside another file. Here, embedding a BPF object is also a normal libbpf development pattern, and no adversary use was observed. T1027 more broadly describes obfuscation, but this CTF encoding is not evidence of a campaign. T1027.001 Binary Padding does not fit: the secondary ELF performs work rather than merely inflating file size. T1014 Rootkit, the legacy T1562.006 Indicator Blocking mapping, and T1480.001 Environmental Keying would each require behavior or a cryptographic environment-derived key not established here. The old T1562.006 URL now resolves to the newer T1685, Disable or Modify Tools; the binary still does not show that behavior. T1140 describes adversary decoding, so my defensive reversal is not an observed T1140 act.

D3-FCOA, File Content Analysis fits the static scan. D3-FCA names File Creation Analysis, so I do not use it for this step. D3-PA, Process Analysis could support a separate live loader review. CAPEC-572 Artificially Inflate File Size and CAPEC-188 Reverse Engineering add little to this embedded-object case. I do not assign CWE-540 or CWE-311 to a challenge flag as if it were a deployed credential. A real software finding would require the actual asset and security requirement. OWASP ASVS and Top 10 do not describe this kernel tracing artifact; STRIDE would need a defined system boundary.

10. Threat Intel and Standards Integration

STIX/TAXII

The illustrative STIX 2.1 bundle records a hypothetical attack pattern, a defensive course of action, and their relationship. It does not call the sample malware or identify an actor. Its JSON and internal references were checked locally; no full STIX schema validator or TAXII exchange was used. I used UUIDs and kept unsupported kill-chain claims out of the bundle. A production intelligence record would add collection provenance, confidence, markings, and a behaviorally valid indicator only after observing an actual campaign or deployment.

STIG references

An applicable Linux STIG may require audit configuration and restrict unprivileged BPF, depending on the distribution and release. I would check the exact current STIG item against the deployed kernel before citing a finding. kernel.unprivileged_bpf_disabled affects unprivileged bpf() calls; it does not make privileged or authorized BPF disappear. The challenge binary alone proves no STIG failure. I would verify any CCI and avoid treating BPF programs as kernel modules when writing a compliance claim.

CIS Benchmarks

The relevant benchmark is the one for the organization's Linux distribution and version. Audit policy, privileged access, and BPF settings are review topics, but "Section 1.5" and "Section 4" are not portable control identifiers across every benchmark. For broader planning, CIS Controls 8.5 (Collect Detailed Audit Logs) and 8.11 (Conduct Audit Log Reviews) can support the telemetry and review workflow. The current CIS 13.7 label is Deploy a Host-Based Intrusion Prevention Solution. That may support prevention where appropriate, but it does not itself inventory embedded BPF objects. Neither a benchmark heading nor a BPF sysctl by itself detects the static answer in this file.

11b. Mitigation Realization

For a real BPF estate, I would inventory approved loaders and their object hashes, audit BPF-related syscalls where the host supports them, and capture loaded-program metadata with an owner and retention policy. The offline inventory script can review host files and suppress an exact approved digest; its output could feed the Sigma candidate. That is a file-analysis workflow, separate from live BPF attach monitoring.

I considered auditd rules for bpf and perf_event_open, a sysctl setting, and signed-BPF enforcement as deployment examples. A bpf() syscall event alone does not identify a successful tracepoint attach; the command, return value, program metadata, and sometimes perf_event_open or link operations must be correlated. A selector of a0: 5 alone does not establish BPF_PROG_ATTACH and would be a poor production rule. Restricting unprivileged BPF is useful where compatible with the system, but it cannot protect a secret already shipped in the file.

12. Indicators, Artifacts, and Detection Engineering

IOCs (illustrative, sanitized)

For this case I recorded the outer ELF, second ELF at offset 250,296, EM_BPF, the raw_syscalls/sys_enter section, 800-byte rodata, four value tables, and the whoami, target_pid_map, and event_map names. These are case features, not general malicious IOCs. No public binary hash, flag, or cover text is needed for the defender pattern. An ordinary observability loader may have most of the same structural features.

YARA: detect host binary containing embedded BPF ELF

A YARA rule can find an ELF magic followed by an EM_BPF machine field, but a byte pattern does not prove the inner section table is valid or that the host loaded it. The offline parser performs that structural check and reports a review lead. I have not tested a benign corpus or compiled a YARA rule, so I do not call such a signature high fidelity.

Sigma: BPF program attached to raw syscall tracepoint by non-allowlisted loader

The linked Sigma rule selects a normalized file inventory event when the companion tool says review_lead=true. It parsed with pySigma. It does not detect a live attachment; an auditd a0 selector by itself cannot prove one. A live rule would need a validated sensor mapping for program load, attach point, loader identity, and success status. A process-name selector cannot measure ringbuf throughput, so I do not present it as a working throughput detector.

KQL: Microsoft Sentinel - alert on BPF syscall by non-allowlisted parent process

DeviceProcessEvents records process activity, not arbitrary bpf() syscalls. A defensible Sentinel hunt would first ingest a custom BPF activity or offline-inventory table with explicit fields for host, loader, attach point, program hash, result, and approval state. For the latter, a scoped template is BpfInventory_CL | where EventType == "embedded_bpf_inventory" and ReviewLead == true | project TimeGenerated, Host, HostSha256, EmbeddedBpfCount. Field names and parser mapping must be checked on the actual table. This is a proposed query, not a run against Sentinel.

Splunk SPL: hunt for embedded ELF magic in non-observability binaries

For a normalized JSON inventory event, a starting query is index=endpoint sourcetype=embedded_bpf_inventory event_type=embedded_bpf_inventory review_lead=true | table _time host host_sha256 embedded_bpf_count. Searching a Base64 prefix with strpos on encoded inventory text, or filtering undefined import fields, would not reliably find an embedded ELF. The linked parser supplies the structural field; the SPL template still needs a real ingestion mapping.

Log source and data pipeline requirements

The offline scan needs the binary bytes and a trusted path from host or repository inventory to the analyst. Live load/attach hunting needs Linux audit or EDR telemetry that actually records bpf() operations, perf_event_open where relevant, return status, process lineage, and program identity. A periodic bpftool snapshot can supplement event telemetry but can miss short-lived objects. Binary-content collection must respect scope and privacy. The artifact guide documents this tool's fields, limits, and how a local allowlist affects output.

Detection engineering notes

Four synthetic tests passed: embedded BPF syscall tracepoint, benign single ELF, wrong-architecture nested ELF, approved hash, and malformed-header handling. The challenge binary produced one structural review lead with the expected offset and rodata size. The Sigma YAML parsed, and the illustrative STIX bundle passed JSON/reference checks. No YARA engine, Sigma backend conversion, Sentinel/Splunk execution, fleet sensor, or production false-positive study was performed. A legitimate libbpf loader is the obvious false-positive class; a packed object with no section table can be a miss.
