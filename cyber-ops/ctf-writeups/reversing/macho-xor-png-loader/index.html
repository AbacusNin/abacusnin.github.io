The PNG Behind the Password

The program wanted a password. Its own output filename told me where to look for one.

Summary

The challenge. Recover the PNG hidden inside a native loader binary without supplying its password or executing it.

What I did. Type the file, inspect strings and imports, locate the encoded blob, XOR its first bytes with the PNG header, and validate the full decode.

The result. I recovered and viewed a PNG containing the flag; the exact key, image, flag, and grading receipt are not retained here.

The limit. The loader and decoded image are unavailable for independent replay. Linked defensive proofs of concept use invented bytes and validate only their local logic.

At-a-Glance Attack Chain

I had a program that would write an image only if given the right argument. It was easier to examine what the program carried than to make it cooperate. The output filename pointed to PNG. The _encrypted symbol pointed to a byte array in __TEXT.__const. PNG supplies 16 known opening bytes, so I could XOR those against the stored bytes and see a readable key prefix. I then checked a candidate key against the entire asset. The flow above follows the work from the outside in.

1. Problem Statement and Threat Scenario

The challenge handed me a small native executable. It accepted a password argument and, when that argument worked, wrote a PNG. I needed the image without knowing the password or running the program. The file was a roughly 33 KB ARM64 Mach-O PIE. I had the on-disk image and whatever names the linker left in it. There was no source or network service.

This shape resembles a loader that hides an asset until it gets a key. The resemblance matters to defenders because an encoded payload can survive static inspection and appear only after an argument or environment value is supplied. Here the protected content was a CTF image. I did not observe a malicious second stage, a victim host, or an adversary deployment.

2. Techniques, Tooling, and Actions Taken

I started with file, then ran strings -n 6 and inspected symbols and imports. The usage text mentioned a password argument; an output name ended in .png; _encrypted named a stored blob. Imports included fopen, fputc, strlen, fclose, fprintf, and perror. I did not see obvious strcmp, memcmp, CommonCrypto, or OpenSSL imports. That absence suggested a small custom routine, but it did not prove how the password was used. A compiler could inline a comparison or resolve functions another way.

LIEF placed _encrypted in __TEXT.__const. The extraction coordinates recorded for this image were file offset 0x720 and size 0x18B4 (6,324 bytes). I treated those as this binary's coordinates, not a Mach-O rule. The output filename made PNG a strong plaintext guess. I XORed the first 16 blob bytes with the PNG signature, fixed IHDR length, and IHDR type. The resulting keystream began as readable ASCII. I used that prefix to choose a repeating-key candidate and decoded the whole blob.

The decoded bytes had PNG magic, an IHDR, and an IEND trailer with a reported valid CRC. I viewed the image and rotated it to read the flag text. The rotation was a viewing step, not part of the cipher. I did not retain the key, decoded image, exact flag, or a platform acceptance receipt in this case record, so I cannot recheck that final result now.

3. Tooling and Scripts

3.1 Triage one-liners

file ./sample, nm -gU ./sample (or llvm-nm -gU), and strings -n 6 ./sample | sort -u supplied the first clues. nm on an unstripped Mach-O and strings on raw bytes can miss names; I treated their output as leads. A Counter-based Shannon entropy calculation is useful for choosing sections to inspect, although I did not record a measured entropy score for this blob. A single high value would not identify encryption: compressed assets can look similar.

3.2 Section enumeration via LIEF

I used LIEF to walk section names, offsets, sizes, virtual addresses, and named symbols. _encrypted led to the __TEXT.__const bytes at 0x720 for 0x18B4 bytes. I checked the file range before reading it. A symbol virtual address is not automatically a file offset; the section or segment mapping supplies that conversion. The review script expects a blob range established this way and checks its bounds. It does not parse the Mach-O itself.

3.3 Known-plaintext recovery against a PNG-bearing blob

The constant I used was 89504e470d0a1a0a0000000d49484452: eight signature bytes, the four-byte length 13, and IHDR. For each opening byte, candidate_keystream[i] = ciphertext[i] XOR known_png[i]. A key of 16 bytes or fewer can be fully observed and checked for repetition in this span. A longer key yields only a prefix. A readable prefix such as exposeTheNega might suggest exposeTheNegative, but that suggestion is a hypothesis until a full-file decode passes checks.

The bounded PNG reviewer tries periodic candidates up to 16 bytes. It can also test a longer candidate supplied through a local key file. It reports key length without printing the key or its hash. It checks chunk bounds and CRCs, terminal IEND, and a bounded IDAT zlib stream. Its README explains the remaining image-validation limits and the optional output file.

3.4 Fallback: brute-force key length when no known plaintext is available

I kept normalized Hamming-distance key-length ranking as a fallback, but I did not need it for this solve. It can suggest repeating periods from a longer ciphertext. It does not by itself recover a key, and frequency scoring aimed at English text is a poor fit for compressed PNG bytes. I would turn to it only after known-format candidates failed and I had enough ciphertext to compare multiple blocks.

4. Concept Explanation

4.1 XOR as a cipher

For a repeating key, C[i] = P[i] XOR K[i mod m]. The same XOR operation decodes it. Reuse of key bytes is the weakness here: one known plaintext byte exposes the matching key byte. XOR is useful as an operation, but this particular repeated-key construction did not protect a known-format image from offline inspection and provided no authentication.

4.2 The known-plaintext attack

I knew the PNG opening bytes and had the corresponding encoded bytes. XORing them gave me the first 16 keystream bytes. If the key period is at most 16, that span covers a whole cycle. A 17-byte phrase such as exposeTheNegative needs one more byte of evidence or an inferred suffix checked against the rest of the file. Readable ASCII helped me choose a candidate; the later PNG checks did the validation work.

4.3 Why PNG is the perfect known-plaintext target

The PNG specification fixes the eight-byte signature, requires IHDR first, and gives IHDR a 13-byte data field. Those facts make the first 16 bytes predictable. The next fields describe dimensions and image format, but they are not fixed across all PNGs. A longer key may be approachable by enumerating plausible dimensions and valid IHDR values, then testing the full decode. I would not assume a guessed width or a human-readable suffix is correct on its own.

4.4 The same primitive applies to most container formats

The opening of a ZIP local-file record (50 4b 03 04), GZIP stream (1f 8b 08), ELF (7f 45 4c 46), little-endian Mach-O 64 (cf fa ed fe), PE (4d 5a), and PDF (%PDF-) can seed the same XOR check. Their reliable known lengths differ. ELF identification fields vary after the magic; JPEG marker sequences and PDF version bytes vary too. A useful format table marks only bytes the format actually guarantees, then lets parser checks decide the rest.

5. Exploit / Analysis Mechanics

The gate relied on a secret argument, but the image's format gave me a way to test the encoding without asking the loader for output. I found the candidate ciphertext by symbol and section location. The .png output name led to a precise 16-byte plaintext guess. I XORed that guess against the first 16 encoded bytes and inspected the keystream for a repeating period or a plausible longer phrase. Then I decoded all 6,324 bytes with a candidate key and checked structure before opening the image.

This computation is linear in the blob length for each key candidate. It does not prove that the binary compares its argument to a constant, nor that it uses no other transformation. The full decoded structure and visible image supplied the case-specific confirmation. A PNG signature and IEND string alone would have been too weak; chunk lengths and CRCs matter, and an image decoder is still needed to confirm the pixels.

6. Lessons Learned (Practitioner Perspective)

6.1 What the exercise validated

The exported name and the output filename shortened the search. I did not have to start with a full disassembly. The fixed PNG header let me recover key material directly from the encoded blob, and structural checks kept an English-looking prefix from becoming a premature answer.

6.2 What the exercise surfaced as gaps

I initially leaned too hard on the absence of imported comparison calls. That is a weak negative signal; an inline loop would leave no strcmp import. I also want to retain exact key bytes, image hash, parser result, and submission status next time. Without them, the final solve can be described but not independently replayed.

6.3 Operational mapping

Step here Use in a real review
File typing, names, and imports Cheap orientation before deeper reversing; no conclusion from missing imports alone.
Section and symbol mapping Extract a precise byte range with provenance and bounds.
Known-format XOR test Try a narrow hypothesis without executing an unknown loader.
CRC and image validation Separate a plausible prefix from a useful decoded asset.
7. Extrapolation

7.1 Individual practitioner skill development

This case joined Mach-O section navigation with a simple cryptanalytic attack. I would repeat it with a stripped binary, a blob whose output type is unknown, and a key longer than the available known prefix. Those variations would force me to distinguish format identification, key-length ranking, and actual validation.

7.2 Security operations (SOC, IR, threat hunting)

For a suspicious native file, I would preserve its hash and signer, inspect sections and imports, then test extracted large data ranges against likely file headers. High entropy can prioritize a range, but does not prove encryption or maliciousness. A successful known-plaintext decode is a stronger lead. I would still inspect what the decoded file contains and how the program uses it. On an endpoint, process creation followed by a file write can guide collection; telemetry alone does not expose the encoded blob or prove it was decrypted with an argv key.

7.3 Intelligence operations

If multiple authorized samples decode with the same key or carry the same asset, I would compare their code, section layout, signatures, and provenance before linking them. Reused key text is a useful search pivot, not an attribution verdict. Metadata in a decoded image might offer another lead, but I would inspect actual bytes before claiming EXIF, URLs, or author information. None of those appeared as a verified finding here.

8. Reusable Tools, Scripts, and Artifacts

8.1 Static-first triage decision tree

I start with file type, hash, signature, imports, strings, and section ranges. A descriptive symbol or output name gives me a candidate payload format. I extract only the relevant range, test fixed plaintext bytes against it, then validate a full decode. If the path fails, I return to disassembly or a controlled dynamic lab with the failed hypothesis recorded. The artifact guide documents the local version of the extraction-and-test path.

8.2 Format-magic known-plaintext table (drop-in)

The review script embeds only the 16-byte PNG constant that this case used. For a broader table I would record a format name, exact fixed prefix, variable fields, and parser to run on a full candidate. ZIP, GZIP, ELF, Mach-O, PE, PDF, and JPEG have useful opening bytes, but few offer 16 unconditional bytes like PNG.

8.3 Generic repeating-XOR oracle

The reusable operation is short: XOR the selected ciphertext prefix with known plaintext; test candidate key periods; decode the whole blob; parse the result. The script's five synthetic tests cover a six-byte periodic key, a 17-byte key supplied after inference, random bytes, a CRC failure, and trailing data. English-frequency scoring remains a possible fallback for text payloads. I would not use it to rank PNG-compressed bytes.

8.4 Triage checklist

Preserve the binary and its hash. Record file type and architecture, names and imports, section and symbol mapping, blob offset and length, candidate plaintext format, recovered keystream span, complete candidate key test, all chunk and CRC results, actual image render, and result verification. The blob range and key must remain tied to the specific sample. This makes the outcome reviewable without turning an inferred word into proof.

9. Framework Mapping

9.1 MITRE ATT&CK

An actual adversary hiding a payload this way would fit T1027.013, Encrypted/Encoded File. If a loader decoded the asset at runtime, T1140 would describe that adversary-side action. T1480, Execution Guardrails might fit a target-specific argument gate, but this case only establishes an argument used to release an image. I do not assign it as observed attacker behavior.

9.2 MITRE D3FEND

D3-FA, File Analysis covers the static review. D3-FCR, File Content Rules is a route for a future tested file rule. D3-SFA means System File Analysis, so I would not use that ID to label this one-off Mach-O review.

9.3 MITRE CAPEC

CAPEC-97, Cryptanalysis describes the known-plaintext method. It is an analogy for what I did as an analyst, not evidence that a real attacker used it. I do not need CAPEC-189 or CAPEC-191 to describe the case; the recovered asset was an encoded PNG, not a demonstrated sensitive constant stolen from a deployed executable.

9.4 Frameworks not applied

I did not find a web application surface for OWASP categories. STRIDE could help design a real product that distributes protected assets, but this challenge gave me a finished binary and a recovery goal, not a design review.

10. Threat Intel and Standards Integration

10.1 STIX 2.1 representation

I did not retain a sample hash, exact key, or decoded asset fingerprint that would support a case-specific indicator. If I had those and permission to share, a STIX 2.1 Indicator could describe a tested file-content pattern with valid IDs, producer, timestamps, confidence, and a precise pattern. A TAXII exchange would require a real collection and recipient. I have neither in this case, so I am not publishing a STIX object.

10.2 STIG references

The challenge does not establish an in-scope system, applicable STIG release, approved crypto requirement, or assessed implementation. I would select an actual Application Security and Development STIG check only during a review of a deployed application. A sample's custom XOR scheme raises a design concern; it cannot support a CAT finding by itself.

10.3 CIS Controls v8

CIS 16.11 favors vetted modules or services for application security components. A product trying to keep an embedded asset confidential should review the threat model and key delivery before choosing a vetted authenticated cipher. CIS 3.11 applies when the asset is sensitive data at rest in an enterprise setting; the CTF image is not evidence of that setting. These are design mappings, not controls deployed here.

11. Controls Mapping and Mitigation Realization

11b. Mitigation Realization

I would first ask who may read the asset and where its decryption key comes from. An asset placed in a binary that every recipient can inspect cannot stay secret merely because the binary asks for a password. If the product has a real confidentiality requirement, use a vetted AEAD implementation and a key-delivery design that does not ship the secret alongside the ciphertext. A human password would need a suitable password-to-key derivation and must withstand offline guessing; Argon2id alone cannot make a weak password strong. Integrity would come from authenticated encryption and separate build/provenance checks as appropriate. Linkage to a library or an AEAD tag alone would not certify a control.

For a build pipeline, I would add a review gate for homegrown XOR used as a confidentiality control, plus test vectors for the selected design. An ASCII-prefix check could flag a weak example, but it would miss nonprintable keys and many formats. I would not label a passing build "KPA safe." The local reviewer serves analyst triage; it cannot certify a design.

12. Indicators, Artifacts, and Detection Engineering

12.1 IOCs

I have no case-specific hash, key, host, or path to share. _encrypted, __TEXT.__const, 0x720, and 0x18B4 are investigative details from this binary, not durable campaign indicators. A future hunt would need file bytes or a trusted extraction from a collected sample. Entropy above 7.0, no crypto imports, and a large const section are hypotheses, not measured traits of this sample.

12.2 YARA rule

A YARA rule can cheaply select Mach-O files or byte ranges for review, but entropy and missing library names cannot prove repeating XOR. I have not compiled a YARA rule for this case. The tested Python proof of concept checks the actual encoded bytes against a PNG hypothesis and parses the resulting candidate. It still needs a correctly extracted range and analyst interpretation.

12.3 Sigma rule

A single Sigma process-creation rule cannot join that event to a file-create event, count arguments accurately in every shell quoting case, or show that the argument became a decryption key. I would use process and file telemetry as separate inputs to a backend correlation after validating a shared process identity and event timing. I have not published a standalone Sigma detector that claims the full chain.

12.4 SIEM queries

The useful normalized event model is process_start(host, process_guid, time, image, argv) followed by file_create(host, process_guid, time, path) within a justified window. Then I would retrieve and inspect the binary and created file. A join only on device or PID can mix processes; a filename extension alone can describe a legitimate utility. SPL path alternatives need explicit grouping, and KQL field names require checking against the actual connector. Without that schema and sample events, I cannot present either as a validated deployment query.

12.5 Log source and data pipeline requirements

Endpoint process and file events need stable process identity, host identity, ordered timestamps, command-line capture policy, file path, and a way to collect file bytes. The static reviewer needs the exact blob offset and length from a parser or analyst. Its JSON contains a candidate method, key length, blob fingerprint, PNG dimensions, chunk list, and review result. No macOS or SIEM events were provided to validate a live correlation.

12.6 Detection engineering notes

The invented test cases cover a positive short-key decode, a longer candidate-key path, random benign bytes, corrupted CRC, and trailing data. Five tests passed locally. They do not measure false positives or prove the original loader's behavior. Legitimate applications can embed encoded or compressed assets; an alert would need signer, source, expected product behavior, and the decoded content reviewed together.

13. Visual Artifact

The flow above keeps the important sequence visible: hints in the native file led to a byte range, then a fixed PNG header led to a key candidate, then the whole image had to pass checks. A defensive deployment would add collection and review around those steps. The case did not test an endpoint rule or a production crypto redesign.
